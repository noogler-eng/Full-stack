Interfaces

Interfaces are how Go says "I don't care what you are, only what you can do." They let your checkout code work with Razorpay today, Stripe tomorrow and a fake gateway in tests, without changing a line. They're also the most elegant and most misunderstood part of the language.

The problem interfaces solve

Say your shop charges customers through Razorpay. The simplest code calls Razorpay directly:

func Checkout(r Razorpay, amount float64) error {
	return r.Pay(amount)
}

Now the business wants Stripe for international customers. And QA wants to test checkout without moving real money. With the code above, you'd copy Checkout three times, once per gateway. Every bug fix, three times.

What Checkout really needs isn't "a Razorpay". It needs "something that can Pay". An interface lets you write exactly that down:

type Payer interface {
	Pay(amount float64) error
}

An interface type is a list of method signatures. Any type that has all those methods (same names, same parameter and result types) is a Payer. No registration, no implements keyword.

Mental model

An interface is a job description: "must be able to Pay(amount)". Razorpay, Stripe and a test fake are candidates. Go hires anyone whose CV (method set) covers every line of the job description. The candidates never have to know the job exists.

Implicit satisfaction: a payment-gateway example

Here's the full design, the same idea as the paymenter interface in your own learning code, cleaned up into a runnable program:

package main

import (
	"errors"
	"fmt"
)

// Payer is anything that can take money. That's the whole contract.
type Payer interface {
	Pay(amount float64) error
}

// --- three unrelated types, none of which mention Payer ---

type Razorpay struct{ KeyID string }

func (r Razorpay) Pay(amount float64) error {
	fmt.Printf("razorpay[%s]: charged ₹%.2f\n", r.KeyID, amount)
	return nil
}

type Stripe struct{ Account string }

func (s Stripe) Pay(amount float64) error {
	fmt.Printf("stripe[%s]: charged ₹%.2f\n", s.Account, amount)
	return nil
}

// FakePayer is for tests and local dev: it records calls and can fail on demand.
type FakePayer struct {
	Fail  bool
	Calls []float64
}

func (f *FakePayer) Pay(amount float64) error {
	f.Calls = append(f.Calls, amount)
	if f.Fail {
		return errors.New("fake: card declined")
	}
	return nil
}

// Checkout depends on the BEHAVIOUR (Payer), not on any concrete gateway.
type Checkout struct {
	gateway Payer
}

func (c Checkout) Process(orderID int, amount float64) {
	if err := c.gateway.Pay(amount); err != nil {
		fmt.Printf("order %d failed: %v\n", orderID, err)
		return
	}
	fmt.Printf("order %d paid\n", orderID)
}

func main() {
	fake := &FakePayer{Fail: true}

	gateways := []Payer{
		Razorpay{KeyID: "rzp_test"},
		Stripe{Account: "acct_42"},
		fake,
	}
	for i, g := range gateways {
		Checkout{gateway: g}.Process(100+i, 499)
	}
	fmt.Println("fake saw calls:", fake.Calls)
}
razorpay[rzp_test]: charged ₹499.00
order 100 paid
stripe[acct_42]: charged ₹499.00
order 101 paid
order 102 failed: fake: card declined
fake saw calls: [499]

What just happened:

  • Razorpay, Stripe and *FakePayer never mention Payer. They each just have a Pay(float64) error method, so the compiler accepts them anywhere a Payer is expected.
  • Checkout stores a Payer and calls c.gateway.Pay(...). At run time Go looks up which concrete Pay to call. This is called dynamic dispatch.
  • FakePayer uses a pointer receiver (it records calls), so it's &FakePayer{} (a *FakePayer) that satisfies Payer. Recall the method-set rule from Chapter 07.
A bug worth spotting in real code

A common first attempt looks like this: type payment struct{ gateway paymenter } with func (p payment) makePayment(amt float32) { g := fakePayment{}; g.pay(amt) }. It declares an interface field but then ignores it and hard-codes a gateway. The whole point is to call p.gateway.pay(amt) so whoever builds the payment chooses the gateway. If you have this in your own learning code, it's a one-line fix!

type Payer interface {
	Pay(amount float64) error
}

func checkout(p Payer, amount float64) {
	err := p.Pay(amount)
	fmt.Println("result:", err)
}

func main() {
	checkout(Razorpay{KeyID: "rzp"}, 499)
	checkout(&FakePayer{Fail: true}, 99)
}
  1. We pass a Razorpay value where a Payer is expected. The compiler checks Razorpay has Pay(float64) error. It does.
  2. Inside checkout, p is an interface value: it remembers both the concrete type (Razorpay) and the value.
  3. p.Pay looks at the stored type, finds Razorpay.Pay, and calls it. Razorpay prints its message.
  4. Payment succeeded, so err is nil.
  5. Second call: same function, totally different concrete type. Now p holds a *FakePayer.
  6. The same line of code now dispatches to (*FakePayer).Pay, which returns an error because Fail is true.
  7. checkout never knew which gateway it had. That's the power: one function, any number of implementations.

It works across packages, too

Because satisfaction is implicit, a type written years ago in another package can satisfy an interface you define today. The standard library's fmt.Stringer is the classic example:

package main

import (
	"fmt"
	"time"
)

type Status string

// String makes Status satisfy fmt.Stringer:
//
//	type Stringer interface { String() string }
//
// We never wrote "implements Stringer". Having the method is enough.
func (s Status) String() string {
	switch s {
	case "pending":
		return "⏳ Pending"
	case "paid":
		return "✅ Paid"
	}
	return "❓ " + string(s)
}

func main() {
	var s fmt.Stringer = Status("paid")
	fmt.Println(s.String())

	// fmt checks for Stringer and calls it automatically.
	fmt.Println(Status("pending"), Status("lost"))

	// Types from other packages satisfy your interfaces too.
	s = 90 * time.Minute // time.Duration has a String method
	fmt.Println(s)
}
  1. No code runs yet. Status gets a String() string method, which is exactly the method set of fmt.Stringer. No implements keyword anywhere.
  2. Assigning a Status to a fmt.Stringer variable compiles because the method set matches. The interface stores the dynamic type Status and the value "paid".
  3. Calling s.String() dispatches to Status.String. The switch hits case "paid".
  4. The returned string is printed.
  5. fmt.Println checks each argument: "do you implement Stringer?" Status("pending") does, so fmt calls String() for you and gets ⏳ Pending.
  6. "lost" matches no case, so it falls through to the ❓ fallback.
  7. The same interface variable now holds a time.Duration. A type from another package satisfies our use of Stringer with zero coordination.
  8. fmt calls Duration.String(), which renders 90 minutes as 1h30m0s.
✅ Paid
⏳ Pending ❓ lost
1h30m0s

time.Duration's authors had never heard of your variable s, yet it fits. In Java you'd need the class to declare implements Stringer up front; in Go, the consumer decides what it needs and any matching type plugs in. This one design choice shapes everything else in this chapter.

Senior engineer tip

Implicit interfaces mean you can introduce an abstraction later, after you have two concrete implementations, without editing them. So don't create an interface on day one "just in case". Start with a concrete type; extract an interface when a second implementation (or a test fake) actually shows up. "Don't design with interfaces, discover them." (Rob Pike)

What an interface value really is

A variable of interface type is a small two-word box. Conceptually it's a pair:

  • type: which concrete type is stored (plus, internally, a table of that type's methods for this interface, called the itab);
  • value: a pointer to the concrete data.

Calling a method looks up the function in the itab and calls it with the data pointer. An interface value is nil only when both words are empty.

package main

import "fmt"

type Payer interface{ Pay(float64) error }

type Razorpay struct{ KeyID string }

func (Razorpay) Pay(float64) error { return nil }

type Stripe struct{}

func (*Stripe) Pay(float64) error { return nil }

func describe(p Payer) {
	fmt.Printf("dynamic type=%-14T value=%v nil? %v\n", p, p, p == nil)
}

func main() {
	var p Payer // zero value: no type, no value
	describe(p)

	p = Razorpay{KeyID: "rzp_1"}
	describe(p)

	p = &Stripe{}
	describe(p)
}
  1. An interface value is a pair: (dynamic type, dynamic value). A freshly declared Payer has neither, so it is nil.
  2. %T of a nil interface prints <nil>. Only when both halves are empty is p == nil true.
  3. Razorpay has a value-receiver Pay, so a plain Razorpay value satisfies Payer. The interface now stores a copy of the struct.
  4. %-14T pads the type name so the columns line up.
  5. Stripe.Pay has a pointer receiver, so only *Stripe satisfies Payer. Writing p = Stripe{} would not compile.
  6. The dynamic type is now *main.Stripe and fmt prints the pointer as &{}.
dynamic type=<nil>          value=<nil> nil? true
dynamic type=main.Razorpay  value={rzp_1} nil? false
dynamic type=*main.Stripe   value=&{} nil? false

%T prints the dynamic type: the concrete type currently inside the box. The variable's static type (Payer) never changes; the dynamic type changes every time you assign something new.

The nil-interface trap

This is the most famous Go gotcha, and it follows directly from the diagram. If you put a nil pointer into an interface, the interface is not nil, because its type word is filled in.

package main

import "fmt"

type PaymentError struct{ Code string }

func (e *PaymentError) Error() string { return "payment failed: " + e.Code }

// BUG: returns a typed nil pointer wrapped in an error interface.
func chargeBuggy(amount float64) error {
	var perr *PaymentError // nil pointer
	if amount <= 0 {
		perr = &PaymentError{Code: "invalid_amount"}
	}
	return perr // interface = (type=*PaymentError, value=nil) -> NOT nil!
}

// FIX: return a literal nil on the success path.
func chargeFixed(amount float64) error {
	if amount <= 0 {
		return &PaymentError{Code: "invalid_amount"}
	}
	return nil
}

func main() {
	err := chargeBuggy(100)
	fmt.Printf("buggy: err == nil? %v  (type %T, value %v)\n", err == nil, err, err)

	err = chargeFixed(100)
	fmt.Printf("fixed: err == nil? %v  (type %T)\n", err == nil, err)
}
buggy: err == nil? false  (type *main.PaymentError, value <nil>)
fixed: err == nil? true  (type <nil>)
func chargeBuggy(amount float64) error {
	var perr *PaymentError
	if amount <= 0 {
		perr = &PaymentError{Code: "invalid_amount"}
	}
	return perr
}

func main() {
	err := chargeBuggy(100)
	if err != nil {
		fmt.Println("failed:", err == nil, err)
	}
}
  1. We call chargeBuggy(100). 100 is a valid amount, so we expect "no error".
  2. perr is a pointer variable. Its zero value is a nil pointer, but its type is *PaymentError.
  3. The amount is positive, so the if body is skipped. perr stays a nil pointer.
  4. Here's the moment: returning perr as an error wraps it in an interface. The box gets type = *PaymentError, value = nil.
  5. err != nil asks "is the interface empty?" No: the type word is set. So the check is true and we go into the failure branch.
  6. We print "failed" for a payment that succeeded, and the error even prints as <nil>. In production this shows up as mysterious "error: <nil>" log lines.
Rule

Never return a concrete pointer type through an interface on the "no error" path. Declare the function to return error, and write return nil literally when there's no error. The same applies to any interface: if a function returns Payer, return nil, not (*Stripe)(nil).

var s *Stripe; var p Payer = s. What does fmt.Println(s == nil, p == nil) print?
s is a nil pointer, so s == nil is true. p holds (type *Stripe, value nil): the type word is set, so p == nil is false.

The empty interface, type assertions and type switches

any: the interface with no methods

An interface with zero methods, interface{}, is satisfied by every type, because every type has "at least zero methods". Since Go 1.18 it has a friendlier alias: any. You've already used it: fmt.Println(a ...any) accepts anything.

package main

import "fmt"

func main() {
	// any is an alias for interface{}: the interface with zero methods.
	// Every type satisfies it.
	var box any
	box = 42
	fmt.Printf("%v (%T)\n", box, box)
	box = "hello"
	fmt.Printf("%v (%T)\n", box, box)
	box = []string{"a", "b"}
	fmt.Printf("%v (%T)\n", box, box)

	// Common in decoded JSON with unknown shape.
	payload := map[string]any{
		"order_id": 101,
		"paid":     true,
		"items":    []any{"pen", "book"},
	}
	fmt.Println(len(payload), "keys")

	// But you can't DO much with an any until you get the type back.
	// n := box + 1 // compile error: mismatched types any and int
}
  1. any is just interface{}: zero methods, so every type satisfies it. It starts as a nil interface.
  2. Storing 42 records both the value and its dynamic type int.
  3. The same variable can be re-assigned a value of a completely different type. The type half of the pair changes too.
  4. Now it holds a slice. %T always reports the dynamic type, never "any".
  5. map[string]any is the shape encoding/json gives you for unknown JSON: values of mixed types under string keys.
  6. Three keys.
  7. The catch: an any has no methods, so you can't add to it, index it, or call anything on it. You must get the concrete type back with a type assertion or type switch first.
42 (int)
hello (string)
[a b] ([]string)
3 keys
Gotcha: any throws away type safety

Once a value is in an any, the compiler can't help you any more; you have to check types at run time. Use any at true boundaries (decoding unknown JSON, generic printing, logging fields). Inside your own code, prefer a real interface with methods, or generics (Chapter 09) when you need "works for many types" with full type checking.

Type assertions: getting the concrete value back

A type assertion x.(T) asks: "is the thing in this interface a T? If so, give it to me as a T." Always prefer the two-value comma-ok form:

package main

import "fmt"

type Payer interface{ Pay(float64) error }

type Razorpay struct{ KeyID string }

func (r Razorpay) Pay(float64) error { return nil }

type Stripe struct{ Account string }

func (s Stripe) Pay(float64) error { return nil }

func main() {
	var p Payer = Razorpay{KeyID: "rzp_live"}

	// Comma-ok form: never panics.
	if r, ok := p.(Razorpay); ok {
		fmt.Println("it's Razorpay, key =", r.KeyID)
	}

	s, ok := p.(Stripe)
	fmt.Printf("Stripe? ok=%v, s=%+v (zero value)\n", ok, s)

	// Asserting to another INTERFACE: "does it also have this method?"
	_, isStringer := p.(fmt.Stringer)
	fmt.Println("is Stringer?", isStringer)

	// Works on any too.
	var v any = 3.14
	f, ok := v.(float64)
	fmt.Println(f, ok)
}
  1. The interface holds a Razorpay value.
  2. p.(Razorpay) asks "is the dynamic type exactly Razorpay?" Yes, so r gets the concrete value and ok is true.
  3. Now r is a real Razorpay, so we can read r.KeyID, which the Payer interface never exposed.
  4. Asserting to Stripe fails. With the comma-ok form there is no panic: ok is false and s is Stripe's zero value.
  5. Always check ok before trusting s.
  6. Asserting to an interface type asks a different question: "does the stored value also have a String() method?" Razorpay doesn't.
  7. Same tool on an any: the untyped constant 3.14 defaulted to float64, so the assertion succeeds.
it's Razorpay, key = rzp_live
Stripe? ok=false, s={Account:} (zero value)
is Stringer? false
3.14 true
  • v, ok := x.(T): if it matches, ok is true and v is the value. If not, ok is false and v is T's zero value. Never panics.
  • T can be a concrete type (Razorpay) or another interface (fmt.Stringer). The second form asks "does it also have these methods?"; we'll use that for optional capabilities shortly.

The single-value form v := x.(T) panics on a mismatch:

package main

import "fmt"

func main() {
	var v any = "forty-two"
	n := v.(int) // single-value form panics on mismatch
	fmt.Println(n)
}

main.main()

Type switches: many assertions at once

When you need to handle several possible types, a type switch is cleaner than a chain of assertions. The special syntax switch x := v.(type) gives you x already converted to the matching case's type.

package main

import (
	"errors"
	"fmt"
)

type Razorpay struct{ KeyID string }
type Stripe struct{ Account string }

func describe(v any) string {
	switch x := v.(type) {
	case nil:
		return "nothing at all"
	case int, int64:
		return fmt.Sprintf("an integer: %v", x) // x is still any here
	case string:
		return fmt.Sprintf("a string of %d bytes", len(x)) // x is a string
	case error:
		return "an error: " + x.Error()
	case Razorpay:
		return "Razorpay with key " + x.KeyID
	case *Stripe:
		return "pointer to Stripe account " + x.Account
	default:
		return fmt.Sprintf("something else: %T", x)
	}
}

func main() {
	fmt.Println(describe(nil))
	fmt.Println(describe(7))
	fmt.Println(describe("₹499"))
	fmt.Println(describe(errors.New("timeout")))
	fmt.Println(describe(Razorpay{KeyID: "rzp_1"}))
	fmt.Println(describe(&Stripe{Account: "acct_9"}))
	fmt.Println(describe(3.5))
}
nothing at all
an integer: 7
a string of 6 bytes
an error: timeout
Razorpay with key rzp_1
pointer to Stripe account acct_9
something else: float64
  • In a case with one type (case string:), x has that type, so len(x) works. Note "₹499" is 6 bytes (₹ takes 3 in UTF-8; see Chapter 06).
  • In a case with several types (case int, int64:), Go can't pick one, so x stays any.
  • Cases can be interfaces (case error:) and are checked top to bottom; the first match wins. Put specific types before broad interfaces.
  • case nil: matches a nil interface.
func describe(v any) string {
	switch x := v.(type) {
	case int:
		return fmt.Sprint("int doubled: ", x*2)
	case string:
		return "string: " + x
	case Razorpay:
		return "gateway key " + x.KeyID
	default:
		return fmt.Sprintf("unknown %T", x)
	}
}

func main() {
	fmt.Println(describe(21))
	fmt.Println(describe(Razorpay{KeyID: "rzp_1"}))
	fmt.Println(describe(true))
}
  1. We pass 21. It gets boxed into v as (type int, value 21).
  2. The switch reads v's dynamic type: int. The first case matches, and x is a real int.
  3. Because x is an int, x*2 compiles. We'd need an assertion to do arithmetic on v directly.
  4. Second call: dynamic type is Razorpay. Cases int and string don't match…
  5. …case Razorpay does. x is a Razorpay, so x.KeyID is accessible.
  6. A bool matches nothing, so default runs. In default, x has the same type as v (any).
Senior engineer tip

If you find yourself writing a type switch over your own types to decide behaviour (case Razorpay: ... case Stripe: ...), that's usually a sign the behaviour should be a method on the interface instead. Every new gateway would otherwise mean editing that switch. Type switches are best at boundaries with genuinely open-ended data: decoded JSON, AST nodes, error classification.

fmt.Stringer and error

package main

import (
	"errors"
	"fmt"
)

// The built-in error interface is just:
//
//	type error interface { Error() string }
type DeclinedError struct {
	OrderID int
	Reason  string
}

func (e *DeclinedError) Error() string {
	return fmt.Sprintf("order %d declined: %s", e.OrderID, e.Reason)
}

type Money struct {
	Paise    int64
	Currency string
}

// Stringer controls how fmt prints the value.
func (m Money) String() string {
	return fmt.Sprintf("%s %d.%02d", m.Currency, m.Paise/100, m.Paise%100)
}

func charge(orderID int, m Money) error {
	if m.Paise > 1_000_000 {
		return &DeclinedError{OrderID: orderID, Reason: "limit exceeded"}
	}
	return nil
}

func main() {
	price := Money{Paise: 49900, Currency: "INR"}
	fmt.Println("charging", price)

	err := charge(7, Money{Paise: 5_000_000, Currency: "INR"})
	fmt.Println(err)

	var de *DeclinedError
	if errors.As(err, &de) { // preview of Chapter 10
		fmt.Println("reason only:", de.Reason)
	}
}
  1. Money is stored in paise (integer) to avoid floating-point rounding.
  2. Money has a String() method, so Println calls it: 49900 / 100 = 499, 49900 % 100 = 0, padded with %02d.
  3. 5,000,000 paise is over the limit, so charge returns a *DeclinedError. It satisfies error because it has Error() string.
  4. Println(err) sees an error and calls its Error() method.
  5. errors.As checks whether the error is a *DeclinedError and, if so, stores it in de. Now we have the concrete type back.
  6. Structured fields like Reason are available to the caller, not just a string.
charging INR 499.00
order 7 declined: limit exceeded
reason only: limit exceeded

Custom error types usually use a pointer receiver for Error(), and you return them as &DeclinedError{...}. Then errors.As(err, &target) with var target *DeclinedError can pull out the fields. Chapter 10 covers this properly.

io.Reader and io.Writer

These two are Go's universal plumbing. Read fills the slice you give it and says how many bytes it wrote; at the end it returns io.EOF. Write takes bytes and pushes them somewhere. Because they're so small, everything implements them, and you can snap them together like Lego.

package main

import (
	"bytes"
	"fmt"
	"io"
	"os"
	"strings"
	"unicode"
)

// upperWriter wraps ANY io.Writer and upper-cases what passes through.
type upperWriter struct {
	w io.Writer
}

func (u upperWriter) Write(p []byte) (int, error) {
	return u.w.Write(bytes.ToUpper(p))
}

// countLetters works with ANY io.Reader: a file, a network socket, a string...
func countLetters(r io.Reader) (int, error) {
	buf := make([]byte, 8) // tiny buffer to show Read is called repeatedly
	n := 0
	for {
		k, err := r.Read(buf)
		for _, b := range buf[:k] {
			if unicode.IsLetter(rune(b)) {
				n++
			}
		}
		if err == io.EOF {
			return n, nil
		}
		if err != nil {
			return n, err
		}
	}
}

func main() {
	receipt := "Order 101: 2 x pen, 1 x book\n"

	n, _ := countLetters(strings.NewReader(receipt))
	fmt.Println("letters:", n)

	// io.Copy moves bytes from any Reader to any Writer.
	io.Copy(os.Stdout, strings.NewReader(receipt))
	io.Copy(upperWriter{w: os.Stdout}, strings.NewReader(receipt))

	// Writers compose: write into a buffer through the upper-caser.
	var buf bytes.Buffer
	fmt.Fprintf(upperWriter{w: &buf}, "total: ₹%d\n", 135)
	fmt.Print("buffered -> ", buf.String())
}
  1. The receipt is 29 bytes long including the newline.
  2. strings.NewReader returns a *strings.Reader, which has a Read method, so it is an io.Reader. countLetters only knows about the interface.
  3. First Read fills all 8 bytes. We only loop over buf[:k], the bytes actually read. 5 letters.
  4. Second call continues where the reader left off. x and p are letters.
  5. Third call: e, n, x.
  6. Only 5 bytes remain, so k=5. Using buf[:k] matters here: the last 3 bytes of buf are stale leftovers.
  7. The fifth call has nothing left: k=0, err=io.EOF. EOF is the normal "done" signal, so we return 14, nil.
  8. Back in main.
  9. io.Copy pumps from any Reader to any Writer. os.Stdout is a Writer, so the receipt prints unchanged.
  10. Same copy, but the destination is our upperWriter. Its Write upper-cases the bytes and forwards them to the wrapped os.Stdout.
  11. Fprintf writes to any Writer. Here the wrapper forwards into a *bytes.Buffer instead of the terminal. Same type, different destination.
  12. Printing the buffer shows the upper-cased text. Small interfaces compose freely.
letters: 14
Order 101: 2 x pen, 1 x book
ORDER 101: 2 X PEN, 1 X BOOK
buffered -> TOTAL: ₹135
  • countLetters doesn't know if it's reading a string, a 2 GB file or a TCP connection. It just loops on Read until io.EOF. (It checks bytes one by one, which is fine for ASCII letters like here.)
  • upperWriter wraps any io.Writer: a stdout, a buffer, a file. Wrapping one implementation of an interface inside another is the decorator pattern; you'll see it again with HTTP middleware.
  • Note the Read loop: process buf[:k] before checking the error. A reader may return data and io.EOF in the same call.

sort.Interface (and the modern alternative)

package main

import (
	"cmp"
	"fmt"
	"slices"
	"sort"
)

type Order struct {
	ID    int
	Total float64
}

// ByTotal implements sort.Interface: Len, Less, Swap.
type ByTotal []Order

func (o ByTotal) Len() int           { return len(o) }
func (o ByTotal) Less(i, j int) bool { return o[i].Total < o[j].Total }
func (o ByTotal) Swap(i, j int)      { o[i], o[j] = o[j], o[i] }

func main() {
	orders := []Order{{1, 899}, {2, 120}, {3, 4500}, {4, 120}}

	sort.Sort(ByTotal(orders)) // the classic, interface-based way
	fmt.Println("sort.Sort:      ", orders)

	// Modern Go (1.21+): a comparison function, no wrapper type needed.
	slices.SortFunc(orders, func(a, b Order) int {
		return cmp.Or(
			cmp.Compare(b.Total, a.Total), // highest total first
			cmp.Compare(a.ID, b.ID),       // then by ID
		)
	})
	fmt.Println("slices.SortFunc:", orders)
}
  1. Four unsorted orders. Two share a total of 120.
  2. ByTotal(orders) is a conversion, not a copy: same backing array, new type. That type has Len, Less, Swap, so it satisfies sort.Interface.
  3. sort.Sort repeatedly calls Less(i, j) and Swap(i, j) through the interface. Because Swap writes into the shared array, orders itself ends up sorted.
  4. Ascending by total. Note sort.Sort is not stable: ties are in no guaranteed order.
  5. The modern way: pass a comparison func that returns negative, zero, or positive. cmp.Compare(b.Total, a.Total) reverses the order; cmp.Or picks the first non-zero result, so ties fall back to ID.
  6. Highest total first, and the 120 tie broken by ID 2 before 4. No wrapper type needed.
sort.Sort:       [{2 120} {4 120} {1 899} {3 4500}]
slices.SortFunc: [{3 4500} {1 899} {2 120} {4 120}]

You'll still see sort.Interface in older code and it's a nice tiny example of interface-driven design. In new code, prefer slices.SortFunc (or slices.SortStableFunc when equal elements must keep their order; sort.Sort isn't stable either). Combining keys with cmp.Or keeps multi-field sorting readable.

Composing interfaces with embedding

Interfaces can embed other interfaces. The result's method set is the union. This is how the stdlib builds io.ReadWriter from io.Reader + io.Writer, and how you can build a store interface from read and write halves:

package main

import (
	"errors"
	"fmt"
	"io"
)

type Order struct {
	ID    int
	Total float64
}

// Small interfaces...
type OrderReader interface {
	Get(id int) (Order, error)
}

type OrderWriter interface {
	Save(o Order) error
}

// ...combined by embedding, exactly like io.ReadWriter = Reader + Writer.
type OrderStore interface {
	OrderReader
	OrderWriter
}

var ErrNotFound = errors.New("order not found")

type memStore struct{ m map[int]Order }

func (s *memStore) Get(id int) (Order, error) {
	o, ok := s.m[id]
	if !ok {
		return Order{}, ErrNotFound
	}
	return o, nil
}

func (s *memStore) Save(o Order) error {
	s.m[o.ID] = o
	return nil
}

// A report only needs to READ, so it asks for the smallest interface.
func printReport(r OrderReader, ids ...int) {
	for _, id := range ids {
		o, err := r.Get(id)
		if err != nil {
			fmt.Printf("#%d: %v\n", id, err)
			continue
		}
		fmt.Printf("#%d: ₹%.2f\n", o.ID, o.Total)
	}
}

func main() {
	var store OrderStore = &memStore{m: map[int]Order{}}
	store.Save(Order{ID: 1, Total: 499})
	store.Save(Order{ID: 2, Total: 1299})

	printReport(store, 1, 2, 3) // an OrderStore IS an OrderReader

	var _ io.ReadWriter // the stdlib does the same thing
}
#1: ₹499.00
#2: ₹1299.00
#3: order not found

Notice printReport asks only for OrderReader. It can't accidentally write, and in a test you only need to fake Get. Small interfaces make both the code and its tests smaller.

Mental model

Think of interfaces as permissions. Handing a function an OrderReader is like handing someone a read-only key. Hand out the narrowest key that does the job.

Designing with interfaces

Keep them small

"The bigger the interface, the weaker the abstraction." (Go proverb). One- or two-method interfaces (Reader, Writer, Stringer, Payer) have dozens of implementations. A 15-method OrderRepository interface has exactly one real implementation and one painful mock. By convention, single-method interfaces are named method + "er": Reader, Payer, Notifier.

Define them at the consumer

In Java, the package that provides a class also declares its interface. In Go, it's usually the opposite: the package that uses a dependency declares a small interface describing just what it needs. The provider exports a plain concrete type. Implicit satisfaction makes that work without the two packages knowing about each other.

Accept interfaces, return structs

A function's parameters should be as general as possible (interfaces, so callers can pass anything suitable), and its return values as specific as possible (concrete types, so callers get every method and field, and can wrap them in whatever interface they need).

// package razorpay (the PROVIDER)
type Client interface { // provider-side, big
	Pay(float64) error
	Refund(float64) error
	Payouts() []Payout
	Webhooks() WebhookAPI
	// ...12 more
}

// returns an interface: callers can't reach
// new methods or fields without asserting
func New(key string) Client { ... }

// consumer must accept the huge interface
func Checkout(c razorpay.Client) { ... }
// package razorpay (the PROVIDER)
type Client struct{ key string }

// return the concrete struct
func New(key string) *Client { ... }
func (c *Client) Pay(float64) error    { ... }
func (c *Client) Refund(float64) error { ... }

// package checkout (the CONSUMER)
// declares only what it needs
type Payer interface {
	Pay(amount float64) error
}

func Checkout(p Payer) { ... }
Senior engineer tip

There are good exceptions to "return structs": returning error (always an interface), constructors in packages whose whole point is hiding implementations (hash.Hash from sha256.New(), cipher.Block), and factory functions that choose an implementation at run time. The rule is a default, not a law. What you really want to avoid is pre-emptive, provider-side, fat interfaces that exist only to be mocked.

Compile-time assertions

Because satisfaction is implicit, a typo in a method signature isn't caught until something tries to use the type as the interface, which might be in a different package or only in production wiring. Pin it down with a one-liner that costs nothing at runtime:

package main

type Payer interface {
	Pay(amount float64) error
}

type Paytm struct{}

// Oops: wrong signature (float32 instead of float64).
func (p *Paytm) Pay(amount float32) error { return nil }

// Compile-time check: "*Paytm must implement Payer".
// Costs nothing at runtime: it's a nil pointer assigned to _ .
var _ Payer = (*Paytm)(nil)

func main() {}
# command-line-arguments
./main.go:14:15: cannot use (*Paytm)(nil) (value of type *Paytm) as Payer value in variable declaration: *Paytm does not implement Payer (wrong type for method Pay)
		have Pay(float32) error
		want Pay(float64) error

var _ Payer = (*Paytm)(nil) means: "assign a nil *Paytm to a throwaway variable of type Payer". If *Paytm doesn't satisfy Payer, the build fails right there with a precise message. For value-receiver types, var _ Payer = Razorpay{} works too.

Optional capabilities: upgrading an interface

Sometimes only some implementations can do an extra thing. Rather than bloating Payer with a Refund method that cash-on-delivery can't implement, define a separate small interface and check for it with a type assertion. The stdlib does this constantly: io.Copy checks whether your Reader is also an io.WriterTo to take a faster path; http.ResponseWriter may also be an http.Flusher.

package main

import (
	"errors"
	"fmt"
)

type Payer interface {
	Pay(amount float64) error
}

// Refunder is an OPTIONAL capability some gateways have.
type Refunder interface {
	Refund(amount float64) error
}

type Razorpay struct{}

func (Razorpay) Pay(a float64) error    { fmt.Printf("razorpay pay %.0f\n", a); return nil }
func (Razorpay) Refund(a float64) error { fmt.Printf("razorpay refund %.0f\n", a); return nil }

type CashOnDelivery struct{}

func (CashOnDelivery) Pay(a float64) error { fmt.Printf("COD collect %.0f\n", a); return nil }

// Compile-time proofs.
var (
	_ Payer    = Razorpay{}
	_ Refunder = Razorpay{}
	_ Payer    = CashOnDelivery{}
)

func cancelOrder(p Payer, amount float64) error {
	// Upgrade check: does this Payer ALSO know how to refund?
	if r, ok := p.(Refunder); ok {
		return r.Refund(amount)
	}
	return errors.New("gateway cannot refund; raise a manual ticket")
}

func main() {
	for _, p := range []Payer{Razorpay{}, CashOnDelivery{}} {
		p.Pay(250)
		if err := cancelOrder(p, 250); err != nil {
			fmt.Println("error:", err)
		}
	}
}

		p.Pay(250)
		if err := cancelOrder(p, 250); err != nil {
			fmt.Println("error:", err)
		}
	}
}
  1. First iteration: p holds a Razorpay, viewed through the narrow Payer interface.
  2. Paying works for every Payer.
  3. Inside cancelOrder, p.(Refunder) asks: "does the concrete type also have Refund(float64) error?" Razorpay does, so ok is true and r is a Refunder.
  4. We call Refund and return its (nil) error, so nothing is printed in main.
  5. Second iteration: cash on delivery. Paying still works.
  6. CashOnDelivery has no Refund, so the assertion fails safely (comma-ok, no panic) and we fall through to the error.
  7. The caller gets a clear error instead of a crash or a fake no-op refund.
Gotcha: wrappers hide optional interfaces

If you wrap a Razorpay in a loggingPayer decorator that only implements Pay, the upgrade check now sees the wrapper and finds no Refund. The capability silently disappears. Either have the wrapper forward the optional method too, or give it an Unwrap() Payer so callers can dig through. (The same issue hits HTTP middleware that wraps ResponseWriter and loses Flush; that's why http.ResponseController exists.)

Mocking with interfaces for tests

Here's where interfaces pay their rent. If your business logic depends on an interface rather than on Razorpay directly, a test can hand it a tiny fake that records what happened and returns whatever result the test wants: success, decline, timeout. No network, no sandbox account, no flakiness, tests run in milliseconds.

Dependency injection, the Go way

Dependency injection (DI) sounds grand, but in Go it just means: a type receives the things it depends on as constructor arguments, instead of creating them itself. The arguments are interfaces, so you can pass real implementations in production and fakes in tests. You already did it above with NewService(p, n).

All the wiring lives in one place, usually main, called the composition root. That's also where decorators get layered on:

package main

import (
	"fmt"
	"time"
)

// ---- interfaces (owned by the consumer: OrderService) ----

type Payer interface {
	Pay(amount float64) error
}

type Notifier interface {
	Notify(customerID int, msg string) error
}

// ---- concrete implementations ----

type Razorpay struct{ KeyID string }

func (r *Razorpay) Pay(amount float64) error {
	fmt.Printf("  razorpay: charging ₹%.2f\n", amount)
	return nil
}

type SMSNotifier struct{ Sender string }

func (s *SMSNotifier) Notify(id int, msg string) error {
	fmt.Printf("  sms from %s to customer %d: %s\n", s.Sender, id, msg)
	return nil
}

// loggingPayer is a DECORATOR: it is a Payer that wraps another Payer.
type loggingPayer struct {
	next Payer
	now  func() time.Time
}

func (l loggingPayer) Pay(amount float64) error {
	start := l.now()
	err := l.next.Pay(amount)
	fmt.Printf("  log: Pay(%.2f) err=%v took=%v\n", amount, err, l.now().Sub(start))
	return err
}

// ---- the business logic: knows only interfaces ----

type OrderService struct {
	payer    Payer
	notifier Notifier
}

func NewOrderService(p Payer, n Notifier) *OrderService {
	return &OrderService{payer: p, notifier: n}
}

func (s *OrderService) PlaceOrder(customerID int, amount float64) error {
	if err := s.payer.Pay(amount); err != nil {
		return err
	}
	return s.notifier.Notify(customerID, "order confirmed")
}

func main() {
	// Wiring happens in ONE place: main (the "composition root").
	fixed := time.Date(2026, 10, 16, 10, 0, 0, 0, time.UTC)
	clock := func() time.Time { return fixed } // deterministic clock for the demo

	var payer Payer = &Razorpay{KeyID: "rzp_live_xxx"}
	payer = loggingPayer{next: payer, now: clock} // add logging without touching Razorpay

	svc := NewOrderService(payer, &SMSNotifier{Sender: "SHOPIN"})

	fmt.Println("placing order:")
	if err := svc.PlaceOrder(42, 1299); err != nil {
		fmt.Println("error:", err)
	}
}

  • OrderService has no idea Razorpay, SMS or logging exist. Swap SMS for email, or Razorpay for Stripe, by changing one line in main.
  • loggingPayer is a Payer wrapping a Payer. You can stack retries, metrics, circuit breakers the same way without touching business code.
  • Even the clock is injected (now func() time.Time), which makes time-dependent code testable. A function type is a perfectly good "one-method interface".

Go projects rarely need a DI framework. Plain constructors called from main stay readable well into dozens of dependencies. If wiring gets genuinely large, Google's wire generates that same plain code for you at build time, so there's still no runtime magic.

Performance notes and practice

Interfaces are cheap, but not free. Worth knowing:

  • A method call through an interface is an indirect call via the itab: a couple of nanoseconds. The bigger cost is that the compiler usually can't inline it (though modern Go does "devirtualize" calls when it can prove the concrete type, especially with profile-guided optimisation).
  • Storing a value in an interface may allocate. The data word must be a pointer, so a non-pointer value that doesn't fit is copied to the heap ("boxing"). Small constants and pointers usually avoid this. In hot loops over millions of items, this can show up in profiles (Chapter 18).
  • For 99% of code (HTTP handlers, business logic, I/O) these costs are invisible next to a network or database call. Design for clarity; optimise from profiles.
Exercise 1: A fan-out Notifier

Define Notifier with Notify(customerID int, msg string) error. Implement EmailNotifier and an SMSNotifier that truncates messages over 20 characters. Then write MultiNotifier, a slice of Notifiers that is itself a Notifier and sends to all of them. Add compile-time assertions.

Solution
package main

import (
	"fmt"
	"strings"
)

type Notifier interface {
	Notify(customerID int, msg string) error
}

type EmailNotifier struct{ From string }

func (e EmailNotifier) Notify(id int, msg string) error {
	fmt.Printf("email from %s to #%d: %s\n", e.From, id, msg)
	return nil
}

type SMSNotifier struct{}

func (SMSNotifier) Notify(id int, msg string) error {
	if len(msg) > 20 {
		msg = msg[:17] + "..."
	}
	fmt.Printf("sms to #%d: %s\n", id, msg)
	return nil
}

// MultiNotifier is itself a Notifier that fans out to many.
type MultiNotifier []Notifier

func (m MultiNotifier) Notify(id int, msg string) error {
	var failed []string
	for _, n := range m {
		if err := n.Notify(id, msg); err != nil {
			failed = append(failed, err.Error())
		}
	}
	if len(failed) > 0 {
		return fmt.Errorf("notify: %s", strings.Join(failed, "; "))
	}
	return nil
}

var (
	_ Notifier = EmailNotifier{}
	_ Notifier = SMSNotifier{}
	_ Notifier = MultiNotifier{}
)

func main() {
	var n Notifier = MultiNotifier{EmailNotifier{From: "orders@shop.in"}, SMSNotifier{}}
	n.Notify(42, "Your order #101 has been shipped")
}
  1. Compile-time assertions: if any of these types stopped satisfying Notifier, the build would fail right here instead of somewhere far away.
  2. MultiNotifier is a slice of Notifiers that is itself a Notifier. The caller sees one notifier and has no idea it fans out.
  3. n.Notify dispatches to MultiNotifier.Notify, which loops over its members.
  4. Member 1 is an EmailNotifier, so the interface call lands in EmailNotifier.Notify. It returns nil, so nothing is added to failed.
  5. Member 2 is an SMSNotifier. The 32-byte message is over 20, so it is cut to 17 bytes plus .... This only reassigns the local msg copy.
  6. The SMS goes out truncated, and returns nil.
  7. The loop is done and failed is empty, so MultiNotifier returns nil. This "composite" pattern works for loggers, metrics, and hooks too.

Exercise 2: Sum a messy cart with a type switch

Write total(items []any) (float64, []string) that adds up int and float64 items and returns a description of everything it skipped. Items that are fmt.Stringer should be described with their String() method; anything else with %T(%v).

Solution
package main

import "fmt"

func total(items []any) (float64, []string) {
	var sum float64
	var skipped []string
	for _, it := range items {
		switch v := it.(type) {
		case int:
			sum += float64(v)
		case float64:
			sum += v
		case fmt.Stringer:
			skipped = append(skipped, v.String())
		default:
			skipped = append(skipped, fmt.Sprintf("%T(%v)", v, v))
		}
	}
	return sum, skipped
}

type SKU string

func (s SKU) String() string { return "sku:" + string(s) }

func main() {
	sum, skipped := total([]any{100, 49.5, "oops", SKU("PEN-1"), 25, nil})
	fmt.Println("sum:", sum)
	fmt.Println("skipped:", skipped)
}
  1. main passes a []any with six mixed values. total starts with zero values.
  2. Item 1: the type switch matches case int. Inside that case v is a real int, so we can convert and add it.
  3. Item 2 is a float64: added directly.
  4. Item 3 is a string. No case for it, so default records its type and value.
  5. Item 4 is a SKU. It isn't int or float64, but it has a String() method, so it matches the interface case fmt.Stringer. Cases are tried top to bottom.
  6. Item 5: another int.
  7. Item 6 is a nil interface. There's no case nil, so it lands in default, and %T of nil prints <nil>.
  8. Both results return to main.
  9. Three items were skipped, each described by the branch that caught it.
sum: 174.5
skipped: [string(oops) sku:PEN-1 <nil>(<nil>)]
Exercise 3: A retrying Payer decorator

Write retryPayer, a Payer that wraps another Payer and retries up to N attempts. Test it with a flaky payer that fails its first few calls. The final error should wrap the last underlying error with %w.

Solution
package main

import (
	"errors"
	"fmt"
)

type Payer interface {
	Pay(amount float64) error
}

// retryPayer is a decorator: a Payer that wraps a Payer.
type retryPayer struct {
	next     Payer
	attempts int
}

func (r retryPayer) Pay(amount float64) error {
	var err error
	for i := 1; i <= r.attempts; i++ {
		if err = r.next.Pay(amount); err == nil {
			return nil
		}
		fmt.Printf("attempt %d failed: %v\n", i, err)
	}
	return fmt.Errorf("gave up after %d attempts: %w", r.attempts, err)
}

// flaky fails the first N calls.
type flaky struct{ failsLeft int }

func (f *flaky) Pay(amount float64) error {
	if f.failsLeft > 0 {
		f.failsLeft--
		return errors.New("gateway timeout")
	}
	fmt.Printf("charged ₹%.2f\n", amount)
	return nil
}

func main() {
	var p Payer = retryPayer{next: &flaky{failsLeft: 2}, attempts: 3}
	fmt.Println("result:", p.Pay(799))

	p = retryPayer{next: &flaky{failsLeft: 5}, attempts: 2}
	fmt.Println("result:", p.Pay(799))
}
  1. A decorator: retryPayer is a Payer wrapping another Payer. The inner one fails its first 2 calls.
  2. Attempt 1: r.next.Pay dispatches to (*flaky).Pay. It decrements failsLeft and fails. flaky needs a pointer receiver so the counter actually goes down.
  3. The wrapper logs and loops.
  4. Attempt 2 fails the same way, using up the last failure.
  5. Attempt 3: failsLeft is 0, so the charge succeeds and returns nil.
  6. The wrapper returns nil immediately. The caller just sees a successful Pay.

  8. Attempt 1 fails.
  9. Attempt 2 fails. i becomes 3, which exceeds attempts, so the loop ends.
  10. %w wraps the last error, so callers can still detect the gateway timeout with errors.Is.

Key takeaways

  • An interface is a set of method signatures. Any type with those methods satisfies it implicitly; no implements keyword.
  • An interface value is a (type, data) pair. It's nil only when both are nil. A nil pointer inside an interface is not a nil interface: return a literal nil.
  • any holds anything but gives up type safety. Get values back with comma-ok type assertions or type switches.
  • Learn the stdlib's tiny interfaces: Stringer, error, io.Reader, io.Writer. They make everything composable.
  • Keep interfaces small, define them where they're used, and "accept interfaces, return structs".
  • Use var _ I = (*T)(nil) to catch broken implementations at compile time.
  • Optional capabilities: assert to a second small interface (p.(Refunder)). Beware wrappers hiding them.
  • Interfaces enable fakes for fast tests, decorators (logging, retry), and plain-constructor dependency injection wired in main.

Variables, Types & Constants

Every program is about storing values and transforming them. In this chapter you'll learn how Go names values, what types it gives them, why it refuses to convert between types behind your back, and how its surprisingly powerful constants (and the little word iota) work.

Why types matter

A variable is a named box in memory that holds a value. A type tells Go two things about that box: how many bytes it takes up, and which operations make sense on it. You can add two numbers, but not a number and a list. You can ask the length of a string, but not of a boolean.

Go is statically typed: every variable's type is fixed at compile time and never changes. That sounds restrictive if you come from Python or JavaScript, but it buys you a lot:

  • Mistakes are caught before the program runs. A typo that would crash a Python script at 2am in production fails the Go build on your laptop.
  • Code documents itself. func Charge(amountCents int64, currency string) tells you exactly what to pass.
  • Speed. The compiler knows the exact memory layout, so it generates tight machine code with no runtime type checks.
  • Tooling. Autocomplete, rename and "find all usages" are exact, not guesses.

And thanks to type inference, you rarely have to write the types: count := 3 is clearly an int, and Go figures it out.

Declaring variables: var and :=

Go has two ways to create a variable. Here are all the forms in one program:

package main

import "fmt"

// Package-level variables: must use var (no := outside functions).
var appName = "inventory"
var maxItems int = 100

var (
	debug   bool
	version = "1.0.0"
)

func main() {
	var count int           // type, no value -> zero value
	var price float64 = 9.5 // type and value
	var label = "widget"    // value only, type inferred (string)
	qty := 3                // short declaration: inferred int

	var x, y int = 1, 2   // several of one type
	var a, b = "hi", true // several, mixed types inferred
	first, second := 10, 20

	fmt.Println(appName, maxItems, debug, version)
	fmt.Println(count, price, label, qty)
	fmt.Println(x, y, a, b, first, second)
}
inventory 100 false 1.0.0
0 9.5 widget 3
1 2 hi true 10 20

The long form: var

var name Type = value. You may leave out the type (Go infers it from the value) or the value (the variable gets its type's zero value), but not both. Several declarations can be grouped in var ( ... ), which is common at package level.

The short form: :=

name := value declares and initializes in one go, with the type inferred. Read := as "is defined as". It's the form you'll use most inside functions. Two rules:

  1. := only works inside functions. At package level, every statement must start with a keyword (var, func, type, …), so the parser can tell declarations apart quickly.
  2. := must declare at least one new variable on its left side.
package main

import "fmt"

name := "gopher"

func main() {
	fmt.Println(name)
}

Multiple assignment, swaps and the "one new variable" rule

Go can assign several variables at once. All the right-hand values are evaluated first, then assigned — which makes swapping trivial. And when a function returns two values (very common: a result and an error), := lets you reuse an existing variable as long as at least one on the left is new.

n, err := strconv.Atoi("42")
fmt.Println(n, err)

m, err := strconv.Atoi("x7") // ok: m is new, err is reused
fmt.Println(m, err)

a, b := 1, 2
a, b = b, a // swap: right side is evaluated first
fmt.Println(a, b)

a, b, c := b, a+b, 99 // c is new, so := is allowed
fmt.Println(a, b, c)
  1. strconv.Atoi converts a string to an int and returns two values: the number and an error. Both n and err are new, so := declares both.
  2. nil means "no error". It prints as <nil>.
  3. Here m is new but err already exists. That's allowed: := declares m and simply assigns to the existing err (same variable, same scope). Parsing "x7" fails, so m is 0 and err describes the problem.
  4. Errors in Go are values that describe what went wrong (Chapter 10).
  5. Two new variables at once.
  6. The swap: Go evaluates the right side (b, a) = (2, 1) completely, then assigns. No temporary variable needed.
  7. Printed.
  8. Right side first: b is 1, a+b is 3, and 99. Then a=1, b=3, and the new c=99. Because c is new, := is legal even though a and b exist.
  9. Done.

Shadowing: the same name, a different variable

A scope is the region of code where a name is visible. Every pair of braces { } opens a new scope. If you declare a variable with the same name as one in an outer scope, the inner one shadows (hides) the outer one until the closing brace. This is legal — and a classic source of bugs, especially with err.

var err error
x := 1
if true {
	x := 2 // NEW x, shadows the outer one
	x++
	fmt.Println("inner x:", x)

	_, err := load() // NEW err! outer err stays nil
	fmt.Println("inner err:", err)
}
fmt.Println("outer x:", x)
fmt.Println("outer err:", err)
  1. Two variables in main's scope.
  2. Inside the if block, x := 2 creates a brand-new variable that happens to be called x. The outer x still exists, untouched, just hidden.
  3. We increment the inner x only.
  4. The bug: _, err := load() uses :=, and since we're in a new scope, it declares a new err instead of assigning to the outer one. The real error gets trapped in here.
  5. Inside, we can see it…
  6. …but at the closing brace both inner variables disappear. The outer x is still 1.
  7. And the outer err is still nil — the program thinks everything went fine. To fix it, declare nothing in the block and use plain assignment: _, err = load().
inner x: 3
inner err: disk on fire
outer x: 1
outer err: <nil>
Gotcha: := inside if/for blocks

Whenever you write := inside a block and the name already exists outside, stop and ask: "do I want a new variable or to update the old one?" Shadowing err is one of the most common real-world Go bugs. The shadow analyzer (go install golang.org/x/tools/go/analysis/passes/shadow/cmd/shadow@latest) and golangci-lint can flag it.

Scope levels

From outermost to innermost:

  1. Universe — predeclared names like int, true, nil, len, append.
  2. Package — top-level declarations, visible in every file of the package.
  3. File — imported package names (each file has its own imports).
  4. Function — parameters, results, and variables declared in the body.
  5. Block — anything inside { }, plus the init statements of if, for and switch.
package main

import "fmt"

var level = "package" // package scope: visible in every file of the package

func main() {
	fmt.Println(level)
	level := "function" // shadows the package variable inside main
	fmt.Println(level)
	{
		level := "block" // a bare block creates a new scope
		fmt.Println(level)
	}
	for i := 0; i < 1; i++ { // i only exists inside the loop
		level := "loop"
		fmt.Println(level, i)
	}
	fmt.Println(level)
	show()
}

func show() { fmt.Println(level) }
  1. A package-level level exists before main starts. Every function in the package can see it.
  2. Inside main there's no local level yet, so the name resolves outward to the package variable.
  3. := declares a new variable in main's scope. It doesn't change the package one; it hides (shadows) it from here on.
  4. The innermost level wins.
  5. A bare { } opens a new scope, and := creates a third variable that lives only until the closing brace.
  6. The block ends and its level disappears.
  7. The loop's i and the body's level exist only inside the loop. One iteration runs.
  8. After the loop we're back to main's own level, untouched by the inner ones.
  9. show is a different function: main's locals are invisible there, so it sees the package variable. Scope is decided by where code is written, not who calls it.
package
function
block
loop 0
function
package

Notice the last two lines: after the blocks close, main sees its own level again, and show() — a different function — only ever sees the package-level one.

Senior engineer tip: scope as small as possible

Declare variables as close as possible to where they're used, in the smallest scope that works. A variable that lives for 3 lines is easy to reason about; one that lives for 300 is a liability. This is also why Go's if v, err := f(); err != nil form (Chapter 03) is so popular: v and err vanish after the if. And keep package-level mutable variables to a minimum — they're global state that every function (and goroutine) can touch.

Zero values: there's no such thing as "uninitialized"

In C, a variable you didn't initialize contains whatever garbage was in that memory. In JavaScript you get undefined. In Go, every variable is always initialized: if you don't give a value, it gets the zero value for its type.

package main

import "fmt"

type Point struct {
	X, Y int
}

func main() {
	var i int
	var f float64
	var b bool
	var s string
	var r rune
	var p *int
	var sl []int
	var m map[string]int
	var fn func()
	var e error
	var pt Point

	fmt.Printf("int     %v\n", i)
	fmt.Printf("float64 %v\n", f)
	fmt.Printf("bool    %v\n", b)
	fmt.Printf("string  %q\n", s)
	fmt.Printf("rune    %v\n", r)
	fmt.Printf("*int    %v\n", p)
	fmt.Printf("[]int   %v (nil? %v)\n", sl, sl == nil)
	fmt.Printf("map     %v (nil? %v)\n", m, m == nil)
	fmt.Printf("func    nil? %v\n", fn == nil)
	fmt.Printf("error   %v\n", e)
	fmt.Printf("Point   %+v\n", pt)

	// Zero values are usable:
	sl = append(sl, 1)                    // append to a nil slice works
	fmt.Println(len(m), m["missing"], sl) // reading a nil map works
}

Mental model: freshly wiped memory

Go hands you memory that's been wiped to all zero bytes. A zero int is all-zero bits; so is an empty string, false, and nil. That's why the zero values are what they are.

Senior engineer tip: make the zero value useful

This is a core Go design principle. The standard library is full of types that work without any constructor: var mu sync.Mutex is an unlocked mutex, var buf bytes.Buffer is an empty buffer ready to write, var wg sync.WaitGroup is ready to use. When you design your own types, aim for the same: if Config{} means "sensible defaults", callers don't need a constructor and can't forget to call one. A common trick is to make the zero value mean "default", e.g. treat Timeout == 0 as "use 30 seconds".

Numbers: integers

Go has integer types of explicit sizes. The number is the size in bits (8 bits = 1 byte). Types starting with u are unsigned: they can't be negative, but reach twice as high.

package main

import (
	"fmt"
	"math"
	"unsafe"
)

func main() {
	fmt.Println("int8   ", math.MinInt8, "to", math.MaxInt8)
	fmt.Println("int16  ", math.MinInt16, "to", math.MaxInt16)
	fmt.Println("int32  ", math.MinInt32, "to", math.MaxInt32)
	fmt.Println("int64  ", math.MinInt64, "to", math.MaxInt64)
	fmt.Println("uint8  ", 0, "to", math.MaxUint8)
	fmt.Println("uint16 ", 0, "to", math.MaxUint16)
	fmt.Println("uint32 ", 0, "to", math.MaxUint32)
	fmt.Println("uint64 ", 0, "to", uint64(math.MaxUint64))

	var u uintptr
	fmt.Println("int is", unsafe.Sizeof(i)*8, "bits; uintptr is", unsafe.Sizeof(u)*8, "bits")
	fmt.Println("float32 max", math.MaxFloat32)
	fmt.Println("float64 max", math.MaxFloat64)

  • int and uint are 32 bits on 32-bit platforms and 64 bits on 64-bit ones (nearly everything today). Use int by default — for counts, indexes, lengths, loop counters. len() returns int.
  • Use sized types when the size matters: binary file formats, network protocols, database columns, or huge arrays where memory adds up ([]int32 is half the size of []int64).
  • uintptr is an integer large enough to hold a memory address. You'll only see it in low-level unsafe code.
  • byte is an alias for uint8; rune is an alias for int32. More on these with strings below.

Integer literals can be written in several bases, and underscores can separate digits for readability:

million := 1_000_000   // underscores are ignored
hex     := 0xFF        // 255
octal   := 0o755       // 493 (Unix file permissions!)
binary  := 0b1010_0101 // 165
char    := 'A'         // 65, a rune literal

Overflow wraps around — silently

What happens when a value doesn't fit? At runtime, Go integer arithmetic wraps around, like a car odometer rolling from 999999 back to 000000. There is no error and no panic.

var small int8 = 127
small++
fmt.Println(small)

var u uint8 = 0
u--
fmt.Println(u)

big := math.MaxInt64
big++
fmt.Println(big)

var count uint = 3
fmt.Println(count - 5)
  1. int8 holds −128 to 127. We start at the very top.
  2. Adding one overflows. The bits 01111111 become 10000000, which in two's complement (how computers store signed integers) means −128.
  3. Unsigned types wrap the other way: 0 minus 1 becomes the maximum, 255.
  4. Same thing with a 64-bit int, just with bigger numbers.
  5. The sneaky one: 3 - 5 on an unsigned int is not −2; it wraps to nearly 264. This is why Go uses int (signed) even for lengths: subtracting lengths would otherwise produce huge numbers instead of negatives.

But when the overflow is visible at compile time — a constant that doesn't fit — Go refuses to compile:

package main

import "fmt"

func main() {
	var b byte = 256
	var i int8 = 200 - 100 + 100
	fmt.Println(b, i)
}

Gotcha: unsigned subtraction

Never use uint just because "this can't be negative". if a - b < 0 is always false for unsigned values, and an accidental len(x) - 1 on an empty unsigned length becomes 18 quintillion. Use int unless you need bit manipulation or an exact wire format.

Senior engineer tip: checking for overflow

Overflow bugs show up in money, counters and size calculations (e.g. width * height * 4 from untrusted input). When values come from outside, check bounds before you compute: if n > math.MaxInt32/4 { return errTooBig }. For arbitrary-size integers use math/big. Note also that math/bits.Add64 and bits.Mul64 return a carry so you can detect overflow precisely.

Integer division

package main

import "fmt"

func main() {
	fmt.Println(7/2, -7/2, 7%3, -7%3) // truncates toward zero
	fmt.Println(7.0 / 2)              // float division
	zero := 0
	fmt.Println(10 / zero) // integer division by zero: runtime panic
}
  1. All four expressions on this line use only untyped integer constants, so each one is integer arithmetic.
  2. Integer / truncates toward zero: 7/2 is 3 and −7/2 is −3 (not −4). % takes the sign of the left operand, so −7%3 is −1.
  3. 7.0 is a floating-point constant, so this is float division and the fraction survives.
  4. A variable holding 0. (Writing 10 / 0 with a literal would be caught at compile time.)
  5. Now 10 / zero is evaluated at run time. The compiler couldn't see that zero is 0, so it couldn't stop you.
  6. Integer division by zero panics at run time: the program prints the error and a stack trace pointing at line 9, then exits with status 2. Floats would give +Inf instead.

Integer division truncates toward zero (-7/2 is -3, not -4), and the remainder % takes the sign of the left operand. Dividing an integer by zero panics — a runtime crash with a stack trace (Chapter 10 explains panics). Dividing by a constant zero (10 / 0) is caught at compile time.

Numbers: floats and complex

Floating-point numbers hold fractions: float32 (about 7 decimal digits of precision) and float64 (about 15–16 digits). Use float64 — it's what untyped float constants become and what the math package uses. Floats follow the IEEE-754 standard, like every other language, which means they have the same famous quirks:

package main

import (
	"fmt"
	"math"
)

func main() {
	a := 0.1
	b := 0.2
	fmt.Println(a+b, a+b == 0.3)
	fmt.Println(math.Abs((a+b)-0.3) < 1e-9) // compare with a tolerance

	var f32 float32 = 16777216 // 2^24
	fmt.Println(f32+1 == f32)  // float32 can't represent 16777217

	fmt.Println(1/math.Inf(1), math.Inf(-1), math.NaN())
	nan := math.NaN()
	fmt.Println(nan == nan, math.IsNaN(nan))

	zero := 0.0
	fmt.Println(1/zero, -1/zero) // floats divide by zero -> ±Inf, no panic

	// Money: use integer cents, not floats.
	priceCents := 1999
	fmt.Printf("$%d.%02d\n", priceCents/100, priceCents%100)
}

  • 0.1 can't be represented exactly in binary (just as 1/3 can't in decimal), so 0.1 + 0.2 is a tiny bit off. Never compare floats with == after arithmetic; check whether the difference is within a small tolerance.

Senior engineer tip: never store money in floats

$0.10 + $0.20 should be $0.30, not $0.30000000000000004. Store money as an integer number of the smallest unit (int64 cents), or use a decimal library such as github.com/shopspring/decimal. Payment APIs like Stripe do exactly this — amounts are integers in cents.

Complex numbers

Go has built-in complex numbers — rare among mainstream languages, and handy for signal processing and scientific code. complex128 (two float64s) is the default; complex64 also exists. Write the imaginary part with i:

package main

import (
	"fmt"
	"math/cmplx"
)

func main() {
	c := 3 + 4i // complex128
	fmt.Println(c, real(c), imag(c), cmplx.Abs(c))
	fmt.Println(c * c)
	fmt.Println(cmplx.Sqrt(-1))
	fmt.Printf("%T\n", c)
}

Booleans, strings, bytes and runes

A bool is true or false. Go never treats numbers or strings as booleans: if 1 { } and if name { } are compile errors. Write if n != 0 or if name != "".

A string is an immutable sequence of bytes, by convention holding UTF-8 encoded text. That definition has consequences:

package main

import "fmt"

func main() {
	ok := true
	ready := !ok || len("go") == 2 // && and || short-circuit
	fmt.Println(ok, ready)

	s := "héllo, 世界"
	fmt.Println(len(s))         // bytes, not characters
	fmt.Println(s[0], s[1])     // indexing gives bytes (uint8)
	fmt.Println(string(s[0]))   // 104 -> "h"
	fmt.Println([]rune(s)[1])   // rune (int32) for 'é'
	fmt.Println(len([]rune(s))) // number of code points

	var b byte = 'A' // byte is an alias for uint8
	var r rune = '世' // rune is an alias for int32
	fmt.Println(b, r, string(r))
	fmt.Printf("%c %c %U\n", b, r, r)

	raw := `C:\path\no\escapes
second line`
	fmt.Println(raw)
	fmt.Println("tab:\tquote:\" newline->\nunicode: \u00e9")
}

  • len(s) counts bytes, not characters. é takes 2 bytes in UTF-8 and each Chinese character takes 3, so our 9-character string is 14 bytes long.
  • s[i] gives you a single byte (uint8). Byte 1 of "héllo" is 195 — the first half of é, not a whole letter.
  • A rune is one Unicode code point (roughly "one character"), stored as an int32. Converting to []rune splits the string into code points. Single quotes make a rune literal: 'A', '世'.
  • Double quotes make an interpreted string that understands escapes (\n \t \" é). Backticks make a raw string: no escapes, and it can span lines — perfect for regexes, JSON, SQL and Windows paths.

Strings are immutable — you can't change a byte in place:

package main

func main() {
	s := "hello"
	s[0] = 'H'

To "modify" a string, build a new one (concatenate, use strings.Replace, or convert to []byte, change it, and convert back). Immutability is what makes strings safe to share between goroutines and cheap to pass around: passing a string copies only a small header (a pointer and a length), never the text itself. Chapter 06 is devoted to strings, UTF-8 and text processing.

What does len("café") return?
len counts bytes. c, a, f are 1 byte each in UTF-8, and é is 2 bytes, so the total is 5. To count characters, use utf8.RuneCountInString("café"), which returns 4.

No implicit conversions — ever

Many languages quietly convert between number types: C will happily multiply an int by a double, or squeeze a 64-bit value into a 32-bit one. Go refuses. Mixing types is a compile error, even between int and int64 on a machine where they're the same size:

package main

import "fmt"

func main() {
	count := 3
	price := 2.5
	total := count * price
	var big int64 = 10
	var n int = big
	fmt.Println(total, n)
}
# command-line-arguments
./main.go:8:11: invalid operation: count * price (mismatched types int and float64)
./main.go:10:14: cannot use big (variable of type int64) as int value in variable declaration

Why so strict? Implicit conversions hide bugs: lost precision, truncated values, sign changes. Go makes every conversion visible in the code, so a reviewer can see exactly where it happens. The syntax is T(value):

package main

import (
	"fmt"
	"math"
)

func main() {
	count := 3
	price := 2.5
	total := float64(count) * price
	fmt.Println(total)

	f := 3.99
	fmt.Println(int(f), int(-f), int(math.Round(f))) // truncates toward zero

	var big int64 = 300
	fmt.Println(int8(big), uint8(big)) // keeps low bits: wraps silently!

	i := 65
	fmt.Println(string(rune(i))) // "A": int -> rune -> string
	fmt.Println(fmt.Sprint(i))   // "65": what you usually want
	fmt.Println([]byte("hi"), string([]byte{104, 105}))
}
  1. Go never mixes numeric types silently. float64(count) makes a new float64 value 3.0, and only then can it be multiplied by price.
  2. The product prints as 7.5.
  3. Float-to-int conversion truncates toward zero: 3.99 → 3 and −3.99 → −3. If you want rounding, call math.Round first.
  4. 300 is 0b1_0010_1100. Converting to an 8-bit type keeps only the low 8 bits (0010_1100 = 44). Gotcha: no error, no panic — the value just changes.
  5. rune(i) means "code point 65", and converting a rune to a string gives that character: "A".
  6. To get the digits of a number, format it: fmt.Sprint (or strconv.Itoa). This is almost always what you meant.
  7. Strings and byte slices convert both ways. []byte("hi") copies the two UTF-8 bytes out; string(...) copies them back in.

strconv: converting between strings and numbers

Constants and untyped constants

A constant is a value fixed at compile time that can never change. Declare one with const. Constants can be numbers, strings, runes or booleans — only things the compiler can compute. You can't make a constant slice, map or struct, or a constant from a function call like time.Now().

const MaxRetries = 3
const Greeting = "hello"
const (
	StatusOK       = 200
	StatusNotFound = 404
)
const Timeout = 2 * MaxRetries // constant expressions are fine

The superpower: untyped constants

Most constants you write are untyped: const Big = 1 << 100 is just "the number 2100", not an int or a float64. The compiler stores it with arbitrary precision (at least 256 bits, in practice exact). It only gets a concrete type at the moment you use it somewhere that needs one.

package main

import (
	"fmt"
	"math"
	"time"
)

const Big = 1 << 100 // way bigger than any int type!
const Small = Big >> 98

const Pi = 3.14159265358979323846264338327950288419716939937510582097494459

func main() {
	fmt.Println(Small) // 4: the huge intermediate was exact

	// Untyped constants adapt to the context they're used in:
	var f32 float32 = Pi
	var f64 float64 = Pi
	fmt.Println(f32, f64)

	const timeout = 5          // untyped integer constant
	d := timeout * time.Second // works: 5 becomes a time.Duration
	fmt.Println(d)

	n := 5 // a typed variable (int)
	// d2 := n * time.Second // compile error: mismatched types int and time.Duration
	d2 := time.Duration(n) * time.Second
	fmt.Println(d2)

	fmt.Println(math.Pi / 2)
	fmt.Println(Big / 1e29) // still exact, converted to float64 for printing
}
  1. Constants are evaluated by the compiler with arbitrary precision. Big doesn't fit any integer type, and that's fine — it never has to exist at run time. Big >> 98 is exactly 4.
  2. Only the final value 4 reaches the program, as an int.
  3. The same untyped Pi is rounded to whatever precision each variable has. The constant itself keeps all 60+ digits.
  4. timeout has no type yet, so in timeout * time.Second it simply becomes a time.Duration.
  5. n is a variable of type int. The commented-out line 27 would fail: int * time.Duration is a type mismatch.
  6. With a variable you must convert explicitly: time.Duration(n).
  7. math.Pi is an untyped constant too, so math.Pi / 2 is computed exactly and then rounded once to float64.
  8. Big / 1e29 is still constant arithmetic — no overflow — and only the small result is converted to float64 for printing.

Mental model: untyped constants are "ideal numbers"

Think of an untyped constant as a number written on a whiteboard in pure math — no size, no rounding. It only gets squeezed into a real box (int, float32, time.Duration…) when you put it in a variable or pass it to a function. If it doesn't fit the box, the compiler tells you.

iota: generating constant sequences

Go has no enum keyword. Instead, inside a const ( … ) block you can use iota, a counter that starts at 0 on the first line of the block and increases by one on each line. Even better: if a line has no expression, it repeats the previous line's expression (with the new iota). Together, these give you enums:

package main

import "fmt"

type Weekday int

const (
	Sunday  Weekday = iota // 0

	Tuesday                // 2
	Wednesday
	Thursday
	Friday
	Saturday

func (d Weekday) String() string {
	return [...]string{"Sun", "Mon", "Tue", "Wed", "Thu", "Fri", "Sat"}[d]
}

func main() {
	fmt.Println(Sunday, Monday, Saturday)
	fmt.Printf("%d %v %T\n", Wednesday, Wednesday, Wednesday)

Skipping values and expressions

type Level int

const (
	_     Level = iota // 0: skip it, so the zero value means "unset"
	Debug              // 1
	Info               // 2
	_                  // 3: reserved, skipped
	Error              // 4
)

const (
	KB = 1 << (10 * (iota + 1)) // 1 << 10
	MB                          // 1 << 20
	GB                          // 1 << 30
)

func main() {
	fmt.Println(Debug, Info, Error)
	fmt.Println(KB, MB, GB)
}
  1. A named type Level, so levels can't be confused with plain ints.
  2. First line of the block: iota is 0. We assign it to the blank identifier _, throwing it away. Now the zero value of Level doesn't match any real level — great for detecting "forgot to set it".
  3. No expression, so Go repeats Level = iota with iota = 1.
  4. Info = 2.
  5. Another _: value 3 is reserved and skipped.
  6. Error = 4.
  7. A new const block resets iota to 0. KB = 1 << (10 * 1) = 1 << 10 = 1024. (<< shifts bits left; each shift doubles the number.)
  8. The expression repeats with iota = 1: 1 << 20.
  9. 1 << 30.
  10. main prints them.

Bit flags

1 << iota gives powers of two: 1, 2, 4, 8, … Each constant has exactly one bit set, so you can combine several in one integer. This is how Unix file permissions and os.O_RDWR|os.O_CREATE work.

package main

import "fmt"

type Perm uint8

const (
	Read  Perm = 1 << iota // 1 << 0 = 0b001
	Write                  // 1 << 1 = 0b010
	Exec                   // 1 << 2 = 0b100
)

func main() {
	p := Read | Write // combine with OR
	fmt.Printf("%03b\n", p)
	fmt.Println("can write?", p&Write != 0) // test with AND
	fmt.Println("can exec? ", p&Exec != 0)

	p |= Exec  // add a flag
	p &^= Read // remove a flag (AND NOT)
	fmt.Printf("%03b\n", p)

	const (
		a, b = iota, iota * 10 // iota is the same on one line
		c, d                   // 1, 10
	)
	fmt.Println(a, b, c, d)
}
  1. 1 << iota shifts a single 1 bit left by 0, 1, 2. Each flag owns exactly one bit.
  2. | (OR) merges bits: 001 | 010 = 011.
  3. %03b prints binary, padded to three digits.
  4. & (AND) keeps only bits set in both. 011 & 010 = 010, which is non-zero, so the flag is present.
  5. 011 & 100 = 000: Exec is not set.
  6. p |= Exec turns the Exec bit on.
  7. &^= (AND NOT, "bit clear") turns the Read bit off without touching the others.
  8. Write and Exec remain.
  9. iota counts lines, not names. On line 24 both uses see 0; line 25 repeats the expressions with iota = 1, giving 1 and 10.
  10. The local constant block prints its four values.

Gotcha: never reorder iota constants that are stored

iota values depend on position. If StatusActive is 1 today and someone inserts a new constant above it, it silently becomes 2 — and every value already stored in your database or sent over the network now means something else. For values that leave the process, either assign explicit numbers (StatusActive = 1) or store a string name instead. Add new iota values only at the end.

What is the value of C? const ( A = iota * 10; B; _; C )
Each line repeats iota * 10. A is on line 0 → 0, B on line 1 → 10, the skipped _ on line 2 → 20, and C on line 3 → 30. Blank lines don't count, but _ lines do.

Named types vs type aliases

You can create a new type based on an existing one: type Celsius float64. This is a named type (also called a defined type). It has the same memory layout as float64, but it's a different type. You can attach methods to it, and the compiler won't let you mix it up with other types by accident.

A type alias uses an equals sign: type MyInt = int. It's not a new type at all — just a second name for the same type, like a nickname. byte (= uint8), rune (= int32) and any (= interface{}) are aliases.

package main

import "fmt"

type Celsius float64
type Fahrenheit float64

type MyInt = int // alias: just another name for int

func CToF(c Celsius) Fahrenheit {
	return Fahrenheit(c*9/5 + 32)
}

func (c Celsius) String() string { return fmt.Sprintf("%.1f°C", float64(c)) }

func main() {
	boiling := Celsius(100)
	fmt.Println(boiling, CToF(boiling))

	var x MyInt = 5
	var y int = x // fine: MyInt IS int
	fmt.Printf("%T %T\n", x, y)

	var raw float64 = 37
	body := Celsius(raw) // explicit conversion needed
	fmt.Println(body)

	// Untyped constants convert implicitly:
	var freezing Celsius = 0
	fmt.Println(freezing)
}
  1. Celsius(100) converts the constant to our named type. Underneath it's a float64, but the compiler treats it as a distinct type.
  2. CToF only accepts a Celsius. Inside, c*9/5 + 32 is computed in Celsius arithmetic (212), then converted to Fahrenheit on the way out.
  3. Println finds a String() method on Celsius and uses it. Fahrenheit has no such method, so it prints as a plain number. Methods belong to the named type, not to float64.
  4. MyInt = int (note the =) is an alias: the same type under another name, so assigning to an int needs no conversion.
  5. %T proves it: both are just int.
  6. A float64 variable does not turn into a Celsius by itself. The explicit Celsius(raw) conversion is required.
  7. body is a Celsius, so it prints through String().
  8. An untyped constant like 0 converts implicitly to any compatible type, so no conversion is needed here.

The blank identifier and unused variables

The underscore _ is the blank identifier: a write-only black hole. Anything assigned to it is discarded. Use it when the language requires a name but you don't need the value:

package main

import (
	"fmt"
	"strconv"
)

func divmod(a, b int) (int, int) { return a / b, a % b }

func main() {
	_, rem := divmod(17, 5) // don't need the quotient
	fmt.Println(rem)

	for _, v := range []string{"a", "b"} { // don't need the index
		fmt.Print(v, " ")
	}
	fmt.Println()

	n, _ := strconv.Atoi("12") // ignoring an error: be careful!
	fmt.Println(n)

	_ = n // explicitly "use" a value
}
  1. divmod(17, 5) runs and returns two values: 3 and 2.
  2. The quotient lands in _ and is thrown away. _ is not a variable: you can't read it, and it never triggers "declared and not used".
  3. Only the remainder is printed.
  4. range yields index and value; we discard the index with _. Print writes "a " without a newline, so nothing is complete on screen yet.
  5. Second element: "b " goes on the same line.
  6. Println() with no arguments just ends the line. Note the trailing space after b.
  7. The error from Atoi is discarded. Fine for a literal "12", but dangerous for user input: a bad string would silently give 0.
  8. Prints the parsed number.
  9. _ = n "uses" a value with no effect. Handy while sketching code, but don't leave it in production.

Remember that Go rejects unused local variables. Note that assigning to a variable doesn't count as using it — only reading it does:

package main

func main() {
	x := 10
	y := 20
	x = 30
}
# command-line-arguments

(Unused package-level variables, constants, functions and function parameters are allowed — the rule only applies to local variables and imports.)

Gotcha: _ for errors

n, _ := strconv.Atoi(input) silently turns bad input into 0. That's occasionally fine (a value you just validated), but in a code review, every _ on an error should have an obvious reason or a comment. "We ignored the error" is behind a lot of production mysteries.

Other uses of _ you'll meet later: import _ "pkg" (import for side effects only), and var _ Interface = (*MyType)(nil) — a compile-time check that a type implements an interface (Chapter 08).

1 · A ByteSize type that prints human-friendly sizes

Define type ByteSize float64 and constants KB, MB, GB, TB using iota (each 1024× the previous). Give it a String() method so fmt.Println(ByteSize(1536)) prints 1.50KB. Hint: skip the first iota value with _, then use 1 << (10 * iota). You'll need a tagless switch (previewed here, covered in Chapter 03).

Solution
package main

import "fmt"

type ByteSize float64

const (
	_           = iota // ignore 0
	KB ByteSize = 1 << (10 * iota)
	MB
	GB
	TB
)

func (b ByteSize) String() string {
	switch {
	case b >= TB:
		return fmt.Sprintf("%.2fTB", b/TB)
	case b >= GB:
		return fmt.Sprintf("%.2fGB", b/GB)
	case b >= MB:
		return fmt.Sprintf("%.2fMB", b/MB)
	case b >= KB:
		return fmt.Sprintf("%.2fKB", b/KB)
	}
	return fmt.Sprintf("%.0fB", float64(b))
}

func main() {
	fmt.Println(ByteSize(512))
	fmt.Println(ByteSize(1536))
	fmt.Println(ByteSize(5 * 1024 * 1024))
	fmt.Println(3.5 * GB)
	fmt.Println(ByteSize(2e12))
}
  1. _ = iota burns the value 0. Then each line repeats ByteSize = 1 << (10 * iota) with iota = 1, 2, 3, 4, giving powers of 1024.
  2. Println calls our String() method. A tagless switch tests each case top to bottom and runs the first true one.
  3. 512 is smaller than KB, so no case matches and we fall out of the switch to the bytes format.
  4. 1536 fails the TB, GB and MB checks but passes b >= KB. b/KB = 1.5. Case order matters: largest unit first.
  5. 5*1024*1024 lands in the MB case.
  6. 3.5 * GB is already a ByteSize (an untyped constant times a typed one), so no conversion is needed and String() still fires.
  7. 2×1012 bytes is a bit less than 2 TB because a TB here is 240, not 1012.

2 · Permission flags with a String method

Using Perm uint8 bit flags Read, Write, Exec, write a String() method that renders rw--style output. Then start with Read|Exec and remove Exec with &^=.

Solution
package main

import "fmt"

type Perm uint8

const (
	Read Perm = 1 << iota
	Write
	Exec
)

// String renders permissions like "rw-".
func (p Perm) String() string {
	out := []byte("---")
	if p&Read != 0 {
		out[0] = 'r'
	}
	if p&Write != 0 {
		out[1] = 'w'
	}
	if p&Exec != 0 {
		out[2] = 'x'
	}
	return string(out)
}

func main() {
	fmt.Println(Read, Read|Write, Read|Write|Exec, Perm(0))
	p := Read | Exec
	p &^= Exec
	fmt.Println(p)
}
  1. 1 << iota gives each constant its own bit, so any combination is a unique number.
  2. Println sees that Perm has a String() method and calls it for each argument. First: Read. We start from "---" as a mutable []byte.
  3. p&Read is non-zero, so slot 0 becomes 'r'. The Write and Exec tests are 0, so they stay -. Returns "r--".
  4. Second argument Read|Write = 0b011: two bits set, two letters.
  5. Read|Write|Exec = 0b111: every test passes.
  6. Perm(0) has no bits, so every if is skipped and "---" comes back unchanged. Now Println joins the four strings with spaces.
  7. Read | Exec sets bits 0 and 2.
  8. &^= is AND NOT: it clears every bit that is set in Exec, leaving the others alone.
  9. Printing calls String() once more: only read permission is left.

3 · Sum only the valid numbers

Given the inputs "42", "-7", "3.9", "abc", "99999999999999999999", use strconv.Atoi to sum the ones that are valid ints, printing a message for each one skipped. Notice the different error messages.

Solution
package main

import (
	"fmt"
	"strconv"
)

func main() {
	inputs := []string{"42", "-7", "3.9", "abc", "99999999999999999999"}
	sum := 0
	for _, in := range inputs {
		n, err := strconv.Atoi(in)
		if err != nil {
			fmt.Printf("skip %q: %v\n", in, err)
			continue
		}
		sum += n
	}
	fmt.Println("sum:", sum)
}
  1. Five strings to parse, and a running total that starts at its zero value.
  2. First iteration. Atoi succeeds, so err is nil. Note n, err are declared fresh with := on each pass.
  3. No error, so we skip the if and add to the total.
  4. Atoi understands a leading minus sign. The total drops to 35.
  5. "3.9" is not an integer — Atoi doesn't round, it refuses. On error, n is 0.
  6. We report it and continue, which jumps straight to the next iteration, so line 17 never runs for bad input.
  7. Same story for letters.
  8. Valid digits but too big for int: a different error. Gotcha: here n is clamped to the max int, not 0 — always check err before trusting n.
  9. The loop is over. Only 42 and −7 were added.

"3.9" is a syntax error for an integer parser, and the 20-digit number is out of range for a 64-bit int. Real input validation looks exactly like this.

Key takeaways

  • x := v inside functions; var x T when you want the zero value or must state the type; var at package level. := needs at least one new name.
  • A := inside a block creates a new variable that shadows the outer one — watch out with err.
  • Every variable starts at its zero value (0, false, "", nil). Design types whose zero value is useful.
  • Use int and float64 by default. Integers wrap silently on overflow; floats are approximate — never use them for money.
  • Strings are immutable UTF-8 bytes: len counts bytes, s[i] is a byte, a rune is a code point.
  • No implicit conversions: write T(x). Use strconv for text ↔ numbers, and never string(int).
  • Untyped constants are exact and adapt to their context; iota builds enums, skips with _, bit flags with 1 << iota, and sizes like KB/MB.
  • type T U makes a new, distinct type (great for units and IDs); type T = U is just an alias.
  • %v %+v %#v %T print anything; go vet checks your format strings.

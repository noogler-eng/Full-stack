Packages: the unit of code in Go

A package is a group of .go files that live in the same directory and start with the same package name line. Everything declared at the top level of any of those files (functions, types, variables, constants) is visible to every other file in that package. You do not import files; you import packages.

A module is one level up: a tree of packages that are versioned and released together. It is defined by a go.mod file at its root. A repository (a git repo) usually holds exactly one module.

Mental model

Think of a module as a book, each package as a chapter, and each .go file as a page. You can split a chapter over as many pages as you like; readers still cite "chapter 3", never "page 47". Readers of the book (other modules) cite chapters by their full path: github.com/sharad/bookstore/internal/catalog.

The rules are simple:

  • One directory = one package. All non-test files in a folder must have the same package name. (Test files may also use package name_test, see Chapter 15.)
  • The import path is the module path plus the directory: module github.com/sharad/bookstore + folder internal/catalog = github.com/sharad/bookstore/internal/catalog.
  • The package name is what you type in code: catalog.New(). By convention it equals the last element of the import path.
  • Package main is special: it builds an executable, and must have a func main(). Any other name builds a library.

Exported vs unexported: capitalization is the access modifier

Go has no public, private or protected keywords. Instead:

  • A name that starts with an uppercase letter is exported: other packages can use it. (Book, New, ErrNotFound, FromRupees.)
  • A name that starts with a lowercase letter (or _) is unexported: only code in the same package can use it. (round, stock, books.)

This applies to everything: functions, types, variables, constants, struct fields and methods. Look at the money package:

// Package money represents prices without floating-point surprises.
package money

import "fmt"

// Cents is an amount of money in the smallest unit (paise, cents).
type Cents int64

// String formats 129900 as "₹1299.00". Exported: starts with a capital.
func (c Cents) String() string {
	return fmt.Sprintf("₹%d.%02d", c/100, c%100)
}

// FromRupees is exported, so other packages can call money.FromRupees.
func FromRupees(r int64) Cents { return Cents(r * 100) }

// round is unexported: only code inside package money can use it.
func round(c Cents) Cents { return (c + 50) / 100 * 100 }

// WithTax adds GST and rounds to the nearest rupee.
func WithTax(c Cents, percent int64) Cents {
	return round(c + c*Cents(percent)/100)
}

And the catalog package. Note the stock field is lowercase, so other packages can see a Book but cannot read or change its stock directly. They must go through methods like InStock. That is encapsulation, done with one letter.

package catalog

import (
	"errors"
	"fmt"
	"slices"

	"github.com/google/uuid"
	"github.com/sharad/bookstore/internal/money"
)

// ErrNotFound is exported: callers check it with errors.Is.
var ErrNotFound = errors.New("book not found")

// Book is exported, and so are its capitalised fields.
type Book struct {
	ID    string
	Title string
	Price money.Cents
	stock int // unexported field: invisible outside package catalog
}

// Catalog is an in-memory store.
type Catalog struct {
	books []Book
}

// New is the conventional constructor name: catalog.New().
func New() *Catalog { return &Catalog{} }

// Add registers a book and returns its generated ID.
func (c *Catalog) Add(title string, price money.Cents, stock int) string {
	id := uuid.NewString()[:8]
	c.books = append(c.books, Book{ID: id, Title: title, Price: price, stock: stock})
	return id
}

// InStock reports whether a book can be sold.
func (c *Catalog) InStock(id string) (bool, error) {
	i := slices.IndexFunc(c.books, func(b Book) bool { return b.ID == id })
	if i < 0 {
		return false, fmt.Errorf("catalog: %q: %w", id, ErrNotFound)
	}
	return c.books[i].stock > 0, nil
}

// All returns a copy so callers can't modify our slice.
func (c *Catalog) All() []Book { return slices.Clone(c.books) }
  1. The file lives in internal/catalog/ and says package catalog. Its full import path is the module path plus the folder: github.com/sharad/bookstore/internal/catalog.
  2. No dot in the first path element means standard library. The go command looks in $GOROOT/src, no go.mod lookup needed.
  3. This path is not in the standard library and not under our module path, so the go command finds the module that provides it in go.mod: github.com/google/uuid v1.6.0.
  4. It checks the hash in go.sum, then reads the source from the module cache, downloading it via GOPROXY the first time.
  5. This path starts with our own module path, so it maps straight to a folder in this repo. No download, no version.
  6. It contains internal, so the go command checks the importer: is it under github.com/sharad/bookstore/? Yes, so it is allowed.
  7. Inside, capitalization decides visibility: ErrNotFound, Book and its capital fields are exported; stock is visible only inside catalog.
  8. Using an imported name always needs the package name as a prefix: money.Cents. The prefix comes from the package clause, which here matches the last path element.

Senior engineer tip

Start everything unexported. Export a name only when another package actually needs it. Every exported identifier is a public promise: once someone depends on it, renaming or removing it is a breaking change. A small exported surface is the single best predictor of a package that is easy to maintain.

Package-level doc comments go right above package x in one file (often a dedicated doc.go, as in internal/catalog/doc.go) and start with "Package x ...". Every exported name should have a comment that starts with the name itself: "// New returns ...".

Naming packages and importing them

Good package names

  • Short, lowercase, one word, no underscores or mixedCaps: catalog, money, httputil, strconv.
  • Name it for what it provides, not what it contains. Avoid util, common, helpers, misc, models: they grow forever and tell the reader nothing.
  • Avoid stutter. The package name is part of every call, so catalog.New and catalog.Book, not catalog.NewCatalog or catalog.CatalogBook. http.Server, not http.HTTPServer.
  • Directory name = package name. The one common exception is a major-version folder like /v2, whose package name is still the base name (greet).
Import formExampleWhen to use it
Normalimport "strings"Almost always.
Aliasimport crand "crypto/rand"Two packages with the same name (crypto/rand vs math/rand/v2), or a very long/unclear name. Use sparingly.
Blank _import _ "image/png"You need only the package's side effects (its init()), e.g. registering an image decoder or a database driver.

package main

import (
	"bytes"
	crand "crypto/rand" // alias: avoids a clash with math/rand
	"encoding/base64"
	"fmt"
	"image"
	_ "image/png" // blank import: registers the PNG decoder in init()
	"math/rand/v2"
	. "strings" // dot import: ToUpper instead of strings.ToUpper (avoid!)
)

  1. Before main runs, every imported package is initialized. image/png's init() calls image.RegisterFormat("png", ...). That side effect is the only reason we import it with _.
  2. Both crypto/rand and math/rand/v2 are named rand. The alias crand lets us use both in one file.
  3. Plain rand now means math/rand/v2. We print only facts that are always true, because the random values change on every run.
  4. The base64 constant decodes to the bytes of a tiny PNG file.
  5. image.Decode looks at the first bytes and searches its list of registered formats. PNG is there only because of the blank import.
  6. Decoding works. Remove line 9 and this prints image: unknown format instead.
  7. The dot import put strings.ToUpper into our file's scope with no prefix. It works, but a reader cannot tell where ToUpper lives.

Imports are grouped by convention: standard library first, a blank line, then everything else. goimports (and most editors) does this for you, and also adds and removes imports automatically.

No import cycles

If package a imports b, then b may not import a, directly or through others. The compiler refuses:

package example.com/cycle/a
	imports example.com/cycle/b from a.go
	imports example.com/cycle/a from b.go: import cycle not allowed

This is a feature. It forces a clean, layered dependency graph, and it is one reason Go compiles so fast. When you hit a cycle, the fix is usually one of: move the shared type into a third, lower package; or have the lower package define a small interface that the higher package satisfies (Chapter 8).

Initialization order: package variables and init()

Before main() runs, Go initializes every package in the program. Each package goes through two steps:

  1. Package-level variables are initialized, in dependency order (if A uses B, B is computed first, even if declared later).
  2. Every func init() runs, in the order they appear (files are processed in the order given to the compiler, which the go command sorts by filename). A package may have many init functions, even several per file. You cannot call init yourself.

And across packages: a package is initialized only after all the packages it imports. Each package is initialized exactly once, no matter how many importers it has. Since Go 1.21 the order between unrelated packages is also fully defined: among packages that are ready, the one with the smallest import path goes first.

Here is a small program with three packages. main imports cache (blank import) and db; both of those import config.

package config

import "fmt"

// Package-level variables are initialised first, in dependency
// order: Port depends on defaultPort, so defaultPort goes first
// even though it is declared later.
var Port = trace("config.Port", defaultPort+1)
var defaultPort = trace("config.defaultPort", 8079)

func init() { fmt.Println("config: init()") }

func trace(name string, v int) int {
	fmt.Println("config: var", name, "=", v)
	return v
}
package db

import (
	"fmt"

	"example.com/initorder/config"
)

var DSN = fmt.Sprintf("postgres://localhost:%d", config.Port)

func init() { fmt.Println("db: init() #1, DSN =", DSN) }
func init() { fmt.Println("db: init() #2 (a file may have many)") }

import (
	"fmt"

	_ "example.com/initorder/cache" // blank import: run init() only
	"example.com/initorder/db"
)

var greeting = say("main: var greeting")

func say(s string) string { fmt.Println(s); return s }

func init() { fmt.Println("main: init()") }

func main() {
	fmt.Println("main: main() starts, DSN =", db.DSN)
}
// ---- config/config.go ----
var Port = trace("config.Port", defaultPort+1)
var defaultPort = trace("config.defaultPort", 8079)

// ---- db/db.go (imports config) ----

func init() { fmt.Println("db: init() #1, DSN =", DSN) }
func init() { fmt.Println("db: init() #2 (a file may have many)") }

// ---- main.go (imports cache, db) ----
var greeting = say("main: var greeting")
func init() { fmt.Println("main: init()") }
func main() {
	fmt.Println("main: main() starts, DSN =", db.DSN)
}
  1. config imports nothing of ours, so it goes first. Port depends on defaultPort, so Go computes defaultPort first, even though it is declared second.
  2. Dependency first.
  3. Now Port can be computed.
  4. All variables done, so config's init runs. config is complete.
  5. Both cache and db are ready. Go picks the smaller import path, .../cache. It has no variables, just an init.
  6. db's variable uses config.Port, which is already set.
  7. Both inits run, top to bottom.
  8. Last, package main: its variables, then its init.
  9. Only now does main() start.

	fmt.Println("var", name, "=", v)
	return v
}

func main() { fmt.Println("main: total =", total, "rate =", rate) }

// ---- b.go (package main, import "fmt") ----
var tax = add("tax", price*rate/100)
var rate = add("rate", 18)

func init() { fmt.Println("b.go: init #1") }
func init() { rate = 0; fmt.Println("b.go: init #2 sets rate = 0") }
  1. The go command passes files to the compiler sorted by name, so declaration order is total, price (a.go), then tax, rate (b.go). Go repeatedly picks the earliest variable whose dependencies are all ready.
  2. total comes first but needs price and tax, which are not set yet. Skip it.
  3. price depends on nothing, so it is initialized first, by calling add.
  4. Back to the top: total still needs tax, and tax needs rate. Both skipped.
  5. rate is ready, so it goes next, even though it is the last declaration.
  6. Now tax can be computed: 100 × 18 / 100 = 18.
  7. Finally total = 100 + 18. All package variables are done.
  8. Only then do the init functions run, in file order: a.go's first.
  9. Then b.go's two inits, top to bottom. The second one changes rate, but tax and total were already computed, so they keep their values.
  10. main runs last. Lesson: relying on init to tweak variables other variables depend on is fragile. Rename a file and the order changes.

Gotcha: keep init() boring

init runs on every program start, including every test binary, before you can parse flags or set up logging. Never do network calls, read files that may be missing, or start goroutines in init. Registering a driver or building a lookup table is fine. Prefer explicit setup functions called from main: they are visible, testable and can return errors.

go.mod and go.sum, line by line

You create a module with go mod init <module path>. The module path is the import prefix of all its packages, and, if you publish it, the place people download it from (so it is usually a repository URL like github.com/you/project). For private experiments, any name works: example.com/x.

  1. module: this module's path. Every package inside is imported as this path + its folder, e.g. github.com/sharad/bookstore/internal/catalog.
  2. go: the minimum Go version needed, and which language semantics apply (for example, per-iteration loop variables need 1.22+). Since Go 1.21 it is a hard minimum: an older toolchain refuses to build, or downloads a newer one if allowed (the toolchain line / GOTOOLCHAIN setting).
  3. The first require block lists direct dependencies: modules our own code imports. go mod tidy writes it.
  4. When the compiler sees import "github.com/google/uuid" in catalog.go, it finds this line, picks v1.6.0, checks the hash in go.sum, and loads it from the module cache ($GOPATH/pkg/mod), downloading if needed.
  5. The second block holds indirect deps: needed by something we use, but not imported by our code. Here they come from the stringer tool. // indirect marks them.
  6. replace says: whenever you need example.com/greet/v2, use the local folder ../greet instead of downloading it. Great for local development and forks.
  7. tool (Go 1.24+): records a developer tool used by the project. go tool stringer now runs the exact version pinned here.

Each dependency version has two lines:

  • github.com/google/uuid v1.6.0 h1:NIva... is a cryptographic hash (h1: = SHA-256 based) of the module's entire source tree.
  • github.com/google/uuid v1.6.0/go.mod h1:TIyP... is the hash of just its go.mod. Go needs this one even for modules it never compiles, to work out the dependency graph. That is why go-cmp appears here but not in go.mod.

Every time Go downloads a module, it checks the hash against go.sum. The first time it sees a version, it also checks the public checksum database (sum.golang.org), a tamper-proof log that guarantees everybody in the world gets the same bytes for uuid v1.6.0. If someone changes a published tag, the build fails loudly instead of silently running different code. Always commit go.sum next to go.mod. It is not a lock file in the npm sense (versions are already exact in go.mod); it is a list of trusted hashes.

How Go chooses versions: Minimal Version Selection

Suppose your module needs uuid v1.4.0 and a library you use needs uuid v1.6.0. Go picks the highest of the minimums: v1.6.0. Not the newest version on the internet, just the lowest version that satisfies everyone's stated minimum. This is called Minimal Version Selection (MVS). Because it never looks at "latest", the same go.mod gives the same build today and in five years, with no lock file and no solver.

Your go.mod requires foo v1.2.0. A dependency requires foo v1.5.0. foo v1.9.0 was released yesterday. Which version builds?
MVS takes the maximum of all required minimums, which is v1.5.0. It never upgrades to v1.9.0 on its own; you must ask with go get foo@latest. Within one major version there is never a conflict, because semver promises v1.5.0 is compatible with code written for v1.2.0.

replace directives

replace old => new swaps a module for another version, a fork, or a local directory. Our project uses one to point at the local greet module. Two rules to remember:

  • replace only applies in the main module (the one you are building). If you publish a library with a replace, your users ignore it.
  • Local-path replaces are handy, but committing replace ../something breaks the build for everyone who does not have that folder. For local multi-module work, prefer go.work (below).

GOPROXY, GOSUMDB and GOPRIVATE

https://proxy.golang.org,direct


sum.golang.org
  • GOPROXY: a comma-separated list of module mirrors. The public proxy caches every public module forever, so a deleted GitHub repo does not break your build.
  • GOSUMDB: the checksum database used to verify first-time downloads.
  • GOPRIVATE: glob patterns of private modules, e.g. go env -w GOPRIVATE='github.com/yourcompany/*'. Matching modules are fetched directly from git (not the public proxy, which cannot see them anyway) and are not sent to the public checksum database (which would leak their names). Authentication then uses your normal git credentials (SSH keys, .netrc, or GOAUTH since Go 1.24).
Senior engineer tip

In a company, set GOPRIVATE once in your shell profile or dev container, and in CI. Many large teams also run their own proxy (Athens, JFrog Artifactory, or a cloud provider's) and set GOPROXY=https://goproxy.corp,https://proxy.golang.org,direct. Then builds survive GitHub outages and you get an audit log of every dependency your org uses.

Semantic import versioning (v2 and beyond)

Go modules use semantic versioning: vMAJOR.MINOR.PATCH. Bump PATCH for bug fixes, MINOR for new backwards-compatible features, MAJOR for breaking changes. v0.x.y means "unstable, anything may change".

Go adds one rule that surprises newcomers: if the major version is 2 or more, it must be part of the module path. Version 2 of example.com/greet is the module example.com/greet/v2:

module example.com/greet/v2

go 1.27.1
// Package greet is published as major version 2.
// Its module path ends in /v2, but the package name is greet.
package greet

// Style was added in v2: Hello's signature changed, which is a
// breaking change, so the major version had to go up.
type Style int

const (
	Casual Style = iota
	Formal
)

func Hello(name string, s Style) string {
	if s == Formal {
		return "Good day, " + name + "."
	}
	return "hey " + name
}
// Command report prints a greeting using a v2 module.
package main

import (
	"fmt"

	"example.com/greet/v2" // package name is still "greet"
)

func main() {
	fmt.Println(greet.Hello("Sharad", greet.Formal))
}
// ---- greet/go.mod ----
module example.com/greet/v2

// ---- greet/greet.go ----
package greet

type Style int

const (
	Casual Style = iota
	Formal
)

func Hello(name string, s Style) string {
	if s == Formal {
		return "Good day, " + name + "."
	}
	return "hey " + name
}

// ---- cmd/report/main.go (bookstore requires example.com/greet/v2 v2.0.0) ----
package main

import (
	"fmt"

	"example.com/greet/v2" // package name is still "greet"
)

func main() {
	fmt.Println(greet.Hello("Sharad", greet.Formal))
}
  1. The compiler meets the import path example.com/greet/v2. The /v2 is part of the path, so this is a different module from plain example.com/greet.
  2. The go command finds the module whose path matches, using bookstore's go.mod: require ... v2.0.0, and here a replace pointing at the local ../greet folder.
  3. The folder ends in v2, but its files say package greet. The package clause decides the name you type, so the code uses greet., not v2..
  4. Package-level declarations are set up before main: iota gives Casual=0, Formal=1.
  5. main calls greet.Hello with the v2-only Style argument. This two-argument signature is the breaking change that forced the major version bump.
  6. s is Formal, so we take the formal branch.
  7. Back in main, the result is printed.
Good day, Sharad.

Why? The import compatibility rule: if two import paths are the same, the code must be compatible. A breaking change gets a new path, so greet (v1) and greet/v2 are treated as different modules. One program can even use both at once, which lets a big codebase migrate gradually. MVS never has to choose between incompatible versions.

  • Two ways to lay out v2 in a repo: change the module line on a branch (most common), or create a v2/ subdirectory with its own go.mod.
  • Old repos tagged v2.0.0 without the /v2 path show up as v2.0.0+incompatible: Go can use them, but without the module guarantees.
  • Users upgrade by changing import paths, e.g. with gofmt -r or a find-and-replace, then go mod tidy.

Breaking changes are expensive for your users. Before reaching for v2, consider adding a new function (HelloStyle) alongside the old one, and deprecating the old one with a // Deprecated: comment. Many popular modules stay on v1 for a decade this way.

Project layout: internal/, cmd/, and not over-structuring

internal/ is enforced by the compiler

A package whose path contains an internal element can be imported only by code rooted at the parent of that internal directory. So github.com/sharad/bookstore/internal/money can be imported by anything under github.com/sharad/bookstore/, and by nothing else. Here is another module trying:

package main

import (
	"fmt"

	"github.com/sharad/bookstore/internal/money"
)

func main() {
	fmt.Println(money.FromRupees(10))
}
  1. This file belongs to a different module, github.com/sharad/outsider. (The workspace lets it see the bookstore module's packages at all.)
  2. fmt is standard library: always importable.
  3. The go command sees an internal element in the path. Everything before it, github.com/sharad/bookstore, is the only tree allowed to import it.
  4. Our importer path does not start with github.com/sharad/bookstore/, so the rule fails. Note this is checked by the go command before compiling, not by a naming convention.
  5. The build stops with an error pointing at line 6, column 2. Line 10 never gets compiled. To share money, you would have to move it out of internal/ on purpose.
package github.com/sharad/outsider
	main.go:6:2: use of internal package github.com/sharad/bookstore/internal/money not allowed

This is the most useful tool you have for keeping your public API small. Put everything in internal/ by default, and move a package out only when you deliberately want outsiders to use it.

cmd/ for executables

When a module produces more than one program, put each in cmd/<name>/main.go. go build ./cmd/bookstore then produces a binary called bookstore, and go install github.com/sharad/bookstore/cmd/bookstore@latest works for users. Keep main thin: parse flags and config, wire dependencies together, call into packages. Logic in main cannot be imported or easily tested.

// Command bookstore is the shop's main program.
package main

import (
	"errors"
	"fmt"
	"os"
	"text/template"

	"github.com/sharad/bookstore/assets"
	"github.com/sharad/bookstore/internal/catalog"
	m "github.com/sharad/bookstore/internal/money" // import alias
	"github.com/sharad/bookstore/internal/platform"
)

func main() {
	fmt.Print(assets.Banner)
	fmt.Printf("running on %s (debug=%v)\n\n", platform.Name(), platform.Debug)

	shop := catalog.New()
	id := shop.Add("The Go Programming Language", m.FromRupees(899), 3)
	shop.Add("Concurrency in Go", m.WithTax(m.FromRupees(650), 18), 0)

	fmt.Println("genre:", catalog.Programming) // String() from go generate

	ok, _ := shop.InStock(id)
	fmt.Println("first book in stock:", ok)

	if _, err := shop.InStock("missing"); errors.Is(err, catalog.ErrNotFound) {
		fmt.Println("lookup error:", err)
	}

	t := template.Must(template.ParseFS(assets.Templates, "templates/receipt.tmpl"))
	if err := t.Execute(os.Stdout, shop.All()); err != nil {
		fmt.Fprintln(os.Stderr, err)
		os.Exit(1)
	}
}
  1. Before main, Go initializes every imported package, dependencies first: money, then catalog (which needs it), assets and platform. The alias m is only a local nickname for money.
  2. assets.Banner is a plain string filled by //go:embed banner.txt. The bytes were copied into the binary by the compiler, so no file is read at run time.
  3. Which Name runs was decided at build time: on a Mac only platform_darwin.go and debug_off.go were compiled.
  4. catalog.New() is the constructor. Add generates an ID with the third-party uuid package and stores the stock in the unexported stock field.
  5. m.WithTax adds 18% GST to 65000 paise (= 76700) and calls the unexported round helper. We can call WithTax but not round from here.
  6. Genre has a String() method written by go generate + stringer, so Println prints the name, not the number 1.
  7. The first book has stock 3. We can't read stock ourselves, but InStock can, because it lives inside catalog.
  8. An unknown ID returns an error wrapping the exported sentinel catalog.ErrNotFound, so errors.Is matches it.
  9. template.ParseFS reads receipt.tmpl out of the embedded embed.FS, which behaves like a read-only folder baked into the binary.
  10. The template ranges over a copy of the books and prints each title and price. Price is a money.Cents, so its String() method formats rupees.

Senior engineer tip

The famous "golang-standards/project-layout" repo is not an official standard, and the Go team has said so. The official guidance (go.dev/doc/modules/layout) is: start flat, add internal/ and cmd/ when you need them. A pkg/ directory adds an extra word to every import and means nothing to the compiler. Layering by technical role (models/services/controllers) creates import cycles and packages that change together but live apart.

Workspaces with go.work

Sometimes you work on two modules at once: say, a service and a library it uses, in sibling folders. Editing replace lines in go.mod and remembering to remove them is error prone. A workspace (Go 1.18+) solves it: a go.work file in a parent folder lists modules that should be built together from local source.

$ go work use ./greet

	./bookstore
	./greet
	./outsider

Our outsider module imports example.com/greet/v2, yet its go.mod has no require line for it:

	"fmt"

  1. We run go run . inside outsider/. The go command walks up the folders, finds go.work, and treats all three listed modules as main modules, built from local source.
  2. outsider's own go.mod has no require lines at all.
  3. The import example.com/greet/v2 is not standard library. The go command first checks the workspace modules: ./greet's module path is exactly example.com/greet/v2.

Gotcha: usually do not commit go.work

go.work describes your machine's folders. Committing it can make CI build against different code than each module's go.mod says. The common practice is to add it to .gitignore, unless the repo is a monorepo designed around it. Before releasing, always test with GOWORK=off.

Developer tools and publishing releases

Tools via the tool directive (Go 1.24)

Projects depend on developer tools too: code generators (stringer, mockgen, sqlc), linters, protobuf plugins. Before Go 1.24 people used a hacky tools.go file with blank imports. Now there is a proper way:

$ go get -tool golang.org/x/tools/cmd/stringer@latest   # adds a `tool` line to go.mod
$ go tool stringer -type=Genre                          # runs the pinned version
$ go tool                                               # lists available tools
$ go get tool                                           # upgrade all tools

Remember the enums you wrote earlier, with Status constants and iota? Writing String() methods by hand is tedious. In the bookstore, genre.go asks stringer to do it, using a //go:generate comment:

package catalog

//go:generate go tool stringer -type=Genre

// Genre is an enum. stringer writes its String method for us.
type Genre int

const (
	Fiction Genre = iota
	Programming
	Poetry
)

go generate ./... scans for //go:generate lines and runs them. It created genre_string.go (starting with a "DO NOT EDIT" header), which is why main printed genre: Programming instead of genre: 1. Everyone on the team, and CI, gets exactly x/tools v0.52.0, because it is pinned in go.mod.

go generate never runs automatically during go build. Commit the generated files, and add a CI step that runs go generate ./... && git diff --exit-code to catch anyone who forgot to regenerate.

Publishing a module and tagging releases

There is no "upload" step in Go. A module is published by pushing it to a public repository whose URL matches the module path, and tagging a version:

$ go mod tidy && go test ./... && go vet ./...
$ git tag v1.3.0
$ git push origin v1.3.0
# optional: ask the proxy to fetch it now, so pkg.go.dev lists it
$ GOPROXY=proxy.golang.org go list -m github.com/sharad/bookstore@v1.3.0
  • Tags must be full semver with a v: v1.3.0, v1.3.0-rc.1. Not 1.3.
  • Untagged commits can still be used; Go gives them a pseudo-version like v0.0.0-20261009151841-97e8ea77aa2a (base version, UTC timestamp, commit hash). You saw one for x/telemetry in go list -m all.
  • Once the proxy has a version, it is cached forever. You cannot change or delete it. If you publish a bad release, add a retract v1.3.0 // broken: panics on empty input line to go.mod and publish a new version; go get will then skip the retracted one.
  • A module in a subdirectory of a repo is tagged with a prefix: tools/v1.0.0 for the module in tools/.

Build tags, file suffixes and go:embed

Conditional compilation

Go has no #ifdef. Instead, whole files are included or excluded from a build, two ways:

  • File name suffixes. name_GOOS.go, name_GOARCH.go or name_GOOS_GOARCH.go are only built for that platform: platform_linux.go, asm_arm64.go, sys_windows_amd64.go. And name_test.go files are only built by go test.
  • Build constraints. A //go:build expr line at the top of a file (before package, followed by a blank line). The expression uses &&, ||, ! and parentheses over tags: OS and arch names, go1.22-style version tags, cgo, and custom tags you pass with -tags.
// platform_darwin.go
package platform
func Name() string { return "macOS" }

// platform_linux.go
package platform
func Name() string { return "Linux" }

// platform_other.go
//go:build !darwin && !linux
package platform
func Name() string { return "some other OS" }

// debug_on.go
//go:build debug
package platform
const Debug = true

// debug_off.go
//go:build !debug
package platform
const Debug = false
  1. On a Mac with no tags: the _darwin suffix matches, !darwin && !linux is false, !debug is true. Exactly one Name and one Debug, so it compiles.
  2. Cross-compile for Linux with GOOS=linux: now the _linux file is chosen and the darwin one is ignored.
  3. Windows matches neither suffix, so the fallback's constraint !darwin && !linux is true. Every OS has exactly one Name.
  4. -tags debug flips the debug pair. Same code, different constant, decided at build time with zero runtime cost.
$ go list -f '{{.GoFiles}}' ./internal/platform
[debug_off.go platform_darwin.go]
$ GOOS=linux go list -f '{{.GoFiles}}' ./internal/platform
[debug_off.go platform_linux.go]
$ GOOS=windows go list -f '{{.GoFiles}}' ./internal/platform
[debug_off.go platform_other.go]
$ go list -tags debug -f '{{.GoFiles}}' ./internal/platform
[debug_on.go platform_darwin.go]
$ GOOS=linux GOARCH=amd64 go build -o bookstore-linux ./cmd/bookstore && file bookstore-linux | cut -c1-60 && rm bookstore-linux
bookstore-linux: ELF 64-bit LSB executable, x86-64, version 
//go:build !darwin && !linux

package platform

// Name is the fallback for every other OS.
func Name() string { return "some other OS" }
Gotcha

The //go:build line must be followed by a blank line, and there must be no space after //. Otherwise it is just a comment and the file is always included. You may see old // +build lines in legacy code; gofmt converts them. Also beware of accidental suffixes: a file named handler_test.go or image_js.go is silently excluded from normal builds.

go:embed: files inside your binary

The //go:embed directive (Go 1.16) copies files into the compiled binary at build time, so you can ship a single executable with its HTML templates, SQL migrations or static assets.

// Package assets bundles static files into the binary.
package assets

import "embed"

// Banner is the whole file as a string.
//
//go:embed banner.txt
var Banner string

// Templates is a read-only file system with every .tmpl file.
//
//go:embed templates/*.tmpl
var Templates embed.FS
Receipt
{{range .}}- {{.Title}} ... {{.Price}}
{{end}}
  • The variable can be a string, a []byte (one file each), or an embed.FS (many files, a read-only file system that works with template.ParseFS, http.FileServerFS, fs.WalkDir).
  • You must import "embed" (use _ "embed" if you only embed into strings/bytes).
  • Paths are relative to the source file's folder, use /, and cannot contain ..: you can only embed files at or below the package directory.
  • Files starting with . or _ are skipped when embedding a directory, unless you write //go:embed all:static.
package main

import (
	"embed"
	"fmt"
	"io/fs"
	"strings"
)

//go:embed version.txt
var version string

//go:embed static
var site embed.FS

func main() {
	fmt.Printf("version: %q\n", strings.TrimSpace(version))

	fs.WalkDir(site, ".", func(path string, d fs.DirEntry, err error) error {
		if !d.IsDir() {
			fmt.Println("embedded:", path)
		}
		return nil
	})

	b, err := site.ReadFile("static/index.html")
	fmt.Printf("index.html: %s (%d bytes) err=%v\n", strings.TrimSpace(string(b)), len(b), err)

	_, err = site.ReadFile("static/.env")
	fmt.Println("dotfile:", err)
}
  1. At build time the compiler reads version.txt (next to this file) and stores its bytes in the binary. The directive must sit directly above the var.
  2. //go:embed static embeds the whole folder as an embed.FS. Files starting with . or _, like static/.env, are skipped unless you write all:static.
  3. Using embed.FS requires importing "embed". With only a string var you would still need _ "embed".
  4. At run time no file is opened: the string is already in memory. We trim the trailing newline the file had.
  5. embed.FS implements fs.FS, so standard helpers like fs.WalkDir work. Paths keep the static/ prefix and always use /. Entries come back in lexical order, so css/ comes first.
  6. The second (and last) file. .env is not listed: it was never embedded.
  7. ReadFile returns the embedded bytes. Deploy the binary alone and this still works.
  8. The dotfile was excluded, so reading it fails with fs.ErrNotExist. Handy: secrets in dotfiles do not leak into the binary by accident.
version: "v1.4.2"
embedded: static/css/site.css
embedded: static/index.html
index.html: <h1>Hi</h1> (12 bytes) err=<nil>
dotfile: open static/.env: file does not exist
Which file is included in a normal go build on Linux/amd64?
_windows and _arm64 are platform suffixes that don't match, and _test.go files are only built by go test. unix is not a recognized suffix (so the file name doesn't restrict it), but it is a build tag (Go 1.19+) that is true on Linux, macOS, the BSDs and friends.

Exercise 2: design a small library package with a command

Make module example.com/x2 with a library package temperature (exported type Celsius with a Fahrenheit() method and String(), an exported Parse(s string) (Celsius, error), and an unexported validation helper) plus a command in cmd/conv that converts each argument. Keep main thin.

Solution
// Package temperature converts between scales.
package temperature

import "fmt"

// Celsius is exported; its methods are part of the API.
type Celsius float64

// Fahrenheit converts c to Fahrenheit.
func (c Celsius) Fahrenheit() float64 { return float64(c)*9/5 + 32 }

func (c Celsius) String() string { return fmt.Sprintf("%.1f°C", float64(c)) }

// Parse reads values like "21.5C".
func Parse(s string) (Celsius, error) {
	var v float64
	if _, err := fmt.Sscanf(s, "%fC", &v); err != nil {
		return 0, fmt.Errorf("temperature: parse %q: %w", s, err)
	}
	if !valid(v) {
		return 0, fmt.Errorf("temperature: %v is below absolute zero", v)
	}
	return Celsius(v), nil
}

// valid is an unexported helper.
func valid(v float64) bool { return v >= -273.15 }
package main

import (
	"fmt"
	"os"

	"example.com/x2/temperature"
)

func main() {
	for _, arg := range os.Args[1:] {
		c, err := temperature.Parse(arg)
		if err != nil {
			fmt.Fprintln(os.Stderr, "error:", err)
			continue
		}
		fmt.Printf("%v = %.1f°F\n", c, c.Fahrenheit())
	}
}
  1. We run the command with four arguments. main only loops and prints; all the logic lives in the imported temperature package.
  2. temperature.Parse scans 21.5 with the pattern %fC, checks it with the unexported valid helper, and returns a Celsius.
  3. %v calls Celsius.String(), and Fahrenheit() is an exported method, so main can call it.
  4. Second argument, same happy path.
  5. -300 parses, but valid rejects it. The error goes to stderr and continue moves to the next argument.
  6. Sscanf cannot read a number from hot. Parse wraps that error with the package name and input, so the message says exactly where it came from.
$ go run ./cmd/conv 21.5C 100C -300C hot

Notice that errors are prefixed with the package name (temperature: ...), a common convention for library errors, and that main only loops, calls and prints.

Exercise 3: break a cycle

orders imports users to look up a customer, and users imports orders to list a user's orders. The build fails with "import cycle not allowed". Suggest two fixes.

Solution

(1) Have users declare the small interface it needs, e.g. type OrderLister interface { OrdersFor(userID string) ([]Order, error) }, with Order moved to a tiny shared package (or defined in users as just the fields it needs); main wires the real orders store in. (2) Move the feature that needs both ("user's order history") into a third, higher package (account) that imports both. Dependencies should point one way: from high-level policy to low-level details.

Key takeaways

  • One directory is one package; a module (go.mod) is a versioned tree of packages. Import path = module path + directory.
  • Capitalized names are exported, lowercase are package-private. Export as little as possible.
  • Short lowercase package names, no util/common, no stutter. Blank imports for side effects; avoid dot imports. No import cycles, ever.
  • Init order: dependencies first; inside a package, variables (in dependency order) then init()s; then main(). Keep init trivial.
  • go.mod lists exact minimum versions; go.sum holds hashes. MVS picks the highest minimum, giving reproducible builds. Run go mod tidy and commit both files.
  • v2+ modules change their path (/v2). Use internal/ to hide code, cmd/ for binaries, and grow structure only when needed.
  • go.work for local multi-module development (usually uncommitted); tool directive for pinned dev tools; GOPRIVATE for company code.
  • Build tags and _os/_arch suffixes select files at build time; //go:embed bundles files into the binary.

Why a playbook? What "senior" means in Go

Go is a small language. You can learn every keyword in a weekend. So why do some Go codebases feel calm and obvious, while others feel like a maze? The difference is almost never clever features. It is taste: a shared set of habits about naming, errors, package boundaries and concurrency that the Go community has agreed on over 15 years.

A senior Go engineer is not someone who writes the trickiest code. It is someone whose code is boring in the best way. Six months later, a new hire can open the file and understand it in one read. Nothing surprising happens at runtime. Errors explain themselves. Goroutines always finish.

Mental model

Think of Go code like a well-run kitchen. Every tool has one obvious place. Every cook uses the same names for things. Nobody invents a new way to chop onions. The food is not more exciting because of it, but the kitchen can serve 500 people on a Friday night without fires. Idioms are the kitchen rules.

The Go proverbs, explained simply

In 2015 Rob Pike (one of Go's creators) gave a talk called "Go Proverbs": short sayings that capture the spirit of the language. They are worth knowing because senior engineers quote them in code reviews all the time. Here are the ones that matter most, in plain English, with what they mean for your code.

Idiomatic naming

Naming is where Go looks most different from Java or C#. Go names are short, and they lean on context. The rule of thumb from the Go team: the further a name is used from where it is declared, the longer and more descriptive it should be.

Short names for short lives

A loop index that lives for three lines is i, not currentIndexOfUser. A reader that lives inside a ten-line function is r. A package-level variable used across many files deserves a real name like defaultTimeout.

func SumAllTheNumbers(listOfNumbers []int) int {
	totalSumValue := 0
	for indexValue := 0; indexValue < len(listOfNumbers); indexValue++ {
		totalSumValue += listOfNumbers[indexValue]
	}
	return totalSumValue
}
func Sum(nums []int) int {
	total := 0
	for _, n := range nums {
		total += n
	}
	return total
}

Receiver names

The receiver is the (s *Server) part of a method. Go style says: use a one or two letter abbreviation of the type, and use the same one on every method. Never use this or self; they hint that you are thinking in another language.

func (this *Client) Get() {}
func (self *Client) Post() {}
func (client *Client) Delete() {}
func (c *Client) Get()    {}
func (c *Client) Post()   {}
func (c *Client) Delete() {}

Package names: short, lowercase, no stutter

A package name is part of every name it exports. Callers write http.Client, not just Client. So the package name is already "half the name". Stutter is when you repeat it: user.UserService reads as "user user service".

  • Lowercase, one word, no underscores or mixedCaps: httputil, strconv, task.
  • Name it after what it provides, not what it contains. Avoid util, common, helpers, models, base. These become junk drawers.
  • Don't repeat the package name in exported names: task.Service, task.New, bytes.Buffer, list.New.
package user

type UserService struct{}
func NewUserService() *UserService
func (s *UserService) GetUserByID(id int)

// caller: user.NewUserService().GetUserByID(7)
package user

type Service struct{}
func NewService() *Service
func (s *Service) ByID(id int)

// caller: user.NewService().ByID(7)

MixedCaps and initialisms

Go uses MixedCaps (exported) or mixedCaps (unexported). Never snake_case, never ALL_CAPS constants. The first letter decides visibility: capital means exported (visible outside the package).

Initialisms (acronyms like ID, URL, HTTP, JSON, API) keep a consistent case: all upper or all lower. So it's userID, ServeHTTP, parseURL, xmlHTTPRequest; never userId, ServeHttp, parseUrl.

Make the zero value useful

Every Go type has a zero value: the value a variable gets when you declare it without assigning anything. 0 for numbers, "" for strings, nil for pointers, slices and maps, and a struct with every field at its zero value.

The proverb asks you to design types so that the zero value already works. The standard library does this everywhere. You never call NewMutex() or NewBuffer(): you just declare one. That means fewer constructors, fewer "forgot to initialise" bugs, and types that embed cleanly in other structs.

package main

import (
	"bytes"
	"fmt"
	"strings"
	"sync"
)

// Counter needs no constructor: its zero value is ready to use.
type Counter struct {
	mu   sync.Mutex     // zero Mutex = unlocked
	hits map[string]int // nil until first write; we handle that
}

func (c *Counter) Hit(page string) {
	c.mu.Lock()
	defer c.mu.Unlock()
	if c.hits == nil {
		c.hits = make(map[string]int)
	}
	c.hits[page]++
}

func (c *Counter) Get(page string) int {
	c.mu.Lock()
	defer c.mu.Unlock()
	return c.hits[page] // reading a nil map is fine: returns 0
}

func main() {
	var buf bytes.Buffer // ready to write
	buf.WriteString("hello ")
	buf.WriteString("buffer")
	fmt.Println(buf.String())

	var sb strings.Builder // ready to write
	sb.WriteString("hello builder")
	fmt.Println(sb.String())

	var nums []int // nil slice: append just works
	nums = append(nums, 1, 2, 3)
	fmt.Println(nums, len(nums))

	var c Counter // no NewCounter() needed
	fmt.Println("before:", c.Get("/home"))
	c.Hit("/home")
	c.Hit("/home")
	fmt.Println("after:", c.Get("/home"))
}
hello buffer
hello builder
[1 2 3] 3
before: 0
after: 2

The trick inside Counter.Hit is lazy initialisation: create the map the first time you need it. Reading a nil map is safe (it returns the zero value), so Get needs no check at all. Only writing to a nil map panics, which is gotcha #2 below.

If your type truly can't have a useful zero value (it needs a database handle, say), that's fine: provide a New... constructor and document "use NewX to create a X". But try first. A struct that works with var x T is a joy to test and to embed.

Errors flow, interfaces and abstraction

How errors should flow through layers

In a real program an error is born deep down (the database, the file system) and travels up through layers until someone can do something about it. Think of it like a parcel being forwarded: each layer adds a label saying what it was doing, but only the final recipient opens it.

  1. The bottom layer reports what happened, ideally as a sentinel (ErrNotFound) or a typed error.
  2. Middle layers add what they were trying to do with fmt.Errorf("...: %w", err). The %w keeps the original error inside so errors.Is can still find it.
  3. The edge (HTTP handler, main, a worker loop) handles it once: log it, translate it to a status code, retry, or show it to the user.
package main

import (
	"errors"
	"fmt"
	"log/slog"
	"os"
)

var ErrNotFound = errors.New("not found") // sentinel: callers can test for it

// --- store layer: reports WHAT happened
func findUser(id int) (string, error) {
	if id != 1 {
		return "", ErrNotFound
	}
	return "ann", nil
}

// --- service layer: adds WHAT IT WAS DOING, keeps the cause with %w
func greet(id int) (string, error) {
	name, err := findUser(id)
	if err != nil {
		return "", fmt.Errorf("greet user %d: %w", id, err)
	}
	return "hello " + name, nil
}

// --- edge (handler/main): handles the error ONCE - log it or translate it
func main() {
	log := slog.New(slog.NewTextHandler(os.Stdout, &slog.HandlerOptions{
		ReplaceAttr: func(_ []string, a slog.Attr) slog.Attr {
			if a.Key == slog.TimeKey {
				return slog.Attr{} // drop time so output is stable
			}
			return a
		},
	}))
	for _, id := range []int{1, 7} {
		msg, err := greet(id)
		switch {
		case errors.Is(err, ErrNotFound):
			log.Warn("user missing", "id", id, "err", err)
		case err != nil:
			log.Error("unexpected", "err", err)
		default:
			fmt.Println(msg)
		}
	}
}
hello ann
level=WARN msg="user missing" id=7 err="greet user 7: not found"

Look at the final error string: greet user 7: not found. It reads like a breadcrumb trail from the top down. And because we wrapped with %w, errors.Is(err, ErrNotFound) is still true at the edge.

Gotcha: log OR return, never both

If every layer logs the error and then returns it, one failure produces five log lines saying the same thing. Each layer must choose: handle it (log, retry, translate) or return it (with context). Not both.

Accept interfaces, return structs

This is one of the most quoted pieces of Go advice. It means:

  • Accept interfaces: when your function only needs a behaviour (something that can Read), ask for the smallest interface that describes it. Then callers can hand you a file, a network connection, a string, a test fake, anything.
  • Return structs: when you build something, return the concrete type (*Store). The caller gets every method and field, can see real documentation, and can define their own small interface on their side if they need one.
package main

import (
	"bufio"
	"bytes"
	"fmt"
	"io"
	"os"
	"strings"
)

// CountLines ACCEPTS an interface: anything that can Read.
func CountLines(r io.Reader) (int, error) {
	sc := bufio.NewScanner(r)
	n := 0
	for sc.Scan() {
		n++
	}
	return n, sc.Err()
}

// Store is a concrete type. NewStore RETURNS the struct, not an interface.
type Store struct{ data map[string]string }

func NewStore() *Store { return &Store{data: map[string]string{}} }

func (s *Store) Put(k, v string)             { s.data[k] = v }
func (s *Store) Get(k string) (string, bool) { v, ok := s.data[k]; return v, ok }

func main() {
	n1, _ := CountLines(strings.NewReader("a\nb\nc\n"))
	n2, _ := CountLines(bytes.NewBufferString("one\ntwo\n"))
	f, _ := os.Open("main.go")
	defer f.Close()
	n3, _ := CountLines(f)
	fmt.Println("string:", n1, "buffer:", n2, "file main.go:", n3)

	s := NewStore()
	s.Put("lang", "go")
	v, ok := s.Get("lang")
	fmt.Println(v, ok)
}
string: 3 buffer: 2 file main.go: 42
go true
Mental model

An interface is a job description written by the person hiring. The employer (the function using the dependency) writes "must be able to Read". Any candidate who can Read gets the job. The candidate (the concrete type) doesn't need to know the job description exists. That's why Go interfaces live in the consumer's package, not the producer's.

Avoid premature abstraction

New Go developers coming from Java often create an interface for every struct "just in case": UserService interface, userServiceImpl struct, a factory, a mock. In Go this is usually wasted effort. Because interfaces are satisfied implicitly, you can add one later, at the moment a second implementation or a test actually needs it, without touching the concrete type at all.

  • Rule of three: write it concretely once, copy it the second time, and abstract on the third.
  • Don't create an interface with exactly one implementation unless it's at a real boundary (database, external API, clock) that tests need to fake.
  • Don't reach for generics until you've written the same function for two or three types.
  • A plain function beats a strategy pattern. A func(int) bool parameter is an interface with zero ceremony.
type UserRepository interface {
	Create(u User) error
	Get(id int) (User, error)
	Update(u User) error
	Delete(id int) error
	List() ([]User, error)
	Count() (int, error)
}

type userRepositoryImpl struct{ db *sql.DB }

func NewUserRepository(db *sql.DB) UserRepository {
	return &userRepositoryImpl{db: db}
}
// Concrete type, returned as a struct.
type UserStore struct{ db *sql.DB }

func NewUserStore(db *sql.DB) *UserStore {
	return &UserStore{db: db}
}

// In the package that NEEDS it, a tiny interface:
type userGetter interface {
	Get(ctx context.Context, id int) (User, error)
}

The 25 gotchas, with runnable demos

Every Go engineer has been bitten by most of these. Each one below is a complete program that was really run; the output shown is what Go 1.27 printed. Read the code, predict the output, then check. That habit of predicting is exactly what makes these stick.

#1 Loop variable capture (before Go 1.22)

Before Go 1.22, a for loop had one variable i shared by every iteration. Closures captured that single variable, so by the time they ran, it held its final value. Go 1.22 changed the rules: each iteration now gets a fresh copy. The rule is decided by the go line in your go.mod. Here is the same program in a module that says go 1.21, and then in our normal go 1.27 module.

package main

import "fmt"

func main() {
	var prints []func()
	for i := 0; i < 3; i++ {
		prints = append(prints, func() { fmt.Print(i, " ") })
	}
	for _, p := range prints {
		p()
	}
	fmt.Println()
}
  1. We collect closures to run later. This walkthrough follows the go 1.21 rules, where the loop has one i for all iterations.
  2. Iteration 0 appends a closure. It captures the variable i, not its current value.
  3. Iteration 1: the same i is incremented to 1, and a second closure captures that same variable.
  4. Iteration 2: a third closure, still the same i.
  5. The loop increments i to 3, the condition i < 3 fails, and the loop ends. All three closures point at an i that now holds 3.
  6. Now we call each closure. Each reads i right now, and right now it is 3.
  7. Output: 3 3 3. With go 1.22 or later in go.mod, each iteration gets its own i, so the closures see 0, 1, 2 and print 0 1 2.
3 3 3 
0 1 2

Old code (and old blog posts) is full of i := i lines to work around this. In a module at Go 1.22+ they are harmless but unnecessary, and go fix / modern linters will offer to remove them. When you upgrade the go line in an old module, the semantics change, so run the tests.

#2 Writing to a nil map

A declared-but-not-made map is nil. Reading from it is fine and returns the zero value. Writing to it panics.

package main

import "fmt"

func main() {
	var counts map[string]int // nil map: reads work, writes panic
	fmt.Println("read from nil map:", counts["go"])
	counts["go"]++
	fmt.Println("never printed")
}
  1. var counts map[string]int declares a map but never makes one. Its value is nil: no hash table exists.
  2. Reading a missing key from a nil map is allowed and returns the zero value, 0. This makes the bug easy to miss.
  3. counts["go"]++ needs to store a value, but there is no table to store into. The runtime panics.
  4. This line never runs; the program exits with status 2. Fix: counts := make(map[string]int) or a map literal.
read from nil map: 0

goroutine 1 [running]:
main.main()

Fix: make the map, use a literal (map[string]int{}), or lazily initialise it as part of a useful zero value:

package main

import "fmt"

type Stats struct {
	counts map[string]int
}

// Add lazily creates the map, so the zero Stats is usable.
func (s *Stats) Add(word string) {
	if s.counts == nil {
		s.counts = make(map[string]int)
	}
	s.counts[word]++
}

func main() {
	var s Stats
	s.Add("go")
	s.Add("go")
	fmt.Println(s.counts)
}
  1. The zero Stats has a nil map. Writing to it now would panic.
  2. First Add. The method has a pointer receiver, so it can modify s. It checks for the nil map...
  3. ...and creates it. This is the only time make runs.
  4. Now the write is safe.
  5. Second Add: the map exists, so we skip make and just increment.
  6. The zero value is useful, which is a Go idiom: callers can write var s Stats with no constructor.

#3 Slice aliasing on append

A slice is a small header: a pointer to a backing array, a length and a capacity. If there is spare capacity, append writes into the same array instead of copying. Two appends from the same base can overwrite each other.

func main() {
	base := make([]int, 3, 10) // len 3, cap 10: room to grow in place
	a := append(base, 1)
	b := append(base, 2) // writes into the SAME backing array slot as a[3]
	fmt.Println("a:", a)
	fmt.Println("b:", b)

	// Fix: force a fresh array with a full slice expression (cap = len).
	safe := base[:len(base):len(base)]
	c := append(safe, 1)
	d := append(safe, 2)
	fmt.Println("c:", c, "d:", d)
}
  1. We make a slice with length 3 but capacity 10. The backing array has 7 unused slots after the visible part.
  2. Appending 1 fits in the spare capacity, so Go writes into slot 3 of the same array. a is a new header pointing at that array with len 4.
  3. Appending 2 to base (still len 3) writes into slot 3 again, overwriting the 1. Both a and b look at that slot.
  4. Surprise: a also ends in 2.
  5. The full slice expression s[low:high:max] caps the capacity at 3. There is no spare room now.
  6. Each append has to allocate a fresh array, so c and d are independent.
  7. Correct, independent results.
a: [0 0 0 2]
b: [0 0 0 2]
c: [0 0 0 1] d: [0 0 0 2]

If a function receives a slice and appends to it, document whether it may modify the caller's data, or defensively slices.Clone first. This bug often appears in "build a list of paths" recursion, where sibling branches share a prefix slice and stomp each other's last element.

#4 The nil interface that isn't nil

An interface value is a pair: (type, value). It is only nil when both parts are empty. If you put a nil *MyErr pointer inside an error, the type part is filled in, so the interface is not nil. This is the most famous Go gotcha of all.

func validate(ok bool) error {
	var p *MyErr // typed nil pointer
	if !ok {
		p = &MyErr{}
	}
	return p // BUG: an interface holding (*MyErr)(nil) is NOT nil
}

func validateFixed(ok bool) error {
	if !ok {
		return &MyErr{}
	}
	return nil // return a literal nil interface
}

func main() {
	err := validate(true)
	fmt.Println("err == nil?", err == nil)
	fmt.Printf("inside the interface: type=%T, pointer is nil=%v\n", err, err.(*MyErr) == nil)
	fmt.Println("fixed == nil?", validateFixed(true) == nil)
  1. main calls validate(true). Everything is fine, so we expect no error.
  2. We declare p as a *MyErr. Its value is a nil pointer, but its static type is *MyErr.
  3. ok is true, so we skip the assignment. p stays nil.
  4. Returning p as an error wraps it in an interface: the type slot says *MyErr, the value slot says nil. That pair is not the empty pair.
  5. err == nil compares against the empty pair (nil, nil). The type slot is filled, so the answer is false.
  6. Looking inside proves it: the dynamic type is *main.MyErr, and the pointer it holds really is nil.
  7. The fix: return the literal nil on the success path. Never return a typed nil pointer through an interface.
err == nil? false
inside the interface: type=*main.MyErr, pointer is nil=true
fixed == nil? true

#5 range copies values

for _, p := range players gives you a copy of each element. Changing p changes the copy, not the slice. To modify in place, index into the slice.

package main

import "fmt"

type Player struct {
	Name  string
	Score int
}

func main() {
	players := []Player{{"ann", 1}, {"bob", 2}}

	for _, p := range players {
		p.Score += 100 // modifies a COPY
	}
	fmt.Println("after value loop:", players)

	for i := range players {
		players[i].Score += 100 // modifies the element itself
	}
	fmt.Println("after index loop:", players)
}
  1. A slice of structs. Each element is stored inline in the backing array.
  2. Iteration 0: p is a copy of players[0]. Adding 100 changes the copy only.
  3. Iteration 1: same story. p is overwritten with a fresh copy of the next element.
  4. The slice is unchanged. No error, no warning.
  5. Now we range over indexes only and write through players[i]. This touches the element in the backing array.
  6. Same for index 1.
  7. Both scores changed. (Storing []*Player also works, but then every element is a separate allocation.)
after value loop: [{ann 1} {bob 2}]
after index loop: [{ann 101} {bob 102}]

Ranging over a slice of big structs also copies each one, which costs time. If the struct is large and you only read it, for i := range s { p := &s[i] ... } avoids the copy.

#6 defer evaluates its arguments immediately

defer f(x) schedules f to run later, but it reads x right now. A deferred closure, on the other hand, reads variables when it finally runs.

package main

import "fmt"

func main() {
	x := 1
	defer fmt.Println("deferred arg sees x =", x) // x evaluated NOW
	defer func() { fmt.Println("closure sees x =", x) }()
	x = 42
	fmt.Println("main returns with x =", x)
}
  1. We set x to 1.
  2. The first defer evaluates its arguments now: it stores the string and the number 1. The call itself waits.
  3. The second defer stores a closure. Closures capture the variable, not its current value.
  4. We change x to 42.
  5. Normal print.
  6. main returns. Defers run in last-in, first-out order, so the closure runs first and reads the current x: 42.
  7. Then the first defer runs with the value it saved long ago: 1.
main returns with x = 42
closure sees x = 42
deferred arg sees x = 1

This matters for things like defer log.Printf("took %v", time.Since(start)): time.Since runs immediately, so it always logs about 0s. Write defer func() { log.Printf("took %v", time.Since(start)) }() instead.

#7 The shadowed err

:= declares new variables. Inside a nested block, it creates a new err that hides (shadows) the outer one. The outer one is never updated.

func run() error {
	var err error
	for i := 1; i <= 3; i++ {
		v, err := step(i) // := declares a NEW err that shadows the outer one
		if err != nil {
			fmt.Println("  inner saw:", err)
			continue
		}
		_ = v
	}
	return err // the outer err was never assigned
}

func main() {
	fmt.Println("run() returned:", run())
  1. The function declares an outer err, meaning to return it.
  2. Inside the loop, v, err := step(i) declares a brand-new v and a brand-new err scoped to the loop body.
  3. On iteration 2 the inner err gets the failure.
  4. We print it and continue. The outer err is untouched.
  5. Iteration 3 succeeds.
  6. We return the outer err, which was never assigned.
  7. The caller thinks everything worked. The failure was silently swallowed.
  inner saw: step 2 failed

#8 time.After in a loop

time.After(d) creates a new timer every call. In a hot select loop that's a fresh timer every iteration. Before Go 1.23 those timers couldn't be garbage-collected until they fired, so a loop with time.After(time.Hour) was a real memory leak. Since Go 1.23, unreferenced timers are collectable, so it's no longer a leak, but it is still needless allocation. Measured:

package main

import (
	"fmt"
	"runtime"
	"time"
)

func allocs(f func()) uint64 {
	var a, b runtime.MemStats
	runtime.ReadMemStats(&a)
	f()
	runtime.ReadMemStats(&b)
	return b.Mallocs - a.Mallocs
}

func main() {
	events := make(chan int)
	const n = 10000

	naive := allocs(func() {
		for range n {
			select {
			case <-events:
			case <-time.After(time.Hour): // a brand-new timer every iteration
			default:
			}
		}
	})

	reused := allocs(func() {
		t := time.NewTimer(time.Hour)
		defer t.Stop()
		for range n {
			t.Reset(time.Hour) // one timer, reset each time
			select {
			case <-events:
			case <-t.C:
			default:
			}
		}
	})

	fmt.Println("time.After in loop: allocations =", naive)
	fmt.Println("reused timer:       allocations =", reused)
}
time.After in loop: allocations = 30000
reused timer:       allocations = 3

Ten thousand iterations, thirty thousand allocations versus three. For a hot loop, create one timer and Reset it. (Since 1.23, Reset and Stop also guarantee no stale value is left in t.C, which removes the old "drain the channel" dance.)

#12 Integer division and overflow

Dividing two integers gives an integer: the fraction is thrown away (truncated toward zero). Converting to float after the division is too late. Integers also wrap silently on overflow.

  6. A uint8 holds 0 to 255. We start at the top.
  7. b++ overflows. Go does not panic; unsigned integers wrap around silently.
  8. 255 + 1 = 0. Watch for this in counters, sizes and anything parsed from untrusted input.

	"encoding/json"
	"fmt"

#15 Copying a mutex

A sync.Mutex must never be copied after first use. A value receiver copies the whole struct, including the lock, so each call locks its own private copy and increments a private n. The program "works", but protects nothing and changes nothing.

package main

import (
	"fmt"
	"sync"
)

type Counter struct {
	mu sync.Mutex
	n  int
}

// Value receiver: c is a COPY, including a copy of the mutex.
func (c Counter) Inc() {
	c.mu.Lock()
	defer c.mu.Unlock()
	c.n++
}

func main() {
	var c Counter
	c.Inc()
	c.Inc()
	fmt.Println("n =", c.n)
}
  1. c is a zero Counter: an unlocked mutex and n = 0. Both zero values are ready to use.
  2. c.Inc() has a value receiver, so Go copies the whole struct into the method's c, mutex included.
  3. The method locks the copy's mutex and increments the copy's n. The caller's lock and counter are never touched.
  4. The method returns and the copy is thrown away, along with its n = 1.
  5. The second call makes a fresh copy and repeats the same useless work.
  6. The counter is still 0. With goroutines this would also be a data race, because no two calls share a lock. Fix: func (c *Counter) Inc(). go vet's copylocks check catches this.
n = 0

go vet catches it:

main.go:14:9: Inc passes lock by value: example/g15.Counter contains sync.Mutex

Fix: use a pointer receiver, func (c *Counter) Inc(), on every method of any type that contains a mutex, and pass such structs by pointer.

#16 Forgetting to close (and drain) a response body

An HTTP response body is a live network stream. If you don't read it to the end and Close it, the connection can't go back into the pool, so the next request has to open a new TCP (and maybe TLS) connection. Under load you run out of file descriptors. This demo uses httptrace to ask "was this connection reused?":

package main

import (
	"fmt"
	"io"
	"net/http"
	"net/http/httptest"
	"net/http/httptrace"
	"strings"
)

func get(url string, drainAndClose bool) {
	reused := false
	trace := &httptrace.ClientTrace{
		GotConn: func(info httptrace.GotConnInfo) { reused = info.Reused },
	}
	req, _ := http.NewRequest("GET", url, nil)
	req = req.WithContext(httptrace.WithClientTrace(req.Context(), trace))
	resp, err := http.DefaultClient.Do(req)
	if err != nil {
		panic(err)
	}
	if drainAndClose {
		defer resp.Body.Close()
		io.Copy(io.Discard, resp.Body)
	}
	fmt.Println("  connection reused:", reused)
}

func main() {
	srv := httptest.NewServer(http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		io.WriteString(w, strings.Repeat("x", 1024))
	}))
	defer srv.Close()

	fmt.Println("forgetting Body.Close():")
	for range 3 {
		get(srv.URL, false)
	}
	http.DefaultClient.CloseIdleConnections()
	fmt.Println("draining + closing the body:")
	for range 3 {
		get(srv.URL, true)
	}
}
  1. We start a local test server that answers every request with 1 KB of x.
  2. First, the buggy client.
  3. get installs an httptrace hook that records whether the TCP connection came from the idle pool, then sends the request.
  4. We never read or close the body, so the connection stays busy. It cannot go back to the pool.
  5. Each later call has to dial a brand-new connection. Under load this means thousands of sockets and "too many open files".
  6. We drop the idle pool, then try the correct version.
  7. The first call dials fresh (the pool is empty). io.Copy(io.Discard, ...) reads the body to the end, and the deferred Close returns the connection to the pool.
  8. Calls 2 and 3 pick up that same idle connection: reused: true.
forgetting Body.Close():
  connection reused: false
  connection reused: false
  connection reused: false
draining + closing the body:
  connection reused: false
  connection reused: true
  connection reused: true

Without closing, every request opens a new connection. With drain + close, after the first request every connection is reused. Always write defer resp.Body.Close() right after checking the error.

#17 Goroutine leaks

A goroutine that blocks forever is never collected. It keeps its stack and everything it references alive. The classic shape: launch N goroutines, take the first answer, and leave the others stuck sending to a channel nobody reads.

package main

import (
	"context"
	"fmt"
	"runtime"
	"time"
)

// leaky returns the first result, but the losing goroutines block forever
// on an unbuffered send that nobody will ever receive.
func leaky() int {
	ch := make(chan int)
	for i := range 3 {
		go func() { ch <- i }()
	}
	return <-ch
}

// fixed gives every sender somewhere to go (buffer) - or use a context.
func fixed(ctx context.Context) int {
	ch := make(chan int, 3)
	for i := range 3 {
		go func() {
			select {
			case ch <- i:
			case <-ctx.Done():
			}
		}()
	}
	return <-ch
}

func main() {
	before := runtime.NumGoroutine()
	for range 100 {
		leaky()
	}
	time.Sleep(50 * time.Millisecond)
	fmt.Println("leaky: goroutines grew from", before, "to", runtime.NumGoroutine())

	before = runtime.NumGoroutine()
	for range 100 {
		fixed(context.Background())
	}
	time.Sleep(50 * time.Millisecond)
	fmt.Println("fixed: goroutines went from", before, "to", runtime.NumGoroutine())
}
  1. We record how many goroutines exist: just main, so 1.
  2. First call to leaky. It makes an unbuffered channel: every send needs a receiver waiting.
  3. It starts three senders. Each tries ch <- i and blocks until someone receives.
  4. leaky receives once and returns. One sender finishes; the other two are blocked on a channel that nothing will ever read again. They leak.
  5. 100 calls leave 2 stuck goroutines each: 200 leaked goroutines that are never garbage collected.
  6. After a short sleep the count is 1 + 200 = 201. In a server this grows until memory runs out.
  7. The fixed version gives the channel a buffer of 3, so every sender has a slot.
  8. All three sends succeed immediately (the ctx.Done() case is a second escape hatch). fixed reads one value and returns; the senders already finished.
  9. 100 calls, zero new goroutines left behind. (The 200 from the leaky phase are still stuck.)
leaky: goroutines grew from 1 to 201
fixed: goroutines went from 201 to 201

100 calls leaked 200 goroutines. In a server that handles a million requests a day, that's a slow-motion outage. Every goroutine you start needs an answer to "how does this goroutine end?".

In tests, check for leaks automatically. Snapshot runtime.NumGoroutine() before and after, or use go.uber.org/goleak, which fails the test if goroutines outlive it. Recent Go releases also ship an experimental goroutine-leak profile in runtime/pprof that finds goroutines blocked on unreachable channels.

#19 Arrays are values; slice headers are copied

An array ([3]int) is copied whole when assigned or passed. A slice passes a header by value: the callee shares the data but has its own length. So a callee can change elements you see, but an append in the callee is invisible to you.

package main

import "fmt"

func zero(a [3]int) { a[0] = 0 }          // gets a copy of the whole array
func zeroS(s []int) { s[0] = 0 }          // gets a header pointing at shared data
func grow(s []int)  { s = append(s, 99) } // caller never sees the new len

func main() {
	arr := [3]int{1, 2, 3}
	zero(arr)
	fmt.Println("array after zero: ", arr)

	sl := []int{1, 2, 3}
	zeroS(sl)
	fmt.Println("slice after zeroS:", sl)
	grow(sl)
	fmt.Println("slice after grow: ", sl)
}
  1. arr is an array: the three ints are the value itself.
  2. Passing an array copies all of it. zero sets a[0] on its own private copy, which is thrown away on return.
  3. The caller's array is untouched.
  4. sl is a slice: a small header (pointer, len, cap) pointing at a hidden array.
  5. zeroS gets a copy of the header, but the copy points at the same backing array. Writing s[0] writes the shared data.
  6. So the caller sees the change.
  7. grow appends. cap is 3, so append allocates a new array and assigns the new header to the local s. The caller's header still says len 3.
  8. The 99 is lost. If a function changes a slice's length, it must return the new slice, like append itself does.
array after zero:  [1 2 3]
slice after zeroS: [0 2 3]
slice after grow:  [0 2 3]

The fix for grow is the pattern the built-in append uses: return the new slice, s = grow(s).

package main

#22 defer inside a loop

defer runs when the function returns, not when the loop iteration ends. Open 10,000 files in a loop with defer f.Close() and you hold 10,000 file descriptors until the very end.

package main

import (
	"fmt"
	"os"
	"path/filepath"
)

func main() {
	dir, _ := os.MkdirTemp("", "defer")
	defer os.RemoveAll(dir)
	for i := range 3 {
		name := filepath.Join(dir, fmt.Sprintf("f%d.txt", i))
		os.WriteFile(name, []byte("hi"), 0o644)
	}

	// BAD: every Close waits until processAll returns.
	processAll := func() {
		for i := range 3 {
			f, _ := os.Open(filepath.Join(dir, fmt.Sprintf("f%d.txt", i)))
			defer func() { fmt.Println("  closing", filepath.Base(f.Name())); f.Close() }()
			fmt.Println("  opened", filepath.Base(f.Name()))
		}
		fmt.Println("  loop done")
	}
	fmt.Println("defer in loop:")
	processAll()

	// GOOD: move the body into a function so defer runs per iteration.
	processOne := func(i int) {
		f, _ := os.Open(filepath.Join(dir, fmt.Sprintf("f%d.txt", i)))
		defer func() { fmt.Println("  closing", filepath.Base(f.Name())); f.Close() }()
		fmt.Println("  opened", filepath.Base(f.Name()))
	}
	fmt.Println("defer in helper:")
	for i := range 3 {
		processOne(i)
	}
}
  1. Setup: create a temp dir with three small files. The defer os.RemoveAll(dir) will clean up when main ends.
  2. We call processAll, the buggy version.
  3. Iteration 0 opens f0.txt and registers a deferred close. The defer belongs to the function, not the loop body, so it does not run at the end of the iteration.
  4. Iteration 1 opens another file. Two files are now open at once.
  5. Iteration 2: three open files. With 10,000 files you would hit the OS limit ("too many open files").
  6. The loop ends and still nothing has been closed.
  7. Only when processAll returns do the defers fire, in LIFO order: f2, f1, f0.
  8. Now the fix: the loop body lives in its own function.
  9. processOne(0) opens f0 and its defer fires as soon as processOne returns. Only one file is open at a time.
  10. The same open-close pair repeats for f1 and f2. Then main returns and its own deferred RemoveAll deletes the directory.

One unprotected go func() that panics takes down your whole server and every in-flight request. net/http recovers panics in handlers for you, but goroutines you start from a handler are not covered. Long-lived background goroutines should have their own defer func() { if r := recover(); r != nil { log... } }().

#24 Comparing wrapped errors with ==

Once an error has been wrapped with %w, it's a different value. == fails; errors.Is unwraps the chain and finds it. errors.As finds an error of a given type and gives you its fields.

package main

import (
	"errors"
	"fmt"
	"io/fs"
	"os"
)

func load(path string) error {
	_, err := os.ReadFile(path)
	if err != nil {
		return fmt.Errorf("load config %q: %w", path, err)
	}
	return nil
}

func main() {
	err := load("/does/not/exist.yaml")
	fmt.Println(err)
	fmt.Println("err == fs.ErrNotExist:         ", err == fs.ErrNotExist)
	fmt.Println("errors.Is(err, fs.ErrNotExist):", errors.Is(err, fs.ErrNotExist))

	var pe *fs.PathError
	if errors.As(err, &pe) {
		fmt.Println("errors.As found PathError, op =", pe.Op)
	}
}
  1. main calls load, which tries to read a file that does not exist. os.ReadFile returns a *fs.PathError.
  2. We add context with %w. That builds a new error whose message is ours plus the original, and whose Unwrap() returns the *fs.PathError.
  3. Back in main, err is the outer wrapper. The chain has three links: wrapper, PathError, and the sentinel fs.ErrNotExist inside it.
  4. Println shows the full message: our context first, then the original text.
  5. The bug: == compares only the outermost error, the wrapper. It is not the sentinel, so the answer is false even though the file really is missing.
  6. errors.Is walks the chain with Unwrap link by link and finds the sentinel deep inside.
  7. errors.As walks the same chain looking for a type. It finds the *fs.PathError, stores it in pe, and we can read its fields.

  2. p := m["a"] copies the struct out of the map. p is an ordinary local variable, so it is addressable.
  3. We change the copy. The map still holds the old value at this moment.
  4. Storing p back replaces the whole value in the map. Now the change is visible.
  5. Printing shows the update.
  6. Alternative: store pointers. The map element is the pointer; the struct it points at lives on the heap and is addressable.
  7. ptrs["a"].X = 10 follows the pointer and writes into the struct directly. No copy-back needed.
  8. Dereferencing prints the updated struct. The trade-off: pointer values mean shared mutable state, so pick deliberately.

Design principles: packages, boundaries, dependencies

Good Go architecture is mostly about packages. A package is Go's unit of encapsulation: everything lowercase is private to it. That's a powerful tool for drawing boundaries.

Small, focused packages

  • A package should have one clear purpose you can describe in a sentence without the word "and".
  • Organise by domain (task, billing, auth), not by technical layer (models, controllers, services). Layer packages force every feature change to touch five packages, and they tend to import each other in circles.
  • Don't split too early, either. One package with five files is better than five packages with one file each. Split when a clear boundary appears.
  • Use internal/ to stop other modules importing code you don't want to support as a public API.

Dependency direction

Dependencies should point inward, toward your core business logic. The domain (what a Task is, the rules about it) depends on nothing. The outer layers (HTTP, Postgres, Kafka) depend on the domain. That way you can swap your database or add a gRPC API without touching the core.

The trick that makes this work is again "interfaces belong to the consumer": the task package declares the Store interface it needs, and postgres satisfies it without task ever importing postgres. Only main knows about both and plugs them together. This also makes import cycles (which Go forbids) nearly impossible.

A quick health check: run go list -deps ./internal/task | grep yourmodule. Your domain package should import almost nothing from your own module.

API design: functional options and config structs

Constructors grow. NewServer(addr) becomes NewServer(addr, timeout, maxConn, logger, tlsConfig, ...), and every new knob breaks every caller. Go has two idiomatic ways to keep constructors stable.

Functional options

An option is a function that tweaks the thing being built. The constructor sets defaults, then applies each option in order. Callers pass only what they care about, and you can add new options without breaking anybody.

package main

import (
	"fmt"
	"time"
)

type Server struct {
	addr    string
	timeout time.Duration
	maxConn int
	logf    func(string, ...any)
}

// Option is a function that tweaks a Server while it is being built.
type Option func(*Server)

func WithTimeout(d time.Duration) Option { return func(s *Server) { s.timeout = d } }
func WithMaxConn(n int) Option           { return func(s *Server) { s.maxConn = n } }
func WithLogger(f func(string, ...any)) Option {
	return func(s *Server) { s.logf = f }
}

// NewServer has one required argument and any number of options.
func NewServer(addr string, opts ...Option) *Server {
	s := &Server{ // sensible defaults first
		addr:    addr,
		timeout: 30 * time.Second,
		maxConn: 100,
		logf:    func(string, ...any) {},
	}
	for _, opt := range opts {
		opt(s)
	}
	return s
}

func main() {
	a := NewServer(":8080")
	fmt.Printf("defaults: addr=%s timeout=%v maxConn=%d\n", a.addr, a.timeout, a.maxConn)

	b := NewServer(":9090",
		WithTimeout(5*time.Second),
		WithMaxConn(10),
		WithLogger(func(f string, args ...any) { fmt.Printf("[log] "+f+"\n", args...) }),
	)
	fmt.Printf("custom:   addr=%s timeout=%v maxConn=%d\n", b.addr, b.timeout, b.maxConn)
	b.logf("listening on %s", b.addr)
}

Go documentation is just comments placed directly above a declaration, with no blank line between. go doc and pkg.go.dev render them. The conventions are simple:

  • Every exported identifier gets a comment that starts with its name: // Client talks to the users service.

Concurrency rules of thumb

Go makes starting goroutines trivially easy, which is exactly why it needs discipline. These rules prevent the vast majority of concurrency bugs we saw above.

  1. Know how every goroutine ends. Before writing go, answer: what makes it return? A closed channel, a cancelled context, finished work. If you can't answer, don't start it.
  2. The caller decides concurrency. Write synchronous functions (func Fetch(ctx, id) (User, error)). Let the caller wrap them in goroutines if they want. Synchronous APIs are easier to test and compose.
  3. The sender closes the channel, never the receiver, and only when there are no more sends. Closing is a broadcast "no more values", not a cleanup requirement.
  4. Pass context.Context as the first parameter to anything that blocks or does I/O, and respect ctx.Done().
  5. Use sync.WaitGroup (wg.Go since 1.25) or errgroup to wait for a group of goroutines; never time.Sleep or a busy-loop.
  6. Protect shared state with exactly one strategy: one mutex, or one owning goroutine with channels. Keep the lock and the data it guards next to each other in the struct, and keep critical sections tiny (no I/O while holding a lock).
  7. Bound your concurrency. 10,000 items doesn't mean 10,000 goroutines hitting the database. Use a worker pool, a semaphore channel, or errgroup.SetLimit.
  8. Prefer giving each goroutine its own slot (results[i] = ...) over sharing one slice under a lock. No contention, no ordering issues.
  9. Run tests with -race, always, in CI.
  10. Start simple. A mutex around a map is fine. Lock-free atomics and sharded maps come after a profile proves you need them.
Mental model

A goroutine is like hiring a contractor. Before you hire, you write down how the job ends and how they'll tell you they're done. You'd never hire someone with "just keep doing stuff forever, I'll never check on you". That's what an unmanaged go func() is.

package main

import (
	"context"
	"encoding/json"
	"errors"
	"fmt"
	"net/http"
	"net/http/httptest"
	"sync"
	"time"
)

// User is a user returned by the users service.
type User struct {
	ID   int    `json:"id"`
	Name string `json:"name"`
}

// Client talks to the users service. Create one with NewClient.
type Client struct {
	baseURL string
	http    *http.Client
}

// NewClient returns a Client with a sane request timeout.
func NewClient(baseURL string) *Client {
	return &Client{baseURL: baseURL, http: &http.Client{Timeout: 5 * time.Second}}
}

// User fetches a single user by ID.
func (c *Client) User(ctx context.Context, id int) (User, error) {
	url := fmt.Sprintf("%s/users/%d", c.baseURL, id)
	req, err := http.NewRequestWithContext(ctx, http.MethodGet, url, nil)
	if err != nil {
		return User{}, fmt.Errorf("build request for user %d: %w", id, err)
	}
	resp, err := c.http.Do(req)
	if err != nil {
		return User{}, fmt.Errorf("get user %d: %w", id, err)
	}
	defer resp.Body.Close()
	if resp.StatusCode != http.StatusOK {
		return User{}, fmt.Errorf("get user %d: unexpected status %s", id, resp.Status)
	}
	var u User
	if err := json.NewDecoder(resp.Body).Decode(&u); err != nil {
		return User{}, fmt.Errorf("decode user %d: %w", id, err)
	}
	return u, nil
}

// Users fetches users concurrently. Results keep the order of ids.
func (c *Client) Users(ctx context.Context, ids []int) ([]User, error) {
	users := make([]User, len(ids))
	errs := make([]error, len(ids))
	var wg sync.WaitGroup
	for i, id := range ids {
		wg.Go(func() { // each goroutine writes only its own index: no lock needed
			users[i], errs[i] = c.User(ctx, id)
		})
	}
	wg.Wait()
	if err := errors.Join(errs...); err != nil {
		return nil, err
	}
	return users, nil
}

func main() {
	srv := httptest.NewServer(http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		var id int
		fmt.Sscanf(r.URL.Path, "/users/%d", &id)
		if id == 13 {
			http.Error(w, "unlucky", http.StatusNotFound)
			return
		}
		fmt.Fprintf(w, `{"id":%d,"name":"user%d"}`, id, id)
	}))
	defer srv.Close()

	c := NewClient(srv.URL)
	ctx, cancel := context.WithTimeout(context.Background(), 2*time.Second)
	defer cancel()

	users, err := c.Users(ctx, []int{1, 2, 3, 4})
	fmt.Println(users, err)

	_, err = c.Users(ctx, []int{1, 13})
	fmt.Println("error:", err)
}
[{1 user1} {2 user2} {3 user3} {4 user4}] <nil>
error: get user 13: unexpected status 404 Not Found

Notice the shape of the fix: Client.User is a plain synchronous function that's trivial to test on its own, and Users adds concurrency on top. That's rule #2 from the concurrency list. In review, suggesting this split is often more valuable than pointing out the individual bugs, because it prevents the next ten.

Exercise 1: Fix the shadowed error and the defer in this function

This function should copy every file in paths into w and return the first error. It has two bugs from this chapter. Find and fix them.

func concatFiles(w io.Writer, paths []string) error {
	var err error
	for _, p := range paths {
		f, err := os.Open(p)
		if err != nil {
			break
		}
		defer f.Close()
		_, err = io.Copy(w, f)
	}
	return err
}

Hint: what does break leave in the outer err? When does each file get closed?

Solution
package main

import (
	"fmt"
	"io"
	"os"
	"path/filepath"
	"strings"
)

func concatFiles(w io.Writer, paths []string) error {
	for _, p := range paths {
		if err := copyFile(w, p); err != nil {
			return err // return at the failure; nothing to shadow
		}
	}
	return nil
}

// copyFile owns one file, so its defer runs once per file.
func copyFile(w io.Writer, path string) error {
	f, err := os.Open(path)
	if err != nil {
		return fmt.Errorf("concat: %w", err)
	}
	defer f.Close()
	if _, err := io.Copy(w, f); err != nil {
		return fmt.Errorf("concat %s: %w", path, err)
	}
	return nil
}

func main() {
	dir, _ := os.MkdirTemp("", "ex1")
	defer os.RemoveAll(dir)
	a := filepath.Join(dir, "a.txt")
	b := filepath.Join(dir, "b.txt")
	os.WriteFile(a, []byte("hello "), 0o644)
	os.WriteFile(b, []byte("world\n"), 0o644)

	var out strings.Builder
	fmt.Println("ok:", concatFiles(&out, []string{a, b}), "->", strings.TrimSpace(out.String()))
	err := concatFiles(&out, []string{a, "missing.txt"})
	fmt.Println("missing:", err)
}
ok: <nil> -> hello world
missing: concat: open missing.txt: no such file or directory

Bug 1 (gotcha #7): f, err := os.Open(p) shadowed the outer err, so the function returned nil on failure. Bug 2 (gotcha #22): all files stayed open until the function returned. Moving the body into copyFile fixes both: defer runs per file, and errors return immediately with context.

Exercise 2: Redesign a constructor with a config struct

A colleague wrote func NewCache(size int, ttl time.Duration, onEvict func(string), metrics bool, name string) *Cache. Every call site looks like NewCache(100, 0, nil, false, ""). Redesign it so that the common call is short, new settings don't break callers, and defaults are applied in one place.

Solution
package main

import (
	"fmt"
	"time"
)

// CacheConfig configures a Cache. The zero value is valid.
type CacheConfig struct {
	Size    int              // max entries; 0 means 1000
	TTL     time.Duration    // 0 means entries never expire
	OnEvict func(key string) // optional callback
	Metrics bool             // export hit/miss counters
	Name    string           // used in logs and metrics; "" means "cache"
}

// Cache is a size-bounded key/value cache.
type Cache struct {
	cfg CacheConfig
}

// NewCache returns a Cache configured by cfg. Defaults are applied here, once.
func NewCache(cfg CacheConfig) *Cache {
	if cfg.Size == 0 {
		cfg.Size = 1000
	}
	if cfg.Name == "" {
		cfg.Name = "cache"
	}
	if cfg.OnEvict == nil {
		cfg.OnEvict = func(string) {}
	}
	return &Cache{cfg: cfg}
}

func main() {
	a := NewCache(CacheConfig{}) // the common case is short
	b := NewCache(CacheConfig{Name: "sessions", TTL: 30 * time.Minute})
	fmt.Printf("a: name=%s size=%d ttl=%v\n", a.cfg.Name, a.cfg.Size, a.cfg.TTL)
	fmt.Printf("b: name=%s size=%d ttl=%v\n", b.cfg.Name, b.cfg.Size, b.cfg.TTL)
}
a: name=cache size=1000 ttl=0s
b: name=sessions size=1000 ttl=30m0s

Required settings would stay positional parameters. Here nothing is truly required, so everything moved into CacheConfig, and the zero config is valid. Adding a new field later breaks nobody.

Exercise 3: Stop the goroutine leak

firstResponse asks three mirrors for a file and returns the fastest answer. Run it 100 times in a loop and runtime.NumGoroutine() keeps growing. Fix it two ways: with a buffered channel, and with a context that cancels the slow mirrors.

func firstResponse(mirrors []string) string {
	ch := make(chan string)
	for _, m := range mirrors {
		go func() { ch <- fetch(m) }()
	}
	return <-ch
}
Solution

Fix A: ch := make(chan string, len(mirrors)). Every sender has a slot, so the losers complete their send and exit. Fix B (better, because it also stops wasted work): pass a context, defer cancel() after receiving the first result, make fetch honour ctx, and have senders select on ch <- v and <-ctx.Done(). The fixed function in gotcha #17 above shows the select pattern, and its output proves the goroutine count stays flat.

Key takeaways

  • Go seniority is about boring, obvious code: short names in small scopes, no stutter, MixedCaps, consistent initialisms (userID, ServeHTTP).
  • Design types whose zero value works; lazy-initialise maps; constructors are optional.
  • Errors flow upward gaining context with %w, and are handled once at the edge. Inspect with errors.Is/errors.As, never == on wrapped errors.
  • Accept interfaces, return structs. Define small interfaces where they're used, and only when a second implementation or a test needs one.
  • Memorise the big traps: typed nil in interfaces, append aliasing, shadowed err, defer argument timing, nil map writes, mutex copies, unclosed bodies, goroutine leaks, panics in goroutines.
  • Automate taste: gofmt, go vet, staticcheck, golangci-lint and -race in CI, so humans can review design.
  • Packages are organised by domain, dependencies point inward, and main wires everything together.
  • Prefer config structs for apps and functional options for growing libraries. Document every exported name, starting with the name.
  • For every goroutine, know how it ends. Write synchronous functions and let callers add concurrency.

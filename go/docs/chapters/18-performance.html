Performance & Memory

Go is fast by default, but "fast by default" still leaves a lot on the table when code allocates carelessly or does needless work in a hot path. This chapter teaches you to measure before you optimize, to understand where memory lives (stack or heap) and what the garbage collector costs, and to use benchmarks, pprof and the execution tracer the way performance engineers do. Every number here was measured on the author's machine (an Apple M1, 8 cores, Go 1.27.1). Your numbers will differ; the ratios are what matter.

Measure first

The most important performance skill isn't a trick. It's discipline. Programmers are famously bad at guessing where time goes. The function you're sure is slow is usually fine, and the real cost is somewhere boring, like a regexp compiled in a loop or JSON encoding a huge struct.

So performance work always follows the same loop:

  1. Define the goal. "p99 latency under 50ms at 2,000 requests/second" is a goal. "Make it faster" is not. Without a goal you don't know when to stop.
  2. Measure with a benchmark or a profile of realistic load.
  3. Find the biggest cost in the profile. Fix only that.
  4. Measure again to prove the change helped, and that it didn't break anything (keep the tests green).
Mental model

Optimizing without a profile is like a doctor operating without an X-ray. You might get lucky, but you'll probably cut the wrong thing. Amdahl's law says the same thing in maths: if a function takes 5% of the run time, making it infinitely fast saves at most 5%.

Here's that loop on a real example. This function counts the most frequent words in a text. It looks reasonable at a glance:

package prof

import (
	"fmt"
	"regexp"
	"slices"
	"strings"
)

// TopWords returns the n most frequent words as "word=count" lines.
// This first version is deliberately naive.
func TopWords(text string, n int) string {
	counts := map[string]int{}
	for _, line := range strings.Split(text, "\n") {
		re := regexp.MustCompile(`[a-zA-Z]+`) // compiled on EVERY line
		for _, w := range re.FindAllString(line, -1) {
			counts[strings.ToLower(w)]++
		}
	}
	keys := make([]string, 0)
	for k := range counts {
		keys = append(keys, k)
	}
	slices.SortFunc(keys, func(a, b string) int {
		if counts[a] != counts[b] {
			return counts[b] - counts[a]
		}
		return strings.Compare(a, b)
	})
	out := ""
	for _, k := range keys[:min(n, len(keys))] {
		out += fmt.Sprintf("%s=%d\n", k, counts[k])
	}
	return out
}

Stack vs heap

Your program's memory has two main areas for variables:

  • The stack. Each goroutine has its own stack, a region that grows and shrinks as functions are called and return. Allocating there is just moving a pointer, and freeing is automatic when the function returns. It costs almost nothing. Go stacks start small (a few KB) and grow by copying when needed.
  • The heap. A shared region for values that must outlive the function that created them, or whose size isn't known at compile time. Allocating there takes real work (finding space, zeroing it), and someone has to clean it up later: that someone is the garbage collector (GC).

In C you choose with malloc. In Go you don't choose: the compiler does, using escape analysis. Writing &x or new(T) doesn't mean "heap"; it means "a pointer", and the compiler decides where the value lives. A value escapes to the heap when the compiler can't prove it's safe on the stack, for example because a pointer to it is returned, stored in a global, or captured by a closure that outlives the function.

Reading escape analysis: go build -gcflags=-m

You can ask the compiler to explain its decisions. Here is a program with several typical cases:

package main

import "fmt"

type point struct{ x, y int }

// Returns a value: the struct is copied to the caller. Stays on the stack.
func newPointValue() point {
	p := point{1, 2}
	return p
}

// Returns a pointer: p must outlive this call, so it moves to the heap.
func newPointPtr() *point {
	p := point{1, 2}
	return &p
}

// A pointer that never leaves the function can stay on the stack.
func sumLocal() int {
	p := &point{3, 4}
	return p.x + p.y
}

// Constant size: fits on the stack. Unknown size: must go to the heap.
func buffers(n int) int {
	small := make([]byte, 64)
	dynamic := make([]byte, n)
	return len(small) + len(dynamic)
}

// A closure that captures a variable and is returned: the variable escapes.
func counter() func() int {
	count := 0
	return func() int {
		count++
		return count
	}
}

// Converting to an interface (fmt.Println takes ...any) often escapes.
func printIt(v int) {
	fmt.Println(v)
}

func main() {
	_ = newPointValue()
	_ = newPointPtr()
	_ = sumLocal()
	_ = buffers(10)
	c := counter()
	c()
	printIt(42)
}

  1. The compiler sees a local struct p. By default it would love to put it on the stack.
  2. But &p flows into the return value. After newPointPtr returns, its stack frame is gone, yet the caller still holds the pointer. So: moved to heap: p.
  3. Here we take a pointer too, with &point{3, 4}. Pointers alone don't force the heap.
  4. The pointer is only dereferenced locally and never stored or returned. Nothing can observe it after the function ends, so it stays on the stack.
  5. The closure refers to count. Closures capture variables by reference, so the function value carries a pointer to count.
  6. The closure itself is returned, so it outlives counter, and so must count. Both are heap-allocated: "moved to heap: count" and "func literal escapes to heap".

Gotcha: "escapes" doesn't always mean "slow"

An escape costs an allocation plus GC work later. That matters in a loop that runs a million times per second, and not at all in startup code. Don't contort readable code to avoid escapes outside proven hot paths. Also note that a function returning a pointer is not automatically worse than one returning a value: for big structs, copying can cost more than allocating. Measure.

The garbage collector, simply

The GC's job: find heap memory that nothing can reach any more and reuse it. Go uses a concurrent, tri-color, mark-and-sweep collector. That sounds scary, so here's what it means.

  • Mark-and-sweep. Start from the roots (global variables and every goroutine's stack), follow every pointer and mark what you reach. Whatever wasn't marked is garbage; sweep it up for reuse.
  • Tri-color. During marking, objects are white (not seen yet), grey (seen, but its pointers not yet followed) or black (seen, and all its pointers followed). Work through grey objects until none are left. Remaining white objects are garbage.
  • Concurrent. Marking runs while your program keeps running, on about 25% of the CPU, with only tiny stop-the-world pauses (typically well under a millisecond) at the start and end. A write barrier (a few extra instructions on pointer writes during marking) keeps the colors correct while your code changes pointers.
  • Non-moving and non-generational. Go doesn't compact memory or split it into young/old generations like Java does. It relies on escape analysis to keep short-lived values off the heap in the first place.
Mental model

Imagine a librarian checking which books are still on someone's reading list. Start with every member's list (roots), tick each book (grey), then look at each ticked book's "see also" references (make it black, tick those). Books nobody ever ticked go back to the store room. Meanwhile, the library stays open; the librarian just asks people to note any new "see also" they add while the check is running (the write barrier).

GOGC: trading memory for CPU

When does a GC cycle start? Go uses a target: after a collection leaves L MB of live heap, the next cycle starts when the heap reaches about L × (1 + GOGC/100). The default GOGC=100 means "let the heap double before collecting again". Higher GOGC = fewer collections and less CPU, but more memory. Lower = the opposite.

Let's watch it. This program keeps ~20 MB alive (like a cache) and then churns through ~2.3 GB of short-lived garbage (like requests would):

package main

import (
	"fmt"
	"math"
	"runtime"
	"runtime/debug"
	"time"
)

type node struct {
	payload [64]byte
	next    *node
}

var (
	live []*node // the long-lived part of the heap
	sink *node   // forces each new node onto the heap
)

func main() {
	// Keep about 20 MB alive, like a cache would.
	for range 300_000 {
		live = append(live, &node{})
	}

	start := time.Now()
	// Then churn through ~2 GB of short-lived garbage, like requests would.
	for i := range 30_000_000 {
		n := &node{}
		n.payload[0] = byte(i)
		sink = n // escapes: garbage as soon as the next one replaces it
	}
	elapsed := time.Since(start)

	var ms runtime.MemStats
	runtime.ReadMemStats(&ms)
	limit := "none"
	if l := debug.SetMemoryLimit(-1); l != math.MaxInt64 { // -1 = just read it
		limit = fmt.Sprintf("%dMB", l>>20)
	}
	fmt.Printf("GOGC=%-4d limit=%-5s gc cycles=%-4d total pause=%-8v heap now=%dMB  took=%v\n",
		debug.SetGCPercent(-1), limit, ms.NumGC,
		time.Duration(ms.PauseTotalNs).Round(time.Microsecond), ms.HeapAlloc>>20, elapsed.Round(time.Millisecond))
	runtime.KeepAlive(live)
}

GOMEMLIMIT: a soft memory ceiling

GOGC alone has a weakness: memory use is relative to the live heap, so a spike in live data can push you past your container's limit. Since Go 1.19, GOMEMLIMIT (or debug.SetMemoryLimit) sets a soft limit on total Go memory. As the process approaches it, the GC runs more often, regardless of GOGC. In the output above, GOGC=off GOMEMLIMIT=200MiB meant "don't collect at all until we near 200 MB": only 16 cycles, the fastest run, and bounded memory.

Senior engineer tip: GC settings for containers

For a service in a container with a 1 GiB memory limit, a good starting point is GOMEMLIMIT at about 80–90% of the limit (e.g. 900MiB), leaving room for non-heap memory, and GOGC at its default. Only use GOGC=off with a memory limit if you understand the risk: if the live heap ever approaches the limit, the GC will run constantly ("death spiral") until the runtime's guard rails cap GC CPU at about 50%. Before tuning knobs at all, reduce allocations; that helps every setting.

After a GC cycle, 300 MB of heap is still live. With GOGC=100 and no memory limit, roughly when does the next cycle start?
The goal is live heap × (1 + GOGC/100) = 300 × 2 = 600 MB. (There is a forced GC every 2 minutes if none has happened, but with an active heap the goal is hit far sooner.)

Benchmarks that tell the truth

Benchmarks are covered in the testing chapter; here's the performance-engineer's view. A benchmark is a function BenchmarkXxx(b *testing.B) with the code to measure inside a for b.Loop() { ... } loop (Go 1.24+). b.Loop is better than the old for i := 0; i < b.N; i++ because it runs setup code above the loop only once, excludes it from the timing, and keeps the compiler from optimizing away the code inside the loop.

go test -run=NONE -bench=. -benchmem          # all benchmarks, with allocation stats
go test -run=NONE -bench=Concat -count=10 > new.txt   # many runs for statistics
benchstat old.txt new.txt                     # golang.org/x/perf/cmd/benchstat

Senior engineer tip: benchmark hygiene

Laptops change clock speed with temperature and battery. Close other programs, plug in, and run with -count=10, then compare with benchstat, which tells you whether a difference is statistically real (it prints ~ when it isn't). Benchmark realistic inputs: a function that's fast on 10 items may be slow on 10,000. And always check allocs/op: in a server, fewer allocations means less GC, which helps every other request too, not just this one.

Reducing allocations

In most Go programs, the cheapest wins come from allocating less. Each pattern below comes with a benchmark from this machine.

Build strings with strings.Builder

Strings are immutable. s += w can't extend s; it allocates a brand-new string and copies everything so far. In a loop that's quadratic: 100 words means 100 allocations and ever-larger copies.

package bench

import (
	"strconv"
	"strings"
	"testing"
)

var words = func() []string {
	w := make([]string, 100)
	for i := range w {
		w[i] = "word" + strconv.Itoa(i)
	}
	return w
}()

func BenchmarkConcatPlus(b *testing.B) {
	for b.Loop() {
		s := ""
		for _, w := range words {
			s += w + "," // creates a brand new string every iteration
		}
	}
}

func BenchmarkConcatBuilder(b *testing.B) {
	for b.Loop() {
		var sb strings.Builder
		for _, w := range words {
			sb.WriteString(w)
			sb.WriteByte(',')
		}
		_ = sb.String()
	}
}

func BenchmarkConcatBuilderGrow(b *testing.B) {
	for b.Loop() {
		var sb strings.Builder
		sb.Grow(800) // one allocation, sized up front
		for _, w := range words {
			sb.WriteString(w)
			sb.WriteByte(',')
		}
		_ = sb.String()
	}
}

func BenchmarkConcatJoin(b *testing.B) {
	for b.Loop() {
		_ = strings.Join(words, ",")
	}
}
  1. Before any benchmark runs, the package-level words is built once. The joined result will be 590 letters plus 100 commas, so 690 bytes. That's the minimum any approach must allocate.
  2. b.Loop() runs the body as many times as needed for a stable timing. Each iteration starts with an empty string, which costs no allocation.
  3. Strings are immutable, so s += w + "," must build a new string and copy the old s into it. The compiler fuses the two + into one concat, so that's one allocation.
  4. By the 100th word we have copied the growing prefix 100 times: 100 allocations and about 36 KB in total for a 690-byte result. The cost is O(n²) bytes.
  5. strings.Builder keeps a []byte and appends in place. When it fills up, append reallocates with roughly double the capacity, so 690 bytes take only about 8 growth steps.
  6. sb.String() returns the bytes as a string without copying. That's why a Builder must never be copied after use.
  7. Grow(800) allocates once up front. The runtime rounds 800 up to its 896-byte size class. Every write after that fits.
  8. No more growth, so 1 alloc/op. If you know (or can estimate) the final size, tell the Builder.
  9. strings.Join measures the total length first, then allocates exactly once (690 rounds to the 704-byte class). The standard library already did the optimization for you.

Preallocate slices and maps

When append runs out of capacity, it allocates a bigger array (roughly double for small slices, about 1.25× for large ones) and copies everything over. If you know the final size, tell Go up front.

var s []int
prevCap := cap(s)
for i := range 2000 {
	s = append(s, i)
	if cap(s) != prevCap {
		fmt.Printf("len=%-5d cap %4d -> %4d (new array, copied %d elements)\n", len(s), prevCap, cap(s), len(s)-1)
		prevCap = cap(s)
	}
}
  1. A nil slice: no array behind it at all.
  2. First append: there's no room, so the runtime allocates an array. It rounds up to a size class, giving capacity 4.
  3. Appends 2–4 fit. The 5th doesn't: allocate 8, copy 4 elements, and the old array becomes garbage.
  4. Below 256 elements, capacity doubles each time.
  5. Past 256, growth slows down smoothly toward 1.25× so big slices don't waste too much memory. In total: 12 allocations and about 5,000 element copies to build 2,000 elements. make([]int, 0, 2000) would have done it in one allocation and zero copies.
package bench

import "testing"

const N = 10_000

func BenchmarkAppendNoPrealloc(b *testing.B) {
	for b.Loop() {
		var s []int
		for i := range N {
			s = append(s, i)
		}
	}
}

func BenchmarkAppendPrealloc(b *testing.B) {
	for b.Loop() {
		s := make([]int, 0, N) // capacity known: one allocation
		for i := range N {
			s = append(s, i)
		}
	}
}

func BenchmarkMapNoHint(b *testing.B) {
	for b.Loop() {
		m := map[int]int{}
		for i := range N {
			m[i] = i
		}
	}
}

func BenchmarkMapSizeHint(b *testing.B) {
	for b.Loop() {
		m := make(map[int]int, N)
		for i := range N {
			m[i] = i
		}
	}
}
  1. A nil slice: no backing array yet, no allocation.
  2. The first append has nowhere to put the element, so the runtime allocates a backing array.
  3. Every time len reaches cap, append allocates a bigger array (about 2x while small, about 1.25x past 256 elements), copies everything over, and the old array becomes garbage.
  4. Reaching 10,000 took 19 allocations, and about 357 KB was allocated in total for 80 KB of final data. Most of it was thrown away.
  5. make([]int, 0, N) asks for the whole capacity at once: 80,000 bytes, rounded to the 81,920 size class. It's too big for the stack, so it goes on the heap.
  6. No append ever overflows, so there are no copies. That's half the time and a quarter of the bytes.
  7. A map without a hint grows as well. Each time it gets too full it allocates bigger tables and rehashes every key into them, which is more expensive than a slice copy.
  8. With make(map, N) the runtime sizes its tables for 10,000 entries up front: no rehashing, and 3.5x faster. A map still makes several allocations internally (its groups and directory), so the count isn't 1.

Avoid needless []byte ↔ string conversions

A string is immutable, a []byte is mutable, so converting between them usually copies the data (otherwise changing the bytes would change the "immutable" string). The compiler removes the copy in a few safe cases, such as a map lookup m[string(b)], comparisons, and for range string(b).

  3. The []byte is built once, outside the loop.

Interface boxing

An interface value is two words: a type pointer and a data pointer. Putting a non-pointer value into an interface usually means copying it to the heap so the data pointer has something to point at. That's called boxing. (Go avoids it for zero-size values, single-byte values and small integers 0–255, which use preallocated static values. That's why the benchmark uses i+1000.) In the results above, 100 ints in a []any cost 101 allocations and 3.4× the time of a []int. Generics usually avoid boxing, which is one reason a Max[T cmp.Ordered] beats a Max(a, b any).

Values vs pointers

"Pointers are faster because they avoid copying" is a half-truth. Returning a pointer often forces a heap allocation, and walking a slice of pointers means jumping around memory, which defeats the CPU caches.

import (
	"cmp"
	"slices"
	"strconv"
	"strings"
	"unicode"
)

type wordCount struct {
	word  string
	count int
}

// TopWordsFast does the same job, guided by the profile.
func TopWordsFast(text string, n int) string {
	counts := make(map[string]int, 1024)
	isNotLetter := func(r rune) bool { return r > unicode.MaxASCII || !unicode.IsLetter(r) }
	for _, w := range strings.FieldsFunc(text, isNotLetter) { // no regexp at all
		counts[strings.ToLower(w)]++
	}
	list := make([]wordCount, 0, len(counts))
	for w, c := range counts {
		list = append(list, wordCount{w, c})
	}
	slices.SortFunc(list, func(a, b wordCount) int {
		return cmp.Or(cmp.Compare(b.count, a.count), strings.Compare(a.word, b.word))
	})
	var sb strings.Builder
	for _, wc := range list[:min(n, len(list))] {
		sb.WriteString(wc.word)
		sb.WriteByte('=')
		sb.WriteString(strconv.Itoa(wc.count))
		sb.WriteByte('\n')
	}
	return sb.String()
}

Profiling a live service: net/http/pprof

Benchmarks are great for a function, but production problems happen under production load. The net/http/pprof package exposes profiling endpoints over HTTP, so you can profile a running server without restarting it. The common import _ "net/http/pprof" registers them on http.DefaultServeMux; it's safer to mount them explicitly on a separate, private port:

package main

import (
	"fmt"
	"log"
	"net/http"
	"net/http/pprof"
	"strings"
)

var cache = map[int]string{}

func work(w http.ResponseWriter, r *http.Request) {
	// Pretend to do real work: build and keep some strings around.
	for i := range 1000 {
		cache[len(cache)] = strings.Repeat("x", 100+i%50)
	}
	fmt.Fprintf(w, "cached %d entries\n", len(cache))
}

func main() {
	// The public API on :8080.
	app := http.NewServeMux()
	app.HandleFunc("GET /work", work)
	go func() { log.Fatal(http.ListenAndServe(":8080", app)) }()

	// Debug endpoints on a separate, private port (never expose publicly!).
	debug := http.NewServeMux()
	debug.HandleFunc("/debug/pprof/", pprof.Index)
	debug.HandleFunc("/debug/pprof/profile", pprof.Profile)
	debug.HandleFunc("/debug/pprof/symbol", pprof.Symbol)
	debug.HandleFunc("/debug/pprof/trace", pprof.Trace)
	log.Fatal(http.ListenAndServe("localhost:6060", debug))
}

Danger

Never expose pprof on a public port. Profiles leak source paths, function names and memory contents, and a CPU profile request costs CPU. Bind to localhost or an internal network, or put it behind auth. Access it with kubectl port-forward or similar.

Senior engineer tip

Most mature teams run continuous profiling (Pyroscope, Parca, Datadog, Google Cloud Profiler): low-overhead profiles are collected all the time and stored. When latency regresses after a deploy, you diff the profiles from before and after instead of trying to reproduce the problem. The same profiles also feed PGO, below.

sync.Pool: reusing temporary objects

Sometimes you can't avoid allocating a temporary object: a buffer to render a response into, a scratch slice for parsing. If that happens thousands of times per second, the allocations and the GC work add up. sync.Pool is a concurrency-safe cache of reusable objects: Get hands you one (or makes a new one with New), and Put returns it for someone else.

package bench

import (
	"bytes"
	"sync"
	"testing"
)

var bufPool = sync.Pool{
	New: func() any { return new(bytes.Buffer) },
}

func render(buf *bytes.Buffer) {
	for range 50 {
		buf.WriteString("<li>an item in a rendered list</li>\n")
	}
}

func BenchmarkBufferNew(b *testing.B) {
	for b.Loop() {
		buf := new(bytes.Buffer)
		render(buf)
		_ = buf.Len()
	}
}

func BenchmarkBufferPool(b *testing.B) {
	for b.Loop() {
		buf := bufPool.Get().(*bytes.Buffer)
		buf.Reset() // pooled objects keep old contents: always reset
		render(buf)
		_ = buf.Len()
		bufPool.Put(buf)
	}
}

func BenchmarkBufferPoolParallel(b *testing.B) {
	b.RunParallel(func(pb *testing.PB) {
		for pb.Next() {
			buf := bufPool.Get().(*bytes.Buffer)
			buf.Reset()
			render(buf)
			bufPool.Put(buf)
		}
	})
}

func BenchmarkBufferNewParallel(b *testing.B) {
	b.RunParallel(func(pb *testing.PB) {
		for pb.Next() {
			buf := new(bytes.Buffer)
			render(buf)
			_ = buf.Len()
		}
	})
}
  1. new(bytes.Buffer) doesn't escape here (the compiler can prove it), so the struct itself lives on the stack. That part is free.
  2. Inside render, the first WriteString finds no backing array. The buffer allocates a small 64-byte slice for the 36-byte line.
  3. Each time the next line doesn't fit, the buffer allocates a larger slice and copies the old bytes over. Writing 50 × 36 = 1,800 bytes takes 6 heap allocations, all of them byte slices.
  4. When the iteration ends, every one of those slices is garbage: 4,032 bytes per op for the GC to clean up.
  5. With the pool, the first Get finds nothing, so it calls New. That one is a heap allocation, because the pool keeps the buffer around.
  6. Reset sets the length to 0 but keeps the capacity. Forget it, and you would render after the previous request's HTML. That's a real data leak bug.
  7. After the first few ops, the buffer already has room for 1,800 bytes, so render never grows it. Put hands it back for the next Get.
  8. Averaged over millions of ops: 0 B/op and 4x faster.
  9. RunParallel runs the body on all 8 cores. sync.Pool keeps a per-P (per-processor) cache, so goroutines rarely contend: 35 ns per op overall.
  10. Without the pool, the parallel version is no faster per op. All 8 cores are busy allocating and the GC has to keep up, so allocation, not CPU, is the bottleneck.

var bufPool = sync.Pool{
	New: func() any { return new(bytes.Buffer) },
}

func handle() {
	buf := bufPool.Get().(*bytes.Buffer)
	buf.Reset()
	render(buf)
	_ = buf.Len()
	bufPool.Put(buf)
}
  1. A package-level pool. New is only called when the pool has nothing to give.
  2. First request: the pool is empty, so Get calls New. We type-assert the any back to *bytes.Buffer.
  3. render writes 1,800 bytes; the buffer grows its internal array (that's where the 6 allocations of the non-pooled version come from).
  4. We give the buffer back. Its grown array comes with it.
  5. Next request: Get returns buffer #1. Reset sets the length to 0 but keeps the 2 KB array, so render needs no new allocations. This is the whole trick.
  6. The pool is not a permanent cache: objects not used across two GC cycles are dropped. That's fine; Get just falls back to New.
sync.Pool rules

1) Always Reset what you Get; it contains the previous user's data. 2) Never use an object after Putting it back; another goroutine may already have it. 3) Don't pool huge objects without a cap: one 10 MB response would keep a 10 MB buffer alive in the pool, so many projects skip Put when buf.Cap() exceeds a limit. 4) Store pointers (*bytes.Buffer), not values, or Put itself allocates. 5) Only add a pool after a profile shows the allocation matters.

Struct field ordering

CPUs read memory most efficiently when values sit at addresses that are multiples of their size: an 8-byte float64 at an address divisible by 8. This is called alignment. To keep fields aligned, the compiler inserts invisible padding bytes between them. Go never reorders struct fields for you, so the order you write is the layout you get.

package main

import (
	"fmt"
	"unsafe"
)

type Bad struct {
	Active bool    // 1 byte  + 7 padding
	Score  float64 // 8 bytes
	Admin  bool    // 1 byte  + 3 padding
	Count  int32   // 4 bytes
	Flag   bool    // 1 byte  + 7 padding
}

type Good struct {
	Score  float64 // 8 bytes
	Count  int32   // 4 bytes
	Active bool    // 1 byte
	Admin  bool    // 1 byte
	Flag   bool    // 1 byte + 1 padding
}

func main() {
	var b Bad
	var g Good
	fmt.Println("Bad  size:", unsafe.Sizeof(b), "align:", unsafe.Alignof(b))
	fmt.Println("  Active @", unsafe.Offsetof(b.Active), " Score @", unsafe.Offsetof(b.Score),
		" Admin @", unsafe.Offsetof(b.Admin), " Count @", unsafe.Offsetof(b.Count), " Flag @", unsafe.Offsetof(b.Flag))
	fmt.Println("Good size:", unsafe.Sizeof(g), "align:", unsafe.Alignof(g))
	fmt.Println("  Score @", unsafe.Offsetof(g.Score), " Count @", unsafe.Offsetof(g.Count),
		" Active @", unsafe.Offsetof(g.Active), " Admin @", unsafe.Offsetof(g.Admin), " Flag @", unsafe.Offsetof(g.Flag))
	fmt.Printf("1M of them: Bad=%d MB, Good=%d MB\n", unsafe.Sizeof(b)*1_000_000>>20, unsafe.Sizeof(g)*1_000_000>>20)
}

type Bad struct {
	Active bool    // 1 byte  + 7 padding
	Score  float64 // 8 bytes
	Admin  bool    // 1 byte  + 3 padding
	Count  int32   // 4 bytes
	Flag   bool    // 1 byte  + 7 padding
}
  1. Start at byte 0. Active takes 1 byte.
  2. Score needs an address divisible by 8. The next free byte is 1, so the compiler skips 7 bytes of padding and puts Score at 8. It ends at 16.
  3. Admin needs no alignment beyond 1, so it sits at 16.
  4. Count (int32) needs a multiple of 4. Next free is 17, so 3 bytes of padding, and it lands at 20.
  5. Flag goes at 24.
  6. The struct's total size must be a multiple of its largest alignment (8), so that in an array every element's Score is aligned too. 25 rounds up to 32. That's 14 bytes of padding for 15 bytes of data. Sorting fields from largest to smallest (Good) gives 16 bytes: half the memory, and twice as many structs per cache line.

Rule of thumb: order fields from largest alignment to smallest (pointers, int64/float64/strings/slices first, then int32, then bool/byte). The fieldalignment analyzer (from golang.org/x/tools) can find and fix this automatically. It only matters for types you keep millions of, or that sit in hot arrays; for a config struct, ordering by meaning is more valuable than saving 8 bytes.

PGO and the execution tracer

Profile-guided optimization (PGO)

The compiler has to guess which code is hot when deciding what to inline. With PGO (Go 1.21+), you give it a real CPU profile and it uses that knowledge: it inlines hot functions more aggressively and turns hot interface calls into direct calls ("devirtualization"). Typical gains are 2–14% with no code changes.

# 1. Collect a CPU profile from production (or a representative benchmark).
curl -o default.pgo "http://localhost:6060/debug/pprof/profile?seconds=30"

# 2. Put it in the main package's directory as default.pgo and commit it.
#    `go build` uses ./default.pgo automatically (-pgo=auto is the default).
go build -o server .

The execution tracer

pprof answers "where is CPU time spent?". But some problems are about time when the CPU isn't busy: goroutines waiting for a lock, a channel, the network, the scheduler or the GC. The execution tracer records every scheduling event with nanosecond timestamps, and go tool trace shows them on a timeline: each P (processor), which goroutine ran when, GC phases, syscalls, and your own annotated tasks and regions.

package main

import (
	"context"
	"fmt"
	"os"
	"runtime/trace"
	"sync"
	"time"
)

func main() {
	f, err := os.Create("trace.out")
	if err != nil {
		panic(err)
	}
	defer f.Close()
	if err := trace.Start(f); err != nil {
		panic(err)
	}
	defer trace.Stop()

	ctx, task := trace.NewTask(context.Background(), "processBatch")
	defer task.End()

	var wg sync.WaitGroup
	for i := range 4 {
		wg.Go(func() { // Go 1.25+: Add(1) + go + Done in one call
			trace.WithRegion(ctx, fmt.Sprintf("worker-%d", i), func() {
				time.Sleep(time.Duration(i+1) * 5 * time.Millisecond) // blocked
				sum := 0
				for j := range 3_000_000 { // on CPU
					sum += j
				}
				_ = sum
			})
		})
	}
	wg.Wait()
	trace.Log(ctx, "status", "batch done")
	fmt.Println("wrote trace.out; open it with: go tool trace trace.out")
}

Maps never shrink

package main

import (
	"fmt"
	"runtime"
)

func heapMB() uint64 {
	runtime.GC() // collect first so we measure what is really retained
	var ms runtime.MemStats
	runtime.ReadMemStats(&ms)
	return ms.HeapAlloc >> 20
}

func main() {
	m := make(map[int][64]byte)
	fmt.Println("empty map:        ", heapMB(), "MB")

	for i := range 1_000_000 {
		m[i] = [64]byte{}
	}
	fmt.Println("1M entries:       ", heapMB(), "MB")

	for i := range 1_000_000 {
		delete(m, i)
	}
	fmt.Println("all deleted:      ", heapMB(), "MB  len =", len(m))

	clear(m) // resets the whole map at once (see the text below)
	fmt.Println("after clear(m):   ", heapMB(), "MB")

	m = make(map[int][64]byte) // drop the old map entirely
	fmt.Println("new map:          ", heapMB(), "MB")
	runtime.KeepAlive(m)
}
  1. heapMB forces a GC first, so we measure what is really retained, not garbage waiting to be collected. An empty map costs almost nothing.
  2. Inserting a million 64-byte values: the map grows its tables over and over as it fills. Each value is stored inline in the table slots, together with the 8-byte key.
  3. That's about 160 MB, more than the 72 MB of raw keys and values, because of load-factor slack and control bytes.
  4. delete only marks each slot as free (a tombstone). The table keeps its size, ready for refills.
  5. The gotcha: the map is empty but still holds 160 MB. A cache that once peaked keeps its peak memory forever.
  6. On this Go version (Swiss-table maps, 1.24+), clear(m) drops the big tables, and the next GC frees them.
  7. Replacing the map works on every Go version: the old map is unreachable, so the GC frees it all. KeepAlive keeps m alive until here so the measurement is honest.
empty map:         0 MB
1M entries:        160 MB
all deleted:       160 MB  len = 0
after clear(m):    0 MB
new map:           0 MB

delete marks slots as free but keeps the table: the map stays sized for its peak. A cache that once held a million entries and now holds ten still costs the memory of a million. On this Go version (with the "Swiss table" maps introduced in Go 1.24), clear(m) released the large tables; replacing the map with a fresh one always works on any version. For long-lived maps with churn, periodically copy the live entries into a new map.

A profile shows 40% of CPU in runtime.mallocgc and GC functions. What is the best first move?
High malloc/GC time means "too many allocations". The heap profile tells you exactly which call sites allocate, so you can preallocate, reuse, or avoid them. Turning GC off just trades CPU for unbounded memory, and defers aren't the cause.

Exercise 1: speed up a hot ID formatter

This function is called millions of times: func FormatID(prefix string, n int) string { return fmt.Sprintf("%s-%06d", prefix, n) }. Write a benchmark, then a faster version that returns exactly the same strings (zero-padded to 6 digits), plus a test proving they match. Hint: build the bytes with append and strconv.AppendInt into a stack buffer like var buf [32]byte. Converting the final []byte to a string is the one allocation you'll keep.

Solution
package id

import (
	"fmt"
	"strconv"
	"testing"
)

func FormatID(prefix string, n int) string {
	return fmt.Sprintf("%s-%06d", prefix, n)
}

func FormatIDFast(prefix string, n int) string {
	var buf [32]byte // stays on the stack
	b := append(buf[:0], prefix...)
	b = append(b, '-')
	if n >= 0 { // zero-pad non-negative numbers to 6 digits
		for d := digits(n); d < 6; d++ {
			b = append(b, '0')
		}
	}
	b = strconv.AppendInt(b, int64(n), 10)
	return string(b) // the single allocation
}

func digits(n int) int {
	d := 1
	for n >= 10 {
		n /= 10
		d++
	}
	return d
}

func TestSame(t *testing.T) {
	for _, n := range []int{0, 7, 42, 999999, 1234567} {
		if a, b := FormatID("ord", n), FormatIDFast("ord", n); a != b {
			t.Errorf("n=%d: %q vs %q", n, a, b)
		}
	}
}

func BenchmarkSprintf(b *testing.B) {
	for b.Loop() {
		_ = FormatID("ord", 4242)
	}
}

func BenchmarkFast(b *testing.B) {
	for b.Loop() {
		_ = FormatIDFast("ord", 4242)
	}
}
  1. go test -bench=. runs the tests first. TestSame checks that the fast version matches Sprintf for edge cases: 0, short numbers, exactly 6 digits, and more than 6.
  2. Step into FormatIDFast("ord", 42). buf is a fixed-size array that doesn't escape, so it lives on the stack: a free scratch space.
  3. buf[:0] is a zero-length slice over that array, so the appends write into the stack array. No heap yet.
  4. Count the digits: 42 → 4 → stop, so d=2.
  5. Pad with 6 − 2 = 4 zeros.
  6. strconv.AppendInt writes digits straight into b instead of returning a new string, the same idea as append.
  7. string(b) must copy, because the string outlives the stack array. That's the only allocation: 10 bytes rounded up to 16.
  8. The loop also checks 7, 999999 and 1234567 (7 digits, so no padding). All match, and the test passes silently because there's no -v.
  9. Sprintf also makes just 1 allocation (the result), but it parses the format string and goes through its interface-based formatting machinery every call.
  10. Same bytes, same single allocation, 3x faster. The win here is CPU, not memory. Do this only in code the profiler points to.

Key takeaways

  • Measure first, with a goal. Change one thing, measure again, keep tests green.
  • The compiler decides stack vs heap through escape analysis; read it with -gcflags=-m (-m=2 for reasons). Returning pointers, globals, closures and interfaces are the usual causes.
  • Go's GC is concurrent tri-color mark-and-sweep with sub-millisecond pauses. Its cost scales with allocation rate. GOGC trades memory for CPU; GOMEMLIMIT sets a soft ceiling. Set it in containers.
  • Cut allocations: preallocate slices and maps, use strings.Builder with Grow, avoid needless []byte/string conversions and interface boxing, prefer values for small structs and contiguous slices for data you scan.
  • Benchmark with b.Loop, -benchmem, -count and benchstat; watch allocs/op.
  • pprof: -cpuprofile/-memprofile from tests, net/http/pprof on a private port for live services; read flat vs cum, use -focus and -list.
  • sync.Pool reuses temporary objects: always Reset, never use after Put, cap the size.
  • Order struct fields large to small to avoid padding in types you have millions of.
  • PGO gives a few to ~15% for free from a production profile; the tracer explains latency that CPU profiles can't.
  • defer is cheap now; maps don't shrink on delete; sub-slices keep big arrays alive; compile regexps once.

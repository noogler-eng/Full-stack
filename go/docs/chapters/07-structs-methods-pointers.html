Structs, Methods & Pointers

Ints and strings get you a long way, but real programs talk about things: an order, a customer, a delivery address. Go models things with structs, gives them behaviour with methods, and lets you share them without copying using pointers. Get these three right and the rest of Go falls into place.

Throughout this chapter we'll build a tiny e-commerce domain: Order, Customer and Address. It's the same shape you've already been sketching in your own learning code, so every example should feel familiar.

Why structs exist

Imagine tracking an order with loose variables: orderID, orderPrice, orderStatus, orderCreatedAt… Now imagine a function that needs an order. You'd pass four arguments. Ten orders? Forty variables. It falls apart fast.

A struct (short for "structure") is a type that groups named values together. Each value is called a field. Once grouped, the whole bundle travels as one thing: you can pass it, return it, store it in a slice, or put it in a map.

Mental model

A struct is a form with labelled boxes. The struct type is the blank form template ("Name: ___, Phone: ___"). A struct value is one filled-in copy of that form. You can photocopy the form (copy the value) and scribble on the copy without changing the original.

Here's how you declare struct types and build values of them:

package main

import (
	"fmt"
	"time"
)

// Address is where an order gets delivered.
type Address struct {
	Street  string
	City    string
	State   string
	ZipCode string
}

// Customer is a person who places orders.
type Customer struct {
	ID        int
	Name      string
	Phone     string
	Address   Address // a struct inside a struct
	CreatedAt time.Time
}

func main() {
	// 1. Named-field literal: the recommended way.
	c := Customer{
		ID:    42,
		Name:  "Asha",
		Phone: "+91-98000-00000",
		Address: Address{
			City:  "Bengaluru",
			State: "KA",
		},
	}

	// 2. Read and write fields with a dot.
	c.Address.ZipCode = "560001"
	fmt.Println(c.Name, "lives in", c.Address.City, c.Address.ZipCode)

	// 3. Fields you leave out get their zero value.
	fmt.Printf("street=%q created=%v\n", c.Address.Street, c.CreatedAt.IsZero())

	// 4. Three ways to print a struct.
	a := Address{"MG Road", "Pune", "MH", "411001"} // positional literal
	fmt.Printf("%v\n", a)
	fmt.Printf("%+v\n", a)
	fmt.Printf("%#v\n", a)

	// 5. The zero value of a whole struct.
	var empty Customer
	fmt.Printf("%+v\n", empty.Address)
}
  1. Two type declarations, no code runs yet. Customer holds a whole Address value in its Address field (a real nested struct, not a pointer).
  2. The named-field literal builds c. Every field we did not mention, like ZipCode and CreatedAt, silently gets its zero value.
  3. Dots chain through nested structs: c.Address.ZipCode writes straight into the inner Address stored inside c.
  4. Println separates its arguments with spaces.
  5. We never set Street or CreatedAt. %q shows the empty string as "", and IsZero() confirms the time is the zero time.
  6. A positional literal: values must be in field order and every field must be given. Fine for tiny types, fragile if fields are ever reordered.
  7. %v prints just the values, in order.
  8. %+v adds field names. This is the one you want in logs and debugging.
  9. %#v prints Go syntax, including the package-qualified type name and quoted strings.
  10. var empty Customer is fully usable: every field, all the way down into the nested Address, is zeroed. No nil, no crash.

A few things to notice:

  • type Customer struct { ... } declares a new named type. The fields go one per line: name first, then type (just like variable declarations).
  • Named-field literals (Customer{ID: 42, Name: "Asha"}) let you set fields in any order and skip the ones you don't care about.
  • Positional literals (Address{"MG Road", "Pune", "MH", "411001"}) must list every field in declaration order. They compile, but they're fragile: add a field to the struct later and every positional literal breaks (or worse, silently shifts meaning if two fields share a type).
  • Fields can themselves be structs (Address inside Customer). You reach in with more dots: c.Address.City.
  • Capitalised field names (Name) are exported: visible outside the package. Lower-case ones (name) are private to the package. We'll come back to this under encapsulation.

Always use named-field literals for structs from other packages. go vet actually warns about unkeyed literals of imported struct types ("composite literal uses unkeyed fields") because the library author may add a field in a minor release. Positional literals are fine only for tiny, stable, local types like a Point{X, Y}.

Zero values make structs useful immediately

Every type in Go has a zero value: what a variable holds before you assign anything. For a struct, the zero value is simply "every field at its own zero value": 0 for numbers, "" for strings, false for bools, nil for pointers/slices/maps, and so on, recursively.

Good Go types are designed so that the zero value is already useful. That means no mandatory init() call, no "forgot to construct it" crashes. The Go proverb is: make the zero value useful.

package main

import (
	"bytes"
	"fmt"
	"strings"
	"sync"
)

// Cart is useful with zero setup: a nil slice can be appended to,
// and a zero sync.Mutex is an unlocked mutex.
type Cart struct {
	mu    sync.Mutex
	items []string
}

func (c *Cart) Add(item string) {
	c.mu.Lock()
	defer c.mu.Unlock()
	c.items = append(c.items, item)
}

func (c *Cart) Count() int {
	c.mu.Lock()
	defer c.mu.Unlock()
	return len(c.items)
}

func main() {
	var cart Cart // no constructor needed
	cart.Add("keyboard")
	cart.Add("mouse")
	fmt.Println("items in cart:", cart.Count())

	// The standard library follows the same idea.
	var buf bytes.Buffer // ready to use
	buf.WriteString("hello ")
	buf.WriteString("buffer")
	fmt.Println(buf.String())

	var sb strings.Builder // also ready to use
	sb.WriteString("zero values rock")
	fmt.Println(sb.String())
}
  1. var cart Cart with no constructor. The mutex's zero value is an unlocked mutex and the slice is nil. Both are ready to use.
  2. We call cart.Add. It has a pointer receiver, so Go passes &cart for us. Lock() grabs the mutex.
  3. append on a nil slice just allocates a fresh backing array. No "make it first" step needed.
  4. The function returns, so the deferred Unlock() fires now.
  5. Same dance for "mouse": lock, append, deferred unlock.
  6. Count() locks, returns len(c.items), then the deferred unlock runs after the return value is computed.
  7. The standard library follows the same rule: a zero bytes.Buffer is an empty buffer you can write to immediately.
  8. Same for strings.Builder. Design your own types this way and callers never need a NewX() just to get started.
items in cart: 2
hello buffer
zero values rock

Our Cart works with no constructor because:

  • a nil slice behaves like an empty slice: len is 0 and append allocates for you;
  • a zero sync.Mutex is an unlocked mutex, ready to use.

The standard library leans on this everywhere: bytes.Buffer, strings.Builder, sync.WaitGroup, sync.Once and http.Client are all usable as var x T.

Gotcha: nil maps are not writable

A nil slice is safe to append to, but a nil map panics on write (assignment to entry in nil map). If your struct has a map field, either initialise it in a constructor or lazily create it inside the method: if c.counts == nil { c.counts = map[string]int{} }.

Anonymous structs, comparison, and structs as map keys

Anonymous structs

Sometimes you need a struct shape exactly once and naming it would be noise. An anonymous struct is a struct type written inline, without a type declaration. You'll see them most in table-driven tests and for one-off config or JSON payloads.

package main

import "fmt"

func main() {
	// A one-off struct type with no name.
	point := struct {
		X, Y int
	}{X: 3, Y: 4}
	fmt.Printf("%+v\n", point)

	// Very common in table-driven tests.
	tests := []struct {
		name  string
		price float64
		qty   int
		want  float64
	}{
		{"single item", 100, 1, 100},
		{"three items", 50, 3, 150},
		{"nothing", 99, 0, 0},
	}
	for _, tt := range tests {
		got := tt.price * float64(tt.qty)
		fmt.Printf("%-12s got=%v want=%v ok=%v\n", tt.name, got, tt.want, got == tt.want)
	}

	// Handy for grouping related config in one variable.
	var config struct {
		Port    int
		Debug   bool
		Version string
	}
	config.Port = 8080
	config.Version = "1.4.0"
	fmt.Printf("%+v\n", config)
}
  1. An anonymous struct: we declare the type and build a value of it in one expression. The type has no name, so nothing else can reuse it.
  2. %+v prints the field names, just like a named struct.
  3. A slice of anonymous structs, the classic table-driven test shape. Each row is a positional literal of the four fields.
  4. Iteration 1: tt is a copy of row 0. float64(tt.qty) is needed because Go never mixes int and float64 implicitly.
  5. %-12s left-aligns the name in a 12-wide column so the results line up.
  6. Iteration 2: 50 × 3 = 150, matches want.
  7. Iteration 3: zero quantity gives 0. Loop ends.
  8. var config struct{...} declares a one-off variable whose fields all start at zero values.
  9. We set two fields; Debug keeps its zero value false.
{X:3 Y:4}
single item  got=100 want=100 ok=true
three items  got=150 want=150 ok=true
nothing      got=0 want=0 ok=true
{Port:8080 Debug:false Version:1.4.0}

If the same anonymous struct shape appears in two places, give it a name. Anonymous structs are for "here and only here".

Comparing structs with ==

Two struct values are equal when every field is equal. That only works if every field type is comparable: numbers, strings, bools, pointers, channels, arrays of comparable things, and other comparable structs. Comparable structs can also be used as map keys, which is a neat trick for composite keys.

package main

import "fmt"

type Address struct {
	City    string
	ZipCode string
}

type OrderKey struct {
	CustomerID int
	OrderID    int
}

func main() {
	a := Address{"Pune", "411001"}
	b := Address{"Pune", "411001"}
	c := Address{"Delhi", "110001"}

	// == compares field by field.
	fmt.Println("a == b:", a == b)
	fmt.Println("a == c:", a == c)

	// Comparable structs can be map keys.
	totals := map[OrderKey]float64{}
	totals[OrderKey{CustomerID: 1, OrderID: 100}] = 499.0
	totals[OrderKey{CustomerID: 1, OrderID: 101}] = 129.5
	fmt.Println(totals[OrderKey{1, 100}])
	fmt.Println(len(totals), "orders tracked")
}
  1. Three separate Address values. a and b are different variables that happen to hold the same field values.
  2. == on structs compares field by field. Every field matches, so it's true. Identity doesn't matter, only contents.
  3. City differs, so the comparison stops there: false.
  4. Because OrderKey has only comparable fields (two ints), it can be a map key. A struct with a slice or map field could not.
  5. Two entries, keyed by a composite (customer, order) pair. No string concatenation hacks like "1:100" needed.
  6. Lookup builds a brand-new key OrderKey{1, 100}. It's equal to the stored key field by field, so the lookup hits.
  7. Two distinct keys, two entries.
a == b: true
a == c: false
499
2 orders tracked

Slices, maps and functions are not comparable. Put one in a struct and == stops compiling:

package main

import "fmt"

type Order struct {
	ID    int
	Items []string // slices are not comparable
}

func main() {
	a := Order{ID: 1, Items: []string{"pen"}}
	b := Order{ID: 1, Items: []string{"pen"}}
	fmt.Println(a == b)
}
# command-line-arguments
./main.go:13:14: invalid operation: a == b (struct containing []string cannot be compared)

To compare structs with slice fields, write an Equal method that uses slices.Equal for the slice field, or in tests use reflect.DeepEqual / github.com/google/go-cmp. Keep reflect.DeepEqual out of hot production code: it's slow and has surprising rules (a nil slice is not "deep equal" to an empty one).

Pointers from scratch

Every variable lives somewhere in memory, and that "somewhere" has an address, a number like 0xc000012080. A pointer is just a variable whose value is an address. It says "the thing you want is over there".

Two operators are all you need:

  • &x ("address of x") gives you a pointer to x.
  • *p ("the value at p", also called dereferencing) follows the pointer to read or write the value it points to.

The type of a pointer to an int is written *int. Yes, * does double duty: in a type (*int) it means "pointer to", in an expression (*p) it means "follow".

package main

import "fmt"

func doubleValue(n int) {
	n = n * 2 // changes the local copy only
}

func doublePointer(n *int) {
	*n = *n * 2 // changes the value at that address
}

func main() {
	price := 100

	p := &price // p holds the ADDRESS of price
	fmt.Println("price:", price)
	fmt.Println("*p   :", *p) // read through the pointer

	*p = 250 // write through the pointer
	fmt.Println("price after *p = 250:", price)

	doubleValue(price)
	fmt.Println("after doubleValue:  ", price)

	doublePointer(&price)
	fmt.Println("after doublePointer:", price)

	var q *int // zero value of a pointer is nil
	fmt.Println("q is nil:", q == nil)
	fmt.Printf("type of p: %T\n", p)
}
price: 100
*p   : 100
price after *p = 250: 250
after doubleValue:   250
after doublePointer: 500
q is nil: true
type of p: *int

Why did doubleValue do nothing? Because Go passes everything by value: a function always receives a copy of its arguments. doubleValue doubled its own private copy and threw it away. doublePointer also received a copy, but a copy of an address. Both addresses point to the same price, so writing through it changes the original.

func doublePointer(n *int) {
	*n = *n * 2
}

func main() {
	price := 100
	p := &price
	fmt.Println(*p)
	*p = 250
	fmt.Println(price)
	doublePointer(&price)
	fmt.Println(price)
}
  1. We create price holding 100. It lives at some address in memory, say 0xc080.
  2. &price asks "where does price live?" and stores that address in p. Type of p is *int.
  3. *p follows the arrow and reads what's there: 100.
  4. *p = 250 writes through the pointer. We never mentioned price, yet price changed.
  5. Printing price confirms it: 250.
  6. We call doublePointer(&price). Go copies the address into the parameter n. Now n and p both point at price.
  7. *n = *n * 2 reads 250 through the pointer, doubles it, and writes 500 back to the same spot.
  8. Back in main, price is 500. The change "escaped" the function because we shared an address, not a value.
Mental model

A value is the house. A pointer is the house's street address written on a sticky note. Copying a sticky note is cheap and both copies lead to the same house. Repainting the house via either note changes the one real house.

new(), &T{}, and automatic dereferencing

new(T) allocates a zeroed T and returns a *T. For structs, people almost always write &Order{...} instead, because it lets you set fields at the same time. Both are equivalent for the zero case.

Go also saves you some typing: when o is a pointer to a struct, o.Status automatically means (*o).Status. There's no -> operator like in C. You just use a dot.

package main

import "fmt"

type Order struct {
	ID     int
	Status string
	Total  float64
}

func main() {
	// new(T) allocates a zeroed T and returns *T.
	n := new(int)
	*n = 7
	fmt.Println("*n =", *n)

	o := new(Order) // same as &Order{}
	fmt.Printf("%+v\n", *o)

	// &T{...} is the idiomatic way for structs.
	o2 := &Order{ID: 2, Status: "pending", Total: 999}

	// Auto-dereference: o2.Status means (*o2).Status
	o2.Status = "paid"
	(*o2).Total = 899 // legal, but nobody writes this
	fmt.Printf("%+v\n", *o2)

	// Two pointers can point at the same struct.
	alias := o2
	alias.Status = "shipped"
	fmt.Println("o2.Status:", o2.Status)
}
  1. new(int) allocates a zeroed int somewhere and hands back its address. n is a *int, never nil here.
  2. Writing *n = 7 stores through the pointer; reading *n follows it back.
  3. new(Order) gives a pointer to a zero Order. We print *o (the struct), not o, so we see fields instead of &{...}.
  4. &Order{...} allocates and fills fields in one go. This is what real Go code uses for structs.
  5. o2.Status on a pointer is auto-dereferenced: Go treats it as (*o2).Status. No -> operator.
  6. The explicit (*o2).Total form does the same thing. Legal, but noisy.
  7. Copying a pointer copies the address, not the struct. alias and o2 now lead to the same Order.
  8. Writing via alias is visible via o2: there is only one order.

Where does the memory live? (escape analysis)

In C you'd worry that &Order{} inside a function returns a pointer to dead stack memory. Not in Go. The compiler runs escape analysis: if a value's address outlives the function, the value is placed on the heap (managed by the garbage collector) instead of the stack. Returning &Order{} is completely safe. You can peek at the compiler's decisions with go build -gcflags=-m; we dig into this in Chapter 18.

nil pointers

The zero value of any pointer type is nil: "points at nothing". Dereferencing a nil pointer, including reading a field through it, crashes the program with a panic. It's the Go flavour of the famous "null pointer exception".

package main

import "fmt"

type Customer struct {
	Name string
}

func find(id int) *Customer {
	if id == 1 {
		return &Customer{Name: "Asha"}
	}
	return nil // not found
}

func main() {
	if c := find(1); c != nil {
		fmt.Println("found:", c.Name)
	}

	c := find(2)
	fmt.Println("is nil?", c == nil)
	fmt.Println(c.Name) // boom
}
  1. The if calls find(1). id == 1, so it returns a pointer to a fresh Customer.
  2. The c != nil guard passes, so reading c.Name is safe. This c only exists inside the if.
  3. Now find(2): the if fails and it returns nil meaning "not found".
  4. A nil pointer is a perfectly valid value to hold, compare, or pass around.
  5. But c.Name must follow the pointer to read the field, and there is nothing there. The program panics with a nil pointer dereference (printed on stderr) and exits with status 2.

The rule is simple: if a function can return a nil pointer, the caller must check before using it. A common Go idiom is to avoid returning a bare nil-or-pointer altogether and return (*Customer, error) or (Customer, bool), so the "not found" case is impossible to ignore.

Gotcha: Go has no pointer arithmetic

You cannot do p++ to walk through memory like in C. That's deliberate: it keeps Go memory-safe and lets the garbage collector move on with confidence. (The unsafe package can do it, and the name is the warning.)

Don't reach for pointers "for performance" by reflex. A pointer can force a value onto the heap, which means more garbage-collector work, and it adds a nil case every reader must think about. For small structs (a few words) passing by value is often faster. Choose pointers for semantics (shared, mutable, identity) first, and for performance only once a benchmark tells you to.

Methods: giving types behaviour

A method is a function attached to a type. You write it like a function, but with an extra parameter in front of the name called the receiver:

func (o Order) Summary() string { ... }
//    ^^^^^^^^ receiver: "o" is the Order this method was called on

Then you call it with a dot: order.Summary(). That's really all a method is: order.Summary() is sugar for "call Summary with order as its first argument". You can attach methods to any named type you declare in your package (structs, but also type Status string or type Celsius float64), but not to types from other packages like int or time.Time.

Value receivers vs pointer receivers

Remember "Go passes everything by value"? The receiver is just a parameter, so the same rule applies:

  • A value receiver (o Order) gets a copy of the order. Changes inside the method vanish when it returns.
  • A pointer receiver (o *Order) gets the address of the order. Changes stick.
package main

import "fmt"

type Order struct {
	ID     int
	Total  float64
	Status string
}

// Value receiver: gets a COPY of the order. Good for reading.
func (o Order) Summary() string {
	return fmt.Sprintf("#%d %s ₹%.2f", o.ID, o.Status, o.Total)
}

// Value receiver that tries to modify: changes the copy only!
func (o Order) MarkPaidBroken() {
	o.Status = "paid"
}

// Pointer receiver: gets the ADDRESS. Changes stick.
func (o *Order) MarkPaid() {
	o.Status = "paid"
}

func (o *Order) ApplyDiscount(percent float64) {
	o.Total -= o.Total * percent / 100
}

func main() {
	o := Order{ID: 7, Total: 1000, Status: "pending"}
	fmt.Println(o.Summary())

	o.MarkPaidBroken()
	fmt.Println("after MarkPaidBroken:", o.Status)

	o.MarkPaid() // Go rewrites this to (&o).MarkPaid()
	o.ApplyDiscount(10)
	fmt.Println("after MarkPaid:      ", o.Summary())

	p := &o
	fmt.Println("via pointer:         ", p.Summary()) // Go rewrites to (*p).Summary()
}
#7 pending ₹1000.00
after MarkPaidBroken: pending
after MarkPaid:       #7 paid ₹900.00
via pointer:          #7 paid ₹900.00

Notice that we called the pointer method o.MarkPaid() on a plain variable o, and the value method p.Summary() on a pointer. Go quietly inserts the & or * for you, as long as the variable is addressable (a named variable, a slice element, a field of an addressable struct, etc.).

func (o Order) MarkPaidBroken() {
	o.Status = "paid"
}

func (o *Order) MarkPaid() {
	o.Status = "paid"
}

func main() {
	o := Order{ID: 7, Status: "pending"}
	o.MarkPaidBroken()
	fmt.Println(o.Status)
	o.MarkPaid()
	fmt.Println(o.Status)
}
  1. We build an order in main. Its status is pending.
  2. Calling a value-receiver method: Go copies the whole struct into the receiver. The method now has its own private Order.
  3. The method sets Status on its copy. main.o is untouched.
  4. The method returns and the copy is thrown away. Printing shows pending. This is the #1 struct bug new Gophers write.
  5. Now the pointer-receiver method. Go rewrites the call to (&o).MarkPaid(); the receiver holds the address of main.o.
  6. o.Status = "paid" auto-dereferences and writes into the real order.
  7. This time the change survived: paid.

The rules for choosing a receiver

Use a pointer receiver if any of these are true:

  1. The method needs to modify the receiver.
  2. The struct is large enough that copying it on every call is wasteful.
  3. The struct contains something that must not be copied (a sync.Mutex, a bytes.Buffer, a "no-copy" field).
  4. Consistency: some other method on the type already uses a pointer receiver.

Use a value receiver for small, immutable, value-like types: time.Time, a Money type, a Point, an enum like type Status string.

Senior engineer tip

Don't mix receiver kinds on one type. If any method on Order needs *Order, make them all *Order. Mixed receivers confuse readers ("is this one safe to call on a copy?"), cause subtle interface-satisfaction surprises (next section), and invite data races where a value method copies the struct while another goroutine mutates it. Most real-world domain types (services, repositories, orders with state) end up all-pointer.

Method sets: the rule behind the magic

The automatic & trick only works when Go can take an address. When you store a value inside an interface (Chapter 08), there's nothing addressable to point to, so Go uses a stricter rule called the method set:

  • The method set of T contains only methods with value receivers.
  • The method set of *T contains methods with value and pointer receivers.
package main

import "fmt"

type Order struct{ Status string }

func (o *Order) Cancel() { o.Status = "cancelled" }

type Canceller interface {
	Cancel()
}

func main() {
	o := Order{Status: "pending"}
	var c Canceller = o // a plain Order does not have Cancel in its method set
	c.Cancel()
	fmt.Println(o.Status)
}
# command-line-arguments
./main.go:15:20: cannot use o (variable of struct type Order) as Canceller value in variable declaration: Order does not implement Canceller (method Cancel has pointer receiver)

The compiler even tells you why: "method Cancel has pointer receiver". Store a pointer instead:

package main

import "fmt"

type Order struct{ Status string }

func (o *Order) Cancel() { o.Status = "cancelled" }

type Canceller interface {
	Cancel()
}

func main() {
	o := Order{Status: "pending"}
	var c Canceller = &o // *Order has Cancel in its method set
	c.Cancel()
	fmt.Println(o.Status)

	// Calling directly on an addressable variable is fine either way:
	o2 := Order{Status: "pending"}
	o2.Cancel() // Go takes &o2 for you
	fmt.Println(o2.Status)
}
  1. o is a plain Order value. Cancel has a pointer receiver, so only *Order has it in its method set.
  2. We store &o in the interface. That satisfies Canceller, and the interface now holds the address of o, not a copy.
  3. c.Cancel() dispatches to (*Order).Cancel with that address, so the write lands on the original o.
  4. Proof: o.Status changed.
  5. Calling a pointer method directly on an addressable variable is fine: Go rewrites o2.Cancel() to (&o2).Cancel(). That convenience does not apply to interface assignment.
  6. The direct call mutated o2 too.
cancelled
cancelled
Why the rule exists

If Go let you put a plain Order into the interface and then call Cancel, it would have to cancel a hidden copy stored inside the interface. You'd think you cancelled your order; you'd actually cancel a clone nobody can see. The method-set rule turns that silent bug into a compile error.

A very common loop bug

The same "copy" rule bites in for ... range loops. The loop variable is a copy of each element:

package main

import "fmt"

type Order struct {
	ID     int
	Status string
}

func main() {
	orders := []Order{{1, "pending"}, {2, "pending"}}

	// BUG: o is a copy of each element.
	for _, o := range orders {
		o.Status = "shipped"
	}
	fmt.Println("range value:", orders)

	// FIX 1: index into the slice.
	for i := range orders {
		orders[i].Status = "shipped"
	}
	fmt.Println("range index:", orders)

	// FIX 2: take a pointer to the element.
	for i := range orders {
		o := &orders[i]
		o.Status = "delivered"
	}
	fmt.Println("pointer:    ", orders)
}
  1. A slice of two Order values (not pointers).
  2. Iteration 1 of the buggy loop: o is a copy of orders[0]. We set the copy's status; the slice element is untouched.
  3. Iteration 2: same thing with a copy of orders[1]. The copy is thrown away at the end of each iteration.
  4. Nothing changed. This is one of the most common Go bugs, and it compiles without a warning.
  5. Fix 1, iteration 1: orders[i].Status writes into the slice's backing array directly.
  6. Iteration 2 does the same for index 1.
  7. Both changes stuck.
  8. Fix 2: &orders[i] is a pointer into the slice, so o.Status edits the real element. Handy when you touch many fields.
  9. Second iteration, second element.
  10. Both delivered. Remember: range hands you copies of values; reach for the index when you need to mutate.
range value: [{1 pending} {2 pending}]
range index: [{1 shipped} {2 shipped}]
pointer:     [{1 delivered} {2 delivered}]
Type Order has func (o Order) Total() float64 and func (o *Order) Ship(). Which of these compiles?
The method set of *Order includes both value and pointer methods, so &Order{} has Total. Option A fails because Order's method set lacks Ship. Option B fails because a composite literal Order{} is not addressable, so Go can't take & to call a pointer method on it.

Constructors and the functional options pattern

NewX constructors

Go has no special constructor syntax. By convention, a plain function named NewX builds and returns an X (often a *X). Write one when the zero value isn't enough: you need to validate input, fill defaults, open a connection, or initialise a map.

package main

import (
	"errors"
	"fmt"
	"time"
)

type Status string

const (
	Pending   Status = "pending"
	Completed Status = "completed"
	Failed    Status = "failed"
)

type Order struct {
	ID        int
	Name      string
	Price     float64
	Status    Status
	CreatedAt time.Time
}

// NewOrder is a constructor: it validates input and fills defaults.
func NewOrder(id int, name string, price float64) (*Order, error) {
	if name == "" {
		return nil, errors.New("order name is required")
	}
	if price <= 0 {
		return nil, fmt.Errorf("invalid price %.2f: must be positive", price)
	}
	return &Order{
		ID:        id,
		Name:      name,
		Price:     price,
		Status:    Pending, // sensible default
		CreatedAt: time.Now(),
	}, nil
}

func main() {
	o, err := NewOrder(1, "Mechanical keyboard", 4999)
	if err != nil {
		fmt.Println("error:", err)
		return
	}
	fmt.Println(o.ID, o.Name, o.Price, o.Status, !o.CreatedAt.IsZero())

	_, err = NewOrder(2, "Mouse", -5)
	fmt.Println("error:", err)

	_, err = NewOrder(3, "", 100)
	fmt.Println("error:", err)
}
  1. main calls the constructor. The name isn't empty, so the first guard passes.
  2. 4999 is positive, so the price guard passes too.
  3. Valid input: build the order with defaults (Status: Pending, CreatedAt: time.Now()) and return it with a nil error.
  4. Back in main, err is nil so we skip the early return. !o.CreatedAt.IsZero() is true because the constructor stamped it.
  5. Second call with price -5. Name is fine, but price <= 0 is true.
  6. The constructor returns nil and an error built with fmt.Errorf. We discard the order with _ and print the error.
  7. Third call: an empty name fails the very first guard, so the price is never checked.
  8. A constructor is the one place that guarantees every *Order your code sees is valid.
1 Mechanical keyboard 4999 pending true
error: invalid price -5.00: must be positive
error: order name is required

Conventions worth copying:

  • If construction can fail, return (*Order, error). Never return a half-built object and hope the caller notices.
  • If the package is named after the type, shorten the name: order.New(...) reads better than order.NewOrder(...).
  • Return a pointer when the type has pointer methods or identity (an order you'll mutate). Return a value for small value types (money.New(100, "INR")).
Gotcha: constructors are optional

Nothing stops a caller from writing Order{} and skipping NewOrder. Either make the zero value safe, or hide the fields (unexported) so the constructor is the only way in. We'll do the latter shortly.

Functional options

What if an order has a handful of optional settings: a coupon, express shipping, a delivery note? A constructor with seven parameters (NewOrder(1, 499, "", false, "", 0, nil)) is unreadable. The functional options pattern fixes that: each option is a small function that tweaks the struct, and the constructor accepts any number of them via a variadic parameter.

package main

import (
	"fmt"
	"time"
)

type Order struct {
	ID       int
	Total    float64
	Coupon   string
	Express  bool
	Note     string
	Deadline time.Duration
}

// Option is a function that tweaks an Order while it is being built.
type Option func(*Order)

func WithCoupon(code string) Option {
	return func(o *Order) { o.Coupon = code }
}

func WithExpressShipping() Option {
	return func(o *Order) {
		o.Express = true
		o.Deadline = 24 * time.Hour
	}
}

func WithNote(note string) Option {
	return func(o *Order) { o.Note = note }
}

// NewOrder takes the required args normally, optional ones as Options.
func NewOrder(id int, total float64, opts ...Option) *Order {
	o := &Order{ // defaults first
		ID:       id,
		Total:    total,
		Deadline: 5 * 24 * time.Hour,
	}
	for _, opt := range opts {
		opt(o) // each option mutates the order
	}
	return o
}

func main() {
	basic := NewOrder(1, 499)
	fmt.Printf("%+v\n", *basic)

	fancy := NewOrder(2, 4999,
		WithCoupon("DIWALI10"),
		WithExpressShipping(),
		WithNote("leave at door"),
	)
	fmt.Printf("%+v\n", *fancy)
}
{ID:1 Total:499 Coupon: Express:false Note: Deadline:120h0m0s}
{ID:2 Total:4999 Coupon:DIWALI10 Express:true Note:leave at door Deadline:24h0m0s}
func NewOrder(id int, opts ...Option) *Order {
	o := &Order{ID: id, Deadline: 120 * time.Hour}
	for _, opt := range opts {
		opt(o)
	}
	return o
}

func main() {
	o := NewOrder(2, WithCoupon("DIWALI10"), WithExpressShipping())
	fmt.Println(o.Coupon, o.Express, o.Deadline)
}
  1. First, the arguments are evaluated. WithCoupon("DIWALI10") doesn't change anything yet: it returns a closure that remembers code. Same for WithExpressShipping(). Both closures land in the opts slice.
  2. The constructor sets defaults first: standard 5-day (120h) delivery.
  3. First loop iteration: calling the coupon closure with o sets o.Coupon.
  4. Second iteration: the express closure flips Express and overrides the default deadline. Later options win.
  5. The finished order comes back and we print it.
Senior engineer tip

Functional options shine for library APIs that will grow (gRPC's grpc.WithTransportCredentials, Uber's zap logger, many SDK clients). Adding a new option never breaks existing callers. For internal code with three fields, a plain config struct (NewServer(Config{Port: 8080})) is simpler and just as clear. Pick options when you need defaults + extensibility + a stable public API; otherwise don't pay the ceremony.

Encapsulation with unexported fields

Go's visibility rule is refreshingly simple: an identifier starting with a capital letter is exported (visible to other packages); lower-case is unexported (visible only inside its own package). There is no public/private keyword and, importantly, the boundary is the package, not the type.

That gives you encapsulation: export the type, hide its fields, and expose only methods that enforce your business rules. Here's a tiny module with an order package:

Embedding: composition, not inheritance

Go has no classes and no inheritance. Instead it has embedding: you put a type inside a struct without giving it a field name. The embedded type's fields and methods are promoted, meaning you can access them directly on the outer struct as if they were its own.

package main

import (
	"fmt"
	"time"
)

// Timestamps is a small reusable piece.
type Timestamps struct {
	CreatedAt time.Time
	UpdatedAt time.Time
}

func (t *Timestamps) Touch(now time.Time) {
	if t.CreatedAt.IsZero() {
		t.CreatedAt = now
	}
	t.UpdatedAt = now
}

type Address struct {
	City string
}

// Customer EMBEDS Timestamps (no field name, just the type).
type Customer struct {
	Timestamps // embedded: fields and methods are promoted
	Name       string
	Address    Address // a normal named field, NOT embedded
}

type Order struct {
	Timestamps
	ID int
}

func main() {
	now := time.Date(2026, 10, 16, 9, 30, 0, 0, time.UTC)

	c := Customer{Name: "Asha", Address: Address{City: "Pune"}}
	// Promoted method: really c.Timestamps.Touch(now)
	c.Touch(now)
	// Promoted field: really c.Timestamps.CreatedAt
	fmt.Println("created:", c.CreatedAt.Format(time.DateTime))
	fmt.Println("same thing:", c.Timestamps.CreatedAt.Format(time.DateTime))
	fmt.Println("city:", c.Address.City) // named field needs the full path

	o := Order{ID: 9}
	o.Touch(now.Add(time.Hour))
	fmt.Println("order updated:", o.UpdatedAt.Format(time.Kitchen))

	// Literal syntax: the embedded field's name is its type name.
	o2 := Order{Timestamps: Timestamps{CreatedAt: now}, ID: 10}
	fmt.Println("order 10 created:", o2.CreatedAt.Year())
}
  1. A fixed time so the output is deterministic.
  2. c contains a whole Timestamps value inside it (the embedded field), both times still zero.
  3. c.Touch(now) is a promoted method: Go rewrites it to (&c.Timestamps).Touch(now). The receiver is the inner struct, not the Customer. CreatedAt is zero, so it gets set.
  4. UpdatedAt is always refreshed.
  5. Promoted field: c.CreatedAt is shorthand for c.Timestamps.CreatedAt.
  6. The long form still works. The embedded field's name is its type name, Timestamps.
  7. Address is a named field, not embedded, so nothing is promoted. You must write c.Address.City.
  8. Order embeds the same Timestamps, so it gets Touch for free. Called with now + 1h.
  9. time.Kitchen formats as 3:04PM style.
  10. In a literal you name the embedded field by its type: Timestamps: Timestamps{...}.
created: 2026-10-16 09:30:00
same thing: 2026-10-16 09:30:00
city: Pune
order updated: 10:30AM
order 10 created: 2026

Under the hood, Customer really does have a field called Timestamps (the field name of an embedded type is its type name). c.Touch(now) is just shorthand that the compiler expands to c.Timestamps.Touch(now). Nothing more magical than that.

Why it's not inheritance

If you come from Java or Python, embedding looks like "Customer extends Timestamps". It isn't, and the difference matters:

package main

import "fmt"

type Notifier struct{ Channel string }

func (n Notifier) Describe() string { return "notifier via " + n.Channel }

// Send calls Describe. Which Describe? Always Notifier's.
func (n Notifier) Send(msg string) {
	fmt.Printf("[%s] %s\n", n.Describe(), msg)
}

type SMSNotifier struct {
	Notifier
	Phone string
}

// This "shadows" Notifier.Describe for SMSNotifier values...
func (s SMSNotifier) Describe() string { return "SMS to " + s.Phone }

func main() {
	s := SMSNotifier{Notifier: Notifier{Channel: "sms"}, Phone: "+91-98000"}

	fmt.Println(s.Describe())          // outer method wins
	fmt.Println(s.Notifier.Describe()) // inner still reachable
	s.Send("your order has shipped")   // ...but Send still calls the INNER one

	// And there is no "is-a" relationship:
	// var n Notifier = s // compile error: cannot use s (SMSNotifier) as Notifier
	var n Notifier = s.Notifier // you must pick the field explicitly
	fmt.Println(n.Channel)
}
  1. s embeds a Notifier. Both types define a Describe method.
  2. s.Describe(): the outer type's own method sits at a shallower depth, so it shadows the promoted one.
  3. The inner method is still reachable through the explicit path s.Notifier.Describe().
  4. s.Send is promoted, so Go calls s.Notifier.Send(msg). Inside, the receiver n is just a Notifier; it has no idea it lives inside an SMSNotifier.
  5. So n.Describe() calls Notifier's version. This is the gotcha: embedding is not inheritance and there are no virtual methods. The outer override is never seen here.
  6. An SMSNotifier is not a Notifier. To get one you pick the embedded field explicitly.
SMS to +91-98000
notifier via sms
[notifier via sms] your order has shipped
sms
  • No virtual dispatch. Notifier.Send calls n.Describe() where n is a Notifier. The inner type has no idea it's been embedded, so it never calls the outer type's Describe. In Java the overridden method would run.
  • No "is-a". An SMSNotifier is not a Notifier; you can't assign one to the other. If you want "anything that can Send", that's an interface (next chapter).
  • Shadowing, not overriding. A field or method on the outer struct simply hides the promoted one of the same name. The inner one is still there via s.Notifier.Describe().
Mental model

Embedding is delegation with free forwarding. The outer struct has a Timestamps, and the compiler writes the boring forwarding methods for you. Think "has-a with shortcuts", never "is-a".

Gotcha: embedding exports more than you think

Embedding a type promotes all its exported methods onto your type, so they become part of your public API. Embedding sync.Mutex in an exported struct means every caller can call yourThing.Lock(). Prefer a named, unexported field: mu sync.Mutex. Also, if two embedded types promote the same name at the same depth, using that name becomes an "ambiguous selector" compile error.

Struct tags and JSON (a preview)

A struct tag is a string literal written after a field's type, in backticks. Tags do nothing by themselves. They're metadata that libraries read at runtime (via the reflect package) to decide how to treat each field. The most famous reader is encoding/json:

package main

import (
	"encoding/json"
	"fmt"
	"reflect"

type Address struct {
	City    string `json:"city"`
	ZipCode string `json:"zip_code"`

type Customer struct {
	ID       int      `json:"id"`
	Name     string   `json:"name"`
	Email    string   `json:"email,omitempty"` // dropped when empty
	Password string   `json:"-"`               // never serialized
	Address  *Address `json:"address,omitempty"`
	note     string   // unexported: json ignores it

	c := Customer{ID: 1, Name: "Asha", Password: "s3cret", note: "vip",

	fmt.Println(string(b))

	b, _ = json.MarshalIndent(Customer{ID: 2, Name: "Ravi"}, "", "  ")

The shallow-copy trap: structs with slices and maps

Assigning a struct copies it, field by field. But a slice field is only a small header (a pointer to a backing array, plus length and capacity), and a map field is a pointer to the map's internals. Copying the struct copies those headers, not the data they point to. Both copies end up sharing the same items.

package main

import (
	"fmt"
	"maps"
	"slices"
)

type Order struct {
	ID    int
	Items []string
	Meta  map[string]string
}

// Clone makes a deep-enough copy: new backing array, new map.
func (o Order) Clone() Order {
	o.Items = slices.Clone(o.Items)
	o.Meta = maps.Clone(o.Meta)
	return o
}

func main() {
	original := Order{
		ID:    1,
		Items: []string{"pen", "book"},
		Meta:  map[string]string{"source": "web"},
	}

	shallow := original // copies the struct... but not what the slice/map point to
	shallow.ID = 2
	shallow.Items[0] = "PENCIL"
	shallow.Meta["source"] = "app"

	fmt.Println("original:", original.ID, original.Items, original.Meta)
	fmt.Println("shallow: ", shallow.ID, shallow.Items, shallow.Meta)

	deep := original.Clone()
	deep.Items[0] = "eraser"
	deep.Meta["source"] = "store"
	fmt.Println("original:", original.Items, original.Meta)
	fmt.Println("deep:    ", deep.Items, deep.Meta)
}
original: 1 [PENCIL book] map[source:app]
shallow:  2 [PENCIL book] map[source:app]
original: [PENCIL book] map[source:app]
deep:     [eraser book] map[source:store]
original := Order{ID: 1, Items: []string{"pen", "book"}}
shallow := original
shallow.ID = 2
shallow.Items[0] = "PENCIL"
fmt.Println(original.ID, original.Items)
fmt.Println(shallow.ID, shallow.Items)
deep := original
deep.Items = slices.Clone(original.Items)
deep.Items[0] = "eraser"
fmt.Println(original.Items, deep.Items)
  1. We create an order. Its Items header points to backing array A.
  2. Struct assignment copies every field. ID is copied as a number; Items is copied as a header, so it still points to A.
  3. Changing shallow.ID only touches shallow. Numbers are truly independent.
  4. Writing shallow.Items[0] writes into array A, the one both structs share.
  5. The IDs differ, but both see PENCIL. Surprise!
  6. slices.Clone allocates a fresh array B and copies the elements. Now deep owns its own data.
  7. Changing B leaves A alone. That's a real (deep-enough) copy.
Senior engineer tip

This bug shows up in production as "a cache entry changed by itself" or "two requests see each other's data". If your type holds slices or maps and is handed out from a cache, a config store, or across goroutines, give it a Clone() method and copy defensively at the boundary: clone what you receive in a constructor, and clone what you return from a getter. slices.Clone and maps.Clone are shallow on the elements, so if elements are themselves pointers or slices, clone one level deeper.

a := Customer{Tags: []string{"vip"}}, then b := a; b.Tags = append(b.Tags, "new"); b.Tags[0] = "x". What is a.Tags?
The slice []string{"vip"} has length 1 and capacity 1. Appending to b.Tags exceeds capacity, so append allocates a new array and copies vip into it. b.Tags[0] = "x" then writes into the new array, leaving a.Tags as [vip]. Whether two copies share data can depend on capacity, which is exactly why relying on it is dangerous. Clone explicitly.

Memory layout: alignment and padding

This one is an advanced detail, but it's cheap to understand. CPUs read memory fastest when a value sits at an address that's a multiple of its size: an 8-byte float64 wants an address divisible by 8. This is called alignment. To keep every field aligned, the compiler inserts invisible filler bytes called padding between fields. Field order therefore changes a struct's size.

package main

import (
	"fmt"
	"unsafe"
)

// Fields in a "bad" order: the compiler inserts padding.
type Loose struct {
	Paid   bool    // 1 byte + 7 bytes padding
	Total  float64 // 8 bytes
	Gift   bool    // 1 byte + 3 bytes padding
	Qty    int32   // 4 bytes
	Urgent bool    // 1 byte + 7 bytes padding
}

// Same fields, largest first.
type Tight struct {
	Total  float64 // 8
	Qty    int32   // 4
	Paid   bool    // 1
	Gift   bool    // 1
	Urgent bool    // 1 + 1 padding
}

func main() {
	fmt.Println("Loose:", unsafe.Sizeof(Loose{}), "bytes")
	fmt.Println("Tight:", unsafe.Sizeof(Tight{}), "bytes")
	fmt.Println("offset of Loose.Total:", unsafe.Offsetof(Loose{}.Total))
	fmt.Println("empty struct:", unsafe.Sizeof(struct{}{}), "bytes")
}
Loose: 32 bytes
Tight: 16 bytes
offset of Loose.Total: 8
empty struct: 0 bytes
  • Rule of thumb: order fields from largest to smallest alignment (8-byte types, then 4, 2, 1) to minimise padding.
  • The empty struct struct{} takes zero bytes. That's why map[string]struct{} is the idiomatic "set" and chan struct{} is the idiomatic "signal".
  • The fieldalignment analyser (from golang.org/x/tools) can report structs that would shrink if reordered.

Only optimise layout for structs you hold millions of (in-memory caches, big slices of records). For an ordinary Order type, readability wins: group fields by meaning, not by size.

Putting it together & practice

Here's the checklist a senior Gopher runs through when designing a new struct type:

  1. Is the zero value useful? If yes, maybe you don't need a constructor at all.
  2. Are there invariants? If yes, unexport the fields and expose methods; add New... returning an error.
  3. Value or pointer semantics? Decide once and make every method's receiver match.
  4. Does it hold slices/maps? Decide who owns them; add Clone() if it crosses boundaries.
  5. Many optional settings? Config struct, or functional options for public APIs.
  6. Need shared behaviour? Embed small pieces (Timestamps) for data and helpers; reach for interfaces for polymorphism.
type Order struct {
	sync.Mutex             // exported Lock/Unlock leak into the API
	Items []string
}

// mixed receivers: Count copies the mutex (vet: "passes lock by value")
func (o Order) Count() int { return len(o.Items) }
func (o *Order) Add(s string) {
	o.Lock()
	defer o.Unlock()
	o.Items = append(o.Items, s)
}

o := Order{sync.Mutex{}, []string{}} // positional, fragile
type Order struct {
	mu    sync.Mutex // unexported, named
	items []string
}

// consistent pointer receivers
func (o *Order) Count() int {
	o.mu.Lock()
	defer o.mu.Unlock()
	return len(o.items)
}
func (o *Order) Add(s string) {
	o.mu.Lock()
	defer o.mu.Unlock()
	o.items = append(o.items, s)
}

var o Order // zero value is ready
Exercise 1: An order with line items

Define LineItem (SKU, Price, Qty) and an Order holding a slice of them. Add AddItem(sku, price, qty) and Total() methods. Make the zero-value Order usable without a constructor. Which receiver kind should each method use?

Solution
package main

import "fmt"

type LineItem struct {
	SKU   string
	Price float64
	Qty   int
}

type Order struct {
	ID    int
	Items []LineItem
}

// AddItem changes the order, so it needs a pointer receiver.
func (o *Order) AddItem(sku string, price float64, qty int) {
	o.Items = append(o.Items, LineItem{SKU: sku, Price: price, Qty: qty})
}

// Total only reads. A value receiver would work, but we keep
// the receivers consistent: Order has a pointer method, so all are pointers.
func (o *Order) Total() float64 {
	sum := 0.0
	for _, it := range o.Items {
		sum += it.Price * float64(it.Qty)
	}
	return sum
}

func main() {
	var o Order // zero value is a valid empty order
	o.AddItem("KB-01", 2499, 1)
	o.AddItem("CABLE", 199, 3)
	fmt.Printf("%d items, total ₹%.2f\n", len(o.Items), o.Total())
}
  1. The zero Order is a valid empty order: Items is nil, which append and range handle fine.
  2. AddItem has a pointer receiver, so Go passes &o. The append result is assigned back to o.Items on the real order.
  3. Second item added. If AddItem had a value receiver, both appends would be lost.
  4. The Printf evaluates o.Total(). It starts with sum := 0.0.
  5. Iteration 1: 2499 × 1.
  6. Iteration 2: 199 × 3 = 597, running total 3096.
  7. Total returns, and Printf formats it with two decimals.
2 items, total ₹3096.00
Exercise 2: Functional options for Customer

Write NewCustomer(name string, opts ...CustomerOption) *Customer with options WithPhone, WithAddress(city, zip) and WithTier. The default tier should be "standard".

Solution
package main

import "fmt"

type Address struct{ City, ZipCode string }

type Customer struct {
	Name    string
	Phone   string
	Address Address
	Tier    string
}

type CustomerOption func(*Customer)

func WithPhone(p string) CustomerOption { return func(c *Customer) { c.Phone = p } }

func WithAddress(city, zip string) CustomerOption {
	return func(c *Customer) { c.Address = Address{City: city, ZipCode: zip} }
}

func WithTier(t string) CustomerOption { return func(c *Customer) { c.Tier = t } }

func NewCustomer(name string, opts ...CustomerOption) *Customer {
	c := &Customer{Name: name, Tier: "standard"}
	for _, opt := range opts {
		opt(c)
	}
	return c
}

func main() {
	fmt.Printf("%+v\n", *NewCustomer("Asha"))
	fmt.Printf("%+v\n", *NewCustomer("Ravi", WithPhone("+91-90000"), WithAddress("Pune", "411001"), WithTier("gold")))
}
{Name:Asha Phone: Address:{City: ZipCode:} Tier:standard}
{Name:Ravi Phone:+91-90000 Address:{City:Pune ZipCode:411001} Tier:gold}
Exercise 3: Make copies safe

A Customer has Tags []string and Prefs map[string]bool. Write a Clone() method so that changing the clone's tags or prefs never affects the original. Prove it in main.

Solution
package main

import (
	"fmt"
	"maps"
	"slices"
)

type Customer struct {
	Name  string
	Tags  []string
	Prefs map[string]bool
}

func (c Customer) Clone() Customer {
	c.Tags = slices.Clone(c.Tags)
	c.Prefs = maps.Clone(c.Prefs)
	return c
}

func main() {
	a := Customer{Name: "Asha", Tags: []string{"vip"}, Prefs: map[string]bool{"sms": true}}
	b := a.Clone()
	b.Tags[0] = "new"
	b.Prefs["sms"] = false
	fmt.Println(a.Tags, a.Prefs)
	fmt.Println(b.Tags, b.Prefs)
}
[vip] map[sms:true]
[new] map[sms:false]

Note the trick: a value receiver already gives us a copy of the struct, so we only need to replace the reference-type fields before returning it.

Key takeaways

  • A struct groups named fields into one type. Use named-field literals; design types so the zero value is useful.
  • Structs are comparable with == (and usable as map keys) only if all their fields are comparable.
  • Go passes everything by value. A pointer (&x, *p) lets you share and mutate one value instead of a copy. Nil pointers panic when dereferenced.
  • Methods are functions with a receiver. Pointer receivers mutate and avoid copies; value receivers suit small immutable types. Keep receivers consistent per type.
  • Method sets: T has only value methods; *T has both. That's why a value with pointer methods can't be stored in an interface that needs them.
  • NewX constructors validate and set defaults; functional options give extensible, readable optional config.
  • Capital letter = exported. Hide fields behind methods to protect invariants; the boundary is the package.
  • Embedding promotes fields and methods (composition with shortcuts). It is not inheritance: no virtual dispatch, no is-a.
  • Struct tags are metadata for libraries like encoding/json; only exported fields are serialised.
  • Copying a struct copies slice/map headers, not their data. Clone at boundaries. Order big-to-small to reduce padding when memory matters.

Generics

Generics let you write a function or a data structure once and use it with many types, while the compiler still checks every type. A Stack[Order] can only hold orders; Max works for ints, floats and strings alike. This chapter shows how they work, where they shine, and when an interface is still the better tool.

The problem generics solve

Before Go 1.18 (2022), if you wanted "sum a slice" for both []int and []float64, you had two bad choices: copy-paste the function once per type, or accept []any / interface{} and check types at run time, losing compile-time safety and paying for boxing.

package main

import "fmt"

// Without generics: one copy per type...
func SumInts(nums []int) int {
	var total int
	for _, n := range nums {
		total += n
	}
	return total
}

func SumFloats(nums []float64) float64 {
	var total float64
	for _, n := range nums {
		total += n
	}
	return total
}

// ...or give up type safety with any.
func SumAny(nums []any) float64 {
	var total float64
	for _, n := range nums {
		switch v := n.(type) {
		case int:
			total += float64(v)
		case float64:
			total += v
		default:
			panic(fmt.Sprintf("can't add %T", v)) // runtime surprise
		}
	}
	return total
}

// With generics: one function, checked at compile time.
type Number interface {
	~int | ~int64 | ~float64
}

func Sum[T Number](nums []T) T {
	var total T
	for _, n := range nums {
		total += n
	}
	return total
}

func main() {
	fmt.Println(SumInts([]int{1, 2, 3}))
	fmt.Println(SumFloats([]float64{1.5, 2.5}))
	fmt.Println(SumAny([]any{1, 2.5}))

	fmt.Println(Sum([]int{1, 2, 3}))         // T = int
	fmt.Println(Sum([]float64{1.5, 2.5}))    // T = float64
	fmt.Printf("%T\n", Sum([]int64{10, 20})) // result keeps its type
}
  1. The pre-generics way: SumInts works only for []int. Simple and type-safe, but we need a copy per type.
  2. SumFloats is the identical loop with float64 pasted in. Bugs fixed in one copy have to be fixed in all of them.
  3. SumAny takes []any. Element 1 is an int, caught by the type switch and converted.
  4. Element 2 is a float64. It works, but passing a string would compile fine and then panic at runtime on line 32.
  5. Generic Sum: the compiler sees []int and infers T = int. var total T is the zero value of int.
  6. += is allowed on T because every type in Number supports +. Returns an int, not an any.
  7. Same source, now instantiated with T = float64.
  8. With []int64 the result is an int64. Pass a []string and you get a compile error, not a runtime panic.

Sum[T Number] is a generic function. Reading the new syntax piece by piece:

  • [T Number] is a type parameter list. T is a placeholder for "some type, decided by the caller". It lives in square brackets, before the normal parameters.
  • Number is the constraint: the rule for which types T may be. Here: int, int64, float64 or anything built on them. Because every allowed type supports +, the compiler lets us write total += n.
  • When you call Sum([]int{1, 2, 3}), the compiler works out T = int. This is instantiation: plugging a real type into the placeholder. The result has type int, not any, so no assertions are needed.
Mental model

A generic function is a recipe with a blank: "Sum of ___". The constraint is the note on the blank: "must be something you can add". Each call fills the blank with a concrete ingredient, and the compiler checks the recipe works with it before the program runs.

Type parameters on functions

A function can have one or more type parameters, each with its own constraint. Common patterns:

package main

import (
	"cmp"
	"fmt"
)

// Contains works for any element type that supports ==.
func Contains[T comparable](items []T, target T) bool {
	for _, it := range items {
		if it == target {
			return true
		}
	}
	return false
}

// Max works for any type that supports < and >.
func Max[T cmp.Ordered](a, b T) T {
	if a > b {
		return a
	}
	return b
}

// Two type parameters: K for keys, V for values.
func Keys[K comparable, V any](m map[K]V) []K {
	out := make([]K, 0, len(m))
	for k := range m {
		out = append(out, k)
	}
	return out
}

func main() {
	fmt.Println(Contains([]string{"pen", "book"}, "book"))
	fmt.Println(Contains([]int{10, 20}, 30))

	fmt.Println(Max(3, 7))
	fmt.Println(Max("apple", "banana"))
	fmt.Println(Max(2.5, -1.0))

	stock := map[string]int{"pen": 5}
	fmt.Println(Keys(stock))
}
  1. T is inferred as string. comparable is what makes it == target legal. First element "pen" doesn't match.
  2. Second element matches, so it returns true early.
  3. Now T = int. Neither 10 nor 20 equals 30, the loop finishes and we return false.
  4. cmp.Ordered permits >. 3 > 7 is false, so b wins.
  5. Strings compare byte-wise (lexically): "apple" < "banana".
  6. Untyped constants 2.5 and -1.0 default to float64.
  7. Two type parameters, both inferred from map[string]int. V is never used in the body, it just has to be named.
  8. One key collected. With more keys, map iteration order is random, so sort the result if order matters.

  • Contains[T comparable]: the body uses ==, so T must be comparable (numbers, strings, pointers, comparable structs; not slices/maps/funcs).
  • Max[T cmp.Ordered]: the body uses >, so T must be ordered.
  • Keys[K comparable, V any]: map keys must be comparable; values can be anything.
func Max[T cmp.Ordered](a, b T) T {
	if a > b {
		return a
	}
	return b
}

func main() {
	fmt.Println(Max(3, 7))
	fmt.Println(Max("apple", "banana"))
}
  1. The compiler sees Max(3, 7). Both arguments are untyped integer constants, which default to int, so it infers T = int.
  2. It checks the constraint: is int in cmp.Ordered? Yes. Conceptually, Max[int](a, b int) int is called.
  3. 3 > 7 is false, so we return b.
  4. Prints 7. The result type is int, a real int.
  5. Same function, new instantiation: T = string. string is also ordered (lexicographic byte order).
  6. "a" sorts before "b", so apple > banana is false and we return b.
  7. Prints banana. Calling Max(3, "x") would be a compile error: no single T fits both.

For simple cases you may not need your own function at all. Go 1.21 added built-in min and max (any number of ordered arguments), and the slices and maps packages are full of generic helpers: slices.Contains, slices.Index, slices.Max, slices.Sort, maps.Keys, maps.Clone… Reach for those first.

Union types and the ~ tilde

A union int | int64 | float64 means "any one of these". The tilde ~int64 means "int64 or any named type whose underlying type is int64". That matters, because real code is full of named types like type Rupees int64, type OrderID int or type Status string.

package main

import (
	"cmp"
	"fmt"
)

// A custom type whose underlying type is int64.
type Rupees int64

// ~int64 means "int64 or ANY type whose underlying type is int64".
type Integer interface {
	~int | ~int32 | ~int64
}

type Float interface {
	~float32 | ~float64
}

// Constraints can be combined: a union of two unions.
type Number interface {
	Integer | Float
}

func Sum[T Number](xs []T) T {
	var s T
	for _, x := range xs {
		s += x
	}
	return s
}

// cmp.Ordered = all integers, floats and strings (with ~).
func Clamp[T cmp.Ordered](v, lo, hi T) T {
	return min(max(v, lo), hi) // built-in min/max are generic too
}

func main() {
	cart := []Rupees{499, 1299, 50}
	total := Sum(cart)
	fmt.Printf("total = %v (%T)\n", total, total)

	fmt.Println(Clamp(150, 0, 100))
	fmt.Println(Clamp(Rupees(-5), 0, 100))
	fmt.Println(Clamp("m", "a", "k"))
}
  1. Rupees is a new named type whose underlying type is int64. The ~ in ~int64 is what lets such types in.
  2. T is inferred as Rupees, not int64. It satisfies Number through Integer's ~int64.
  3. The loop adds 499 + 1299 + 50. All arithmetic stays in Rupees.
  4. The result keeps the caller's type, so any methods on Rupees are still available. No conversion back needed.
  5. max(150, 0) is 150, then min(150, 100) is 100. The built-in min/max are generic too.
  6. Once v is Rupees(-5), the untyped constants 0 and 100 become Rupees too. max(-5, 0) is 0.
  7. cmp.Ordered includes strings. "m" is past "k", so it is clamped to "k".

The compiler even suggests the fix. And one more rule: an interface that contains a type list (a union or a ~T) can only be used as a constraint, never as an ordinary variable type:

package main

type Number interface {
	~int | ~float64
}

func main() {
	var n Number = 5 // constraint interfaces are not ordinary types
	_ = n
}
# command-line-arguments

Senior engineer tip

Almost always write ~T in numeric and string constraints. Without it, your generic helper silently rejects every domain type (Rupees, UserID, Status) that teams create precisely to make code safer. Prefer the ready-made cmp.Ordered over hand-rolled lists, and if you need "all integers", golang.org/x/exp/constraints has Integer, Signed, Float, etc. (or write a small one like ours; it's three lines).

Type inference

You rarely have to write the type arguments yourself. Type inference looks at the ordinary arguments you passed and works out each type parameter. When it can't, you supply them explicitly in square brackets, all of them or just the first few.

package main

import (
	"fmt"
	"strconv"
)

func Map[T, U any](xs []T, f func(T) U) []U {
	out := make([]U, 0, len(xs))
	for _, x := range xs {
		out = append(out, f(x))
	}
	return out
}

// T only appears in the RESULT, so it can't be inferred.
func Zero[T any]() T {
	var z T
	return z
}

func main() {
	prices := []int{499, 1299}

	// Inferred: T = int (from prices), U = string (from strconv.Itoa).
	labels := Map(prices, strconv.Itoa)
	fmt.Printf("%q\n", labels)

	// Explicit instantiation: same thing, spelled out.
	labels2 := Map[int, string](prices, func(p int) string { return "₹" + strconv.Itoa(p) })
	fmt.Println(labels2)

	// Partial: give T, let U be inferred.
	doubled := Map[int](prices, func(p int) float64 { return float64(p) * 2 })
	fmt.Println(doubled)

	fmt.Printf("%q %v %v\n", Zero[string](), Zero[int](), Zero[*int]())

	// You can even take a generic function as a value once instantiated.
	toStr := Map[int, string]
	fmt.Println(toStr([]int{1, 2}, strconv.Itoa))
}
  1. Our input slice.
  2. Both type parameters are inferred: T = int from prices, U = string from the signature of strconv.Itoa.
  3. f(x) is called once per element and the results appended.
  4. %q quotes each string, proving these are strings, not ints.
  5. Explicit instantiation Map[int, string] spells out what inference would have worked out anyway.
  6. Partial instantiation: we give T, and U is inferred as float64 from the closure.
  7. Zero uses T only in its result, so there is nothing to infer from. You must write Zero[string](). Each returns its type's zero value.
  8. An instantiated generic function is an ordinary function value. An uninstantiated Map could not be assigned like this.
["499" "1299"]
[₹499 ₹1299]
[998 2598]
"" 0 <nil>
[1 2]

Inference needs something to infer from. If a type parameter appears only in the result, you must name it:

package main

func Zero[T any]() T {
	var z T
	return z
}

func main() {
	x := Zero() // nothing to infer T from
	_ = x
}
# command-line-arguments
./main.go:9:11: in call to Zero, cannot infer T (declared at ./main.go:3:11)

Order type parameters so the ones callers usually need to spell out come first. Partial instantiation only fills from the left: Map[int](...) sets T and infers U, but you can't skip T to set only U.

Generic types: Stack, Queue, Set, Pair

Types can have type parameters too. type Stack[T any] struct{...} declares a generic type; Stack[string] and Stack[Order] are two different, fully type-checked instantiations. Methods on a generic type name the parameter in the receiver: func (s *Stack[T]) Push(v T).

package main

import "fmt"

// Stack is a generic type: a type with a type parameter.
type Stack[T any] struct {
	items []T
}

// Methods use the receiver's type parameter: Stack[T].
func (s *Stack[T]) Push(v T) {
	s.items = append(s.items, v)
}

// Pop returns the zero value of T and false when empty.
func (s *Stack[T]) Pop() (T, bool) {
	var zero T
	if len(s.items) == 0 {
		return zero, false
	}
	last := s.items[len(s.items)-1]
	s.items = s.items[:len(s.items)-1]
	return last, true
}

func (s *Stack[T]) Len() int { return len(s.items) }

// Queue: first in, first out.
type Queue[T any] struct {
	items []T
}

func (q *Queue[T]) Enqueue(v T) { q.items = append(q.items, v) }

func (q *Queue[T]) Dequeue() (T, bool) {
	var zero T
	if len(q.items) == 0 {
		return zero, false
	}
	first := q.items[0]
	q.items[0] = zero // let the GC reclaim it if T holds pointers
	q.items = q.items[1:]
	return first, true
}

type Order struct {
	ID    int
	Total float64
}

func main() {
	var undo Stack[string] // zero value is ready to use
	undo.Push("add pen")
	undo.Push("add book")
	undo.Push("apply coupon")
	for undo.Len() > 0 {
		action, _ := undo.Pop()
		fmt.Println("undo:", action)
	}
	_, ok := undo.Pop()
	fmt.Println("pop on empty ok?", ok)

	var q Queue[Order]
	q.Enqueue(Order{1, 499})
	q.Enqueue(Order{2, 1299})
	o, _ := q.Dequeue()
	fmt.Printf("processing %+v\n", o)
}

  1. Instantiating with T = string. The zero value has a nil slice, which is a perfectly good empty stack: no constructor needed.
  2. Push appends. The compiler would reject s.Push(42): this stack only takes strings.
  3. Second push goes on top.
  4. Pop takes the last element (LIFO) and shrinks the slice.
  5. Most recent action first, exactly what an undo history needs.
  6. Next pop empties the stack.
  7. Popping an empty stack can't return "nothing" of type T, so it returns var zero T (here "") and ok = false.
  8. The comma-ok result tells the caller the difference between "an empty string was stored" and "there was nothing".
Gotcha: memory leaks in generic containers

In Dequeue we set q.items[0] = zero before reslicing. Reslicing (q.items[1:]) doesn't free the old element: the backing array still references it. If T is a pointer or holds pointers (like *Order), the garbage collector can't reclaim it. Clearing the slot is cheap insurance.

Set and Pair

A Set[T comparable] wraps a map[T]struct{}, the classic Go set (empty struct values take zero bytes; see Chapter 07). Pair[K, V] shows a type with two parameters:

package main

import (
	"fmt"
	"maps"
	"slices"
	"strings"
)

// Set uses a map with empty-struct values (zero bytes each).
type Set[T comparable] struct {
	m map[T]struct{}
}

func NewSet[T comparable](items ...T) *Set[T] {
	s := &Set[T]{m: make(map[T]struct{}, len(items))}
	for _, it := range items {
		s.Add(it)
	}
	return s
}

func (s *Set[T]) Add(v T)      { s.m[v] = struct{}{} }
func (s *Set[T]) Has(v T) bool { _, ok := s.m[v]; return ok }
func (s *Set[T]) Len() int     { return len(s.m) }
func (s *Set[T]) Items() []T   { return slices.Collect(maps.Keys(s.m)) }
func (s *Set[T]) Union(o *Set[T]) *Set[T] {
	out := NewSet(s.Items()...)
	for v := range o.m {
		out.Add(v)
	}
	return out
}

// Pair holds two values of possibly different types.
type Pair[K comparable, V any] struct {
	Key   K
	Value V
}

func (p Pair[K, V]) String() string { return fmt.Sprintf("%v=%v", p.Key, p.Value) }

// SortedPairs turns a map into a slice of Pairs, sorted by key.
func SortedPairs[V any](m map[string]V) []Pair[string, V] {
	out := make([]Pair[string, V], 0, len(m))
	for _, k := range slices.Sorted(maps.Keys(m)) {
		out = append(out, Pair[string, V]{k, m[k]})
	}
	return out
}

func main() {
	tagsA := NewSet("electronics", "sale")
	tagsB := NewSet("sale", "new")
	all := tagsA.Union(tagsB)
	items := all.Items()
	slices.Sort(items) // map order is random; sort for stable output
	fmt.Println(all.Len(), strings.Join(items, ","), all.Has("new"), all.Has("old"))

	ids := NewSet(101, 102, 101)
	fmt.Println("unique order IDs:", ids.Len())

	stock := map[string]int{"pen": 40, "book": 12, "bag": 3}
	fmt.Println(SortedPairs(stock))
}
  1. NewSet infers T = string from its variadic args and allocates the map. The values are struct{}, which take zero bytes.
  2. Each item goes through Add, which just sets s.m[v] = struct{}{}.
  3. A second *Set[string].
  4. Union starts by copying tagsA's items into a fresh set. Union takes *Set[T], so you can't union a set of strings with a set of ints.
  5. Adding tagsB's items: "sale" is already a key, so the map doesn't grow. Only "new" is added.
  6. Items() collects the keys in random map order, so we sort before printing to keep the output stable.
  7. Has uses the comma-ok map lookup. "old" was never added.
  8. Same generic type, now Set[int]. The duplicate 101 collapses into one key.
  9. SortedPairs infers V = int. slices.Sorted(maps.Keys(m)) gives the keys in order, and each becomes a Pair[string, int].
  10. Pair has a String() method, so fmt prints each element as key=value.
3 electronics,new,sale true false
unique order IDs: 2
[bag=3 book=12 pen=40]
  • Inside the package, a generic type is always written with its parameters: *Set[T], Pair[string, V]. A bare Set is not a type.
  • NewSet("electronics", "sale") infers T = string from the variadic arguments.
  • Pair[K, V] has a String() method, so it's a fmt.Stringer and prints nicely as bag=3. Generic types can satisfy ordinary interfaces.

Methods on generic types, and generic methods (Go 1.27)

For years Go had a famous limitation: methods could use their type's parameters, but couldn't declare new type parameters of their own. You couldn't write list.Map(f) where f returns a different type; you had to write a top-level function Map(list, f) instead.

Go 1.27 lifted that restriction. A method can now declare its own type parameter list after its name, making it a generic method. It's instantiated and inferred just like a generic function:

package main

import (
	"fmt"
	"strconv"
)

// List is a generic type with element type E.
type List[E any] []E

// A GENERIC METHOD (Go 1.27+): Map declares its own type parameter F,
// in addition to the receiver's E.
func (l List[E]) Map[F any](f func(E) F) List[F] {
	out := make(List[F], len(l))
	for i, x := range l {
		out[i] = f(x)
	}
	return out
}

// An ordinary method that only uses the receiver's type parameter.
func (l List[E]) Filter(keep func(E) bool) List[E] {
	var out List[E]
	for _, x := range l {
		if keep(x) {
			out = append(out, x)
		}
	}
	return out
}

func main() {
	totals := List[int]{120, 4999, 80, 1500}

	// Methods chain nicely: F is inferred as string from strconv.Itoa.
	labels := totals.
		Filter(func(t int) bool { return t >= 1000 }).
		Map(strconv.Itoa)
	fmt.Printf("%q %T\n", labels, labels)

	// Explicit instantiation works like with generic functions.
	halves := totals.Map[float64](func(t int) float64 { return float64(t) / 2 })
	fmt.Println(halves)
}
  1. List[int] instantiates the generic type, so E = int for all its methods.
  2. Filter runs first. It only uses the receiver's E. 120 fails the >= 1000 test.
  3. 4999 kept, 80 dropped, 1500 kept. A new List[int] is returned.
  4. The chain continues with Map, a generic method (Go 1.27+) that declares its own type parameter F. It is inferred as string from strconv.Itoa.
  5. Each element is converted into the pre-sized output.
  6. The result type is List[string]: the method changed the element type, which a plain method on List[E] could never do.
  7. Explicit Map[float64] on the original (unfiltered) list. Filtering earlier didn't change totals.
  8. All four halved.
["4999" "1500"] main.List[string]
[60 2499.5 40 750]

What generic methods still can't do

The reason Go waited so long is interfaces. An interface method call is resolved at run time, but a generic method needs to be compiled for its type arguments, which a running program can't do on the fly. So the rule is: interfaces cannot declare generic methods, and therefore a generic method never satisfies an interface method.

package main

// Interfaces still cannot declare generic methods.
type Mapper interface {
	Map[F any](f func(int) F) []F
}

func main() {}
# command-line-arguments
./main.go:5:5: interface method must have no type parameters
./main.go:5:25: undefined: F
package main

import "fmt"

type Box struct{ v int }

// Generic method...
func (b Box) Show[U any](u U) string { return fmt.Sprint(b.v, " ", u) }

// ...does NOT satisfy a non-generic interface method, even "any".
type Shower interface{ Show(u any) string }

func main() {
	var b Box
	fmt.Println(b.Show("ok")) // calling it directly is fine
	var s Shower = b
	_ = s
}
# command-line-arguments

Senior engineer tip

Generic methods are great for fluent APIs on your own collection types (list.Map(...).Filter(...)). But remember that callers can't abstract over them with an interface, and code that must build with older Go versions can't use them. For library code, top-level functions like slices.Map-style helpers remain the most portable, most composable choice. Use generic methods where chaining clearly reads better, and check your module's go directive.

Map, Filter, Reduce (and friends)

The classic functional trio becomes type-safe one-liners with generics. Here they are over a slice of orders, plus a GroupBy with two type parameters:

package main

import (
	"fmt"
	"strings"
)

func Map[T, U any](xs []T, f func(T) U) []U {
	out := make([]U, 0, len(xs))
	for _, x := range xs {
		out = append(out, f(x))
	}
	return out
}

func Filter[T any](xs []T, keep func(T) bool) []T {
	var out []T
	for _, x := range xs {
		if keep(x) {
			out = append(out, x)
		}
	}
	return out
}

func Reduce[T, A any](xs []T, init A, f func(A, T) A) A {
	acc := init
	for _, x := range xs {
		acc = f(acc, x)
	}
	return acc
}

// GroupBy buckets items by a key you compute.
func GroupBy[T any, K comparable](xs []T, key func(T) K) map[K][]T {
	out := make(map[K][]T)
	for _, x := range xs {
		k := key(x)
		out[k] = append(out[k], x)
	}
	return out
}

type Order struct {
	ID       int
	Customer string
	Total    float64
	Status   string
}

func main() {
	orders := []Order{
		{1, "asha", 499, "paid"},
		{2, "ravi", 1299, "pending"},
		{3, "asha", 2500, "paid"},
		{4, "meera", 80, "paid"},
	}

	paid := Filter(orders, func(o Order) bool { return o.Status == "paid" })
	revenue := Reduce(paid, 0.0, func(sum float64, o Order) float64 { return sum + o.Total })
	ids := Map(paid, func(o Order) int { return o.ID })
	names := Map(orders, func(o Order) string { return strings.ToUpper(o.Customer) })

	fmt.Println("paid IDs:", ids)
	fmt.Println("revenue: ", revenue)
	fmt.Println("names:   ", names)

	byCustomer := GroupBy(orders, func(o Order) string { return o.Customer })
	fmt.Println("asha has", len(byCustomer["asha"]), "orders")
}

  2. The accumulator starts at init.
  3. First element: acc = f(0, 499) = 499.
  4. Second: f(499, 2500) = 2999.
  5. Third: f(2999, 80) = 3079.

Gotcha: don't turn Go into a different language

A plain for loop is idiomatic Go, readable by everyone, and often faster than a chain of Filter → Map → Reduce that allocates an intermediate slice at each step. Use these helpers when they genuinely clarify intent (often in tests and data-wrangling code), not as a replacement for every loop. That's part of why the stdlib has (so far) held off on adding slices.Map/Filter, offering lazy iterators instead.

Constraints with methods

Constraints can require methods, just like regular interfaces, and can mix methods with type sets. Three increasingly advanced patterns:

package main

import (
	"fmt"
	"strings"
)

// 1) A plain method constraint: any type with String().
func JoinAll[T fmt.Stringer](xs []T, sep string) string {
	parts := make([]string, len(xs))
	for i, x := range xs {
		parts[i] = x.String()
	}
	return strings.Join(parts, sep)
}

// 2) Type set + method: "a string-based type that can validate itself".
type Enum interface {
	~string
	Valid() bool
}

func Parse[E Enum](raw string) (E, error) {
	e := E(strings.ToLower(raw)) // allowed: every type in the set is ~string
	if !e.Valid() {
		var zero E
		return zero, fmt.Errorf("invalid %T %q", zero, raw)
	}
	return e, nil
}

type Status string

func (s Status) Valid() bool    { return s == "pending" || s == "paid" || s == "shipped" }
func (s Status) String() string { return "status:" + string(s) }

// 3) The "pointer method" pattern: T is a struct, *T has the method.
type Defaulter[T any] interface {
	*T
	SetDefaults()
}

func NewWithDefaults[T any, PT Defaulter[T]]() T {
	var v T
	PT(&v).SetDefaults() // convert *T to PT to call the method
	return v
}

type Config struct {
	Port    int
	Retries int
}

func (c *Config) SetDefaults() { c.Port, c.Retries = 8080, 3 }

func main() {
	fmt.Println(JoinAll([]Status{"paid", "shipped"}, ", "))

	s, err := Parse[Status]("PAID")
	fmt.Println(s, err)
	_, err = Parse[Status]("lost")
	fmt.Println(err)

	cfg := NewWithDefaults[Config]() // PT is inferred as *Config
	fmt.Printf("%+v\n", cfg)
}
  1. T = Status, which satisfies the fmt.Stringer constraint. Inside, x.String() calls Status.String, and the slice elements are never boxed into interface values.
  2. The parts are joined with ", ".
  3. Parse[Status] must be explicit: E appears only in the result. Converting a string to E is allowed because Enum requires ~string.
  4. The Valid() part of the constraint lets us call the method. "paid" is valid, so we return it.
  5. Printing s goes through Status.String().
  6. "lost" fails validation. var zero E gives the empty Status, and %T of it names the concrete type.
  7. A helpful error, generic over every enum type.
  8. The pointer-method pattern: we pass T = Config, and PT is inferred as *Config from the *T core of Defaulter.
  9. PT(&v) converts *Config to the type parameter so we can call SetDefaults, which has a pointer receiver and mutates v in place.
  10. We return a Config value with defaults filled in.
status:paid, status:shipped
status:paid <nil>
invalid main.Status "lost"
{Port:8080 Retries:3}
  1. [T fmt.Stringer]: any type with String(). Unlike taking []fmt.Stringer, a []Status can be passed directly, without converting each element into an interface value.
  2. Enum combines a type set (~string) with a method (Valid()). That lets Parse both convert a raw string into E and call e.Valid(). One generic parser now works for every string enum in your codebase.
  3. The pointer-method pattern: SetDefaults has a pointer receiver, so Config itself doesn't satisfy the constraint, only *Config does. The constraint interface{ *T; SetDefaults() } says "PT is a pointer to T and has SetDefaults". The caller writes NewWithDefaults[Config]() and PT is inferred. You'll see this in libraries that decode into or pool generic values.

The zero value of T

Inside generic code you don't know what T is, so you can't write return 0 or return nil or return "". The idiom for "the zero value of whatever T is" is var zero T. You've already seen it in Pop and Parse.

package main

import "fmt"

// var zero T is the standard way to get T's zero value.
func FirstOr[T any](xs []T, fallback T) T {
	if len(xs) == 0 {
		return fallback
	}
	return xs[0]
}

func Last[T any](xs []T) (T, bool) {
	if len(xs) == 0 {
		var zero T
		return zero, false
	}
	return xs[len(xs)-1], true
}

// With comparable you can compare against the zero value.
func IsZero[T comparable](v T) bool {
	var zero T
	return v == zero
}

// Compact drops zero values ("", 0, nil...) from a slice.
func Compact[T comparable](xs []T) []T {
	var out []T
	for _, x := range xs {
		if !IsZero(x) {
			out = append(out, x)
		}
	}
	return out
}

type Address struct{ City, Zip string }

func main() {
	fmt.Println(FirstOr([]string{}, "guest"))
	v, ok := Last([]float64{})
	fmt.Println(v, ok)
	a, ok := Last([]Address{})
	fmt.Printf("%+v %v\n", a, ok)

	fmt.Println(IsZero(Address{}), IsZero(Address{City: "Pune"}))
	fmt.Printf("%q\n", Compact([]string{"pen", "", "book", ""}))
	fmt.Println(*new(int), *new(string) == "") // *new(T) also gives a zero value
}
  1. The slice is empty, so the caller-supplied fallback is returned.
  2. Last has no fallback. var zero T is the standard way to produce "nothing" for an unknown type: here 0.0.
  3. Always pair a zero value with an ok flag, so callers can tell "empty" from a real 0.
  4. For a struct, the zero value is all fields zeroed.
  5. comparable lets us write v == zero. Address has only string fields, so it's comparable.
  6. Inside Compact: "pen" is not zero, kept. "" is, dropped.
  7. "book" kept, the final "" dropped.
  8. *new(T) is another one-liner for a zero value, handy inside expressions.
guest
0 false
{City: Zip:} false
true false
["pen" "book"]
0 true
  • var zero T is the clearest spelling. *new(T) works too and fits in an expression, but reads worse.
  • You can only compare against the zero value (v == zero) if T is comparable.
  • Pair "zero" results with a bool or error whenever the zero value could also be legitimate data (an order total of 0, an empty name).
Which of these compiles inside func F[T any]() T { ... }?
nil and 0 are only valid for some types, and T{} is a composite literal that only works for struct, slice, map or array types. Since T could be anything, the only always-valid option is var z T (or *new(T)).

Generic iterators: range over func (Go 1.23)

How do users loop over your LinkedList[T]? Before Go 1.23 you'd expose a callback (l.Each(func(v T) {...})) or a cursor type. Now you can return an iterator and users write a normal for ... range.

An iterator is just a function with a specific shape. The iter package names two of them:

type Seq[V any]     func(yield func(V) bool)
type Seq2[K, V any] func(yield func(K, V) bool)

The iterator calls yield once per element. yield returns false when the loop body hits break (or return), and the iterator must then stop. That's the whole protocol, and it's generic by design.

package main

import (
	"fmt"
	"iter"
	"slices"
)

type node[T any] struct {
	val  T
	next *node[T]
}

// LinkedList is a singly linked list of T.
type LinkedList[T any] struct {
	head, tail *node[T]
	size       int
}

func (l *LinkedList[T]) PushBack(v T) {
	n := &node[T]{val: v}
	if l.tail == nil {
		l.head, l.tail = n, n
	} else {
		l.tail.next = n
		l.tail = n
	}
	l.size++
}

func (l *LinkedList[T]) Len() int { return l.size }

// All returns an iterator over the values: usable with for-range (Go 1.23+).
func (l *LinkedList[T]) All() iter.Seq[T] {
	return func(yield func(T) bool) {
		for n := l.head; n != nil; n = n.next {
			if !yield(n.val) { // caller did "break": stop walking
				return
			}
		}
	}
}

// Indexed yields (position, value) pairs.
func (l *LinkedList[T]) Indexed() iter.Seq2[int, T] {
	return func(yield func(int, T) bool) {
		i := 0
		for n := l.head; n != nil; n = n.next {
			if !yield(i, n.val) {
				return
			}
			i++
		}
	}
}

func main() {
	var l LinkedList[string]
	for _, s := range []string{"placed", "paid", "packed", "shipped", "delivered"} {
		l.PushBack(s)
	}

	for status := range l.All() {
		fmt.Print(status, " → ")
	}
	fmt.Println("done")

	for i, status := range l.Indexed() {
		if status == "shipped" {
			fmt.Println("stopping at index", i)
			break // yield returns false inside All/Indexed
		}
	}

	// Iterators plug into the slices/maps packages.
	fmt.Println(slices.Collect(l.All()), l.Len())
}
placed → paid → packed → shipped → delivered → done
stopping at index 3
[placed paid packed shipped delivered] 5
func (l *LinkedList[T]) All() iter.Seq[T] {
	return func(yield func(T) bool) {
		for n := l.head; n != nil; n = n.next {
			if !yield(n.val) {
				return
			}
		}
	}
}

// list holds: placed → paid → shipped
for s := range list.All() {
	if s == "shipped" {
		break
	}
	fmt.Println(s)
}
  1. The range calls list.All(), which returns an iterator function. The compiler turns your loop body into the yield callback and calls the iterator with it.
  2. The iterator walks to the first node and calls yield("placed"). Control jumps into your loop body with s = "placed".
  3. Not "shipped", so we print it. The body finishes, and yield returns true ("keep going").
  4. Back in the iterator: next node, yield("paid").
  5. Printed; yield returns true again.
  6. Third node: yield("shipped"). This time the body hits break, so yield returns false.
  7. The iterator sees false and returns immediately. It must not call yield again (the runtime panics if it does). The for loop is done.

Lazy pipelines

Because iterators produce values on demand, you can chain generic adapters and do only the work needed. Here we look for the first two big orders and stop; later elements are never even examined:

package main

import (
	"fmt"
	"iter"
	"maps"
	"slices"
)

// Lazy, generic iterator adapters: nothing runs until someone ranges.
func Filter[T any](seq iter.Seq[T], keep func(T) bool) iter.Seq[T] {
	return func(yield func(T) bool) {
		for v := range seq {
			if keep(v) && !yield(v) {
				return
			}
		}
	}
}

func Map[T, U any](seq iter.Seq[T], f func(T) U) iter.Seq[U] {
	return func(yield func(U) bool) {
		for v := range seq {
			if !yield(f(v)) {
				return
			}
		}
	}
}

// Take stops the whole pipeline after n items.
func Take[T any](seq iter.Seq[T], n int) iter.Seq[T] {
	return func(yield func(T) bool) {
		if n <= 0 {
			return
		}
		count := 0
		for v := range seq {
			if !yield(v) {
				return
			}
			count++
			if count == n {
				return
			}
		}
	}
}

func main() {
	totals := []float64{120, 4999, 80, 1500, 2300, 999, 7000}

	checked := 0
	bigOrders := Filter(slices.Values(totals), func(t float64) bool {
		checked++
		return t >= 1000
	})
	labels := Map(bigOrders, func(t float64) string { return fmt.Sprintf("₹%.0f", t) })

	for l := range Take(labels, 2) {
		fmt.Println("big:", l)
	}
	fmt.Println("elements examined:", checked, "of", len(totals)) // lazy!

	// The stdlib speaks iterators too.
	stock := map[string]int{"pen": 40, "book": 12, "bag": 3}
	for _, k := range slices.Sorted(maps.Keys(stock)) {
		fmt.Print(k, "=", stock[k], " ")
	}
	fmt.Println()
}

Senior engineer tip

Expose All() iter.Seq[T] (and iter.Seq2 for key/value) on your collection types instead of returning a freshly copied slice. Callers who need a slice can do slices.Collect(c.All()); callers who stop early save work. Follow the stdlib naming: All, Keys, Values, Backward. And make iterators honour yield's return value; ignoring it is the #1 iterator bug and causes a runtime panic.

When NOT to use generics

Generics and interfaces both give you "write once, use with many types", but they answer different questions:

  • Generics: "The code is the same for every type; only the type changes." Containers, algorithms over slices/maps, Max, Sum, caches.
  • Interfaces: "The behaviour differs per type." Razorpay pays differently from Stripe. Each type brings its own method.
package main

import "fmt"

type Payer interface{ Pay(amount float64) error }

type Razorpay struct{}

func (Razorpay) Pay(a float64) error { fmt.Printf("razorpay ₹%.0f\n", a); return nil }

type Stripe struct{}

func (Stripe) Pay(a float64) error { fmt.Printf("stripe ₹%.0f\n", a); return nil }

// Generic version: compiles, works... and adds nothing.
func CheckoutGeneric[P Payer](p P, amount float64) error { return p.Pay(amount) }

// Interface version: simpler, and it can hold MIXED gateways in one slice.
func Checkout(p Payer, amount float64) error { return p.Pay(amount) }

func main() {
	CheckoutGeneric(Razorpay{}, 100)
	Checkout(Stripe{}, 200)

	// Only the interface version handles a runtime mix:
	for _, p := range []Payer{Razorpay{}, Stripe{}} {
		Checkout(p, 300)
	}
}
  1. The generic version is instantiated with P = Razorpay. The constraint is just the Payer interface.
  2. p.Pay runs Razorpay.Pay. It works, but the generic signature bought nothing over a plain interface parameter.
  3. The interface version: Stripe{} is boxed into a Payer and the call is dynamically dispatched. Same result, simpler signature.
  4. A []Payer holds different concrete types. First iteration dispatches to Razorpay.
  5. Second iteration, Stripe. A generic P is fixed to one type per instantiation, so it could never iterate a mix like this.
razorpay ₹100
stripe ₹200
razorpay ₹300
stripe ₹300

CheckoutGeneric works, but it's strictly worse: longer signature, and it can't handle a []Payer holding different gateways, because each P is fixed at compile time. If a type parameter is only used to call methods on it, you almost always want the interface directly.

// Type parameter only used to call a method
func Notify[N Notifier](n N, msg string) error {
	return n.Notify(msg)
}

// Generic for its own sake: only ever used with Order
func SaveOrder[T Order](db *sql.DB, o T) error { ... }

// any-typed "generic" that type-switches inside
func Format[T any](v T) string {
	switch x := any(v).(type) { ... }
}
// Behaviour varies: plain interface
func Notify(n Notifier, msg string) error {
	return n.Notify(msg)
}

// One concrete type: just write it
func SaveOrder(db *sql.DB, o Order) error { ... }

// Same algorithm, many element types: generics
func Dedupe[T comparable](xs []T) []T { ... }
Senior engineer tip

The Go team's guideline is: write the concrete code first. Introduce a type parameter when you find yourself writing the exact same code a second or third time for different types. If you're type-switching on T inside a generic function, that's a smell: generics are for code that doesn't care what T is. Also resist generic "frameworks" (Repository[T Entity] with ten methods); they tend to fight the real differences between entities.

How Go compiles generics (and what it costs)

There are two classic ways to implement generics. C++ and Rust stencil: generate a separate copy of the code for every type argument (fast, but binaries and compile times grow). Java boxes: one copy for everything, with values behind pointers (small, but slower). Go takes a middle road called GC shape stenciling with dictionaries.

  • A type's GC shape is roughly "how it looks in memory to the garbage collector": its size, alignment and where its pointers are. int64 and Rupees (underlying int64) share a shape. All pointer types share one shape.
  • The compiler generates one copy of the function per shape, not per type.
  • Each call also passes a hidden dictionary describing the actual type: how to call its methods, its type descriptor for conversions, and so on.

What does that mean in practice? Let's measure. We sum 1,000 numbers five ways, using Go 1.24's b.Loop() benchmark style:

Mental model

Generics are zero-cost for operators on concrete value types (+, <, ==, indexing, appending). Generics that call methods on T cost roughly like interfaces, sometimes slightly more. So: use generics for type safety and less duplication, not as a performance trick to "avoid interface overhead". For the 1% of hot paths where it matters, benchmark (the compiler keeps improving, and PGO can devirtualize hot calls).

Exercise 1: MaxBy

Write MaxBy[T any, K cmp.Ordered](xs []T, key func(T) K) (T, bool) that returns the element whose key is largest. Use it to find the most expensive order and the alphabetically-last customer. Handle the empty slice.

Solution
package main

import (
	"cmp"
	"fmt"
)

// MaxBy returns the element with the largest key, or false if xs is empty.
func MaxBy[T any, K cmp.Ordered](xs []T, key func(T) K) (T, bool) {
	var best T
	if len(xs) == 0 {
		return best, false
	}
	best = xs[0]
	bestKey := key(best)
	for _, x := range xs[1:] {
		if k := key(x); k > bestKey {
			best, bestKey = x, k
		}
	}
	return best, true
}

type Order struct {
	ID       int
	Customer string
	Total    float64
}

func main() {
	orders := []Order{{1, "asha", 499}, {2, "ravi", 2500}, {3, "meera", 80}}

	top, _ := MaxBy(orders, func(o Order) float64 { return o.Total })
	fmt.Printf("biggest order: %+v\n", top)

	last, _ := MaxBy(orders, func(o Order) string { return o.Customer })
	fmt.Println("last name alphabetically:", last.Customer)

	_, ok := MaxBy([]Order{}, func(o Order) int { return o.ID })
	fmt.Println("empty ok?", ok)
}
  1. Three orders.
  2. T = Order from the slice and K = float64 from the key func's return type. We seed best with the first element.
  3. 2500 > 499, so order 2 becomes the best. K must be cmp.Ordered for that > to compile.
  4. 80 is smaller, nothing changes. Return order 2 and true.
  5. The caller gets a real Order back, no type assertion.
  6. Same function, now K = string. "ravi" > "asha" so ravi wins; "meera" < "ravi" so it stays.
  7. The last name alphabetically.
  8. Empty input: we return the zero Order and false before touching xs[0], which would have panicked.
  9. The caller checks ok.
biggest order: {ID:2 Customer:ravi Total:2500}
last name alphabetically: ravi
empty ok? false

Two type parameters: T for the element (anything) and K for the key (must be ordered). The stdlib equivalent is slices.MaxFunc with a comparison function.

Exercise 2: A concurrency-safe generic Cache with an iterator

Build Cache[K, V] with Set, Get (comma-ok) and an All() iter.Seq2[K, V] that yields entries in sorted key order. It must be safe to use from multiple goroutines, and callers must not hold the lock while their loop body runs.

Solution
package main

import (
	"cmp"
	"fmt"
	"iter"
	"maps"
	"slices"
	"sync"
)

// Cache is a concurrency-safe map with typed keys and values.
type Cache[K cmp.Ordered, V any] struct {
	mu sync.RWMutex
	m  map[K]V
}

func NewCache[K cmp.Ordered, V any]() *Cache[K, V] {
	return &Cache[K, V]{m: make(map[K]V)}
}

func (c *Cache[K, V]) Set(k K, v V) {
	c.mu.Lock()
	defer c.mu.Unlock()
	c.m[k] = v
}

func (c *Cache[K, V]) Get(k K) (V, bool) {
	c.mu.RLock()
	defer c.mu.RUnlock()
	v, ok := c.m[k]
	return v, ok
}

// All iterates over a sorted snapshot, so callers never hold the lock.
func (c *Cache[K, V]) All() iter.Seq2[K, V] {
	c.mu.RLock()
	keys := slices.Sorted(maps.Keys(c.m))
	snap := maps.Clone(c.m)
	c.mu.RUnlock()
	return func(yield func(K, V) bool) {
		for _, k := range keys {
			if !yield(k, snap[k]) {
				return
			}
		}
	}
}

type Customer struct{ Name, City string }

func main() {
	customers := NewCache[int, Customer]()
	customers.Set(2, Customer{"Ravi", "Delhi"})
	customers.Set(1, Customer{"Asha", "Pune"})

	if c, ok := customers.Get(1); ok {
		fmt.Println("hit:", c.Name)
	}
	_, ok := customers.Get(99)
	fmt.Println("99 cached?", ok)

	for id, c := range customers.All() {
		fmt.Printf("%d → %s (%s)\n", id, c.Name, c.City)
	}
}
hit: Asha
99 cached? false
1 → Asha (Pune)
2 → Ravi (Delhi)

Taking a snapshot under the read lock and then iterating it means a slow loop body (or one that calls Set!) can't block or deadlock the cache. K is cmp.Ordered rather than just comparable because we sort keys.

Exercise 3: Batch orders with an iterator

Write Batch[T any](xs []T, size int) iter.Seq[[]T] that yields consecutive chunks of at most size elements, e.g. to send order IDs to an API 3 at a time. Then compare with the stdlib.

Solution
package main

import (
	"fmt"
	"iter"
	"slices"
)

// Batch yields consecutive sub-slices of at most size elements.
func Batch[T any](xs []T, size int) iter.Seq[[]T] {
	return func(yield func([]T) bool) {
		if size <= 0 {
			return
		}
		for start := 0; start < len(xs); start += size {
			end := min(start+size, len(xs))
			if !yield(xs[start:end:end]) { // full slice expr: caps the batch
				return
			}
		}
	}
}

func main() {
	orderIDs := []int{101, 102, 103, 104, 105, 106, 107}
	for batch := range Batch(orderIDs, 3) {
		fmt.Println("sending batch:", batch)
	}

	// The stdlib has this built in since Go 1.23:
	for batch := range slices.Chunk(orderIDs, 3) {
		fmt.Print(len(batch), " ")
	}
	fmt.Println()
}
  1. Batch doesn't loop yet. It returns an iter.Seq[[]int]: a function that takes a yield callback. The range then calls it, passing the loop body as yield.
  2. First batch: xs[0:3:3]. The third index caps the capacity at 3, so a caller's append can't overwrite element 104.
  3. yield runs the loop body. It returns true, meaning "keep going".
  4. Back inside the iterator, start advances by 3.
  5. min(9, 7) is 7, so the last batch is short.
  6. 9 is not < 7, so the iterator function returns and the range loop ends.
  7. slices.Chunk does the same thing from the standard library. We print each chunk's length with Print, which adds no newline.
  8. Println() ends the line. Note the trailing space after the last length.
sending batch: [101 102 103]

sending batch: [107]
3 3 1

The three-index slice xs[start:end:end] caps each batch's capacity, so if a caller appends to a batch it can't overwrite the next batch's elements. slices.Chunk does the same thing.

Key takeaways

  • Type parameters ([T Constraint]) let one function or type work across many types with full compile-time checking.
  • Constraints are interfaces: any, comparable, cmp.Ordered, unions like ~int | ~float64, and method requirements. Use ~ so named types like Rupees fit.
  • Type inference usually fills in type arguments; specify them when a parameter appears only in the result.
  • Generic types (Stack[T], Set[T], Pair[K, V]) are written with their parameters everywhere, including receivers.
  • Go 1.27 adds generic methods, but interface methods can't be generic, so generic methods never satisfy interfaces.
  • var zero T is the zero value of any T; return it with a bool or error.
  • Iterators (iter.Seq[T], range-over-func) are the idiomatic way to let callers loop over generic collections. Always respect yield's return value.
  • Same code, different types → generics. Different behaviour per type → interfaces. Write concrete code first.
  • Go compiles one copy per GC shape plus a dictionary: operators are free, method calls on T cost about as much as interface calls.

Data races: the bug you can't see

In the last chapter you learned to start goroutines. The moment two goroutines touch the same variable, a new kind of bug appears. A data race happens when two goroutines access the same memory at the same time, and at least one of them is writing, with nothing coordinating them.

Why is that a problem? Because even something tiny like counter++ is not one step. The CPU does three: read the value, add one, write it back. If two goroutines interleave those steps, one update gets lost.

package main

import (
	"fmt"
	"sync"
)

func main() {
	counter := 0
	var wg sync.WaitGroup

	for range 1000 {
		wg.Add(1)
		go func() {
			defer wg.Done()
			counter++ // read, add, write: three steps, not one!
		}()
	}

	wg.Wait()
	fmt.Println("counter =", counter)
}

Run it a few times. You'll get a different wrong answer each time (and sometimes, by luck, the right one — which is what makes races so nasty):

$ go run ./race
counter = 981
$ go run ./race
counter = 983
$ go run ./race
counter = 977
// counter starts at 41. Goroutines A and B both run counter++.
// The CPU really does three separate steps for each:

// goroutine A                 // goroutine B
a := counter     // read
                               b := counter     // read
a = a + 1        // add
                               b = b + 1        // add
counter = a      // write
                               counter = b      // write

// Two increments happened... but counter is 42, not 43.
  1. Both goroutines want to add one. We expect the result to be 43.
  2. Goroutine A reads counter into its private register: 41.
  3. Before A writes, the scheduler runs B. B also reads 41. This is the fatal moment.
  4. A adds one in its own copy: 42.
  5. B adds one in its own copy: also 42.
  6. A writes 42 back.
  7. B writes 42 back, overwriting A's work with the same number.
  8. Two increments ran, one was lost. Multiply this by 1000 goroutines and you get 971 instead of 1000.

Senior engineer tip

Run your test suite with go test -race ./... in CI on every pull request. The detector only finds races that actually happen during the run, so it needs code paths exercised — tests are perfect for that. It slows code down roughly 2–10x and uses more memory, so don't ship -race binaries to production, but do run a canary or load test with it now and then.

Gotcha: "it works on my machine"

A race may not show up for months, then corrupt data under production load. There is no such thing as a "benign" data race in Go: the memory model says a racy program can behave in any way, including torn reads of multi-word values like strings, slices and interfaces (which can crash). Fix every race the detector reports.

Mental model

Shared memory is a whiteboard in a shared office. A race is two people erasing and writing on the same spot at once. You have two fixes: give the marker to one person at a time (a mutex), or stop sharing the whiteboard and pass notes instead (a channel). Go's proverb: "Don't communicate by sharing memory; share memory by communicating." But both are legitimate tools.

sync.WaitGroup: waiting for a group of goroutines

main doesn't wait for goroutines. When main returns, the program exits, even if goroutines are mid-work. A sync.WaitGroup is a thread-safe counter that lets one goroutine wait for others to finish. It has three methods:

  • Add(n) — "n more goroutines are about to start."
  • Done() — "one goroutine finished" (same as Add(-1)).
  • Wait() — block until the counter reaches zero.
package main

import (
	"fmt"
	"sync"
	"time"
)

func download(name string, d time.Duration) {
	time.Sleep(d)
	fmt.Println("downloaded", name)
}

func main() {
	files := map[string]time.Duration{
		"a.txt": 30 * time.Millisecond,
		"b.txt": 10 * time.Millisecond,
		"c.txt": 20 * time.Millisecond,
	}

	var wg sync.WaitGroup
	start := time.Now()

	for name, d := range files {
		wg.Add(1) // 1. count BEFORE starting the goroutine
		go func() {
			defer wg.Done() // 2. always signal, even on panic/early return
			download(name, d)
		}()
	}

	wg.Wait() // 3. block until the counter is back to zero
	fmt.Printf("all done in ~%dms\n", time.Since(start).Round(10*time.Millisecond).Milliseconds())
}
downloaded b.txt
downloaded c.txt
downloaded a.txt
all done in ~30ms

The three downloads ran at the same time, so the total time is about the slowest one (30ms), not the sum (60ms).

var wg sync.WaitGroup

for i := range 3 {
	wg.Add(1)
	go func() {
		defer wg.Done()
		fmt.Println("job", i)
	}()
}

wg.Wait()
fmt.Println("all jobs finished")
  1. A zero WaitGroup is ready to use. Its counter is 0.
  2. First iteration: Add(1) happens in main, before the goroutine exists.
  3. The goroutine is started. It may not have run yet — that's fine, the counter already accounts for it.
  4. After the loop, three goroutines are in flight and the counter is 3. (Since Go 1.22, each iteration has its own i, so every goroutine sees its own value.)
  5. Main reaches Wait() and blocks.
  6. A goroutine runs (scheduling order is not guaranteed!), prints, and its deferred Done() drops the counter to 2.
  7. Another finishes. Counter is 1.
  8. The last one finishes. The counter hits 0, and Wait() wakes main.
  9. Main continues. Every job is guaranteed to have finished before this line.
Gotcha: Add inside the goroutine

If you call wg.Add(1) inside the goroutine, main may reach Wait() before any goroutine has run, see a counter of 0, and return immediately. Always Add before the go statement. Also: never copy a WaitGroup (pass *sync.WaitGroup), and never let the counter go negative — that panics.

wg.Go (Go 1.25+): the easy way

Because forgetting Add or Done is so common, Go 1.25 added WaitGroup.Go(f). It does Add(1), starts f in a goroutine, and calls Done when f returns. Use it in new code; you'll still see the classic form everywhere.

package main

import (
	"fmt"
	"sync"
)

func main() {
	var wg sync.WaitGroup
	results := make([]int, 5)

	for i := range 5 {
		// Go 1.25+: wg.Go does Add(1), starts the goroutine, and calls Done for you.
		wg.Go(func() {
			results[i] = i * i // each goroutine writes its OWN index: no race
		})
	}

	wg.Wait()
	fmt.Println(results)
}
  1. A zero-value WaitGroup is ready to use. results is pre-sized to 5, so every goroutine has its own slot waiting.
  2. wg.Go does Add(1) for us and starts a goroutine. Since Go 1.22 each iteration has its own i, so the closure captures 0.
  3. The loop runs to i=4 almost instantly. Five goroutines exist, but none may have run yet: the counter is 5.
  4. The goroutines run in any order. In one representative run, goroutines 2 and 4 finish first and write their squares. When each closure returns, wg.Go calls Done.
  5. The rest finish. No mutex is needed: each goroutine writes a different index, so nobody touches the same memory.
  6. wg.Wait() blocks main until the counter hits zero. This is also what makes the writes visible to main.
  7. The slice is printed. The order of execution varied, but the result is always the same because each slot is fixed by its index.
[0 1 4 9 16]

Notice the pattern in wggo: each goroutine writes to results[i], its own slot. Different elements of a slice are different memory locations, so this is race-free without a lock. Appending to a shared slice, however, is a race — append reads and writes the slice header.

sync.Mutex and RWMutex: one at a time, please

A mutex ("mutual exclusion") is a lock. Only one goroutine can hold it. Everyone else calling Lock() waits until the holder calls Unlock(). The code between Lock and Unlock is called the critical section. Its zero value is an unlocked mutex, ready to use.

The idiomatic way is to put the mutex inside the struct it protects, right above the fields it guards, and keep it unexported so callers can't misuse it:

package main

import (
	"fmt"
	"sync"
)

// Account is safe for concurrent use.
// The mutex sits right above the fields it protects (a common convention).
type Account struct {
	mu      sync.Mutex
	balance int
	history []string
}

func (a *Account) Deposit(amount int) {
	a.mu.Lock()
	defer a.mu.Unlock() // runs even if something below panics

	a.balance += amount
	a.history = append(a.history, fmt.Sprintf("+%d", amount))
}

func (a *Account) Withdraw(amount int) error {
	a.mu.Lock()
	defer a.mu.Unlock()

	if amount > a.balance {
		return fmt.Errorf("insufficient funds: have %d, want %d", a.balance, amount)
	}
	a.balance -= amount
	a.history = append(a.history, fmt.Sprintf("-%d", amount))
	return nil
}

func (a *Account) Balance() int {
	a.mu.Lock()
	defer a.mu.Unlock()
	return a.balance
}

func main() {
	acc := &Account{}
	var wg sync.WaitGroup

	for range 100 {
		wg.Go(func() { acc.Deposit(10) })
	}
	wg.Wait()

	fmt.Println("balance:", acc.Balance())
	fmt.Println(acc.Withdraw(5000))
	fmt.Println(acc.Withdraw(400), "->", acc.Balance())
}
  1. acc is a pointer, so every goroutine shares the same Account and the same mutex.
  2. The loop starts 100 goroutines, each calling Deposit(10). They all race to the lock.
  3. One goroutine wins Lock(); the other 99 block right here. defer Unlock() is registered so the lock is released even on panic.
  4. Inside the lock, the read-modify-write of balance and the append happen as one unit. Nobody else can see a half-done update.
  5. The function returns, the deferred Unlock fires, and the next waiting goroutine gets the lock.
  6. This repeats 99 more times, one at a time. Unlike the racy counter, no update is lost.
  7. wg.Wait() returns, then Balance() takes the lock just to read. Reads need the lock too, or they could see a torn value.
  8. Withdraw(5000): 5000 > 1000, so it returns an error. The deferred Unlock still runs on this early return.
  9. Withdraw(400) succeeds: balance drops to 600 and it returns nil.
  10. Arguments are evaluated left to right, so Balance() runs after the withdraw and sees 600. It locks again, which is fine: the withdraw already unlocked.
balance: 1000
insufficient funds: have 1000, want 5000
<nil> -> 600

Three details to notice:

  • defer a.mu.Unlock() right after Lock(). You can't forget to unlock on an early return (see Withdraw), and a panic won't leave the lock held forever. The cost of defer is now tiny (a couple of nanoseconds).
  • Pointer receivers everywhere. The mutex must not be copied (more on this below).
  • Even reads lock. Balance() takes the lock too. Reading while someone else writes is still a race.

RWMutex: many readers, one writer

sync.RWMutex has two modes. RLock/RUnlock is a shared lock: any number of readers can hold it together. Lock/Unlock is exclusive: a writer waits until all readers leave, and while it holds the lock, nobody else gets in. Perfect for read-heavy caches.

package main

import (
	"fmt"
	"sync"
)

// Cache: many readers, few writers. RWMutex lets readers share the lock.
type Cache struct {
	mu   sync.RWMutex
	data map[string]string
}

func NewCache() *Cache {
	return &Cache{data: make(map[string]string)}
}

func (c *Cache) Get(key string) (string, bool) {
	c.mu.RLock() // shared: many goroutines can hold RLock at once
	defer c.mu.RUnlock()
	v, ok := c.data[key]
	return v, ok
}

func (c *Cache) Set(key, value string) {
	c.mu.Lock() // exclusive: waits for all readers to leave
	defer c.mu.Unlock()
	c.data[key] = value
}

func main() {
	c := NewCache()
	c.Set("lang", "Go")

	var wg sync.WaitGroup
	var hitsMu sync.Mutex
	hits := 0

	for range 50 {
		wg.Go(func() {
			if _, ok := c.Get("lang"); ok {
				hitsMu.Lock()
				hits++
				hitsMu.Unlock()
			}
		})
	}
	wg.Go(func() { c.Set("version", "1.27") })
	wg.Wait()

	v, _ := c.Get("version")
	fmt.Println("hits:", hits, "version:", v)
}
  1. NewCache builds the map (a nil map would panic on write).
  2. Set takes the exclusive lock and stores lang. Nobody else is around yet.
  3. 50 reader goroutines start. Exact interleaving varies run to run.
  4. Each reader calls Get, which takes RLock. Many readers can hold it at the same time, so reads do not queue behind each other.
  5. hits is a plain int touched by many goroutines, so it gets its own mutex. The RLock on the cache does not protect it.
  6. The writer goroutine calls Set. Lock waits until current readers leave, writes, and unlocks. New readers wait while a writer is pending.
  7. After Wait, all 50 readers found lang (it was set before any started).
  8. Main reads version. Because Wait ran first, the writer has definitely finished.
hits: 50 version: 1.27
Senior engineer tip

Don't reach for RWMutex by default. It has more bookkeeping than Mutex, so for short critical sections (a map lookup) a plain Mutex is often as fast or faster. Use RWMutex when reads vastly outnumber writes and the read section does real work. Measure with a benchmark (Chapter 15) before switching. Also: keep critical sections short — never do network I/O, disk I/O, or channel sends while holding a lock.

The copied-mutex gotcha (and go vet)

A Mutex is a plain struct holding some state. If you copy a struct that contains one, you copy the lock state too, and the two copies are completely unrelated locks. The most common way to do this by accident is a value receiver:

package main

import (
	"fmt"
	"sync"
)

type Counter struct {
	mu sync.Mutex
	n  int
}

// BUG: value receiver copies the whole struct, including the mutex.
// Each call locks its own private copy, so nothing is protected.
func (c Counter) Inc() {
	c.mu.Lock()
	c.n++
	c.mu.Unlock()
}

func main() {
	var c Counter
	c.Inc()
	c.Inc()
	fmt.Println(c.n) // prints 0: increments happened on copies
}
  1. var c Counter creates one struct holding a mutex and n=0. So far so good.
  2. Calling c.Inc() on a value receiver copies the whole struct into the parameter c inside Inc, mutex included.
  3. The copy's mutex is locked, the copy's n goes to 1, and the copy is unlocked. The original was never touched.
  4. When Inc returns, the copy is thrown away, and its n=1 with it.
  5. The second call makes a fresh copy (still n=0), bumps it to 1, and discards it again.
  6. We print the original: 0. The fix is a pointer receiver, func (c *Counter) Inc(). go vet flags this as "passes lock by value".

Go's sync.Mutex is not re-entrant: it has no idea which goroutine holds it. The second Lock() waits forever for an Unlock() that can never come. The usual fix is an unexported helper (countLocked()) that assumes the caller already holds the lock.

sync.Once and friends: exactly once, safely

Some work should happen exactly one time: loading config, opening a database pool, compiling a big regex. If many goroutines might ask for it at the same moment, a plain if cfg == nil { load() } is a race. sync.Once guarantees the function runs once, and every other caller waits until that one run has finished.

Since Go 1.21 there are three helpers that wrap the pattern even more neatly:

  • sync.OnceFunc(f) → returns a function that runs f only the first time.
  • sync.OnceValue(f) → returns a function that computes a value once and caches it.
  • sync.OnceValues(f) → same, for (value, error).
package main

import (
	"fmt"
	"os"
	"sync"
)

type Config struct{ Env string }

// 1. Classic sync.Once: run setup exactly once, no matter how many callers.
var (
	cfgOnce sync.Once
	cfg     *Config
)

func GetConfig() *Config {
	cfgOnce.Do(func() {
		fmt.Println("  (loading config...)")
		cfg = &Config{Env: "prod"}
	})
	return cfg
}

// 2. sync.OnceValue (Go 1.21+): a function that computes a value once and caches it.
var hostname = sync.OnceValue(func() string {
	fmt.Println("  (looking up hostname...)")
	return "build-box-01"
})

// 3. sync.OnceValues: same, but for (value, error) pairs.
var readMotd = sync.OnceValues(func() ([]byte, error) {
	fmt.Println("  (reading file...)")
	return os.ReadFile("/does/not/exist")
})

// 4. sync.OnceFunc: wrap a side-effecting func so it only ever runs once.
var closeLogs = sync.OnceFunc(func() { fmt.Println("  (logs flushed and closed)") })

func main() {
	var wg sync.WaitGroup
	for range 10 {
		wg.Go(func() { GetConfig() })
	}
	wg.Wait()
	fmt.Println("env:", GetConfig().Env)

	fmt.Println("host:", hostname())
	fmt.Println("host:", hostname())

	_, err := readMotd()
	_, err2 := readMotd()
	fmt.Println("err:", err)
	fmt.Println("same error cached:", err == err2)

	closeLogs()
	closeLogs() // safe: does nothing the second time
}
  (loading config...)
env: prod
  (looking up hostname...)
host: build-box-01
host: build-box-01
  (reading file...)
err: open /does/not/exist: no such file or directory
same error cached: true
  (logs flushed and closed)

Ten goroutines called GetConfig() but "loading config" printed once. hostname() computed once and returned the cached value after. readMotd cached the error too — the file is never re-read.

Gotcha

Once doesn't retry. If the first call fails (like the file read above), every later caller gets that same failure. If you need "retry until success", use a mutex and a flag instead. And if the function passed to Do panics, Once considers it done (OnceFunc/OnceValue re-panic with the same value on every call).

sync/atomic: lock-free counters and flags

Atomic operations are single, indivisible CPU instructions: "add one to this number" happens as one step that nobody can interrupt. They're the fastest way to share a simple counter or flag. Since Go 1.19, use the typed atomics — atomic.Int32, atomic.Int64, atomic.Uint64, atomic.Bool, atomic.Pointer[T], atomic.Value — instead of the old functions like atomic.AddInt64(&x, 1). Typed atomics can't accidentally be read non-atomically, and they're automatically aligned correctly (an old trap on 32-bit platforms).

package main

import (
	"fmt"
	"sync"
	"sync/atomic"
)

type Stats struct {
	requests atomic.Int64 // typed atomics: the zero value is ready to use
	errors   atomic.Int64
	healthy  atomic.Bool
}

type Settings struct {
	MaxConns int
}

func main() {
	var s Stats
	s.healthy.Store(true)

	var wg sync.WaitGroup
	for i := range 1000 {
		wg.Go(func() {
			s.requests.Add(1)
			if i%10 == 0 {
				s.errors.Add(1)
			}
		})
	}
	wg.Wait()
	fmt.Println("requests:", s.requests.Load(), "errors:", s.errors.Load(), "healthy:", s.healthy.Load())

	// CompareAndSwap: "set it to new ONLY IF it is still old".
	var state atomic.Int32 // 0 = idle, 1 = running
	fmt.Println("start #1:", state.CompareAndSwap(0, 1))
	fmt.Println("start #2:", state.CompareAndSwap(0, 1)) // already running

	// atomic.Pointer[T]: swap a whole immutable config in one step.
	var current atomic.Pointer[Settings]
	current.Store(&Settings{MaxConns: 10})
	old := current.Swap(&Settings{MaxConns: 50})
	fmt.Println("old:", old.MaxConns, "new:", current.Load().MaxConns)
}
  1. The zero value of every typed atomic is ready. Store(true) sets healthy in one indivisible step.
  2. 1000 goroutines start. Each does requests.Add(1), a single CPU instruction, so no increment is lost (unlike plain counter++).
  3. Goroutine i=0 is a multiple of 10, so it also bumps errors. Order across goroutines varies run to run; the totals do not.
  4. After Wait, all 1000 adds have landed: 100 of the indexes (0, 10, ... 990) counted an error.
  5. CompareAndSwap(0, 1): state is 0, so it becomes 1 and returns true. Exactly one caller can ever win this.
  6. The second CAS expects 0 but finds 1, so nothing changes and it returns false: "already running".
  7. atomic.Pointer[Settings] holds a pointer to an immutable config.
  8. Swap installs the new config and hands back the old one, atomically. Readers see either the old or the new, never a mix.
  9. Both values are printed.
requests: 1000 errors: 100 healthy: true
start #1: true
start #2: false
old: 10 new: 50

CompareAndSwap (CAS) is the building block of all lock-free code: "if the value is still old, set it to new and return true; otherwise do nothing and return false." It's a safe way to say "only one goroutine gets to start this."

atomic.Pointer[T] lets you swap a whole immutable struct in one step. Readers always see either the old config or the new one, never half of each. This is a great pattern for hot-reloadable config.

Senior engineer tip

Atomics are for one independent value. As soon as two values must change together ("increment count AND append to history"), use a mutex. Two atomics updated one after the other are each safe, but the pair isn't consistent — a reader can see the new count with the old history. Most bugs in "clever" lock-free code come from this.

sync.Map and sync.Cond: specialised tools

sync.Map

A regular Go map is not safe for concurrent writes (the runtime will often crash with fatal error: concurrent map writes). Usually you fix that with a map plus a Mutex, like the cache above. sync.Map is a built-in concurrent map, but it's untyped (any keys and values) and it's tuned for two specific cases:

  1. Keys are written once and read many times (e.g., a cache that only grows).
  2. Many goroutines read, write and overwrite disjoint sets of keys.
package main

import (
	"fmt"
	"sync"
)

func main() {
	var m sync.Map // zero value is ready; keys and values are 'any'

	var wg sync.WaitGroup
	for i := range 5 {
		wg.Go(func() {
			m.Store(i, i*100)
		})
	}
	wg.Wait()

	v, ok := m.Load(3)
	fmt.Println("load 3:", v, ok)

	// LoadOrStore: "give me the existing value, or store mine".
	actual, loaded := m.LoadOrStore(3, 999)
	fmt.Println("LoadOrStore 3:", actual, "already there:", loaded)
	actual, loaded = m.LoadOrStore(7, 700)
	fmt.Println("LoadOrStore 7:", actual, "already there:", loaded)

	m.Delete(0)

	count := 0
	m.Range(func(k, v any) bool {
		count++
		return true // return false to stop early
	})
	fmt.Println("entries:", count)

	// You must type-assert values back out.
	if v, ok := m.Load(7); ok {
		n := v.(int)
		fmt.Println("7 as int + 1 =", n+1)
	}
}
  1. A zero-value sync.Map is ready. Keys and values are typed any.
  2. Five goroutines each Store one key at the same time. Plain maps would crash with "concurrent map writes"; sync.Map is safe.
  3. Load(3) finds the value 300 stored by goroutine 3.
  4. Key 3 already exists, so LoadOrStore ignores our 999 and returns the existing 300 with loaded=true.
  5. Key 7 is new, so 700 is stored and returned with loaded=false. This check-and-insert is atomic.
  6. Delete(0) removes key 0.
  7. Range calls our func once per entry. There is no Len(), so counting means ranging. 5 entries remain.
  8. Values come back as any, so we type-assert with v.(int) before doing arithmetic.
load 3: 300 true
LoadOrStore 3: 300 already there: true
LoadOrStore 7: 700 already there: false
entries: 5
7 as int + 1 = 701

Default to map + sync.Mutex (or RWMutex). It's typed, easier to reason about, and lets you do multi-step operations under one lock. Reach for sync.Map only when profiling shows lock contention and your access pattern matches one of the two cases above.

sync.Cond (briefly)

A condition variable lets goroutines sleep until some condition on shared state becomes true, and be woken by Signal() (one waiter) or Broadcast() (all waiters). Wait() atomically unlocks the mutex and sleeps, then re-locks it before returning. You almost always wait inside a for loop because the condition might have changed again by the time you wake up.

package main

import (
	"fmt"
	"sync"
	"time"
)

// A tiny bounded queue: consumers wait on a Cond until items appear.
type Queue struct {
	mu    sync.Mutex
	cond  *sync.Cond
	items []string
}

func NewQueue() *Queue {
	q := &Queue{}
	q.cond = sync.NewCond(&q.mu)
	return q
}

func (q *Queue) Put(item string) {
	q.mu.Lock()
	q.items = append(q.items, item)
	q.mu.Unlock()
	q.cond.Signal() // wake ONE waiter
}

func (q *Queue) Get() string {
	q.mu.Lock()
	defer q.mu.Unlock()
	for len(q.items) == 0 { // ALWAYS loop: re-check after waking
		q.cond.Wait() // unlocks mu, sleeps, re-locks mu on wake
	}
	item := q.items[0]
	q.items = q.items[1:]
	return item
}

func main() {
	q := NewQueue()
	done := make(chan struct{})

	go func() {
		for range 3 {
			fmt.Println("got", q.Get())
		}
		close(done)
	}()

	for _, s := range []string{"a", "b", "c"} {
		time.Sleep(10 * time.Millisecond)
		q.Put(s)
	}
	<-done
}
got a
got b
got c

In Go, channels cover nearly every case where other languages use condition variables, and they compose with select and timeouts (a Cond.Wait can't be cancelled). You will rarely write sync.Cond in application code. It's good to recognise it when you read library code.

Pattern: the worker pool

Imagine 10,000 images to resize. Starting 10,000 goroutines works but might open 10,000 files at once and exhaust memory. A worker pool starts a fixed number of workers that all pull jobs from one shared channel. It's like a bank with three tellers and one queue: customers (jobs) wait in line, and whichever teller is free takes the next one.

package main

import (
	"fmt"
	"sync"
	"time"
)

type Job struct {
	ID int
	N  int
}

type Result struct {
	JobID  int
	Square int
	Worker int
}

func worker(id int, jobs <-chan Job, results chan<- Result) {
	for j := range jobs { // loop ends when 'jobs' is closed and drained
		time.Sleep(10 * time.Millisecond) // pretend this is real work
		results <- Result{JobID: j.ID, Square: j.N * j.N, Worker: id}
	}
}

func main() {
	const numWorkers = 3
	const numJobs = 9

	jobs := make(chan Job)
	results := make(chan Result)

	// 1. Start a FIXED number of workers.
	var wg sync.WaitGroup
	for w := 1; w <= numWorkers; w++ {
		wg.Go(func() { worker(w, jobs, results) })
	}

	// 2. Feed jobs from a separate goroutine, then close to say "no more".
	go func() {
		for i := 1; i <= numJobs; i++ {
			jobs <- Job{ID: i, N: i}
		}
		close(jobs)
	}()

	// 3. Close results once every worker has returned.
	go func() {
		wg.Wait()
		close(results)
	}()

	// 4. Collect.
	start := time.Now()
	sum := 0
	perWorker := map[int]int{}
	for r := range results {
		sum += r.Square
		perWorker[r.Worker]++
	}
	fmt.Println("sum of squares:", sum)
	fmt.Println("jobs per worker:", perWorker)
	fmt.Printf("took ~%dms (9 jobs x 10ms / 3 workers)\n", time.Since(start).Round(10*time.Millisecond).Milliseconds())
}
sum of squares: 285
jobs per worker: map[1:3 2:3 3:3]
took ~30ms (9 jobs x 10ms / 3 workers)

The four-step shape is worth memorising: start workers → feed and close jobs → close results after wg.Wait() → range over results. The goroutine that closes results is the key trick: only it knows when every worker is done, so only it may close.

jobs := make(chan int)
results := make(chan int)

for range 2 { // two workers
	go func() {
		for j := range jobs {
			results <- j * 10
		}
	}()
}

go func() {
	for i := 1; i <= 3; i++ {
		jobs <- i
	}
	close(jobs)
}()

for range 3 {
	fmt.Println(<-results)
}
  1. Two unbuffered channels. A send blocks until someone receives.
  2. Two workers start. Each blocks in range jobs because nothing has been sent yet.
  3. The feeder sends job 1. Exactly one worker receives it — say W1.
  4. W1 tries to send 10 on results (blocks until main reads). Meanwhile the feeder sends job 2 to the free W2.
  5. Main receives 10 and prints it. W1 is free again and goes back to range jobs.
  6. The feeder sends job 3; W1 grabs it.
  7. The feeder closes jobs: "no more work". Workers' range loops will end once they come back for more.
  8. Main receives W2's 20.
  9. Main receives W1's 30. Both workers find jobs closed and empty, so they exit. (Order of results can differ between runs.)

Pattern: fan-out, fan-in and pipelines

Fan-out and fan-in

Fan-out means several goroutines read from the same channel, splitting the work between them. Fan-in (also called merge) means combining several channels into one. Together they let you parallelise one slow step of a process.

package main

import (
	"fmt"
	"sync"
)

// producer: emits numbers on a channel it owns and closes.
func gen(nums ...int) <-chan int {
	out := make(chan int)
	go func() {
		defer close(out)
		for _, n := range nums {
			out <- n
		}
	}()
	return out
}

// stage worker: squares whatever it reads.
func square(id int, in <-chan int) <-chan string {
	out := make(chan string)
	go func() {
		defer close(out)
		for n := range in {
			out <- fmt.Sprintf("w%d: %d^2=%d", id, n, n*n)
		}
	}()
	return out
}

// merge = fan-in: many channels in, one channel out.
func merge(chans ...<-chan string) <-chan string {
	out := make(chan string)
	var wg sync.WaitGroup
	for _, c := range chans {
		wg.Go(func() {
			for v := range c {
				out <- v
			}
		})
	}
	go func() {
		wg.Wait()
		close(out)
	}()
	return out
}

func main() {
	in := gen(1, 2, 3, 4, 5, 6)

	// fan-out: three workers read from the SAME input channel.
	w1 := square(1, in)
	w2 := square(2, in)
	w3 := square(3, in)

	count := 0
	for line := range merge(w1, w2, w3) {
		fmt.Println(line)
		count++
	}
	fmt.Println("total:", count)
}
w1: 1^2=1
w1: 3^2=9
w3: 2^2=4
w3: 5^2=25
w1: 4^2=16
w3: 6^2=36
total: 6

Notice that worker 2 got nothing in this run: whichever worker is free first gets the next value. That's the point — work goes to whoever is ready.

Pipelines

A pipeline is a chain of stages connected by channels, like an assembly line. Each stage is a function that takes an input channel and returns an output channel. It owns its output: it creates it, writes to it, and closes it when its input is exhausted. Closing ripples down the line, so the whole pipeline shuts down cleanly once the source runs out.

package main

import (
	"fmt"
	"strings"
)

// Each stage: reads from 'in', writes to its own 'out', closes 'out' when done.

func source(words []string) <-chan string {
	out := make(chan string)
	go func() {
		defer close(out)
		for _, w := range words {
			out <- w
		}
	}()
	return out
}

func filterShort(in <-chan string, min int) <-chan string {
	out := make(chan string)
	go func() {
		defer close(out)
		for w := range in {
			if len(w) >= min {
				out <- w
			}
		}
	}()
	return out
}

func upper(in <-chan string) <-chan string {
	out := make(chan string)
	go func() {
		defer close(out)
		for w := range in {
			out <- strings.ToUpper(w)
		}
	}()
	return out
}

func main() {
	words := []string{"go", "is", "simple", "and", "concurrent", "by", "design"}

	// source -> filterShort -> upper -> main
	for w := range upper(filterShort(source(words), 3)) {
		fmt.Println(w)
	}
}
  1. The innermost call runs first: source(words) makes an unbuffered channel, starts a goroutine, and returns the channel immediately. Nothing has been sent yet.
  2. filterShort wires a second goroutine that ranges over source's channel. It returns its own out.
  3. Then upper wires a third goroutine. Main now ranges over upper's output. Four goroutines, three channels, all connected.
  4. Source sends "go". Unbuffered sends wait for a receiver, so this hands off directly to the filter. Length 2 < 3: dropped.
  5. "is" is also too short and dropped.
  6. "simple" passes the filter, upper turns it into "SIMPLE", and main prints it. Each value is handed down one stage at a time.
  7. "and" has length 3, which passes >= 3.
  8. "concurrent" flows through. Stages run concurrently: source may already be sending the next word.
  9. "by" is dropped, and "design" makes it to main.
  10. Source runs out of words; its deferred close(out) ends filter's range, whose close ends upper's range, whose close ends main's loop. The shutdown ripples down the chain.
SIMPLE
AND
CONCURRENT
DESIGN

Each stage runs concurrently: while upper is converting "simple", filterShort can already be checking "and". Stages compose like functions, and you can fan-out any slow stage.

Gotcha: leaking pipeline goroutines

If main stops reading early (say, it only wanted the first result), every upstream stage blocks forever on its send. Those goroutines leak. Real pipelines pass a context.Context (next chapter) and each send becomes select { case out <- v: case <-ctx.Done(): return } so the consumer can tell everyone to stop.

Pattern: limiting concurrency and rate

Bounded parallelism with a semaphore channel

Sometimes you do want a goroutine per task (simple code), but you need to limit how many run at once — maybe the API you call allows only 3 concurrent requests. A buffered channel makes a perfect counting semaphore: its capacity is the number of slots. Sending takes a slot (and blocks when they're all taken); receiving gives one back.

package main

import (
	"fmt"
	"sync"
	"sync/atomic"
	"time"
)

func main() {
	const maxInFlight = 3
	sem := make(chan struct{}, maxInFlight) // a buffered channel = counting semaphore

	var inFlight, peak atomic.Int32
	var wg sync.WaitGroup

	for range 10 {
		wg.Go(func() {
			sem <- struct{}{}        // acquire: blocks when 3 are already running
			defer func() { <-sem }() // release

			now := inFlight.Add(1)
			for {
				p := peak.Load()
				if now <= p || peak.CompareAndSwap(p, now) {
					break
				}
			}
			time.Sleep(20 * time.Millisecond) // "call the API"
			inFlight.Add(-1)
		})
	}
	wg.Wait()
	fmt.Println("tasks: 10, peak concurrency:", peak.Load())
}
  1. A buffered channel with capacity 3 acts as a counting semaphore: each value in the buffer is one "slot in use".
  2. The loop launches all 10 goroutines immediately. Starting them is cheap; the semaphore decides how many do real work.
  3. Interleaving varies; this traces one representative run. Three goroutines manage to send into sem; the buffer is now full, so the other 7 block on line 19.
  4. Each running goroutine bumps inFlight and uses a CAS loop to raise peak only if its value is higher. Peak reaches 3.
  5. They "call the API" for 20ms, then decrement inFlight.
  6. Each function returns and its deferred <-sem frees a slot.
  7. Three of the waiting goroutines grab the freed slots. inFlight never goes above 3, so peak stays 3.
  8. The pattern repeats (3, then the last 1) until all 10 tasks are done.
  9. wg.Wait() returns and we print the peak: never more than 3 at once.
tasks: 10, peak concurrency: 3
sem := make(chan struct{}, 2) // capacity 2 = 2 slots

for i := range 3 {
	wg.Go(func() {
		sem <- struct{}{}        // take a slot (blocks if none free)
		defer func() { <-sem }() // give it back
		callAPI(i)
	})
}

  1. Buffered channel with capacity 2: two "slots".
  2. Three goroutines start (thanks to wg.Go).
  3. Task 0 sends into sem: there's room, so it continues immediately.
  4. Task 1 takes the second slot.
  5. Task 2 tries to send — the buffer is full, so it blocks. Only 2 API calls happen at once.
  6. Task 0 finishes callAPI; its deferred receive frees a slot.
  7. Task 2's send now succeeds, and it runs.
  8. All three finish and release their slots; wg.Wait() returns.

Worker pool or semaphore? A worker pool keeps N long-lived goroutines and is great when there is per-worker setup (a DB connection, a buffer). A semaphore is simpler when tasks are independent. There's also golang.org/x/sync/semaphore for weighted semaphores (e.g., "this job uses 3 units of memory") with context support.

Rate limiting with time.Ticker

Bounded parallelism limits how many at once. Rate limiting limits how many per second. A time.Ticker delivers a value on its channel C at a regular interval; waiting on it before each request spaces requests out evenly. Pre-filling a buffered channel with tokens allows a short burst first — a tiny "token bucket".

package main

import (
	"fmt"
	"time"
)

func main() {
	requests := []string{"r1", "r2", "r3", "r4", "r5"}

	// Allow one request every 50ms (= 20 per second).
	tick := time.NewTicker(50 * time.Millisecond)
	defer tick.Stop() // always stop tickers you create

	start := time.Now()
	for _, r := range requests {
		<-tick.C // wait for the next "token"
		fmt.Printf("%-3s at +%3dms\n", r, time.Since(start).Round(10*time.Millisecond).Milliseconds())
	}

	// Bursty limiter: a buffered channel pre-filled with 3 tokens.
	fmt.Println("-- bursty --")
	tokens := make(chan struct{}, 3)
	for range 3 {
		tokens <- struct{}{}
	}
	go func() {
		t := time.NewTicker(50 * time.Millisecond)
		defer t.Stop()
		for range t.C {
			select {
			case tokens <- struct{}{}:
			default: // bucket full, drop the token
			}
		}
	}()

	start = time.Now()
	for _, r := range requests {
		<-tokens
		fmt.Printf("%-3s at +%3dms\n", r, time.Since(start).Round(10*time.Millisecond).Milliseconds())
	}
}

Pattern: errgroup and graceful stop

errgroup — goroutines that can fail

A WaitGroup waits, but it doesn't collect errors or stop siblings when one fails. The errgroup package (from the official extended library golang.org/x/sync) does both. Install it with go get golang.org/x/sync (this chapter used v0.24.0).

  • g.Go(func() error) starts a goroutine.
  • g.Wait() waits for all of them and returns the first non-nil error.
  • errgroup.WithContext(ctx) gives you a context that's cancelled as soon as any goroutine fails, so the others can stop early.
  • g.SetLimit(n) caps how many goroutines run at once — g.Go blocks when the limit is reached. Bounded parallelism for free.
package main

import (
	"context"
	"fmt"
	"time"

	"golang.org/x/sync/errgroup"
)

func fetch(ctx context.Context, url string) (int, error) {
	select {
	case <-time.After(20 * time.Millisecond): // simulated network call
	case <-ctx.Done():
		return 0, ctx.Err() // stop early if a sibling already failed
	}
	if url == "https://bad.example" {
		return 0, fmt.Errorf("fetch %s: 503 service unavailable", url)
	}
	return len(url), nil
}

func main() {
	urls := []string{
		"https://a.example",
		"https://b.example",
		"https://bad.example",
		"https://c.example",
		"https://d.example",
	}

	g, ctx := errgroup.WithContext(context.Background())
	g.SetLimit(2) // at most 2 goroutines running at once

	sizes := make([]int, len(urls))
	for i, url := range urls {
		g.Go(func() error {
			n, err := fetch(ctx, url)
			if err != nil {
				return err
			}
			sizes[i] = n // each goroutine owns its own index
			return nil
		})
	}

	// Wait blocks until all goroutines return, then gives the FIRST error.
	if err := g.Wait(); err != nil {
		fmt.Println("error:", err)
	}
	fmt.Println("sizes:", sizes)
}
  1. WithContext returns a group and a ctx that is cancelled as soon as any goroutine returns an error. SetLimit(2) caps concurrency.
  2. Timing varies; this traces the run shown below. g.Go for a and b start right away. For the third URL, g.Go itself blocks main until a slot frees.
  3. After 20ms both fetches return len(url) = 17 and store it in their own index.
  4. Two slots freed, so main launches bad and c.
  5. bad waits 20ms then returns an error. errgroup records it as the first error and cancels ctx.
  6. c's timer fired at about the same moment, so its select took the time.After case and it stored 17.
  7. Main launches d. Its select sees ctx.Done() already closed and returns context.Canceled immediately, so its slot stays 0.
  8. Wait returns only the first error. d's "context canceled" is discarded.
  9. The slice shows which fetches finished. Use ctx inside each task so siblings stop early after a failure.
error: fetch https://bad.example: 503 service unavailable
sizes: [17 17 0 17 0]

Let's read the result: with a limit of 2, a and b ran first and succeeded (17 bytes each). Then bad and c ran together; bad failed, which cancelled ctx. c had already finished its 20ms wait at the same moment and stored its size; d started after the cancel and returned context.Canceled right away, so its slot stayed 0. Wait returned only the first error. (The exact pattern depends on timing; this one was stable across our runs.)

Without a context, the zero-value errgroup.Group is a WaitGroup that also collects errors:

package main

import (
	"fmt"

	"golang.org/x/sync/errgroup"
)

func main() {
	var g errgroup.Group // zero value: no context, no limit
	results := make([]string, 3)

	for i, name := range []string{"users", "orders", "invoices"} {
		g.Go(func() error {
			results[i] = "loaded " + name
			return nil
		})
	}

	if err := g.Wait(); err != nil {
		fmt.Println("error:", err)
		return
	}
	for _, r := range results {
		fmt.Println(r)
	}
}
  1. A zero-value errgroup.Group works like a WaitGroup that also collects errors.
  2. g.Go starts a goroutine for users. Each iteration has its own i and name (Go 1.22+).
  3. The loop finishes quickly: three goroutines are now running in some order.
  4. Each writes its own index and returns nil. The order they ran in does not matter: results land in fixed slots.
  5. Wait blocks until all three return. No one failed, so it returns nil and we skip the error branch.
  6. Back on main, we range over results in index order.
  7. Second entry.
  8. Third entry. Output order is deterministic even though execution order was not.

Senior engineer tip

errgroup.WithContext + SetLimit is the default answer to "fetch these N things concurrently, but not too many at once, and give up if any fails." It replaces a page of WaitGroup + mutex + error-channel code. One subtlety: the derived ctx is cancelled when Wait returns too, so don't keep using it afterwards.

Graceful stop

Long-running goroutines (background jobs, consumers, tickers) need a way to be told "please stop", and the owner needs a way to know "they have stopped." The classic recipe: a quit channel that you close (closing is a broadcast — every receiver wakes up) plus a WaitGroup to wait for cleanup.

package main

import (
	"fmt"
	"sync"
	"time"
)

type Worker struct {
	quit chan struct{}
	wg   sync.WaitGroup
}

func NewWorker() *Worker {
	return &Worker{quit: make(chan struct{})}
}

func (w *Worker) Start(n int) {
	for id := 1; id <= n; id++ {
		w.wg.Go(func() {
			tick := time.NewTicker(15 * time.Millisecond)
			defer tick.Stop()
			for {
				select {
				case <-tick.C:
					// do one unit of work
				case <-w.quit:
					fmt.Printf("worker %d: cleaning up\n", id)
					return
				}
			}
		})
	}
}

// Stop signals every worker (close = broadcast) and waits for them to finish.
func (w *Worker) Stop() {
	close(w.quit)
	w.wg.Wait()
}

func main() {
	w := NewWorker()
	w.Start(3)
	time.Sleep(50 * time.Millisecond)

	fmt.Println("main: stopping")
	w.Stop()
	fmt.Println("main: all workers stopped")
}
main: stopping
worker 1: cleaning up
worker 3: cleaning up
worker 2: cleaning up
main: all workers stopped

In modern code, the quit channel is usually replaced by a context.Context: case <-ctx.Done():. It's the same idea, standardised across every library. That's exactly what the next chapter is about.

You need to call a payment API for 500 orders, at most 10 at a time, and stop everything if any call fails. What's the most idiomatic tool?
errgroup.WithContext cancels the shared context on the first error, SetLimit(10) bounds concurrency, and Wait returns the first error. A WaitGroup alone neither limits concurrency nor reports errors.

Channels or mutexes? Choosing the right tool

Both are correct tools; the question is which makes the code clearer. A rule of thumb: channels for passing ownership of data and coordinating work; mutexes for protecting state that lives in one place.

Mental model

A mutex is a lock on a room: the data stays put and people take turns going in. A channel is a conveyor belt: the data moves, and whoever holds it is the only one using it. If you find yourself building a "manager goroutine" just to guard a map with request/response channels, a mutex is probably simpler. If you find yourself juggling a mutex, a slice and a "ready" flag to pass work around, a channel is probably simpler.

Senior engineer tip

Every goroutine you start should have an answer to "how does it stop?" before you write the go keyword. Goroutine leaks are the most common concurrency bug in production Go: they slowly eat memory until the service restarts. Expose stop mechanisms (context, close, Stop()), wait for shutdown (WaitGroup), and check runtime.NumGoroutine() or a pprof goroutine profile when memory creeps up.

Exercise 1 — Fix the racy word counter

This code counts words from several "documents" concurrently but has a data race on the map (and would crash with concurrent map writes under load). Fix it with a mutex inside a small type with an Add(word) method and a Get(word) method, and use wg.Go. Verify with go run -race.

counts := map[string]int{}
var wg sync.WaitGroup
for _, doc := range docs {
	wg.Add(1)
	go func() {
		defer wg.Done()

			counts[w]++ // RACE

Solution
package main

import (
	"fmt"
	"strings"
	"sync"
)

type WordCount struct {
	mu     sync.Mutex
	counts map[string]int // guarded by mu
}

func NewWordCount() *WordCount {
	return &WordCount{counts: make(map[string]int)}
}

func (wc *WordCount) Add(word string) {
	wc.mu.Lock()
	defer wc.mu.Unlock()
	wc.counts[word]++
}

func (wc *WordCount) Get(word string) int {
	wc.mu.Lock()
	defer wc.mu.Unlock()
	return wc.counts[word]
}

func main() {
	docs := []string{
		"go is fun and go is fast",
		"channels and mutexes",
		"go go go",
	}

	wc := NewWordCount()
	var wg sync.WaitGroup
	for _, doc := range docs {
		wg.Go(func() {
			for _, w := range strings.Fields(doc) {
				wc.Add(w)
			}
		})
	}
	wg.Wait()

	fmt.Println("go:", wc.Get("go"), "and:", wc.Get("and"), "is:", wc.Get("is"))
}
go: 5 and: 2 is: 2
Exercise 2 — Parallel checksum with errgroup and a limit

Given a list of strings, compute the SHA-256 of each concurrently with at most 2 goroutines in flight. If any input is empty, return an error "item N is empty" and stop. Print the first 8 hex chars of each hash in input order.

Solution
package main

import (
	"crypto/sha256"
	"fmt"

	"golang.org/x/sync/errgroup"
)

func checksums(items []string) ([]string, error) {
	var g errgroup.Group
	g.SetLimit(2)

	out := make([]string, len(items))
	for i, item := range items {
		g.Go(func() error {
			if item == "" {
				return fmt.Errorf("item %d is empty", i)
			}
			sum := sha256.Sum256([]byte(item))
			out[i] = fmt.Sprintf("%x", sum[:4])
			return nil
		})
	}
	if err := g.Wait(); err != nil {
		return nil, err
	}
	return out, nil
}

func main() {
	sums, err := checksums([]string{"alpha", "beta", "gamma"})
	fmt.Println(sums, err)

	sums, err = checksums([]string{"alpha", "", "gamma"})
	fmt.Println(sums, err)
}
[8ed3f6ad f44e64e7 be9d587d] <nil>
[] item 1 is empty
Exercise 3 — A stoppable ticker job

Write a Heartbeat type with Start() and Stop(). While running it increments an atomic.Int64 every 10ms. Stop() must be safe to call twice (hint: sync.OnceFunc) and must wait until the goroutine has exited.

Solution
package main

import (
	"fmt"
	"sync"
	"sync/atomic"
	"time"
)

type Heartbeat struct {
	beats atomic.Int64
	quit  chan struct{}
	wg    sync.WaitGroup
	Stop  func()
}

func NewHeartbeat() *Heartbeat {
	h := &Heartbeat{quit: make(chan struct{})}
	h.Stop = sync.OnceFunc(func() {
		close(h.quit) // only ever closed once
		h.wg.Wait()
	})
	return h
}

func (h *Heartbeat) Start() {
	h.wg.Go(func() {
		t := time.NewTicker(10 * time.Millisecond)
		defer t.Stop()
		for {
			select {
			case <-t.C:
				h.beats.Add(1)
			case <-h.quit:
				return
			}
		}
	})
}

func main() {
	h := NewHeartbeat()
	h.Start()
	time.Sleep(55 * time.Millisecond)
	h.Stop()
	h.Stop() // second call is a no-op, no "close of closed channel" panic
	fmt.Println("beats:", h.beats.Load())
}
beats: 5

Key takeaways

  • A data race = two goroutines, same memory, at least one write, no synchronization. Results are undefined. Find them with -race; run it in CI.
  • sync.WaitGroup waits for goroutines. Add before go, or simply use wg.Go (Go 1.25+).
  • Guard shared state with a Mutex inside the struct, defer Unlock(), pointer receivers. go vet catches copied locks. Mutexes aren't re-entrant.
  • RWMutex only pays off for read-heavy workloads with non-trivial reads — benchmark first.
  • sync.Once, OnceFunc, OnceValue(s) make lazy initialisation race-free; they don't retry failures.
  • Typed atomics (atomic.Int64, atomic.Bool, atomic.Pointer[T]) are for single independent values.
  • sync.Map and sync.Cond are specialised; prefer map + Mutex and channels.
  • Core patterns: worker pool, fan-out/fan-in, pipeline (each stage closes its output), semaphore channel, ticker rate limit, errgroup with SetLimit, close-to-broadcast graceful stop.
  • Channels move data and coordinate; mutexes protect data that stays put. Every goroutine needs a clear way to stop.

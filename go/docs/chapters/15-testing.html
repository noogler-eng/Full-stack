go test basics

Why do tests matter so much in Go? Because Go code tends to live a long time in production, gets changed by many people, and runs concurrently. Tests are how you change code without fear. Go makes writing them so cheap that there's no excuse not to.

The rules are simple:

  • Tests live in files ending in _test.go, next to the code they test. The normal build ignores these files; only go test compiles them.
  • A test is a function named TestXxx(t *testing.T) — it must start with Test followed by a capital letter (or nothing).
  • You report failures through t. If a test returns without reporting a failure, it passes. There are no assertion keywords — just if statements.

Here's the package we'll test throughout the chapter, textkit, with a few small text helpers:

// Package textkit has small text helpers used to demonstrate Go testing.
package textkit

import (
	"fmt"
	"os"
	"sort"
	"strings"
	"unicode"
)

// Slugify turns a title into a URL-friendly slug: "Hello, World!" -> "hello-world".
func Slugify(title string) string {
	var b strings.Builder
	dash := false
	for _, r := range strings.ToLower(title) {
		switch {
		case unicode.IsLetter(r) || unicode.IsDigit(r):
			b.WriteRune(r)
			dash = false
		case !dash && b.Len() > 0:
			b.WriteByte('-')
			dash = true
		}
	}
	return strings.TrimSuffix(b.String(), "-")
}

// WordFreq counts words case-insensitively, ignoring punctuation.
func WordFreq(text string) map[string]int {
	freq := make(map[string]int)
	words := strings.FieldsFunc(strings.ToLower(text), func(r rune) bool {
		return !unicode.IsLetter(r) && !unicode.IsDigit(r) && r != '\''
	})
	for _, w := range words {
		freq[w]++
	}
	return freq
}

// Truncate shortens s to at most n runes, adding "…" if it cut anything.
func Truncate(s string, n int) (string, error) {
	if n < 1 {
		return "", fmt.Errorf("truncate: n must be >= 1, got %d", n)
	}
	r := []rune(s)
	if len(r) <= n {
		return s, nil
	}
	return string(r[:n-1]) + "…", nil
}

// Report renders word counts as an aligned, sorted table.
func Report(freq map[string]int) string {
	words := make([]string, 0, len(freq))
	for w := range freq {
		words = append(words, w)
	}
	sort.Slice(words, func(i, j int) bool {
		if freq[words[i]] != freq[words[j]] {
			return freq[words[i]] > freq[words[j]]
		}
		return words[i] < words[j]
	})
	var b strings.Builder
	fmt.Fprintf(&b, "%-10s %5s\n", "WORD", "COUNT")
	for _, w := range words {
		fmt.Fprintf(&b, "%-10s %5d\n", w, freq[w])
	}
	return b.String()
}

// SaveLines writes lines to path, one per line.
func SaveLines(path string, lines []string) error {
	return os.WriteFile(path, []byte(strings.Join(lines, "\n")+"\n"), 0o644)
}

// LoadLines reads a file written by SaveLines.
func LoadLines(path string) ([]string, error) {
	data, err := os.ReadFile(path)
	if err != nil {
		return nil, err
	}
	return strings.Split(strings.TrimSuffix(string(data), "\n"), "\n"), nil
}

// JoinPlus concatenates with + (allocates a new string every time).
func JoinPlus(parts []string) string {
	s := ""
	for _, p := range parts {
		s += p
	}
	return s
}

// JoinBuilder concatenates with a pre-sized strings.Builder.
func JoinBuilder(parts []string) string {
	n := 0
	for _, p := range parts {
		n += len(p)
	}
	var b strings.Builder
	b.Grow(n)
	for _, p := range parts {
		b.WriteString(p)
	}
	return b.String()
}

And the simplest possible test:

package textkit

import "testing"

func TestSlugifyBasic(t *testing.T) {
	got := Slugify("Hello, World!")
	want := "hello-world"
	if got != want {
		t.Errorf("Slugify(%q) = %q, want %q", "Hello, World!", got, want)
	}
}
  1. The file ends in _test.go and sits in the same package, so it can see unexported names. go test compiles it into a temporary test binary; -run selects tests by regex.
  2. The runner finds every func TestXxx(t *testing.T) and calls it with a fresh *testing.T. -v prints a RUN line for each.
  3. We call the code under test. Slugify lowercases, drops the punctuation and joins words with a dash.
  4. The expected value, named want by convention.
  5. They match, so t.Errorf is never called. A test with no failures passes; there is no "assert true" step.
  6. The function returns. The runner records a PASS and the time taken.
  7. Every selected test passed, so the binary prints PASS and go test prints the ok line with the package and total time.

t.Error vs t.Fatal

There are two families of failure methods, and the difference is whether the test keeps going:

  • t.Error / t.Errorf — mark the test failed, log the message, continue. Use it when later checks are still meaningful, so one run shows you every problem.
  • t.Fatal / t.Fatalf — mark failed, log, and stop this test immediately (it calls runtime.Goexit). Use it when continuing makes no sense: setup failed, or a nil value would make the next line panic.
  • t.Log / t.Logf — just log (shown with -v or when the test fails). t.Skip marks the test skipped.

Here's a package with two bugs, and tests showing both styles:

package failing

func Add(a, b int) int { return a + b + 1 } // oops: off by one

type User struct{ Name string }

func Find(id int) *User { return nil } // bug: never finds anyone
package failing

import "testing"

func TestAddError(t *testing.T) {
	// t.Error: report and KEEP GOING, so we see every bad case at once.
	if got := Add(1, 2); got != 3 {
		t.Errorf("Add(1, 2) = %d, want 3", got)
	}
	if got := Add(0, 0); got != 0 {
		t.Errorf("Add(0, 0) = %d, want 0", got)
	}
	t.Log("still running after two t.Errorf calls")
}

func TestFindFatal(t *testing.T) {
	u := Find(1)
	if u == nil {
		// t.Fatal: report and STOP this test, because the next line would panic.
		t.Fatal("Find(1) returned nil")
	}
	t.Log("never printed")
	if u.Name != "ana" {
		t.Errorf("name = %q", u.Name)
	}
}
  1. Tests run in source order. First up: TestAddError.
  2. The buggy Add returns 4. t.Errorf logs the message with file:line and marks the test failed, but execution continues.
  3. So the second check also runs and reports. One run shows you every broken case.
  4. t.Log proves we're still running. (Without -v, logs only show for failing tests.)
  5. The function returns and the runner reports FAIL.
  6. Next test. Find is buggy and returns nil.
  7. t.Fatal logs, marks failed and stops this test immediately. Continuing would dereference a nil pointer on line 23.
  8. Lines 22-25 never run, so "never printed" really is never printed. Only this test stopped; others would still run.
  9. The package fails, and go test exits non-zero, which is what makes CI go red.

Gotcha: t.Fatal from another goroutine

t.Fatal, t.FailNow and t.Skip must be called from the test's own goroutine. Called from a goroutine you started, they only stop that goroutine, and the test keeps running. In spawned goroutines, use t.Error (which is safe from any goroutine) or send the error back over a channel. go vet's testinggoroutine check flags this mistake.

Table-driven tests and subtests

Writing one function per case gets repetitive fast. The idiomatic Go style is a table-driven test: a slice of anonymous structs, one per case, and one loop that runs them. Adding a case becomes a one-line change. Wrap each case in t.Run(name, func) to make it a subtest: it gets its own name in the output, its own pass/fail, and can be run on its own.

package textkit

import (
	"maps"
	"testing"
)

// The simplest possible test: one input, one expected output.
func TestSlugifyBasic(t *testing.T) {
	got := Slugify("Hello, World!")
	want := "hello-world"
	if got != want {
		t.Errorf("Slugify(%q) = %q, want %q", "Hello, World!", got, want)
	}
}

// Table-driven test with subtests: the idiomatic Go style.
func TestSlugify(t *testing.T) {
	tests := []struct {
		name  string
		input string
		want  string
	}{
		{"simple", "Hello World", "hello-world"},
		{"punctuation", "Go: 1.27 is out!", "go-1-27-is-out"},
		{"extra spaces", "  lots   of   space  ", "lots-of-space"},
		{"unicode", "Crème Brûlée", "crème-brûlée"},
		{"empty", "", ""},
		{"only symbols", "!!!", ""},
	}
	for _, tt := range tests {
		t.Run(tt.name, func(t *testing.T) {
			if got := Slugify(tt.input); got != tt.want {
				t.Errorf("Slugify(%q) = %q, want %q", tt.input, got, tt.want)
			}
		})
	}
}

func TestWordFreq(t *testing.T) {
	got := WordFreq("The cat and the hat. THE END")
	want := map[string]int{"the": 3, "cat": 1, "and": 1, "hat": 1, "end": 1}
	if !maps.Equal(got, want) {
		t.Errorf("WordFreq() = %v, want %v", got, want)
	}
}

func TestTruncate(t *testing.T) {
	tests := []struct {
		name    string
		s       string
		n       int
		want    string
		wantErr bool
	}{
		{"short enough", "go", 5, "go", false},

		{"cut", "gopher", 4, "gop…", false},
		{"runes not bytes", "héllo wörld", 5, "héll…", false},
		{"invalid n", "x", 0, "", true},

	for _, tt := range tests {
		t.Run(tt.name, func(t *testing.T) {
			got, err := Truncate(tt.s, tt.n)
			if (err != nil) != tt.wantErr {
				t.Fatalf("Truncate(%q, %d) error = %v, wantErr %v", tt.s, tt.n, err, tt.wantErr)
			}
			if got != tt.want {
				t.Errorf("Truncate(%q, %d) = %q, want %q", tt.s, tt.n, got, tt.want)
			}
		})
	}
}

Senior engineer tip

Good tables include the boring edge cases: empty input, one element, unicode, the maximum, the invalid. Most production bugs live at the edges, not in the happy path. Name every case — "runes not bytes" tells the next reader why the case exists. For complex structs, compare with reflect.DeepEqual or (very popular) github.com/google/go-cmp/cmp.Diff, which prints a readable diff.

Since Go 1.22 every loop iteration has its own tt variable, so the old tt := tt line you'll see in older code (needed for parallel subtests) is no longer necessary.

Test helpers: Helper, Cleanup, TempDir, Parallel, Context

t.Helper: blame the right line

When you write your own assertion function, failures are reported at the line inside the helper, which is useless when it's called 20 times. Calling t.Helper() at the top marks the function as a helper, so the reported line is the caller's.

package helper

import "testing"

func assertEqualNoHelper(t *testing.T, got, want int) {
	if got != want {
		t.Errorf("got %d, want %d", got, want) // reported at THIS line
	}
}

func assertEqual(t *testing.T, got, want int) {
	t.Helper() // "I'm a helper: blame my caller's line instead"
	if got != want {
		t.Errorf("got %d, want %d", got, want)
	}
}

func TestWithoutHelper(t *testing.T) {
	assertEqualNoHelper(t, 1+1, 2)
	assertEqualNoHelper(t, 2*2, 5) // which call failed? the output won't say
}

func TestWithHelper(t *testing.T) {
	assertEqual(t, 1+1, 2)
	assertEqual(t, 2*2, 5) // the failure points right here
}
  1. TestWithoutHelper calls the helper with 2 and 2. They match, nothing is reported.
  2. The second call fails. t.Errorf records the line where it was called: line 7, inside the helper.
  3. Without -v, logs print under the FAIL line. "line 7" points into the helper, so you can't tell which of the two calls failed.
  4. TestWithHelper uses assertEqual, whose first line is t.Helper(). The first call passes.
  5. The second call fails. Because the function is marked as a helper, the testing package skips its frame and blames the caller's line.
  6. Now the report says line 25: exactly the failing assertion.
  7. Both tests failed (on purpose). Put t.Helper() first in every assertion helper.

t.Cleanup and t.TempDir

t.Cleanup(f) registers a function to run when the test (and all its subtests) finishes, in last-in, first-out order — like defer, but it can be registered from inside a helper function, which defer can't. t.TempDir() creates a fresh, unique directory and registers a cleanup that deletes it.

package textkit

import (
	"path/filepath"
	"slices"
	"testing"
)

func TestSaveLoadLines(t *testing.T) {
	dir := t.TempDir() // fresh directory, deleted automatically after the test
	path := filepath.Join(dir, "notes.txt")

	want := []string{"buy milk", "write tests", "ship it"}
	if err := SaveLines(path, want); err != nil {
		t.Fatalf("SaveLines: %v", err)
	}
	got, err := LoadLines(path)
	if err != nil {
		t.Fatalf("LoadLines: %v", err)
	}
	if !slices.Equal(got, want) {
		t.Errorf("round trip = %q, want %q", got, want)
	}
}

func TestLoadLinesMissing(t *testing.T) {
	_, err := LoadLines(filepath.Join(t.TempDir(), "nope.txt"))
	if err == nil {
		t.Fatal("expected an error for a missing file, got nil")
	}
}
  1. t.TempDir() creates a fresh, empty directory unique to this test (the exact path varies). It registers a cleanup that deletes it afterwards.
  2. We build a path inside it and the lines we expect to survive the round trip.
  3. SaveLines writes the file. If it failed, t.Fatalf would stop here, because nothing after it makes sense without the file.
  4. LoadLines reads it back.
  5. slices.Equal compares element by element. Equal, so no error is reported.
  6. The test returns and the TempDir cleanup removes the directory. No leftover files, no clashes between tests.
  7. The second test asks for a file that does not exist in another fresh TempDir.
  8. An error came back, as expected, so t.Fatal is skipped and the test passes. Testing the failure path matters as much as the happy path.

A helper that creates something should clean it up itself: func newTestDB(t *testing.T) *DB { t.Helper(); db := open(); t.Cleanup(func() { db.Close() }); return db }. Callers get a one-liner, and can never forget the cleanup. Similarly, t.Setenv("KEY", "v") sets an env var and restores it after the test, and t.Chdir(dir) (Go 1.24) does the same for the working directory.

t.Parallel and t.Context

t.Parallel() tells the runner "this test may run at the same time as other parallel tests." The test pauses at that call, and resumes once the non-parallel tests at its level are done. Then all paused tests run together (up to -parallel, default GOMAXPROCS). t.Context() (Go 1.24) returns a context that is cancelled just before cleanups run — perfect for passing into code under test.

package lifecycle

import (
	"context"
	"testing"
	"time"
)

func TestCleanupOrder(t *testing.T) {
	t.Cleanup(func() { t.Log("cleanup 1: close database") })
	t.Cleanup(func() { t.Log("cleanup 2: stop server") })
	t.Log("test body runs")
	// Cleanups run after the test (and its subtests) finish, last-registered first.
}

func TestParallel(t *testing.T) {
	for _, name := range []string{"a", "b", "c"} {
		t.Run(name, func(t *testing.T) {
			t.Parallel() // pause here; resume alongside the other parallel subtests
			time.Sleep(100 * time.Millisecond)
			t.Log("done", name)
		})
	}
}

// waitReady blocks until ready is closed or ctx is done.
func waitReady(ctx context.Context, ready <-chan struct{}) error {
	select {
	case <-ready:
		return nil
	case <-ctx.Done():
		return ctx.Err()
	}
}

func TestContext(t *testing.T) {
	ctx := t.Context() // Go 1.24+: cancelled just before Cleanup functions run
	t.Cleanup(func() { t.Log("in cleanup, ctx.Err() =", ctx.Err()) })

	ready := make(chan struct{})
	go func() { time.Sleep(10 * time.Millisecond); close(ready) }()
	if err := waitReady(ctx, ready); err != nil {
		t.Fatal(err)
	}
	t.Log("ready; ctx.Err() =", ctx.Err())
}
  1. t.Cleanup only registers functions; nothing runs yet. Two are queued.
  2. The body runs.
  3. After the test returns, cleanups run last-registered first, like defer: the server stops before the database closes.
  4. Each t.Run starts a subtest, which hits t.Parallel() and immediately pauses. t.Run returns, so the loop moves on.
  5. When the parent function returns, the paused subtests are released to run together.
  6. All three sleep at the same time. The finish order varies; this run finished c, b, a. === NAME lines say whose log follows.
  7. Each subtest took 0.10s, but they overlapped, so the whole group took about 100ms.
  8. t.Context() gives a context tied to this test. A cleanup is registered that will inspect it later.
  9. A goroutine closes ready after 10ms. waitReady selects on ready and ctx.Done(); ready wins.
  10. During the test body the context is still live.
  11. The test returns. The context is cancelled just before cleanups run, so the cleanup sees context canceled. Goroutines using t.Context() get told to stop.
  12. All three tests pass.

Gotcha

Parallel tests share package-level state. If two parallel tests write to the same global variable, map or file, you've created a race (and -race will tell you). Also, t.Setenv and t.Chdir affect the whole process, so they panic in parallel tests.

Fixtures, testdata and golden files

A fixture is input data a test needs: a sample config file, a JSON payload, an image. Put them in a directory named testdata/. The Go tool ignores it completely (it's never treated as a package), and tests run with the package directory as their working directory, so os.ReadFile("testdata/x") just works.

A golden file stores the expected output of a test, for outputs too big to write inline: rendered reports, generated code, HTML. The test compares fresh output to the golden file. When the output changes on purpose, you regenerate the file with a flag and review the diff in your pull request.

package textkit

import (
	"flag"
	"os"
	"path/filepath"
	"testing"
)

		t.Fatal(err)

		}

		t.Fatalf("missing golden file (run go test -update): %v", err)

	if got != string(want) {
		t.Errorf("Report() mismatch\n--- got ---\n%s--- want ---\n%s", got, want)
	}
}

Mocking with interfaces and fakes

Real code talks to databases, payment APIs, email servers and the clock. Tests shouldn't: they'd be slow, flaky and expensive. The Go way to isolate code is simple: depend on a small interface, and give tests a fake implementation. No mocking framework needed — a fake is just a struct you write in the test file.

// Package users exposes a tiny user service over HTTP.
package users

import (
	"context"
	"encoding/json"
	"errors"
	"fmt"
	"net/http"
	"strconv"
)

type User struct {
	ID   int    `json:"id"`
	Name string `json:"name"`
}

var ErrNotFound = errors.New("user not found")

// Store is the dependency we will fake in tests. Keep it small.
type Store interface {
	GetUser(ctx context.Context, id int) (User, error)
}

// Service holds business logic and depends only on the interface.
type Service struct {
	Store Store
}

func (s *Service) Greeting(ctx context.Context, id int) (string, error) {
	u, err := s.Store.GetUser(ctx, id)
	if err != nil {
		return "", fmt.Errorf("greeting for %d: %w", id, err)
	}
	return "Hello, " + u.Name + "!", nil
}

// Handler serves GET /users/{id}.
func Handler(store Store) http.Handler {
	mux := http.NewServeMux()
	mux.HandleFunc("GET /users/{id}", func(w http.ResponseWriter, r *http.Request) {
		id, err := strconv.Atoi(r.PathValue("id"))
		if err != nil {
			http.Error(w, "bad id", http.StatusBadRequest)
			return
		}
		u, err := store.GetUser(r.Context(), id)
		if errors.Is(err, ErrNotFound) {
			http.Error(w, "not found", http.StatusNotFound)
			return
		}
		if err != nil {
			http.Error(w, "internal error", http.StatusInternalServerError)
			return
		}
		w.Header().Set("Content-Type", "application/json")
		json.NewEncoder(w).Encode(u)
	})
	return mux
}

// Client calls a remote users API.
type Client struct {
	BaseURL string
	HTTP    *http.Client
}

func (c *Client) GetUser(ctx context.Context, id int) (User, error) {
	req, err := http.NewRequestWithContext(ctx, http.MethodGet, fmt.Sprintf("%s/users/%d", c.BaseURL, id), nil)
	if err != nil {
		return User{}, err
	}
	resp, err := c.HTTP.Do(req)
	if err != nil {
		return User{}, err
	}
	defer resp.Body.Close()
	switch resp.StatusCode {
	case http.StatusOK:
		var u User
		err := json.NewDecoder(resp.Body).Decode(&u)
		return u, err
	case http.StatusNotFound:
		return User{}, ErrNotFound
	default:
		return User{}, fmt.Errorf("users api: unexpected status %d", resp.StatusCode)
	}
}

	"context"
	"errors"
	"testing"
)

}

func (f *fakeStore) GetUser(ctx context.Context, id int) (User, error) {
	f.calls++
	if f.err != nil {
		return User{}, f.err
	}
	u, ok := f.users[id]
	if !ok {
		return User{}, ErrNotFound
	}
	return u, nil
}

		t.Errorf("got %q", got)
	}
	if store.calls != 1 {
		t.Errorf("store called %d times, want 1", store.calls)
	}
}

func TestGreetingErrors(t *testing.T) {

		name  string

		want  error

Mental model

A fake is a stunt double. The director (your test) needs a scene shot safely and repeatably, so a double that looks the same from the camera's point of view (implements the same interface) stands in for the real actor (the database). Fakes have working, simplified behaviour (an in-memory map); mocks just record calls and return canned answers. In Go, simple hand-written fakes are usually the clearest.

Define interfaces where they're used (in the consumer package), and keep them small — one or two methods. "Accept interfaces, return structs." A 30-method interface is painful to fake; a 1-method one takes four lines. The same trick works for time: inject a Clock interface (see Exercise 3), or use testing/synctest (below).

Testing HTTP with httptest

The net/http/httptest package gives you two tools:

  • httptest.NewRecorder() — an in-memory http.ResponseWriter. You call your handler directly with a request from httptest.NewRequest and inspect rec.Code, rec.Header(), rec.Body. No network, microseconds per test. Use it to test handlers.
  • httptest.NewServer(handler) — a real HTTP server on a random 127.0.0.1 port. Use it to test clients: code that makes HTTP calls. Point the client at srv.URL.
package users

import (
	"net/http"
	"net/http/httptest"
	"strings"
	"testing"
)

// httptest.NewRecorder: call the handler directly, no network at all.
func TestHandler(t *testing.T) {
	h := Handler(&fakeStore{users: map[int]User{7: {ID: 7, Name: "Bo"}}})

	tests := []struct {
		path     string
		wantCode int
		wantBody string
	}{
		{"/users/7", http.StatusOK, `{"id":7,"name":"Bo"}`},
		{"/users/8", http.StatusNotFound, "not found"},
		{"/users/abc", http.StatusBadRequest, "bad id"},
	}
	for _, tt := range tests {
		t.Run(tt.path, func(t *testing.T) {
			req := httptest.NewRequest(http.MethodGet, tt.path, nil)
			rec := httptest.NewRecorder()

			h.ServeHTTP(rec, req)

			if rec.Code != tt.wantCode {
				t.Errorf("status = %d, want %d", rec.Code, tt.wantCode)
			}
			if body := strings.TrimSpace(rec.Body.String()); body != tt.wantBody {
				t.Errorf("body = %q, want %q", body, tt.wantBody)
			}
		})
	}
}

// httptest.NewServer: a real HTTP server on a random localhost port,
// perfect for testing code that MAKES requests (our Client).
func TestClient(t *testing.T) {
	srv := httptest.NewServer(Handler(&fakeStore{users: map[int]User{1: {ID: 1, Name: "Ana"}}}))
	defer srv.Close()
	t.Log("test server at", srv.URL)

	c := &Client{BaseURL: srv.URL, HTTP: srv.Client()}

	u, err := c.GetUser(t.Context(), 1)
	if err != nil || u.Name != "Ana" {
		t.Fatalf("GetUser(1) = %+v, %v", u, err)
	}
	if _, err := c.GetUser(t.Context(), 2); err != ErrNotFound {
		t.Errorf("GetUser(2) err = %v, want ErrNotFound", err)
	}
}

// A hand-written HandlerFunc lets you simulate a misbehaving upstream.
func TestClientServerError(t *testing.T) {
	srv := httptest.NewServer(http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		w.WriteHeader(http.StatusServiceUnavailable)
	}))
	defer srv.Close()

	c := &Client{BaseURL: srv.URL, HTTP: srv.Client()}
	_, err := c.GetUser(t.Context(), 1)
	if err == nil || !strings.Contains(err.Error(), "503") {
		t.Fatalf("err = %v, want a 503 error", err)
	}
}

  2. Create a request. httptest.NewRequest never fails (it panics on bad input) — handy in tests.
  3. A fresh recorder. Its code defaults to 200 until the handler writes one.
  4. We call ServeHTTP directly: no sockets. The mux matches GET /users/{id}, the fake returns ErrNotFound.
  5. http.Error writes a 404 and the body into the recorder.
  6. Assert on the status. It matches, so no error.
  7. Inspect the body — trimmed, since http.Error adds a newline.

TestMain: package-wide setup

If you define func TestMain(m *testing.M), Go calls it instead of running tests directly. You do setup, call m.Run() to run all the tests, do teardown, and exit with the code it returned. Use it sparingly — for genuinely expensive shared setup like starting a database container.

Example tests: documentation that can't go stale

An example function is named ExampleXxx (for function Xxx), ExampleType_Method, or just Example for the package. It ends with an // Output: comment. go test runs it and fails if stdout doesn't match. And pkg.go.dev (and the local pkgsite doc server) display it in your package documentation under the function — runnable docs that are guaranteed to be correct.

This file also shows an external test package: package textkit_test. Files in the same directory may declare the package name with a _test suffix. Benchmarks with b.Loop and -benchmem

A benchmark measures how long code takes. It's named BenchmarkXxx(b *testing.B) and lives in a _test.go file. Since Go 1.24, the body is a for b.Loop() { ... } loop. The framework runs the loop many times, increasing the count until the measurement is stable (about 1 second by default), and reports time per iteration.

package textkit

import (
	"strings"
	"testing"
)

var parts = strings.Fields(strings.Repeat("gopher ", 100)) // 100 words

func BenchmarkJoinPlus(b *testing.B) {
	for b.Loop() { // Go 1.24+: replaces for i := 0; i < b.N; i++
		JoinPlus(parts)
	}
}

func BenchmarkJoinBuilder(b *testing.B) {
	for b.Loop() {
		JoinBuilder(parts)
	}
}

func BenchmarkSlugify(b *testing.B) {
	title := "The Go Handbook: Testing & Benchmarking, Chapter 15"
	for b.Loop() {
		Slugify(title)
	}
}
  1. Package-level setup runs once, before any benchmark. -bench=. selects all benchmarks; the package's normal tests run first unless you add -run=^$. The header describes the machine: numbers only compare on the same hardware.
  2. b.Loop() returns true while the framework wants more iterations. It starts small to estimate how long one call takes.
  3. The framework keeps going until about 1 second of work has been measured. Setup outside the loop is not timed, and b.Loop stops the compiler from optimising the call away.
  4. Result: iterations, time per call, bytes and allocations per call (from -benchmem). + in a loop allocates a new string every step: 99 allocations for 100 words. -8 is GOMAXPROCS.
  5. Same input with strings.Builder: about 10x faster and a single allocation. Because each call is faster, the framework ran it ten times as often.
  6. The title is built once outside the loop; only Slugify is measured.
  7. Roughly a second per benchmark, plus overhead. Your numbers will differ; compare runs with benchstat, not by eye.

Why b.Loop?

The older style was for i := 0; i < b.N; i++ { ... }, plus b.ResetTimer() after setup. b.Loop is better in three ways: setup before the loop is automatically excluded from timing; the function body runs only once per measurement so expensive setup isn't repeated; and the compiler is prevented from optimising away the call under test even if you ignore its result (with b.N loops, you had to assign results to a global "sink").

Senior engineer tip

One benchmark run proves nothing — numbers vary with CPU frequency, background load and thermal state. For real decisions: run go test -bench=X -count=10 > old.txt, make your change, run again into new.txt, and compare with benchstat old.txt new.txt (from golang.org/x/perf/cmd/benchstat). It reports the delta and whether it's statistically significant. Also benchmark with realistic input sizes (see Exercise 2 with b.Run sub-benchmarks).

Fuzzing: let the computer find your bugs

Table tests check the cases you thought of. Fuzzing generates millions of inputs you didn't think of. You write a FuzzXxx(f *testing.F) function: add some seed inputs with f.Add, then give f.Fuzz a function that checks properties — things that must be true for any input. The fuzzer mutates inputs, guided by code coverage, looking for one that breaks a property.

Here's a string reverser that looks correct and passes its unit test:

package reverse

// Reverse returns s reversed... byte by byte. (Can you spot the bug?)
func Reverse(s string) string {
	b := []byte(s)
	for i, j := 0, len(b)-1; i < j; i, j = i+1, j-1 {
		b[i], b[j] = b[j], b[i]
	}
	return string(b)
}
package reverse

import (
	"testing"
	"unicode/utf8"
)

func TestReverse(t *testing.T) {
	for in, want := range map[string]string{"abc": "cba", "": "", "Go!": "!oG"} {
		if got := Reverse(in); got != want {
			t.Errorf("Reverse(%q) = %q, want %q", in, got, want)
		}
	}
}

// FuzzReverse checks PROPERTIES that must hold for any input,
// instead of specific input/output pairs.
func FuzzReverse(f *testing.F) {
	f.Add("hello") // seed corpus: example inputs to start mutating from
	f.Add("Go is fun!")
	f.Fuzz(func(t *testing.T, s string) {
		rev := Reverse(s)
		if Reverse(rev) != s {
			t.Errorf("double reverse changed %q into %q", s, Reverse(rev))
		}
		if utf8.ValidString(s) && !utf8.ValidString(rev) {
			t.Errorf("Reverse produced invalid UTF-8 from valid %q: %q", s, rev)
		}
	})
}

Two properties: reversing twice gives back the original; and reversing valid UTF-8 gives valid UTF-8. The unit test passes. Now we fuzz:

func Reverse(s string) string {
	if !utf8.ValidString(s) {
		return s
	}
	r := []rune(s)
	for i, j := 0, len(r)-1; i < j; i, j = i+1, j-1 {

	}
	return string(r)

Mental model

Coverage is a flashlight, not a grade. It shows dark corners nobody tested. But 100% coverage doesn't mean the code is right: a test can execute a line without checking its result. testing/synctest: tests with a fake clock

Code with timeouts, TTLs and retries is hard to test: real sleeps make tests slow, and short sleeps make them flaky. testing/synctest (stable since Go 1.25) solves this. synctest.Test(t, f) runs f in an isolated bubble with a fake clock. Time inside the bubble only moves when every goroutine in it is blocked — and then it jumps straight to the next timer. A one-hour time.Sleep returns instantly, deterministically.

package cache

import (
	"sync"
	"time"
)

// Cache stores values that expire after a TTL.
type Cache struct {
	mu   sync.Mutex
	ttl  time.Duration
	data map[string]entry
}

type entry struct {
	val     string
	expires time.Time
}

func New(ttl time.Duration) *Cache {
	return &Cache{ttl: ttl, data: make(map[string]entry)}
}

func (c *Cache) Set(k, v string) {
	c.mu.Lock()
	defer c.mu.Unlock()
	c.data[k] = entry{v, time.Now().Add(c.ttl)}
}

func (c *Cache) Get(k string) (string, bool) {
	c.mu.Lock()
	defer c.mu.Unlock()
	e, ok := c.data[k]
	if !ok || time.Now().After(e.expires) {
		return "", false
	}
	return e.val, true
}
package cache

import (
	"context"
	"testing"
	"testing/synctest"
	"time"
)

// Inside synctest.Test, time is FAKE: it only advances when every goroutine
// in the "bubble" is blocked. A 1-hour sleep finishes instantly.
func TestExpiry(t *testing.T) {
	synctest.Test(t, func(t *testing.T) {
		c := New(time.Hour)
		c.Set("k", "v")

		time.Sleep(59 * time.Minute)
		if _, ok := c.Get("k"); !ok {
			t.Fatal("expired too early")
		}

		time.Sleep(2 * time.Minute)
		if _, ok := c.Get("k"); ok {
			t.Fatal("should have expired after 61 minutes")
		}
	})
}

func TestTimeoutWithFakeClock(t *testing.T) {
	synctest.Test(t, func(t *testing.T) {
		start := time.Now()
		ctx, cancel := context.WithTimeout(t.Context(), 5*time.Second)
		defer cancel()

		<-ctx.Done() // blocks; fake clock jumps straight to the deadline
		t.Logf("ctx done after %v of fake time: %v", time.Since(start), ctx.Err())
	})
}

  2. The entry expires one fake hour from now.
  3. The test goroutine sleeps. It's the only goroutine in the bubble and it's blocked, so the clock jumps 59 minutes instantly.
  4. Not expired yet.
  5. Another jump: 2 more minutes.
  6. Now it's expired. We tested an hour of behaviour in microseconds, with no flakiness.
  7. synctest.Test waits for all goroutines started in the bubble to exit, which also catches goroutine leaks.

Exercise 1 — Table-test a palindrome checker

Write IsPalindrome(s string) bool that ignores case, spaces and punctuation, then a table-driven test with parallel subtests covering: empty, one letter, mixed case, a full sentence with punctuation, a non-ASCII word, and two negatives.

package ex1

import (
	"strings"
	"unicode"
)

// IsPalindrome reports whether s reads the same backwards,
// ignoring case, spaces and punctuation.
func IsPalindrome(s string) bool {
	var r []rune
	for _, c := range strings.ToLower(s) {
		if unicode.IsLetter(c) || unicode.IsDigit(c) {
			r = append(r, c)
		}
	}
	for i, j := 0, len(r)-1; i < j; i, j = i+1, j-1 {
		if r[i] != r[j] {
			return false
		}
	}
	return true
}

type Sender interface {

Key takeaways

  • Tests are TestXxx(t *testing.T) functions in _test.go files; run them with go test ./.... No assertion library needed.
  • t.Error records and continues; t.Fatal records and stops the test goroutine. Write messages as Func(in) = got, want want.
  • Table-driven tests + t.Run subtests are the idiomatic default. Name every case.
  • t.Helper fixes line numbers, t.Cleanup runs LIFO teardown, t.TempDir gives a self-deleting dir, t.Parallel runs tests concurrently, t.Context gives a per-test context.
  • Fixtures go in testdata/; golden files + an -update flag handle big outputs.
  • Depend on small interfaces and write tiny fakes. Use httptest.NewRecorder for handlers and httptest.NewServer for clients.
  • ExampleXxx with // Output: is documentation that's tested. External _test packages test the public API.
  • Benchmarks use for b.Loop(); add -benchmem; compare runs with benchstat.
  • Fuzz parsers and transformations with property checks; failing inputs become permanent seeds in testdata/fuzz.
  • Use -cover as a flashlight, -race in CI, synctest for time-dependent code, and TestMain only for expensive package-wide setup.

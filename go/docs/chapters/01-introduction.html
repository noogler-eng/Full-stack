What is Go, and why does it exist?

Go (often called Golang because "go" is hard to search for) is a programming language created at Google in 2007 by Robert Griesemer, Rob Pike and Ken Thompson. Ken Thompson co-created Unix and the B language (the ancestor of C); Rob Pike worked on Unix, Plan 9 and UTF-8. These are people who had been writing systems software for decades, and they were frustrated.

The story goes that Go was sketched out while they were waiting for a giant C++ program to compile. At Google's scale, builds took tens of minutes, codebases had millions of lines, thousands of engineers touched the same code, and the languages in use made it easy to write clever code that nobody else could read. Go was their answer to one question:

The question Go answers

"How do we make a large team of ordinary engineers productive on a large, long-lived codebase that runs on many networked machines with many CPU cores?"

Go became public as open source in November 2009, and Go 1.0 shipped in March 2012 with a famous promise: the Go 1 compatibility guarantee. Code written for Go 1.0 should still compile and run with every later 1.x release. That promise has held for more than a decade, and it's a big reason companies trust Go for long-lived systems.

Two words you'll hear a lot

Compiled means your source code is translated ahead of time into machine code (the instructions your CPU runs directly). Statically typed means every variable has a type known at compile time, so the compiler can catch "you passed a string where a number was expected" before your program ever runs.

Where Go is used

Go is the language of the cloud. A large share of the infrastructure that runs the modern internet is written in it:

  • Cloud infrastructure: Docker, Kubernetes, containerd, etcd, Terraform, Prometheus, Grafana's backend, Consul, Vault.
  • Network services and APIs: microservices, gRPC services, API gateways, proxies (Caddy, Traefik).
  • Command-line tools: GitHub's gh, Hugo, kubectl, many DevOps CLIs — because a single binary is trivial to distribute.
  • Data pipelines and backend systems: at companies like Google, Uber, Cloudflare, Twitch, Dropbox, Monzo and many more.

Where Go is a weaker fit: GUI desktop apps, machine-learning model training (Python's ecosystem dominates), hard real-time systems where a garbage collector pause is unacceptable, and situations where you need every last nanosecond of control (C, C++ or Rust).

Senior engineer tip

Go's "boring" reputation is a feature. In a production team the expensive thing is not typing code — it's reading, reviewing, debugging and changing it two years later. Go deliberately trades expressiveness for uniformity: any Go engineer can open any Go codebase and feel at home within an hour. When you catch yourself missing a clever feature from another language, ask "would my teammate understand this at 3am during an outage?"

Installing Go

Go is distributed as an official installer from go.dev/dl. You get the compiler, the standard library, and the go tool in one package. Pick your platform:

macOS

The easiest route is the official .pkg installer from go.dev/dl (choose ARM64 for Apple Silicon M-series Macs, x86-64 for Intel). It installs Go into /usr/local/go and adds /usr/local/go/bin to your PATH. Homebrew works too:

brew install go

Linux

Distribution packages (apt, dnf) are often several versions behind. The official tarball is the reliable way:

# replace the version with the latest from go.dev/dl
curl -LO https://go.dev/dl/go1.27.1.linux-amd64.tar.gz
sudo rm -rf /usr/local/go
sudo tar -C /usr/local -xzf go1.27.1.linux-amd64.tar.gz

# add to your shell profile (~/.bashrc, ~/.zshrc, ...)
export PATH=$PATH:/usr/local/go/bin:$HOME/go/bin

Windows

Download the .msi installer from go.dev/dl and click through it. It installs to C:\Program Files\Go and sets up PATH for you. Open a new terminal (PowerShell or cmd) afterwards so it picks up the new PATH. winget install GoLang.Go also works.

Check that it works

$ go version
go version go1.27.1 darwin/arm64

The output tells you three things: the Go version, the operating system (darwin is macOS's internal name), and the CPU architecture (arm64). You can ask a running program the same thing:

package main

import (
	"fmt"
	"runtime"
)

func main() {
	fmt.Println("Go version:", runtime.Version())
	fmt.Println("OS/Arch:   ", runtime.GOOS+"/"+runtime.GOARCH)
	fmt.Println("CPUs:      ", runtime.NumCPU())
}
  1. Two packages are imported in a parenthesized block: fmt for printing and runtime for facts about the running program.
  2. runtime.Version() returns the Go release that compiled this binary — it's baked in, so it doesn't matter what Go is installed where the binary later runs.
  3. runtime.GOOS and runtime.GOARCH are constants, not calls. + glues the strings together. Cross-compile and these would say e.g. linux/amd64.
  4. runtime.NumCPU() asks the OS how many logical CPUs exist right now, so this one varies by machine. Then main returns.
Go version: go1.27.1
OS/Arch:    darwin/arm64
CPUs:       8

(The CPU count depends on your machine.)

Keeping Go up to date: toolchains

Go releases a new minor version every six months (February and August), each supported until two newer releases are out. Since Go 1.21, the go command can even download the right toolchain automatically: if a project's go.mod says it needs a newer Go than you have installed, go fetches that version and uses it. This is controlled by the GOTOOLCHAIN setting (default auto).

Need several Go versions side by side? Run go install golang.org/dl/go1.22.12@latest and then go1.22.12 download. You now have a go1.22.12 command next to your normal go.

GOPATH vs modules: where your code lives

If you read older Go tutorials, you'll see a lot about GOPATH. Here's the history, briefly, so it doesn't confuse you.

The old way: GOPATH (before Go 1.11)

GOPATH is an environment variable pointing at a single workspace directory (default ~/go). In the old days, all Go code had to live inside $GOPATH/src, in a folder matching its import path, e.g. ~/go/src/github.com/you/project. There was no notion of versions: everyone shared one copy of each dependency. That made reproducible builds painful.

The modern way: modules (Go 1.11+, default since 1.16)

A module is a collection of Go packages that are versioned together. It's defined by a file named go.mod at its root. With modules:

  • Your project can live anywhere on disk — ~/code/myapp, your Desktop, wherever.
  • Every dependency has an exact version, recorded in go.mod, with checksums in go.sum.
  • Builds are reproducible: the same go.mod + go.sum gives the same build on every machine.

GOPATH still exists, but only as a place for Go to keep things: downloaded modules go into $GOPATH/pkg/mod (the module cache), and programs you go install land in $GOPATH/bin. You never put your own code there anymore.

TermMeaningExample
PackageA directory of .go files compiled together. The unit of code organization and visibility.fmt, net/http, your ./internal/store
ModuleA tree of packages with a go.mod at the root; the unit of versioning and release.github.com/google/uuid
Import pathModule path + directory inside it. Used in import statements.example.com/shop/internal/cart
GOROOTWhere Go itself (compiler + standard library) is installed./usr/local/go
GOPATHGo's workspace for caches and installed binaries.~/go

Creating a module with go mod init

Every new project starts the same way. Make a folder, then initialize a module with a module path — the name other code would use to import it. By convention this is where the code is (or will be) hosted, like github.com/you/hello. For local experiments, anything works; example.com/... is a common placeholder.

$ mkdir hello && cd hello
$ go mod init example.com/hello
go: creating new go.mod: module example.com/hello
$ cat go.mod
module example.com/hello

go 1.27.1

That's the whole file for now. The module line names your module. The go line says which version of the Go language this module is written for — it controls language features and some behaviors (you'll see in Chapter 03 how it changes loop variable semantics). When you add dependencies, require lines appear here too.

Senior engineer tip

Pick the module path you'll actually publish under from day one (e.g. github.com/acme/billing). Renaming a module later means rewriting every import in the codebase and in every consumer. For internal company code, use the internal Git host's path (git.acme.corp/team/billing) and set GOPRIVATE=git.acme.corp so the public proxy is never asked about it.

Hello, World — line by line

Create main.go in your hello folder:

package main

import "fmt"

func main() {
	fmt.Println("Hello, Gopher!")
}
  1. The compiler reads the package clause first. package main means "build an executable", not a library.
  2. import "fmt" makes the standard formatting package available. Before main runs, the runtime initializes fmt (and everything it imports).
  3. Execution of your code begins here, at func main() in package main. It takes no arguments and returns nothing.
  4. fmt.Println writes its argument to standard output and adds a newline.
  5. main returns, so the program exits with status 0. No explicit return 0 needed.
$ go run .
Hello, Gopher!

Seven lines. Let's take every one seriously, because each teaches a rule you'll use forever.

  1. package main — Every Go file starts by saying which package it belongs to. All files in one directory must use the same package name. main is special: it tells Go "this package builds an executable program, not a library."
  2. (blank line) — purely for humans. gofmt puts it there.
  3. import "fmt" — Pulls in the standard library package fmt (short for format; Gophers say "fumpt"), which handles formatted input and output. You may only use packages you import, and you must use every package you import.
  4. (blank line)
  5. func main() { — Declares a function named main that takes no arguments and returns nothing. In package main, the function main is the entry point: the program starts here, and when it returns, the program exits.
  6. fmt.Println("Hello, Gopher!") — Calls the Println function from package fmt. The capital P matters: in Go, a name starting with an uppercase letter is exported (visible outside its package). Lowercase names are private to the package. Println prints its arguments separated by spaces and adds a newline.
  7. } — Closes the function body.

Notice what's not there: no semicolons, no class wrapper, no public static void, no return code. If main returns normally, the exit code is 0.

Mental model: packages are folders

Think of a package as a folder of files that share one namespace — every file in it can see every other file's names, even lowercase ones. The outside world only sees the Capitalized names. That's the whole visibility system: no public, private or protected keywords.

Let's watch a slightly bigger program run. Every line inside main executes top to bottom, exactly once:

name := "gopher"
shout := strings.ToUpper(name)
fmt.Println("Hello,", name)
fmt.Println("HELLO,", shout+"!")
n := len(name)
fmt.Printf("%q has %d letters\n", name, n)
  1. := declares a new variable name and gives it the string "gopher". Go infers the type string from the value.
  2. We call strings.ToUpper (from the strings package we imported). It returns a new string — strings in Go are immutable, so name is unchanged.
  3. Println receives two arguments and prints them with a single space between, then a newline.
  4. + concatenates strings, so the second argument is "GOPHER!".
  5. len is a built-in function. For a string it returns the number of bytes (here 6, since every letter is one byte in UTF-8).
  6. Printf uses a format string: %q prints a quoted string, %d a decimal integer, and \n is a newline (Printf doesn't add one for you). Then main returns and the program exits with code 0.
Hello, gopher
HELLO, GOPHER!
"gopher" has 6 letters

go run vs go build

go run is go build + execute + throw the binary away. It's for development. go build leaves the binary on disk:

$ go build -o hello .
$ ls -lh hello
2.3M hello
$ ./hello
Hello, Gopher!

Without -o, the binary is named after the module's last path element (here hello). Both commands cache compiled packages, so the second build is nearly instant.

go vet: the friendly bug-finder

The compiler checks that your program is legal. go vet checks whether it's sensible. A classic example — the wrong formatting verb:

package main

import "fmt"

func main() {
	name := "gopher"
	fmt.Printf("Hello, %d\n", name) // wrong verb: %d is for integers
}

This compiles and runs (printing garbage like %!d(string=gopher)). But vet catches it:

main.go:7:21: fmt.Printf format %d has arg name of wrong type string

Vet checks for dozens of mistakes: wrong Printf arguments, unreachable code, copying a lock by value, misuse of struct tags, loop variables captured incorrectly, suspicious shifts and more. go test automatically runs a subset of vet checks before running tests.

go fmt / gofmt: one true style

Here's some messy, legal Go code:

package main
import "fmt"
func main(){
x:=1
    if x>0 {fmt.Println( "positive" )}
}

Running gofmt main.go prints the canonical version (add -w to write it back to the file, -l to just list files that need formatting, -d to see a diff):

package main

import "fmt"

func main() {
	x := 1
	if x > 0 {
		fmt.Println("positive")
	}
}

Tabs for indentation, spaces for alignment, one statement per line, spaces around binary operators where it helps readability. There are no options to configure. That's the point.

go test: testing is built in

Any file ending in _test.go is a test file. Any function named TestXxx(t *testing.T) inside it is a test. No framework to install:

package hellotest

// Greeting returns a greeting for name.
func Greeting(name string) string {
	return "Hello, " + name + "!"
}
package hellotest

import "testing"

func TestGreeting(t *testing.T) {
	got := Greeting("Go")
	want := "Hello, Go!"
	if got != want {
		t.Errorf("Greeting(%q) = %q, want %q", "Go", got, want)
	}
}
  1. go test compiles hello.go and hello_test.go together into a temporary test binary, finds every func TestXxx(t *testing.T), and calls them. With -v it announces each one.
  2. The test calls the real Greeting function. Same package (hellotest), so even unexported names would be visible here.
  3. The expected value is written out literally. Keep expectations dumb and explicit — never recompute them with the same logic you are testing.
  4. They are equal, so t.Errorf is skipped. Had they differed, Errorf would log the message and mark the test failed, but keep running the rest of the function.
  5. The function returns without any failure recorded, so the test passes.
  6. All tests in the package passed. The last line shows the package path and how long the run took (this number varies).
=== RUN   TestGreeting
--- PASS: TestGreeting (0.00s)
PASS
ok  	example.com/hellotest	0.477s

(The timing on the last line varies run to run.) Chapter 15 covers testing in depth: table-driven tests, subtests, benchmarks, fuzzing and coverage.

Senior engineer tip: the pre-commit trio

Make this muscle memory, and enforce it in CI so nobody has to argue about it in code review:

gofmt -l . | (! grep .)   # fail if anything is unformatted
go vet ./...
go test -race ./...       # -race finds data races in concurrent code

Many teams add staticcheck or golangci-lint on top, and run go mod tidy in CI and fail if it changes anything (git diff --exit-code go.mod go.sum).

How compilation works: one static binary

When you run go build, a lot happens in a second or two. Here's the pipeline, simplified:

  1. Resolve dependencies. The go tool reads go.mod, downloads any missing modules into the module cache, and verifies them against go.sum.
  2. Compile each package. Packages form a graph with no cycles (Go forbids import cycles), so independent packages compile in parallel. Each is parsed, type-checked, analyzed (e.g. escape analysis decides whether a value can live on the fast stack or must go on the garbage-collected heap — Chapter 18), optimized and turned into machine code.
  3. Cache. Compiled packages are stored in the build cache (go env GOCACHE). Unchanged packages are never recompiled.
  4. Link. The linker combines your code, your dependencies, the parts of the standard library you use, and the Go runtime (the garbage collector, goroutine scheduler and memory allocator) into one executable file.

"Static" means: just copy it

The resulting binary doesn't need Go installed on the target machine. Cross-compiling for another platform is just two environment variables — no extra toolchain to install:

$ GOOS=linux GOARCH=amd64 go build -o hello-linux .
$ file hello-linux
hello-linux: ELF 64-bit LSB executable, x86-64, version 1 (SYSV), statically linked, Go BuildID=…, with debug_info, not stripped

$ GOOS=windows GOARCH=amd64 go build -o hello.exe .
$ file hello.exe
hello.exe: PE32+ executable (console) x86-64, for MS Windows

From a Mac, we just built a Linux server binary and a Windows program. Run go tool dist list to see every supported GOOS/GOARCH pair (there are dozens, including linux/arm64 for Raspberry Pi and AWS Graviton, and js/wasm / wasip1/wasm for WebAssembly).

Gotcha: "static" has fine print

On Linux, a pure-Go binary is fully static. But if your program (or a dependency) uses cgo — calling C code — or certain packages like net and os/user choose the system's C library for DNS/user lookups, the binary may link dynamically against libc. Build with CGO_ENABLED=0 to force a pure-Go static binary; this is what you want for minimal Docker images like scratch or distroless. (On macOS, binaries always link the system library libSystem, because Apple requires it.)

Senior engineer tip: production build flags

A typical release build looks like:

CGO_ENABLED=0 go build -trimpath -ldflags="-s -w -X main.version=v1.4.2" -o app ./cmd/app

-trimpath removes your local file paths from the binary (reproducible builds, no leaked home directory). -s -w strip the symbol table and debug info (our hello went from 2.3M to 1.5M). -X injects a value into a string variable at link time — the standard way to stamp a version. Also know go version -m ./app: it prints the exact module versions baked into any Go binary, which is gold during incident response.

Editor setup: gopls, VS Code and friends

Go has an official language server called gopls ("go please"). A language server is a background program your editor talks to for smart features: autocomplete, go-to-definition, find references, rename across the project, inline errors as you type, and organizing imports. Because it's one shared tool, every editor gets the same quality.

VS Code (most popular)

  1. Install the Go extension (published by the Go team at Google).
  2. Open a folder containing a go.mod. The extension offers to install gopls and other tools — accept.
  3. Turn on format-on-save. The extension formats with gofmt and organizes imports automatically: type strings.ToUpper and the import "strings" line appears on save.
{
  "[go]": {
    "editor.formatOnSave": true,
    "editor.codeActionsOnSave": { "source.organizeImports": "explicit" }
  },
  "gopls": {
    "ui.semanticTokens": true,
    "ui.diagnostic.staticcheck": true
  }
}

Other editors

  • GoLand (JetBrains): a full commercial IDE with excellent refactoring and debugging out of the box.
  • Neovim / Vim / Emacs / Helix / Zed: point the built-in LSP client at gopls.

For debugging, the standard Go debugger is Delve (dlv). VS Code and GoLand use it under the hood when you set a breakpoint and press F5.

Learn three gopls features early: Go to Definition (jump into the standard library source — it's very readable and the best way to learn idiomatic Go), Find References, and Rename Symbol (safe, project-wide renames).

The Go Playground

At go.dev/play you can run Go in the browser with nothing installed. It's perfect for trying a snippet or sharing a reproducible example in a bug report or code review ("here's a playground link that shows the problem"). Limitations: no network access, limited time and memory, and — a classic surprise — the clock starts at a fixed date (2009-11-10 23:00:00 UTC, Go's open-source birthday), so time.Now() looks frozen and output is deterministic.

Reading docs at pkg.go.dev

pkg.go.dev hosts documentation for the standard library and every public Go module. Search a package (try strings), and you'll see: the package overview, an index of every exported function and type, runnable examples, the module's version history, its license, and who imports it. Docs are generated directly from code comments — which brings us to comments.

Comments and doc comments

Go has two comment styles, same as C:

// A line comment runs to the end of the line. This is what you'll use 99% of the time.

/* A block comment
   can span lines. Mostly used for temporarily disabling code
   or for long license headers. */

A doc comment is simply a comment placed directly above a top-level declaration (package, function, type, const, var), with no blank line between. Tools like go doc, pkg.go.dev and your editor's hover display them. The conventions:

  • Start with the name of the thing: // Hello returns ..., // Package greet builds ....
  • Write full sentences. The first sentence is the summary shown in indexes.
  • Since Go 1.19, doc comments support light formatting: blank-line paragraphs, lists starting with -, indented code blocks, # Headings, and links like [DefaultName] or [strings.ToUpper].
// Package greet builds friendly greetings.
//
// It is a tiny example package used to show how
// doc comments become documentation.
package greet

import "fmt"

// DefaultName is used when Hello is called with an empty name.
const DefaultName = "Gopher"

// Hello returns a greeting for name.
// If name is empty, it greets [DefaultName] instead.
func Hello(name string) string {
	if name == "" {
		name = DefaultName
	}
	return fmt.Sprintf("Hello, %s!", name)
}
package main

import (
	"fmt"

	"example.com/doccmt/greet"
)

func main() {
	fmt.Println(greet.Hello(""))
	fmt.Println(greet.Hello("Ada"))
}
  1. The import path is the module path plus the folder: example.com/doccmt + /greet. Inside this file we refer to the package by its name, greet.
  2. We call greet.Hello(""). Only Hello (capital H) is reachable from here — a lowercase function in greet would be invisible.
  3. Inside Hello, the empty name triggers the if name == "" branch and name is replaced with the exported constant DefaultName.
  4. fmt.Sprintf builds the string and Hello returns it; Println prints it.
  5. Second call: a non-empty name skips the if, so the greeting uses "Ada" directly. main returns and the program exits.
Hello, Gopher!
Hello, Ada!

Now ask go doc about it. Notice how the comments became documentation, and [DefaultName] became a cross-reference:

$ go doc ./greet

Senior engineer tip

Document every exported identifier, and explain the why and the contract, not the how: what are valid inputs, what's returned on error, is it safe to call from multiple goroutines, who owns (closes) the returned resource. A comment like // GetUser gets the user is noise. // GetUser returns ErrNotFound if no user has the given id. It is safe for concurrent use. saves your teammates real time. Linters like revive can enforce that exported names have doc comments.

Semicolons you don't write

Go's grammar actually uses semicolons to end statements, like C. You just never type them, because the lexer (the part of the compiler that splits source text into tokens) inserts them automatically. The rule, simplified:

The semicolon rule

When a line ends with something that could end a statement — an identifier, a literal (42, "hi"), one of the keywords break continue fallthrough return, the operators ++ --, or a closing ) ] } — Go puts a semicolon there.

This has one huge consequence: an opening brace must be on the same line. Look what happens if you put it on the next line, C#-style:

package main

import "fmt"

func main()
{
	fmt.Println("brace on its own line")
}
# command-line-arguments
./main.go:6:1: syntax error: unexpected semicolon or newline before {

The line func main() ends with ), so Go inserted a semicolon after it — and func main(); followed by a lonely { is a syntax error. The same rule explains why a multi-line list needs a trailing comma:

nums := []int{
	1,
	2,
	3
}
// syntax error: unexpected newline in
// composite literal; possibly missing
// comma or }
nums := []int{
	1,
	2,
	3, // trailing comma required
}
// Bonus: adding a 4th line later is a
// one-line diff in code review.

You can write semicolons yourself to put two statements on one line (a := 1; b := 2), and you'll see them in for loop headers (for i := 0; i < n; i++). gofmt will split the first form onto separate lines anyway.

Strict by design: unused imports and variables

Go refuses to compile a program with an unused import or an unused local variable. Beginners find this annoying for about a week. Then they come to love it.

package main

import (
	"fmt"
	"os"
)

func main() {
	x := 42
	fmt.Println("hi")
}
# command-line-arguments
./main.go:5:2: "os" imported and not used
./main.go:9:2: declared and not used: x

Why so strict? An unused import slows down every build and can drag in side effects (a package's init code runs whenever it's imported). An unused variable is very often a bug — you computed something and forgot to use it, or a typo meant you used a different variable.

While experimenting, assign to the blank identifier _ to silence the error temporarily: _ = x. For imports, import _ "image/png" means "import only for its side effects" (here: registering the PNG decoder). Chapter 02 covers _ fully. Better still, let your editor's organize-imports fix imports for you.

How a Go program starts

When you run a Go binary, a precise sequence happens before your main function's first line. Knowing it removes a whole category of "why is this nil?" bugs.

  1. Runtime setup. The Go runtime initializes memory, the garbage collector and the goroutine scheduler.
  2. Imported packages first. If main imports fmt, and fmt imports os, then os is initialized before fmt, which is initialized before main. Each package is initialized exactly once, no matter how many packages import it.
  3. Package-level variables are initialized. Order: by dependency first — if a's initializer uses b, then b is initialized first, even if it's declared later or in another file. Otherwise, in the order they appear.
  4. init() functions run. Any file can have any number of func init(). They take no arguments, return nothing, and you cannot call them yourself. Within a package they run in the order the files are presented to the compiler (alphabetical by filename with the go tool) and top to bottom within a file.
  5. main() runs. When it returns, the program exits — immediately, even if other goroutines are still running.
var greeting = makeGreeting()

func makeGreeting() string {
	fmt.Println("1. package var initialized")
	return "hi"
}

func init() {
	fmt.Println("2. init() runs, greeting =", greeting)
	greeting += " there"
}

func main() {
	fmt.Println("3. main() runs:", greeting)
}
  1. Before anything in main, Go initializes package-level variables. greeting's initializer is a function call, so Go calls makeGreeting().
  2. makeGreeting prints and returns "hi".
  3. The returned value is stored in greeting. All package variables are now initialized.
  4. Next, init() runs automatically. It can rely on every package variable already having its value.
  5. init modifies the package variable. This is a typical use: finishing setup that can't be written as a simple expression.
  6. Finally main() runs and sees the fully prepared state. When it returns, the program exits with status 0.
1. package var initialized
2. init() runs, greeting = hi
3. main() runs: hi there

Across multiple files

Here's a package split over three files. Watch how dependency order beats file order for variables, while init functions follow file order:

package main

import "fmt"

// total depends on base, so Go initializes base first,
// even though base is declared later (in b.go).
var total = trace("total", base*2)

func init() {
	fmt.Println("init() in a.go")
}
package main

import "fmt"

var base = trace("base", 21)

func init() {
	fmt.Println("init() in b.go")
}

func trace(name string, v int) int {
	fmt.Printf("initializing %s = %d\n", name, v)
	return v
}
package main

import "fmt"

func init() {
	fmt.Println("init() in main.go (first one)")
}

func init() {
	fmt.Println("init() in main.go (second one)")
}

func main() {
	fmt.Println("main() starts; total =", total)
}
  1. Before any line of main.go runs, Go initializes package variables across all three files. a.go sorts first, but its total = trace("total", base*2) needs base, so Go jumps to b.go.
  2. base = trace("base", 21) in b.go runs first and prints.
  3. With base ready, total's initializer computes 21*2. Every package variable is now set.
  4. Now the init functions run in file order: a.go, then b.go. Variable order followed dependencies; init order follows files.
  5. main.go is last alphabetically. Its first init runs. Yes, one file can have several.
  6. Its second init runs, top to bottom within the file.
  7. Only after all of that does main start, and it sees total fully initialized.
initializing base = 21
initializing total = 42
init() in a.go
init() in b.go
init() in main.go (first one)
init() in main.go (second one)
main() starts; total = 42

total lives in a.go, which comes first alphabetically, but it needs base, so base is initialized first. Then all the inits run: a.go's, b.go's, then main.go's two in order.

Gotcha: init() is a trap in large codebases

init runs whenever a package is imported — including in tests and in tools that merely import your package. If it opens a database connection, reads a config file or calls the network, every import becomes slow and fragile, and errors can only be handled by panicking. Prefer explicit setup functions called from main (db, err := store.Open(cfg)). Reserve init for cheap, can't-fail work like registering a driver or building a lookup table.

Exiting: return from main vs os.Exit

Returning from main exits with status 0. To exit with a different status, call os.Exit(code). But beware: os.Exit stops the program instantly — deferred functions (Chapter 03) do not run.

package main

import (
	"fmt"
	"os"
)

func main() {
	defer fmt.Println("cleanup (never printed!)")
	fmt.Println("doing work...")
	os.Exit(3) // exits immediately: deferred calls do NOT run
}
  1. main starts. Nothing is scheduled yet.
  2. defer registers the Println to run when main returns. Nothing prints now.
  3. Ordinary work prints its line.
  4. Gotcha: os.Exit(3) terminates the process on the spot. main never returns, so the deferred call never fires — flushes, file closes and unlocks registered with defer are all skipped.
  5. This closing brace is never reached. The shell sees exit status 3 and only one line of output.
doing work...

The standard fix is to move the real work into a run function that returns an exit code. Its defers fire on the way out, and main becomes a thin shell around it:

package main

import (
	"fmt"
	"os"
)

func run(args []string) int {
	defer fmt.Println("run: deferred cleanup")
	if len(args) < 2 {
		fmt.Println("run: missing argument")
		return 2
	}
	fmt.Println("run: hello,", args[1])
	return 0
}

func main() {
	code := run([]string{"prog"})
	fmt.Println("main: exiting with", code)
	os.Exit(code)
}
  1. main calls run with a fake argument list containing only the program name, as if the user typed no arguments.
  2. defer does not print yet: it schedules the call to run when run returns, however it returns.
  3. len(args) is 1, which is less than 2, so we take the error branch.
  4. return 2 starts leaving the function, and right before control goes back to the caller, the deferred call fires.
  5. Back in main, code holds 2. Lines 14–15 never ran.
  6. We log the exit code.
  7. os.Exit(2) ends the process immediately with status 2. That's safe now: main has no defers of its own, and run's cleanup already happened.
run: missing argument
run: deferred cleanup
main: exiting with 2

Programs receive command-line arguments in os.Args, a list of strings where os.Args[0] is the program's own name. Let's trace a small CLI run as go run . Ada Linus:

args := os.Args[1:]
if len(args) == 0 {
	fmt.Fprintln(os.Stderr, "usage: greet NAME...")
	os.Exit(2)
}
for i, name := range args {
	fmt.Printf("%d: Hello, %s!\n", i+1, name)
}
fmt.Println("greeted", len(args), "people")
  1. os.Args[1:] takes everything after the program name. (The [1:] syntax is a slice expression — Chapter 05.)
  2. The length is 2, not 0, so we skip the usage branch. With no arguments, we'd print usage to stderr and exit with status 2 (the Unix convention for "bad usage").
  3. range walks the list, giving an index i and the element name. First iteration: index 0, so we print i+1.
  4. Second iteration.
  5. The loop is done. We print a summary and main returns: exit status 0.
1: Hello, Ada!
2: Hello, Linus!
greeted 2 people
usage: greet NAME...
In the multi-file example, why is base initialized before total, even though a.go (which declares total) comes first?
Package-level variables are initialized in dependency order. total = base*2 needs base, so base goes first. All init() functions run only after every package variable is initialized.
Which of these will NOT compile?
The automatic semicolon rule inserts a ; after the ) at the end of func main(), leaving the { stranded. The other three are all legal Go.

The gofmt philosophy

Most languages have style wars: tabs vs spaces, where braces go, how to align things. Go ended them by shipping a formatter on day one and making its output the community standard. As Rob Pike put it, "Gofmt's style is no one's favorite, yet gofmt is everyone's favorite."

  • Code reviews focus on substance. Nobody comments on spacing.
  • Diffs are clean. Changes show only real changes, never reformatting noise.
  • Tools can rewrite code safely. Because there's one canonical form, tools like gofmt -r, gopls renames and go fix can edit code and re-format it without anyone noticing a difference in style.
  • All Go looks the same. The standard library, Kubernetes and your company's code are visually identical, so reading unfamiliar code is easier.

The same philosophy shows up across the toolchain: one build tool, one test runner, one doc format, one dependency system. Go prefers one obvious way.

goimports is gofmt plus automatic adding/removing of import lines; editors usually run it on save. gofumpt is a stricter, community-maintained superset of gofmt that some teams adopt. Either is fine — just make it automatic.

A senior engineer's workflow

Let's put it all together into the workflow experienced Go engineers actually use day to day.

# start a project
mkdir billing && cd billing
go mod init github.com/acme/billing
git init

# inner loop (seconds)
go run ./cmd/billing          # run the program
go test ./...                 # run all tests
go test -run TestInvoice -v ./internal/invoice   # one test, verbose

# before pushing
gofmt -l .                    # should print nothing
go vet ./...
go test -race -count=1 ./...  # -count=1 disables test result caching
go mod tidy && git diff --exit-code go.mod go.sum

# ship
CGO_ENABLED=0 go build -trimpath -ldflags="-s -w" -o bin/billing ./cmd/billing

A typical project layout

Small programs can be a single main.go. As a service grows, most Go teams converge on a layout like this (Chapter 11 explains each piece and Chapter 21 builds one):

billing/
├── go.mod              # module github.com/acme/billing
├── go.sum              # checksums of every dependency (commit it!)
├── cmd/
│   └── billing/
│       └── main.go     # package main: wiring only, flags, startup
├── internal/           # importable ONLY from inside this module
│   ├── invoice/
│   │   ├── invoice.go
│   │   └── invoice_test.go
│   └── store/
│       └── postgres.go
└── README.md
  • cmd/<name>/ holds one directory per executable. Keep main thin: parse config, build dependencies, start things.
  • internal/ is enforced by the go tool: code outside your module can't import it. It's the safe default for everything that isn't a deliberate public API.
  • Tests live next to the code they test, in _test.go files of the same directory.
  • There's no src/ directory, no Makefile requirement, and no build config file — go build ./... just works.

Don't start with this structure for a 200-line tool. Start flat (main.go plus a few files in package main), and split into packages when a clear boundary appears. Over-structured small Go projects are a common beginner habit carried over from Java.

Senior engineer tip: pin your tools

Teams waste hours when everyone's linter or code generator is a different version. Since Go 1.24, you can record tool dependencies directly in go.mod with go get -tool golang.org/x/tools/cmd/stringer@v0.30.0 and run them with go tool stringer. The version is pinned and checksummed like any other dependency, so CI and every laptop use exactly the same tool.

Senior engineer tip: read the standard library

The Go standard library is some of the best Go code ever written, and it's right there: go env GOROOT, then open src/strings/strings.go or src/net/http/server.go. When you're unsure what's idiomatic — how to name things, structure errors, write doc comments — copy what the standard library does.

Exercises

1 · Make a module that prints its own version, stamped at build time

Create a module with a package-level variable var version = "dev" and a main that prints app version: <version>. Run it with go run ., then build it so that it prints v1.0.0 without editing the source. Hint: look at the -ldflags tip above.

Solution
package main

import "fmt"

// version is overridden at build time with -ldflags "-X main.version=...".
var version = "dev"

func main() {
	fmt.Println("app version:", version)
}
  1. At startup the package variable version gets its initial value "dev" — unless the linker overwrote it. With plain go run . nothing overrides it.
  2. main prints the current value. This is the first line of output in the solution.
  3. Now build with -ldflags="-X main.version=v1.0.0". The linker patches the string's initial value inside the binary; the source still says "dev". It only works on package-level string variables, never constants.
  4. Running ./app prints the stamped version. Release pipelines use exactly this to embed a Git tag or commit hash.
$ go run . && go build -ldflags="-X main.version=v1.0.0" -o app . && ./app
app version: dev
app version: v1.0.0

-X importpath.name=value only works on package-level string variables (not constants). For package main, the import path is simply main.

2 · Predict the startup order

Without running it, write down what this program prints. Then run it and check. Hint: remember the order — package variables (by dependency), then inits (in source order), then main.

package main

import "fmt"

var a = show("a", b+1)
var b = show("b", 2)

func show(name string, v int) int {
	fmt.Println("var", name)
	return v
}

func init() { fmt.Println("init 1") }
func init() { fmt.Println("init 2") }

func main() {
	fmt.Println("main: a =", a)
}
  1. Before main, Go initializes package variables. a is declared first, but its initializer reads b, so Go must set b first. Dependency order beats source order.
  2. b's initializer calls show("b", 2), which prints and returns 2.
  3. b now holds 2, so a's dependency is ready.
  4. Now a's initializer runs: show("a", b+1) is called with v = 3.
  5. All package variables are set. Only now do the init functions get a turn.
  6. The first init runs. A file may declare several init functions; they run top to bottom.
  7. The second init runs.
  8. Finally main runs and prints a, which is b + 1 = 3. Then the program exits with status 0.
Solution
var b
var a
init 1
init 2
main: a = 3

a depends on b, so b is initialized first (printing "b"), then a (printing "a"). Next both inits run top to bottom. Finally main prints a, which is b + 1 = 3.

Solution

Key takeaways

  • Go was designed at Google for large teams and large codebases: simple, fast to compile, concurrent, and deployable as one binary.
  • Install from go.dev/dl; check with go version. Toolchains can auto-upgrade per project via go.mod.
  • Use modules: go mod init <path> anywhere on disk. GOPATH is now just a cache and install location.
  • package main + func main() = an executable. Capitalized names are exported; lowercase names are package-private.
  • Daily tools: go run, build, fmt, vet, test, doc, mod tidy. Automate fmt/vet/test in CI.
  • Builds produce a self-contained binary; cross-compile with GOOS/GOARCH; use CGO_ENABLED=0 for fully static Linux builds.
  • Startup order: imported packages → package variables (dependency order) → init()s → main(). os.Exit skips deferred calls.
  • Semicolons are inserted automatically at line ends, so opening braces go on the same line and multi-line literals need trailing commas.
  • Unused imports and variables are compile errors. gofmt is non-negotiable — let your editor run it on save.

Shipping Go to Production

Writing the code is half the job. The other half is turning it into a small, versioned, observable binary that starts fast, configures itself from the environment, tells you when it's sick, shuts down politely and gets rebuilt and checked by CI on every commit. Go is famously good at this part. Let's see why, and how.

Why Go is great at shipping

Before containers were everywhere, deploying a Python or Java service meant installing the right interpreter or JVM, the right libraries, the right system packages, on every server. Go took a different path: go build produces one self-contained executable file. The Go runtime (scheduler, garbage collector) and every library you use are compiled into it. Copy the file to a machine with the same OS and CPU type, run it, done.

  • Single static binary: no runtime to install, tiny container images.
  • Cross-compiling is built in: from a Mac you can build for Linux on ARM with two environment variables.
  • Fast startup: milliseconds, which matters for autoscaling and serverless.
  • Batteries included: HTTP server, TLS, JSON, structured logging, metrics (expvar) and profiling (pprof) all live in the standard library.

Build flags and version embedding

Here's a tiny program we'll ship. It has three package-level variables, version, commit and date, that default to placeholder values. We'll overwrite them at build time.

package main

import (
	"flag"
	"fmt"
	"os"
	"runtime/debug"
)

// Set at build time with: -ldflags "-X main.version=1.4.2 -X main.commit=abc123"
var (
	version = "dev"
	commit  = "none"
	date    = "unknown"
)

func main() {
	showBuild := flag.Bool("buildinfo", false, "print embedded build info")
	flag.Parse()

	fmt.Printf("hello %s (commit %s, built %s)\n", version, commit, date)

	if !*showBuild {
		return
	}
	info, ok := debug.ReadBuildInfo()
	if !ok {
		fmt.Fprintln(os.Stderr, "no build info")
		return
	}
	fmt.Println("go version:", info.GoVersion)
	fmt.Println("module:    ", info.Main.Path, info.Main.Version)
	for _, s := range info.Settings {
		switch s.Key {
		case "-ldflags", "-trimpath", "CGO_ENABLED", "GOOS", "GOARCH",
			"vcs", "vcs.revision", "vcs.time", "vcs.modified":
			fmt.Printf("  %-12s = %s\n", s.Key, s.Value)
		}
	}
}
  1. We run the binary built with -X main.version=... -X main.commit=... -X main.date=.... The linker already replaced the defaults, before main starts.
  2. The -buildinfo flag is set on the command line.
  3. The stamped strings print. A plain go build would print hello dev (commit none, built unknown).
  4. *showBuild is true, so we keep going. debug.ReadBuildInfo reads data the Go toolchain embeds in every binary.
  5. The exact Go version that compiled this binary.
  6. Go 1.24+ fills the main module's version from the git tag automatically.
  7. We loop over the build settings and print only the interesting keys. The switch skips the rest.
  8. Build flags and target platform. -ldflags is missing: with -trimpath, Go leaves linker flags out of the build info.
  9. The VCS stamp: full commit hash, commit time, and whether the tree had uncommitted changes. vcs.modified = false means the binary matches the commit exactly.

A plain build prints the defaults:

$ go build -o bin/hello .
$ ./bin/hello
hello dev (commit none, built unknown)

Gotcha

-X only works on package-level variables of type string. var version = "dev" works (and with current toolchains even var version = getVersion() is overwritten); const version = "dev" silently doesn't, and a non-string variable is a link error. The path must be the full import path: -X main.version for package main, -X example.com/app/internal/build.Version for anything else. A typo produces no error, just the default value.

Let's test those rules. We build this program with go run -ldflags "-X main.version=1.4.2 -X main.Commit=abc123 -X main.release=1.4.2 -X main.built=2026-10-16" ., where main.Commit is a deliberate typo:

package main

import "fmt"

var version = "dev" // plain string var: -X sets it

var commit = "none" // we will misspell this one on purpose

const release = "dev" // a constant: -X cannot touch it

var built = today() // function initialiser: the -X value still wins

func today() string { return "unknown" }

func main() {
	fmt.Println("version:", version)
	fmt.Println("commit: ", commit)
	fmt.Println("release:", release)
	fmt.Println("built:  ", built)
}
  1. The linker finds a package-level string variable named main.version and replaces its initial value. This happens at link time, before any code runs.
  2. We asked for main.Commit with a capital C. No such symbol exists, and the linker ignores it without a warning, so commit keeps its default.
  3. A const has no storage in the binary to patch; it is folded into the code at compile time. -X main.release also does nothing.
  4. built has a function initialiser. The toolchain sees that -X targets it and uses the flag's value; today() does not overwrite it.
  5. The good case.
  6. The typo. In CI this ships a binary that claims commit "none". Check the output of -version in your release pipeline.
  7. The constant never changes.
  8. The linker value won. (Passing -X for an int variable would fail the build: "cannot set with -X: not a var of type string".)
version: 1.4.2
commit:  none
release: dev
built:   2026-10-16

Free version info: debug.ReadBuildInfo

Even without -X, Go embeds a lot of information into every binary: the Go version, the module path, every dependency with its version, the build settings, and (when built inside a git checkout) the commit hash, commit time and whether the working tree had uncommitted changes. Since Go 1.24, go build also stamps the main module's version from the git tag. You can read all of it at runtime:

What CGO_ENABLED=0 means

cgo is the feature that lets Go call C code. A few standard packages optionally use it: net (to ask the system's C library for DNS lookups) and os/user (to read user accounts). When cgo is on, your binary dynamically links against the system's C library (libc), so it only runs where a compatible libc exists. Alpine Linux, for example, uses musl instead of glibc, and a cgo binary built on Ubuntu may fail there with a confusing "not found" error.

With CGO_ENABLED=0, Go uses its pure-Go DNS resolver and user lookup, and the result is a fully static binary that depends on nothing but the kernel.

Setting CGO_ENABLED=0 explicitly makes it independent of the machine you build on, so always set it in CI and Dockerfiles.

If you truly need cgo (SQLite via mattn/go-sqlite3, image libraries), cross-compiling gets hard: you need a C cross-compiler (zig cc is a popular trick) or you build inside a container for each target. Prefer pure-Go alternatives when they exist, such as modernc.org/sqlite.

Containers: multi-stage Dockerfiles

A multi-stage build uses one big image that has the Go toolchain to build, then copies just the binary into a tiny image to run. The final image doesn't contain the compiler, your source code, or a shell. Smaller images download faster, start faster, and give attackers almost nothing to work with.

# syntax=docker/dockerfile:1

# ---------- stage 1: build ----------
FROM --platform=$BUILDPLATFORM golang:1.27 AS build
WORKDIR /src

# Download modules first: this layer is cached until go.mod/go.sum change.
COPY go.mod go.sum ./
RUN --mount=type=cache,target=/go/pkg/mod go mod download

COPY . .
ARG TARGETOS TARGETARCH VERSION=dev
RUN --mount=type=cache,target=/go/pkg/mod \
    --mount=type=cache,target=/root/.cache/go-build \
    CGO_ENABLED=0 GOOS=$TARGETOS GOARCH=$TARGETARCH \
    go build -trimpath -ldflags="-s -w -X main.version=${VERSION}" -o /out/app ./cmd/api

# ---------- stage 2: run ----------
# distroless/static: CA certs, tzdata, /etc/passwd, no shell, no package manager.
FROM gcr.io/distroless/static-debian12:nonroot
COPY --from=build /out/app /app
USER nonroot:nonroot
EXPOSE 8080
ENTRYPOINT ["/app"]

Line by line, the important ideas:

  • Copy go.mod/go.sum first, then go mod download: Docker caches each layer. Your dependencies change rarely, your code changes constantly, so this ordering means most builds skip the download entirely.
  • --mount=type=cache (BuildKit) keeps Go's module and build caches between builds, so rebuilds are incremental.
  • --platform=$BUILDPLATFORM plus TARGETOS/TARGETARCH: the build stage runs natively on your machine and cross-compiles for the target. docker buildx build --platform linux/amd64,linux/arm64 . then builds a multi-arch image without slow CPU emulation. This is where Go's cross-compiling really pays off.
  • distroless/static:nonroot: about 2 MB, containing only CA certificates (for HTTPS calls), timezone data and a non-root user. Your final image is typically 10–20 MB.
  • USER nonroot: never run as root inside the container.

If you want the absolute minimum, use scratch, a completely empty image. Then you must bring CA certificates and timezone data yourself:

FROM golang:1.27 AS build
WORKDIR /src
COPY . .
RUN CGO_ENABLED=0 go build -trimpath -ldflags="-s -w" -o /app ./cmd/api

FROM scratch
# scratch is truly empty: bring your own CA certificates and timezone data.
COPY --from=build /etc/ssl/certs/ca-certificates.crt /etc/ssl/certs/
COPY --from=build /usr/share/zoneinfo /usr/share/zoneinfo
COPY --from=build /app /app
USER 65534:65534
ENTRYPOINT ["/app"]

Configuration the 12-factor way

The 12-factor app is a well-known set of principles for cloud services. Factor III says: store config in the environment. The same binary (the same Docker image) should run in dev, staging and production. Only the environment variables differ. That means no config.prod.yaml baked into the image and no "if env == production" branches.

A good config loader in Go:

  1. Has sensible defaults so the app runs locally with zero setup.
  2. Reads environment variables (what Kubernetes, Docker and every PaaS give you).
  3. Lets command-line flags override everything (handy for local experiments).
  4. Validates everything at startup and refuses to start with bad config. Failing fast at boot is far better than failing at 3 a.m. on the first request that needs the value.
  5. Builds one typed Config struct that's passed to the rest of the program. Nothing else calls os.Getenv.
package main

import (
	"flag"
	"fmt"
	"os"
	"strconv"
	"time"
)

type Config struct {
	Addr            string
	LogLevel        string
	ShutdownTimeout time.Duration
	MaxWorkers      int
}

// env returns the environment variable or a fallback.
func env(key, fallback string) string {
	if v, ok := os.LookupEnv(key); ok {
		return v
	}
	return fallback
}

// Load builds config with precedence: defaults < environment < flags.
func Load(args []string) (Config, error) {
	var c Config
	fs := flag.NewFlagSet("app", flag.ContinueOnError)
	fs.StringVar(&c.Addr, "addr", env("APP_ADDR", ":8080"), "listen address (env APP_ADDR)")
	fs.StringVar(&c.LogLevel, "log-level", env("APP_LOG_LEVEL", "info"), "debug|info|warn|error (env APP_LOG_LEVEL)")

	timeout, err := time.ParseDuration(env("APP_SHUTDOWN_TIMEOUT", "10s"))
	if err != nil {
		return c, fmt.Errorf("APP_SHUTDOWN_TIMEOUT: %w", err)
	}
	fs.DurationVar(&c.ShutdownTimeout, "shutdown-timeout", timeout, "graceful shutdown limit")

	workers, err := strconv.Atoi(env("APP_MAX_WORKERS", "4"))
	if err != nil {
		return c, fmt.Errorf("APP_MAX_WORKERS: %w", err)
	}
	fs.IntVar(&c.MaxWorkers, "max-workers", workers, "worker pool size")

	if err := fs.Parse(args); err != nil {
		return c, err
	}
	if c.MaxWorkers < 1 {
		return c, fmt.Errorf("max-workers must be >= 1, got %d", c.MaxWorkers)
	}
	return c, nil
}

func main() {
	cfg, err := Load(os.Args[1:])
	if err != nil {
		fmt.Fprintln(os.Stderr, "config error:", err)
		os.Exit(2)
	}
	fmt.Printf("%+v\n", cfg)
}

  1. We run APP_ADDR=:9000 app -addr :7000 -max-workers 16. Load receives the arguments after the program name.
  2. An empty Config and a fresh FlagSet. ContinueOnError makes bad flags return an error instead of exiting, which makes Load testable.
  3. The flag's default comes from env("APP_ADDR", ":8080"). The env var is set, so the default becomes :9000. StringVar writes that default into c.Addr straight away.
  4. APP_LOG_LEVEL isn't set, so we fall back to info.
  5. Non-string values need parsing. A bad duration in the env returns a clear error naming the variable.
  6. Same for the integer: default 4.
  7. fs.Parse applies the flags last, so they win: -addr :7000 beats the env var, -max-workers 16 beats the default.
  8. Validation runs on the final values. 16 is ≥ 1, so we're fine.
  9. We return the finished config, and main prints it.

The happy path is only half the story. A config loader earns its keep by refusing bad values at startup, with a message that names the culprit. This trimmed-down Load runs three times in one process:

package main

import (
	"flag"
	"fmt"
	"os"
	"strconv"
)

type Config struct {
	Addr       string
	MaxWorkers int
}

func env(key, fallback string) string {
	if v, ok := os.LookupEnv(key); ok {
		return v
	}
	return fallback
}

// Load: defaults < environment < flags.
func Load(args []string) (Config, error) {
	var c Config
	fs := flag.NewFlagSet("app", flag.ContinueOnError)
	fs.StringVar(&c.Addr, "addr", env("APP_ADDR", ":8080"), "listen address")
	workers, err := strconv.Atoi(env("APP_MAX_WORKERS", "4"))
	if err != nil {
		return c, fmt.Errorf("APP_MAX_WORKERS: %w", err)
	}
	fs.IntVar(&c.MaxWorkers, "max-workers", workers, "pool size")
	if err := fs.Parse(args); err != nil {
		return c, err
	}
	if c.MaxWorkers < 1 {
		return c, fmt.Errorf("max-workers must be >= 1, got %d", c.MaxWorkers)
	}
	return c, nil
}

func main() {
	os.Setenv("APP_ADDR", ":9000")
	os.Setenv("APP_MAX_WORKERS", "8")
	cfg, err := Load([]string{"-addr", ":7000"})
	fmt.Printf("1) %+v err=%v\n", cfg, err)

	os.Setenv("APP_MAX_WORKERS", "eight")
	_, err = Load(nil)
	fmt.Println("2) err:", err)

	os.Setenv("APP_MAX_WORKERS", "8")
	_, err = Load([]string{"-max-workers", "0"})
	fmt.Println("3) err:", err)
}
  1. Run 1: both env vars set, plus one flag. os.Setenv stands in for the real environment.
  2. The flag default comes from env, which finds APP_ADDR: the default is now :9000 instead of :8080.
  3. APP_MAX_WORKERS=8 parses fine and becomes the default for -max-workers.
  4. fs.Parse runs last and applies -addr :7000, overriding the env value. No -max-workers flag, so 8 stays.
  5. Validation passes. Precedence in one line: default :8080 < env :9000 < flag :7000.
  6. Run 2: someone typed a word in the deployment manifest. strconv.Atoi("eight") fails.
  7. We wrap with %w and prefix the variable name. Without the prefix the operator would only see "invalid syntax" and have to guess which setting.
  8. In main of the real program this is os.Exit(2): the pod crash-loops with a clear log line instead of running half-configured.
  9. Run 3: the env is valid again, but the flag -max-workers 0 overrides it with a value that parses but makes no sense.
  10. Parsing is not validation. The range check runs on the final merged value, after all sources are applied.
  11. A zero-worker pool would accept jobs and never process them. Failing fast at startup is far cheaper than finding that out in production.
1) {Addr::7000 MaxWorkers:8} err=<nil>
2) err: APP_MAX_WORKERS: strconv.Atoi: parsing "eight": invalid syntax
3) err: max-workers must be >= 1, got 0

Treat secrets (database passwords, API keys) as config too, but never log them, never put them in flags (flags show up in ps output) and never bake them into images. Read them from env vars injected by your platform's secret manager, or from a mounted file (DB_PASSWORD_FILE=/run/secrets/db). Libraries like github.com/caarlos0/env or kelseyhightower/envconfig fill a struct from env vars using tags, but the hand-written version above is often all a service needs.

Structured logging with slog

A plain log line like charging card for user 42 took 12ms is easy for humans to read but painful for machines: to find all slow charges you'd need a regex. A structured log is a set of key/value pairs, usually JSON, that log systems (Loki, Elasticsearch, CloudWatch, Datadog) can index and query: took_ms > 500 AND msg = "charging card".

log/slog (standard library since Go 1.21) gives you leveled, structured logging with zero dependencies:

package main

import (
	"context"
	"errors"
	"log/slog"
	"os"
	"time"
)

// Secret never prints its value, even by accident.
type Secret string

func (Secret) LogValue() slog.Value { return slog.StringValue("[REDACTED]") }

func main() {
	var level slog.LevelVar // can be changed at runtime
	level.Set(slog.LevelInfo)

	logger := slog.New(slog.NewJSONHandler(os.Stdout, &slog.HandlerOptions{
		Level:     &level,
		AddSource: false,
	})).With("service", "billing", "version", "v1.4.2")
	slog.SetDefault(logger) // log.Printf and slog.Info now go here too

	slog.Info("server starting", "addr", ":8080")
	slog.Debug("this is hidden at info level")

	reqLog := logger.With(slog.Group("req", "id", "r-42", "method", "POST", "path", "/charge"))
	reqLog.Info("charging card",
		"amount_cents", 1999,
		"api_key", Secret("sk_live_abc123"),
		"took", 12*time.Millisecond,
	)
	reqLog.Error("charge failed", "err", errors.New("card declined"))

	level.Set(slog.LevelDebug) // e.g. flipped by an admin endpoint
	slog.DebugContext(context.Background(), "debug now visible", "cache_hits", 17)
}
  1. A slog.LevelVar is a level you can change while the program runs. We start at INFO.
  2. A JSON handler writing to stdout, filtered by &level. .With(...) returns a child logger that adds service and version to every record.
  3. slog.SetDefault makes the top-level slog.Info functions (and the old log package) use our logger.
  4. One JSON object per line: time, level, message, the With attributes, then this call's key-value pairs.
  5. DEBUG is below INFO, so the handler drops this record. Nothing is printed and the arguments are barely evaluated.
  6. slog.Group nests attributes under one key. reqLog carries the request's identity on every line it writes.
  7. Secret implements slog.LogValuer, so the handler calls LogValue() and logs [REDACTED] instead of the key. A time.Duration is logged in nanoseconds by the JSON handler.
  8. An error value becomes its Error() string. Same request group, so you can grep every line for r-42.
  9. Flip the level at runtime, as an admin endpoint might during an incident. No restart, no new logger.
  10. The debug record now passes the filter. It uses the default logger, so it has service and version but no req group.

One more slog pattern worth watching step by step: a base logger with a minimum level, and child loggers per component. Text handler this time, which is what you want on your laptop.

package main

import (
	"context"
	"log/slog"
	"os"
)

func main() {
	opts := &slog.HandlerOptions{
		Level: slog.LevelWarn,
		ReplaceAttr: func(_ []string, a slog.Attr) slog.Attr {
			if a.Key == slog.TimeKey {
				return slog.Attr{} // drop time for stable output
			}
			return a
		},
	}
	base := slog.New(slog.NewTextHandler(os.Stdout, opts))

	db := base.With("component", "db")
	api := base.With("component", "api")

	db.Info("connected", "host", "pg-1") // below WARN: dropped
	db.Warn("slow query", "ms", 950)
	api.Error("upstream failed", "status", 502)
	if base.Enabled(context.Background(), slog.LevelDebug) {
		base.Debug("expensive dump", "state", "...")
	}
	api.WithGroup("user").Warn("rate limited", "id", 7, "plan", "free")
}
  1. Only records at WARN or above will be written. DEBUG and INFO are dropped at the door.
  2. ReplaceAttr runs on every attribute before it is written. Returning an empty slog.Attr{} for the time key removes it, which keeps test output stable.
  3. The base logger. NewTextHandler writes key=value pairs instead of JSON.
  4. With creates two children. They share the handler but each carries its own component attribute.
  5. db.Info is below WARN, so the handler's Enabled check says no and the record is never built. No output.
  6. WARN passes. The child's component=db comes first, then this call's ms=950. Messages with spaces are quoted.
  7. The api child tags its line with component=api.
  8. Enabled lets you skip expensive work (building a big dump) when the level would drop it anyway. The block is skipped.
  9. WithGroup("user") prefixes the following keys. The text handler shows groups as dotted names; JSON would nest them.
level=WARN msg="slow query" component=db ms=950
level=ERROR msg="upstream failed" component=api status=502
level=WARN msg="rate limited" component=api user.id=7 user.plan=free

Log rules that save you money and pain: use JSON in production and text locally; log to stdout and let the platform ship it (12-factor, factor XI); put a request ID on every line; log at Info for business events and Error only for things a human must look at; and never log secrets, tokens or full request bodies. High-volume debug logs cost real money in log storage.

Metrics with expvar and Prometheus

A metric is a number tracked over time: requests per second, error rate, latency percentiles, queue depth. The standard library's expvar package publishes counters as JSON at /debug/vars, which is great for small services and quick debugging. You'll see it running in the next section.

In most companies, though, the standard is Prometheus. Its Go client (github.com/prometheus/client_golang) exposes a /metrics endpoint that a Prometheus server scrapes every few seconds. A typical setup looks like this (not run here because it needs the third-party module):

var httpDuration = promauto.NewHistogramVec(prometheus.HistogramOpts{
	Name:    "http_request_duration_seconds",
	Help:    "Latency of HTTP requests.",
	Buckets: prometheus.DefBuckets,
}, []string{"method", "route", "status"})

// in middleware, after the handler runs:
httpDuration.WithLabelValues(r.Method, r.Pattern, strconv.Itoa(rec.status)).
	Observe(time.Since(start).Seconds())

// in main:
mux.Handle("GET /metrics", promhttp.Handler())
Gotcha: label cardinality

Every unique combination of label values creates a new time series. Use the route pattern (r.Pattern, e.g. GET /tasks/{id}, available since Go 1.23) as a label, never the raw path /tasks/81723, and never user IDs or emails. Otherwise you'll create millions of series and take down your monitoring.

Tracing with OpenTelemetry

When one user click fans out to five services, logs and metrics tell you that it was slow but not where. A distributed trace follows one request across every service: each step is a span with a start time and duration, and the trace ID travels between services in HTTP headers. OpenTelemetry (OTel) is the vendor-neutral standard; you instrument once and send data to Jaeger, Tempo, Honeycomb, Datadog or whatever your company uses.

// Wrap the whole mux: every request becomes a span, and incoming trace headers are honoured.
handler := otelhttp.NewHandler(mux, "taskapi")

// Inside your code, add child spans around interesting work:
ctx, span := otel.Tracer("task").Start(ctx, "store.Create")
defer span.End()

This is one more reason to pass context.Context everywhere: the current span lives in the context, so child spans and outgoing HTTP calls link up automatically.

Health checks and graceful shutdown

Orchestrators like Kubernetes keep asking your service two different questions, and it's important not to mix them up:

ProbeQuestionIf it fails…What to check
Liveness /healthz"Is the process alive and not stuck?"The container is restartedAlmost nothing. Just respond. Don't check the database here, or a DB blip restarts every pod at once.
Readiness /readyz"Should I send you traffic right now?"Removed from the load balancer, not restartedWarm-up finished, critical dependencies reachable, not shutting down.

Here's a production-shaped main that brings together everything so far: config from env, JSON logs with the version, a logging middleware that also feeds expvar metrics, liveness and readiness endpoints, server timeouts, and graceful shutdown on SIGTERM.

package main

import (
	"context"
	"errors"
	"expvar"
	"fmt"
	"log/slog"
	"net/http"
	"os"
	"os/signal"
	"strconv"
	"sync/atomic"
	"syscall"
	"time"
)

var version = "dev"

// Metrics, published automatically at /debug/vars by importing expvar.
var (
	requests = expvar.NewInt("http_requests_total")
	byStatus = expvar.NewMap("http_responses_by_status")
)

func main() {
	logger := slog.New(slog.NewJSONHandler(os.Stdout, nil)).With("version", version)
	if err := run(logger); err != nil {
		logger.Error("fatal", "err", err)
		os.Exit(1)
	}
}

func run(log *slog.Logger) error {
	addr := os.Getenv("ADDR")
	if addr == "" {
		addr = ":8080"
	}

	// Cancelled on Ctrl-C (SIGINT) or `docker stop` / Kubernetes (SIGTERM).
	ctx, stop := signal.NotifyContext(context.Background(), os.Interrupt, syscall.SIGTERM)
	defer stop()

	var ready atomic.Bool // flips to true once dependencies are warm

	mux := http.NewServeMux()
	mux.HandleFunc("GET /healthz", func(w http.ResponseWriter, r *http.Request) {
		fmt.Fprintln(w, "ok") // liveness: "the process is not wedged"
	})
	mux.HandleFunc("GET /readyz", func(w http.ResponseWriter, r *http.Request) {
		if !ready.Load() { // readiness: "send me traffic"
			http.Error(w, "not ready", http.StatusServiceUnavailable)
			return
		}
		fmt.Fprintln(w, "ready")
	})
	mux.HandleFunc("GET /hello/{name}", func(w http.ResponseWriter, r *http.Request) {
		fmt.Fprintf(w, "hello, %s\n", r.PathValue("name"))
	})
	mux.Handle("GET /debug/vars", expvar.Handler())

	srv := &http.Server{
		Addr:              addr,
		Handler:           logRequests(log, mux),
		ReadHeaderTimeout: 5 * time.Second,
		ReadTimeout:       10 * time.Second,
		WriteTimeout:      10 * time.Second,
		IdleTimeout:       60 * time.Second,
	}

	errCh := make(chan error, 1)
	go func() {
		log.Info("listening", "addr", addr)
		if err := srv.ListenAndServe(); !errors.Is(err, http.ErrServerClosed) {
			errCh <- err
		}
		close(errCh)
	}()

	// Pretend to warm caches / connect to the database.
	go func() {
		time.Sleep(300 * time.Millisecond)
		ready.Store(true)
		log.Info("ready")
	}()

	select {
	case err := <-errCh:
		return fmt.Errorf("listen: %w", err)
	case <-ctx.Done():
	}

	log.Info("shutdown signal received")
	ready.Store(false) // fail readiness first so the load balancer drains us

	shutdownCtx, cancel := context.WithTimeout(context.Background(), 10*time.Second)
	defer cancel()
	if err := srv.Shutdown(shutdownCtx); err != nil {
		return fmt.Errorf("shutdown: %w", err)
	}
	log.Info("shutdown complete")
	return nil
}

// statusRecorder remembers the status code a handler wrote.
type statusRecorder struct {
	http.ResponseWriter
	status int
}

func (r *statusRecorder) WriteHeader(code int) {
	r.status = code
	r.ResponseWriter.WriteHeader(code)
}

func logRequests(log *slog.Logger, next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		start := time.Now()
		rec := &statusRecorder{ResponseWriter: w, status: http.StatusOK}
		next.ServeHTTP(rec, r)
		requests.Add(1)
		byStatus.Add(strconv.Itoa(rec.status), 1)
		log.Info("request", "method", r.Method, "path", r.URL.Path,
			"status", rec.status, "dur_ms", time.Since(start).Milliseconds())
	})
}

  2. A request for GET /hello/gopher arrives. We note the start time.
  3. We wrap the real ResponseWriter in a statusRecorder. Embedding means it has every method of the original, but our WriteHeader remembers the code. It defaults to 200 because handlers that never call WriteHeader send 200.
  4. The mux matches GET /hello/{name}, and the handler writes the body. If it had been a POST, the mux itself would call WriteHeader(405) and we'd record 405.

  6. One structured log line per request (time and version fields trimmed here).

  1. main waits in a select for one of two things: the server failing to start, or a shutdown signal.

  3. Kubernetes sends SIGTERM. signal.NotifyContext turns that into a cancelled context, and this case fires.
  4. We flip readiness to false first. Any probe now gets 503, so the load balancer stops sending new requests.
  5. We give shutdown a hard deadline. It uses a fresh background context, because ctx is already cancelled.
  6. Shutdown closes the listeners (no new connections), closes idle connections, and waits for in-flight requests to finish. Meanwhile ListenAndServe returns ErrServerClosed, which the goroutine ignores.
  7. All requests done within the deadline. We return nil, deferred cleanups run, and the process exits with code 0.

The two probes answer different questions, and the difference shows up over time. This small program probes both endpoints in three phases of a pod's life, using httptest instead of a real port:

package main

import (
	"fmt"
	"net/http"
	"net/http/httptest"
	"sync/atomic"
)

var ready atomic.Bool // false until warm-up finishes

func healthz(w http.ResponseWriter, r *http.Request) {
	w.WriteHeader(http.StatusOK) // liveness: the process is alive
}

func readyz(w http.ResponseWriter, r *http.Request) {
	if !ready.Load() {
		http.Error(w, "not ready", http.StatusServiceUnavailable)
		return
	}
	fmt.Fprintln(w, "ok")
}

func probe(h http.Handler, path string) {
	rec := httptest.NewRecorder()
	h.ServeHTTP(rec, httptest.NewRequest("GET", path, nil))
	fmt.Println(path, rec.Code)
}

func main() {
	mux := http.NewServeMux()
	mux.HandleFunc("GET /healthz", healthz)
	mux.HandleFunc("GET /readyz", readyz)

	fmt.Println("-- starting (cache cold)")
	probe(mux, "/healthz")
	probe(mux, "/readyz")

	ready.Store(true) // warm-up done
	fmt.Println("-- warmed up")
	probe(mux, "/readyz")

	ready.Store(false) // SIGTERM: stop taking new traffic
	fmt.Println("-- draining")
	probe(mux, "/healthz")
	probe(mux, "/readyz")
}
  1. atomic.Bool is safe to flip from one goroutine (startup, signal handler) while request goroutines read it. Its zero value is false.
  2. Two routes. healthz always answers 200: "the process is alive, don't restart me". readyz asks "should I get traffic right now?".
  3. probe sends a fake request through the mux. Liveness is 200 even during warm-up, so Kubernetes won't kill a pod that is just slow to start.
  4. Readiness returns 503 while warming up, so the load balancer keeps traffic away from a cold cache.
  5. Warm-up done: flip the flag. The next readiness probe gets 200 and the pod joins the rotation.
  6. On SIGTERM we flip readiness back to false first. Liveness stays 200: the process is healthy, it is just leaving.
  7. Readiness 503 tells the load balancer to stop sending new requests while in-flight ones finish. Never make liveness depend on a database: an outage would restart every pod at once.

srv.Shutdown is the heart of graceful shutdown. Here it is in isolation: a slow request is already running when shutdown starts. Watch the order of events.

package main

import (
	"context"
	"fmt"
	"io"
	"net"
	"net/http"
	"time"
)

func main() {
	started := make(chan struct{})
	mux := http.NewServeMux()
	mux.HandleFunc("GET /slow", func(w http.ResponseWriter, r *http.Request) {
		close(started)
		time.Sleep(200 * time.Millisecond) // a request still in flight
		fmt.Println("handler: finished")
		io.WriteString(w, "done")
	})

	ln, _ := net.Listen("tcp", "127.0.0.1:0")
	srv := &http.Server{Handler: mux}
	go srv.Serve(ln)

	got := make(chan string)
	go func() {
		resp, err := http.Get("http://" + ln.Addr().String() + "/slow")
		if err != nil {
			got <- "client error: " + err.Error()
			return
		}
		b, _ := io.ReadAll(resp.Body)
		resp.Body.Close()
		got <- fmt.Sprintf("client: %d %s", resp.StatusCode, b)
	}()

	<-started
	fmt.Println("main: shutdown begins")
	ctx, cancel := context.WithTimeout(context.Background(), 2*time.Second)
	defer cancel()
	err := srv.Shutdown(ctx) // waits for the in-flight request
	fmt.Println("main: shutdown returned, err =", err)
	fmt.Println(<-got)

	_, err = http.Get("http://" + ln.Addr().String() + "/slow")
	fmt.Println("new request after shutdown fails:", err != nil)
}
  1. A handler that signals when it starts, then takes 200 ms. That simulates a real request in progress.
  2. Listen on a random free port and serve in a background goroutine.
  3. A client goroutine sends GET /slow. It will block until the response arrives.
  4. The server runs the handler, which closes started and begins sleeping. main was waiting on <-started, so it now knows a request is in flight.
  5. Shutdown closes the listener at once (no new connections), then waits until every active connection goes idle, bounded by the 2 s context.
  6. 200 ms later the handler finishes and writes its response. The request was not cut off.
  7. Only now, with no requests left, does Shutdown return. nil means it drained before the deadline; otherwise it would return context.DeadlineExceeded.
  8. The client got a complete 200 done. Nothing was dropped.
  9. A new request now fails: the listener is closed, so the connection is refused.

client: 200 done

The Kubernetes shutdown race

When a pod is deleted, Kubernetes sends SIGTERM and removes it from service endpoints at roughly the same time, but load balancers take a few seconds to notice. If you shut down instantly, those last few seconds of requests fail. Production services often sleep 5–10 seconds after flipping readiness and before calling Shutdown (or use a preStop hook). Make sure terminationGracePeriodSeconds (default 30s) is longer than that sleep plus your shutdown timeout.

Your service's database goes down for 20 seconds. Which design avoids making the outage worse?
If liveness depends on the database, every pod restarts at once, and when the DB comes back you have a cold-start stampede. Readiness failing just takes pods out of rotation temporarily, and they come back on their own when the dependency recovers.

Automating builds: Makefile, Taskfile and CI

A Makefile everyone can use

A Makefile is a shared list of the commands your project needs, so nobody has to remember the long go build invocation. make is installed almost everywhere. A self-documenting help target makes it friendly for new teammates.

# ---- variables -------------------------------------------------------------
APP      := hello
PKG      := ./...
VERSION  ?= $(shell git describe --tags --always --dirty 2>/dev/null || echo dev)
COMMIT   := $(shell git rev-parse --short HEAD 2>/dev/null || echo none)
DATE     := $(shell date -u +%Y-%m-%dT%H:%M:%SZ)
LDFLAGS  := -s -w -X main.version=$(VERSION) -X main.commit=$(COMMIT) -X main.date=$(DATE)
PLATFORMS := linux/amd64 linux/arm64 darwin/arm64 windows/amd64

.DEFAULT_GOAL := help
.PHONY: help fmt vet test race build cross clean check

help: ## show this help
	@grep -E '^[a-zA-Z_-]+:.*?## ' $(MAKEFILE_LIST) | \
		awk 'BEGIN {FS = ":.*?## "}; {printf "  \033[36m%-8s\033[0m %s\n", $$1, $$2}'

fmt: ## format code (fails in CI if anything changes)
	@test -z "$$(gofmt -l .)" || (gofmt -l . && exit 1)

vet: ## run go vet
	go vet $(PKG)

test: ## run unit tests
	go test $(PKG)

race: ## run tests with the race detector
	go test -race -count=1 $(PKG)

check: fmt vet race ## everything CI runs

build: ## build a release binary for this machine
	CGO_ENABLED=0 go build -trimpath -ldflags "$(LDFLAGS)" -o bin/$(APP) .

cross: ## build for every platform in PLATFORMS

Continuous integration with GitHub Actions

CI runs your checks on every push and pull request, on a clean machine, so "works on my laptop" stops being a thing. A solid Go pipeline runs: formatting, go mod tidy check, vet, tests with the race detector, a vulnerability scan, lint, and builds for every target platform.

name: ci

on:
  push:
    branches: [main]
  pull_request:

permissions:
  contents: read

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v5
      - uses: actions/setup-go@v6
        with:
          go-version-file: go.mod     # one source of truth for the Go version
          cache: true

      - name: Check formatting and go.mod
        run: |
          test -z "$(gofmt -l .)" || (gofmt -l . && exit 1)
          go mod tidy -diff

      - name: Vet
        run: go vet ./...

      - name: Test (race + coverage)
        run: go test -race -count=1 -coverprofile=coverage.out ./...

      - name: Vulnerabilities
        run: go run golang.org/x/vuln/cmd/govulncheck@latest ./...

      - name: Build
        run: CGO_ENABLED=0 go build -trimpath -o bin/app ./cmd/api

  lint:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v5
      - uses: actions/setup-go@v6
        with:
          go-version-file: go.mod
      - uses: golangci/golangci-lint-action@v8
        with:
          version: v2.5

  cross-build:
    needs: [test, lint]
    runs-on: ubuntu-latest
    strategy:
      matrix:
        goos: [linux, darwin, windows]
        goarch: [amd64, arm64]
    steps:
      - uses: actions/checkout@v5
      - uses: actions/setup-go@v6
        with:
          go-version-file: go.mod
      - run: CGO_ENABLED=0 GOOS=${{ matrix.goos }} GOARCH=${{ matrix.goarch }} go build -trimpath -o /dev/null ./cmd/api
  • go-version-file: go.mod means CI uses exactly the Go version your module declares. Upgrade Go in one place.
  • -count=1 disables test result caching so every CI run actually runs the tests.
  • permissions: contents: read follows least privilege: the CI token can't push code.
  • The matrix job cross-builds to /dev/null, just proving every platform compiles.

Scanning for vulnerabilities with govulncheck

govulncheck is the Go team's official vulnerability scanner. It checks your dependencies (and the standard library version you build with) against the Go vulnerability database. Its superpower: it does call-graph analysis, so it only reports a vulnerability if your code actually calls the affected function. That cuts the noise that makes most scanners useless.

go install golang.org/x/vuln/cmd/govulncheck@latest
govulncheck ./...                 # scan source (call-graph aware)
govulncheck -mode=binary ./bin/app  # scan an already-built binary
govulncheck -show verbose ./...   # also list vulns in modules you don't call

When it finds something, it prints the vulnerability ID (like GO-2025-1234), the module and version that fixes it, and the exact call stack from your code to the vulnerable function. The usual fix is go get module@fixed-version, or upgrading Go itself for standard-library issues. A clean run exits 0; findings exit 3, which fails CI.

Runtime tuning: GOMAXPROCS and GOMEMLIMIT

Go's defaults are good, and you should rarely touch the runtime knobs. But two of them matter a lot in containers.

GOMAXPROCS: how many threads run Go code

GOMAXPROCS is the number of OS threads that can execute Go code at the same time. By default it's the number of CPU cores. The problem: in a container limited to 2 CPUs on a 64-core machine, older Go versions saw 64 cores and set GOMAXPROCS=64. The Linux scheduler then throttled the container every 100 ms for using more than its quota, causing nasty latency spikes. The usual fix was importing go.uber.org/automaxprocs.

Since Go 1.25, the runtime is container-aware: on Linux it reads the cgroup CPU limit and sets GOMAXPROCS to match when the limit is lower than the core count. It also re-checks periodically, so if the orchestrator changes the limit, Go adjusts. This only applies when the go line in go.mod is 1.25 or later, and it's switched off if you set GOMAXPROCS yourself. So for new code: delete automaxprocs and let the runtime handle it.

GOMEMLIMIT: a soft memory ceiling

The garbage collector normally decides when to run based on GOGC (default 100: collect when the heap has doubled since the last collection). It knows nothing about your container's memory limit. So a service with a 400 MB live heap might grow towards 800 MB before collecting, and if the container limit is 512 MB, the kernel's OOM killer ends it.

GOMEMLIMIT (Go 1.19+) tells the GC: "try hard to stay under this much total memory". As usage approaches the limit, the GC runs more often. It's a soft limit: if your live data genuinely needs more, Go uses more rather than freezing in GC forever. Unlike GOMAXPROCS, it is not set automatically from the container limit.

package main

import (
	"fmt"
	"math"
	"runtime"
	"runtime/debug"
)

func main() {
	fmt.Println("NumCPU:     ", runtime.NumCPU())
	fmt.Println("GOMAXPROCS: ", runtime.GOMAXPROCS(0)) // 0 = just read it

	limit := debug.SetMemoryLimit(-1) // negative = just read it
	if limit == math.MaxInt64 {
		fmt.Println("GOMEMLIMIT:  none (math.MaxInt64)")
	} else {
		fmt.Printf("GOMEMLIMIT:  %d MiB\n", limit>>20)
	}
	gc := debug.SetGCPercent(-1) // read old value...
	debug.SetGCPercent(gc)       // ...and restore it
	fmt.Println("GOGC:       ", gc)
}
  1. runtime.NumCPU reports the logical CPUs the process can use.
  2. GOMAXPROCS(0) reads the current value without changing it. By default it equals the CPU count (or the container's CPU limit on Linux, Go 1.25+).
  3. SetMemoryLimit(-1) is a read. With no GOMEMLIMIT set, the limit is the max int64: effectively none.
  4. There is no getter for GOGC, so we set it to -1 to learn the old value, then put the old value straight back.
  5. Second run with environment variables. The CPU count is the same, but only 2 threads now run Go code at once.
  6. The limit is now 512 MiB in bytes; limit>>20 converts bytes to MiB. The GC works harder as the heap nears this.
  7. GOGC=50 means a GC cycle starts when the heap grows 50% over the live heap: less memory, more CPU.
$ go run ./tune

GOMAXPROCS:  8
GOMEMLIMIT:  none (math.MaxInt64)
GOGC:        100
$ GOMAXPROCS=2 GOMEMLIMIT=512MiB GOGC=50 go run ./tune
NumCPU:      8
GOMAXPROCS:  2
GOMEMLIMIT:  512 MiB
GOGC:        50

GOMEMLIMITnone~80–90% of the container memory limit, e.g. GOMEMLIMIT=900MiB for a 1 GiB container

In Kubernetes, you can wire GOMEMLIMIT to the container's real limit so they never drift apart:

containers:
  - name: api
    image: ghcr.io/acme/taskapi:v1.5.0
    resources:
      limits:
        memory: 1Gi
        cpu: "2"            # Go 1.25+ sets GOMAXPROCS=2 automatically
    env:
      - name: GOMEMLIMIT
        valueFrom:
          resourceFieldRef:
            resource: limits.memory
            divisor: "1"    # bytes; or compute 90% in your entrypoint
    readinessProbe:
      httpGet: { path: /readyz, port: 8080 }
    livenessProbe:
      httpGet: { path: /healthz, port: 8080 }

Setting GOMEMLIMIT to exactly the container limit leaves no room for memory Go doesn't manage (cgo, thread stacks, the binary itself). Leave 10–20% headroom. And never set GOGC=off with a limit unless you've load-tested it: if live memory nears the limit, the GC can end up running constantly ("death spiral").

Exercise 1: Add a /version endpoint that works with or without -ldflags

Add GET /version to the ops server. It should return JSON with version, commit and go. If version is still "dev" (no -X flag), fall back to the module version and vcs.revision from debug.ReadBuildInfo.

Solution
package main

import (
	"encoding/json"
	"fmt"
	"net/http"
	"net/http/httptest"
	"runtime"
	"runtime/debug"
)

var (
	version = "dev"
	commit  = "none"
)

type versionInfo struct {
	Version string `json:"version"`
	Commit  string `json:"commit"`
	Go      string `json:"go"`
}

// buildVersion prefers -ldflags values, then falls back to embedded build info.
func buildVersion() versionInfo {
	v := versionInfo{Version: version, Commit: commit, Go: runtime.Version()}
	info, ok := debug.ReadBuildInfo()
	if !ok {
		return v
	}
	if v.Version == "dev" && info.Main.Version != "" && info.Main.Version != "(devel)" {
		v.Version = info.Main.Version
	}
	if v.Commit == "none" {
		for _, s := range info.Settings {
			if s.Key == "vcs.revision" && len(s.Value) >= 7 {
				v.Commit = s.Value[:7]
			}
		}
	}
	return v
}

func versionHandler(w http.ResponseWriter, r *http.Request) {
	w.Header().Set("Content-Type", "application/json")
	json.NewEncoder(w).Encode(buildVersion())
}

func main() {
	mux := http.NewServeMux()
	mux.HandleFunc("GET /version", versionHandler)

	rec := httptest.NewRecorder()
	mux.ServeHTTP(rec, httptest.NewRequest("GET", "/version", nil))
	fmt.Print(rec.Code, " ", rec.Body.String())
}
  1. Package-level string variables with placeholder values. -ldflags -X can overwrite them at link time.
  2. First build: no -X flags. We serve one fake request with httptest, so no network is needed.
  3. The mux routes GET /version to versionHandler, which calls buildVersion. It starts from the ldflags values, still the defaults.
  4. debug.ReadBuildInfo succeeds. The version is still "dev", and Go 1.24+ stamped the module version from the git tag, so we take v1.5.0.
  5. The commit is still "none", so we look for vcs.revision in the build settings and keep its first 7 characters.
  6. The handler encodes the struct as JSON. Zero build flags, and we still know exactly what is running.
  7. Second build sets main.version at link time.
  8. Now v.Version is not "dev", so the build-info fallback is skipped: the explicit value wins.
  9. The commit still comes from VCS stamping because nobody overrode it.
$ go build -o v ./cmd/version
$ ./v
200 {"version":"v1.5.0","commit":"e5bc484","go":"go1.27.1"}
$ go build -ldflags "-X main.version=v9.9.9-custom" -o v ./cmd/version
$ ./v
200 {"version":"v9.9.9-custom","commit":"e5bc484","go":"go1.27.1"}

Built inside the tagged git repo without any -X flags, the binary still knows it's v1.5.0 and which commit it came from, thanks to Go 1.24+ VCS stamping. With -X, the explicit value wins.

Exercise 2: Make shutdown wait for a background worker

The ops server has no background work. Add a goroutine that "flushes metrics" every second, and make sure that on SIGTERM it finishes its current flush and exits before the process does. Use the existing ctx and a sync.WaitGroup.

Solution
package main

import (
	"context"
	"errors"
	"log/slog"
	"net/http"
	"os"
	"os/signal"
	"sync"
	"syscall"
	"time"
)

func flusher(ctx context.Context, log *slog.Logger) {
	t := time.NewTicker(time.Second)
	defer t.Stop()
	for {
		select {
		case <-ctx.Done():
			log.Info("flusher: final flush, exiting")
			return
		case <-t.C:
			log.Info("flusher: flushed metrics")
		}
	}
}

func main() {
	log := slog.New(slog.NewTextHandler(os.Stdout, &slog.HandlerOptions{
		ReplaceAttr: func(_ []string, a slog.Attr) slog.Attr {
			if a.Key == slog.TimeKey {
				return slog.Attr{}
			}
			return a
		},
	}))
	ctx, stop := signal.NotifyContext(context.Background(), os.Interrupt, syscall.SIGTERM)
	defer stop()

	var wg sync.WaitGroup
	wg.Go(func() { flusher(ctx, log) })

	srv := &http.Server{Addr: "127.0.0.1:18081", ReadHeaderTimeout: 5 * time.Second}
	go func() {
		if err := srv.ListenAndServe(); !errors.Is(err, http.ErrServerClosed) {
			log.Error("listen", "err", err)
			stop()
		}
	}()
	log.Info("running")

	<-ctx.Done()
	log.Info("signal received, shutting down")
	shutdownCtx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
	defer cancel()
	if err := srv.Shutdown(shutdownCtx); err != nil {
		log.Error("shutdown", "err", err)
	}
	wg.Wait() // background goroutines finish before main returns
	log.Info("bye")
}
  1. A text logger whose ReplaceAttr drops the time key, so the output is stable.
  2. signal.NotifyContext returns a context that is cancelled when SIGINT or SIGTERM arrives. defer stop() unregisters the handler on the way out.
  3. wg.Go (Go 1.25+) does Add(1), starts flusher in a goroutine and calls Done when it returns.
  4. The HTTP server runs in its own goroutine. ErrServerClosed is the normal result of Shutdown, so it is not logged as an error.
  5. main blocks on <-ctx.Done(). Meanwhile the ticker fires after one second and the flusher does its work.
  6. A second tick. Then we send SIGTERM (what Kubernetes does on a rolling update).
  7. The signal cancels ctx, so main wakes up and starts shutting down.
  8. srv.Shutdown stops accepting new connections and waits for in-flight requests, but never longer than 5 seconds.
  9. The flusher's select sees ctx.Done() too, does a final flush and returns. That calls wg.Done.
  10. wg.Wait() makes sure the flusher finished before main returns. Without it, the process could exit mid-flush and lose data.
level=INFO msg=running
level=INFO msg="flusher: flushed metrics"
level=INFO msg="flusher: flushed metrics"
level=INFO msg="signal received, shutting down"
level=INFO msg="flusher: final flush, exiting"
level=INFO msg=bye
exit code 0

The key is the ordering: cancel the context (the signal does that), let the HTTP server drain, then wg.Wait() for background goroutines before returning from main. Otherwise main returns and the runtime kills the worker mid-flush.

You build with go build -ldflags "-X main.Version=1.2.0", but the program still prints "dev". Your code has var version = "dev" in package main. Why?
The flag says main.Version but the variable is version. The linker can't find it and silently does nothing. For package main, main.version is the right path.

Key takeaways

  • Release builds: CGO_ENABLED=0 go build -trimpath -ldflags "-s -w -X main.version=...". Static, smaller, reproducible, versioned.
  • Go embeds module, dependency and VCS info in every binary. Read it with debug.ReadBuildInfo or go version -m.
  • Cross-compiling is just GOOS/GOARCH. Combine it with $BUILDPLATFORM in Docker for fast multi-arch images.
  • Ship on distroless or scratch, as non-root, via a multi-stage build with cached module downloads.
  • Config comes from env (12-factor), flags can override, and everything is validated at startup into one typed struct.
  • slog JSON logs with request IDs, RED metrics per route pattern, and OpenTelemetry traces that ride on context.
  • Liveness is trivial; readiness is meaningful. On SIGTERM: fail readiness, drain with Shutdown, stop workers, exit 0.
  • CI runs fmt, tidy, vet, race tests, lint, govulncheck and cross-builds. goreleaser turns tags into releases.
  • Go 1.25+ sets GOMAXPROCS from the container's CPU limit; set GOMEMLIMIT yourself to about 90% of memory.

Error Handling

In Go, an error is not an exception that flies up the stack. It is a plain value that a function hands back, and you decide what to do with it. This chapter shows you why Go made that choice, and how to build errors that are easy to read, easy to check and easy to debug at 3 a.m.

Why Go treats errors as values

Most languages you may know (Java, Python, JavaScript) use exceptions. When something fails, the code "throws", and the error jumps up through function after function until some try/catch grabs it. That is convenient to write, but hard to read: by looking at a line of code you cannot tell whether it can fail, or where the failure will land.

Go's designers chose a different path. In Go, a function that can fail simply returns an extra value that describes the failure. That value is called an error. It is not magic. It is a normal value, just like an int or a string, so you can store it, compare it, pass it to functions, put it in a slice, or wrap it inside another error.

Mental model

An exception is a fire alarm: it goes off and everyone runs, and you are not sure who will deal with it. A Go error is a receipt the function hands you saying "this did not work, here is why". You hold it in your hand. You decide: fix it, retry, add a note and pass it to your boss, or throw it away (on purpose).

This gives you three big benefits:

  • Visible failure points. If a call returns (T, error), you can see right there that it can fail.
  • Explicit control flow. There are no hidden jumps. The code runs top to bottom, and failure handling is ordinary if and return.
  • Errors are programmable. Because they are values, you can attach data (which field was invalid, which HTTP status, how long to wait before retrying).

The price is that you type if err != nil a lot. We will see why that is less painful than it looks, and how seniors make every one of those checks useful.

The error interface, errors.New and fmt.Errorf

Here is the complete definition of error, built into the language:

type error interface {
	Error() string
}

That is all. An interface (Chapter 8) is a set of methods. Any type that has a method Error() string is an error. The zero value of an interface is nil, so "no error" is written nil.

There are two everyday ways to make one:

  • errors.New("text") makes an error with a fixed message.
  • fmt.Errorf("format %d", x) makes an error with a formatted message, using the same verbs as fmt.Printf.

By convention, the error is the last return value, and when the error is non-nil the other return values should be treated as meaningless (usually zero values).

package main

import (
	"errors"
	"fmt"
	"strconv"
)

// divide returns an error value instead of crashing.
func divide(a, b int) (int, error) {
	if b == 0 {
		return 0, errors.New("division by zero")
	}
	return a / b, nil
}

func main() {
	// 1. A standard library function that can fail.
	n, err := strconv.Atoi("42x")
	if err != nil {
		fmt.Println("Atoi failed:", err)
	} else {
		fmt.Println("parsed:", n)
	}

	// 2. Our own function.
	q, err := divide(10, 2)
	if err != nil {
		fmt.Println("error:", err)
		return
	}
	fmt.Println("10 / 2 =", q)

	_, err = divide(1, 0)
	fmt.Println("err is nil?", err == nil)
	fmt.Println("err message:", err.Error())

	// 3. fmt.Errorf builds a message with formatting.
	user := "sharad"
	err = fmt.Errorf("user %q: quota exceeded (%d/%d)", user, 11, 10)
	fmt.Println(err)
	fmt.Printf("type: %T\n", err)
}
  1. strconv.Atoi("42x") cannot parse the trailing x. It returns 0 and a non-nil error instead of crashing.
  2. We check err first. Its message already says who failed and why.
  3. Now our own divide(10, 2). b is not zero, so we skip the guard and return 5, nil.
  4. err is nil, so the early return is skipped and we print the result.
  5. divide(1, 0) hits the guard and returns errors.New("division by zero"). We discard the int with _.
  6. An error is an ordinary value: you can compare it with nil and call its Error() method.
  7. fmt.Errorf builds the message with Printf verbs. %q adds the quotes.
  8. Without %w, Errorf returns the same simple type as errors.New.
Atoi failed: strconv.Atoi: parsing "42x": invalid syntax
10 / 2 = 5
err is nil? false
err message: division by zero
user "sharad": quota exceeded (11/10)
type: *errors.errorString

Notice a few things:

  • strconv.Atoi's message already says who failed and why: strconv.Atoi: parsing "42x": invalid syntax. Good errors read like a sentence.
  • The concrete type behind errors.New is *errors.errorString, a tiny struct with one string field. You never use that type directly; you only see it through the error interface.
  • Calling err.Error() gives the text. fmt.Println(err) calls it for you.
Style rule: how to word messages

Error strings start with a lowercase letter and have no trailing punctuation, because they usually get glued into a bigger message: "open config: permission denied" reads well, while "Open config.: Permission denied." does not. go vet's friends (staticcheck ST1005) will flag this.

You cannot "forget" that a function returns an error, because Go makes you deal with every return value:

package main

import (
	"fmt"
	"strconv"
)

func main() {
	n := strconv.Atoi("5")
	fmt.Println(n)
}
./main.go:9:7: assignment mismatch: 1 variable but strconv.Atoi returns 2 values

You can still explicitly throw an error away with the blank identifier, n, _ := strconv.Atoi("5"), but now the decision is visible in code review.

The if err != nil pattern, and why it is fine

Every Go programmer writes this shape thousands of times:

v, err := doSomething()
if err != nil {
	return fmt.Errorf("do something: %w", err)
}
// happy path continues here, using v

Why not something shorter? A few reasons the Go team (and most experienced Go developers) like it:

  • The happy path stays on the left. Errors are handled early and the function returns. The normal logic is never buried in nested else blocks. This is called the guard clause or "line of sight" style.
  • Each check is a chance to add context. The return fmt.Errorf("do something: %w", err) line is where you write what you were doing. Exceptions give you a stack trace; Go gives you a human sentence.
  • It is obvious. A new teammate can read it on day one.

Proposals for shorter syntax (try, ?) have been debated for years. In 2025 the Go team officially said they will stop pursuing syntax changes for error handling, so this pattern is here to stay. Learn to love it.

Let's trace one function that has two different ways to fail.

func parsePort(s string) (int, error) {
	n, err := strconv.Atoi(s)
	if err != nil {
		return 0, fmt.Errorf("parse port %q: %w", s, err)
	}
	if n < 1 || n > 65535 {
		return 0, fmt.Errorf("port %d out of range", n)
	}
	return n, nil
}

func main() {
	for _, s := range []string{"8080", "http", "99999"} {
		p, err := parsePort(s)
		if err != nil {
			fmt.Println("error:", err)
			continue
		}
		fmt.Println("port:", p)
	}
}
  1. The loop starts with s = "8080" and calls parsePort.
  2. Atoi succeeds. err is nil, so the first guard is skipped.
  3. 8080 is in range, so the second guard is skipped too. We return 8080, nil.
  4. Back in main, err == nil, so we fall through to the happy path and print the port.
  5. Next value "http": Atoi fails. We wrap its error with context (which input) and return immediately.
  6. main sees a non-nil error, prints it, and continues. Notice p is 0: never trust the other values when err != nil.
  7. Third value parses fine, but the second guard catches it. This error is new (nothing to wrap), so we use Errorf without %w.
  8. Printed, and the loop ends.
port: 8080
error: parse port "http": strconv.Atoi: parsing "http": invalid syntax
error: port 99999 out of range
func load(path string) (*Config, error) {
	f, err := os.Open(path)
	if err == nil {
		defer f.Close()
		cfg, err := parse(f)
		if err == nil {
			if cfg.Valid() {
				return cfg, nil
			} else {
				return nil, errors.New("invalid")
			}
		} else {
			return nil, err
		}
	} else {
		return nil, err
	}
}
func load(path string) (*Config, error) {
	f, err := os.Open(path)
	if err != nil {
		return nil, fmt.Errorf("load config: %w", err)
	}
	defer f.Close()

	cfg, err := parse(f)
	if err != nil {
		return nil, fmt.Errorf("load config %s: %w", path, err)
	}
	if !cfg.Valid() {
		return nil, fmt.Errorf("load config %s: invalid", path)
	}
	return cfg, nil
}

Wrapping with %w, and errors.Is / As / Unwrap

When a low-level error bubbles up, you usually want two things at once:

  1. A message for humans that explains the whole story ("read config app.yaml: open app.yaml: no such file").
  2. The original error kept intact for code to inspect ("was it a not-exist error? then create a default file").

fmt.Errorf with the special verb %w ("wrap") gives you both. It formats the message like %v, and it stores the original error inside the new one. The new error has an Unwrap() error method that returns the inner error. Errors that wrap errors that wrap errors form an error chain.

package main

import (
	"errors"
	"fmt"
	"io/fs"
	"os"
)

func readConfig(path string) ([]byte, error) {
	data, err := os.ReadFile(path)
	if err != nil {
		// %w wraps: the original error stays inside, reachable later.
		return nil, fmt.Errorf("read config %s: %w", path, err)
	}
	return data, nil
}

func readConfigV(path string) ([]byte, error) {
	data, err := os.ReadFile(path)
	if err != nil {
		// %v only copies the text: the original error is gone.
		return nil, fmt.Errorf("read config %s: %v", path, err)
	}
	return data, nil
}

func main() {
	_, err := readConfig("/no/such/app.yaml")
	fmt.Println("message:   ", err)
	fmt.Println("Is NotExist:", errors.Is(err, fs.ErrNotExist))

	inner := errors.Unwrap(err)
	fmt.Printf("unwrapped:  %v (%T)\n", inner, inner)

	_, errV := readConfigV("/no/such/app.yaml")
	fmt.Println("with %v, Is NotExist:", errors.Is(errV, fs.ErrNotExist))
	fmt.Println("with %v, Unwrap:", errors.Unwrap(errV))
}
  1. We call readConfig. Inside, os.ReadFile fails because the file does not exist.
  2. The error it returns is a *fs.PathError whose own cause is the sentinel fs.ErrNotExist. So the guard fires.
  3. %w builds a *fmt.wrapError: new text plus a pointer to the original error. The chain is now three links long.
  4. Printing shows every layer's text joined by ": ", outermost first.
  5. errors.Is walks the chain link by link and finds fs.ErrNotExist at the bottom.
  6. errors.Unwrap peels exactly one layer, giving back the *fs.PathError we wrapped.
  7. Now the %v version. Same failure, but %v just formats the text into a brand-new error. Nothing points back at the cause.
  8. The text still says "no such file", but errors.Is has no chain to walk, so it says false. Callers can no longer react to the cause.
  9. Unwrap returns nil: there is no inner error. Use %w whenever callers might need the cause.
message:    read config /no/such/app.yaml: open /no/such/app.yaml: no such file or directory
Is NotExist: true
unwrapped:  open /no/such/app.yaml: no such file or directory (*fs.PathError)
with %v, Is NotExist: false
with %v, Unwrap: <nil>

The text looks identical with %v and %w. The difference is invisible until code asks "is this a not-found error?". With %v the chain is cut, and the answer is a wrong false.

The three inspection tools in the errors package:

FunctionQuestion it answersTypical use

Seeing the chain

Let's build a chain of four errors and walk it by hand, which is exactly what errors.Is does internally:

package main

import (
	"errors"
	"fmt"
)

func main() {
	base := errors.New("disk full")
	l1 := fmt.Errorf("write block 7: %w", base)
	l2 := fmt.Errorf("save photo.jpg: %w", l1)
	l3 := fmt.Errorf("upload album: %w", l2)

	// Walk the chain by hand, exactly like errors.Is does.
	for e := error(l3); e != nil; e = errors.Unwrap(e) {
		fmt.Printf("%-22T %v\n", e, e)
	}
}
  1. The root cause: a plain *errors.errorString. It has no Unwrap method, so it will end the chain.
  2. Each %w adds a layer that points at the one below. l3 is the outermost; it knows about l2, which knows about l1, and so on.
  3. The loop starts at l3. Its text already contains every message below it, because Errorf formatted them in.
  4. errors.Unwrap(e) calls e.Unwrap() and moves one link down, to l2.
  5. One more link down: l1.
  6. Now we reach base. Note the type changed: this is the original error, not a wrapper.
  7. base has no Unwrap, so errors.Unwrap returns nil and the loop stops. errors.Is does this same walk, comparing each link to the target.
*fmt.wrapError         upload album: save photo.jpg: write block 7: disk full
*fmt.wrapError         save photo.jpg: write block 7: disk full
*fmt.wrapError         write block 7: disk full
*errors.errorString    disk full
func main() {
	ErrNotFound := errors.New("not found")
	e1 := fmt.Errorf("query users: %w", ErrNotFound)
	e2 := fmt.Errorf("find user 7: %w", e1)
	e3 := fmt.Errorf("send welcome: %w", e2)

	fmt.Println(e3 == ErrNotFound)
	fmt.Println(errors.Is(e3, ErrNotFound))
}
  1. We create one sentinel value. Remember: it is a pointer, so equality means "the very same object".
  2. e1 is a new *fmt.wrapError whose inner error is ErrNotFound.
  3. Two more layers. e3 is the outermost box.
  4. == only compares the outer box with the sentinel. They are different objects, so false. This is why you must stop using == on errors once anyone wraps them.
  5. errors.Is compares e3, then unwraps to e2, then e1, then finds ErrNotFound. Match: true.
Gotcha: wrapping is part of your API

Once you write %w, callers can (and will) check the inner error with errors.Is. If you later swap Postgres for SQLite, code that checked for a Postgres-specific error breaks. Use %w when you want callers to see the cause. Use %v when the cause is an implementation detail you want to hide. A common middle ground: translate low-level errors into your own sentinel (sql.ErrNoRows becomes ErrNotFound) at the boundary.

err := fmt.Errorf("load: %v", fs.ErrNotExist). What is errors.Is(err, fs.ErrNotExist)?
%v formats the error as a string and forgets the original value. Only %w stores the inner error so Unwrap (and therefore Is/As) can find it. errors.Is never compares text.

Sentinel errors

A sentinel error is a package-level variable holding one specific error value that callers can test for. The standard library is full of them: io.EOF ("the stream ended normally"), sql.ErrNoRows, fs.ErrNotExist, context.Canceled, http.ErrServerClosed. The name comes from the old idea of a "sentinel value" that signals a special condition.

package main

import (
	"errors"
	"fmt"
)

// Sentinel errors: package-level values callers can compare against.
var (
	ErrNotFound     = errors.New("not found")
	ErrOutOfStock   = errors.New("out of stock")
	ErrInvalidQuant = errors.New("quantity must be positive")
)

var stock = map[string]int{"apple": 3, "pear": 0}

func reserve(item string, qty int) error {
	if qty <= 0 {
		return ErrInvalidQuant
	}
	have, ok := stock[item]
	if !ok {
		return fmt.Errorf("reserve %q: %w", item, ErrNotFound)
	}
	if have < qty {
		return fmt.Errorf("reserve %d x %q (have %d): %w", qty, item, have, ErrOutOfStock)
	}
	stock[item] -= qty
	return nil
}

func main() {
	tries := []struct {
		item string
		qty  int
	}{{"apple", 2}, {"kiwi", 1}, {"pear", 1}, {"apple", 0}}

	for _, t := range tries {
		err := reserve(t.item, t.qty)
		switch {
		case err == nil:
			fmt.Println("ok:", t.item)
		case errors.Is(err, ErrNotFound):
			fmt.Println("404 ->", err)
		case errors.Is(err, ErrOutOfStock):
			fmt.Println("409 ->", err)
		default:
			fmt.Println("400 ->", err)
		}
	}

	// Why == is not enough once errors are wrapped:
	err := reserve("kiwi", 1)
	fmt.Println("err == ErrNotFound:", err == ErrNotFound)
	fmt.Println("errors.Is:         ", errors.Is(err, ErrNotFound))
}
ok: apple
404 -> reserve "kiwi": not found
409 -> reserve 1 x "pear" (have 0): out of stock
400 -> quantity must be positive
err == ErrNotFound: false
errors.Is:          true

The pattern: create the sentinel once with errors.New, wrap it with details where it happens (fmt.Errorf("reserve %q: %w", item, ErrNotFound)), and check it with errors.Is where it is handled. The switch { case errors.Is(...) } shape is the idiomatic way to branch on several kinds.

Senior engineer tip

Keep sentinels few and meaningful. Export one only if callers need to behave differently because of it (return 404 instead of 500, stop reading, retry). If no caller would ever branch on it, a plain fmt.Errorf is enough. Every exported sentinel is a promise you have to keep across versions.

Gotcha: io.EOF is never wrapped

A few old sentinels, most famously io.EOF, are compared with == by lots of existing code. If you implement an io.Reader, return io.EOF itself, never fmt.Errorf("...: %w", io.EOF), or you will break callers that do err == io.EOF.

Custom error types with fields

A sentinel is just "a kind of failure". Sometimes callers need data: which field failed validation, which file, which HTTP status, how long to wait. Then you define your own type and give it an Error() string method. Because error is an interface, your struct is now an error.

package main

import (
	"errors"
	"fmt"
)

// ValidationError carries structured data, not just a string.
type ValidationError struct {
	Field  string
	Value  any
	Reason string
}

// Error makes *ValidationError satisfy the error interface.
func (e *ValidationError) Error() string {
	return fmt.Sprintf("invalid %s=%v: %s", e.Field, e.Value, e.Reason)
}

type User struct {
	Name string
	Age  int
}

func validate(u User) error {
	if u.Name == "" {
		return &ValidationError{Field: "name", Value: `""`, Reason: "required"}
	}
	if u.Age < 0 || u.Age > 150 {
		return &ValidationError{Field: "age", Value: u.Age, Reason: "must be 0..150"}
	}
	return nil
}

func createUser(u User) error {
	if err := validate(u); err != nil {
		return fmt.Errorf("create user: %w", err)
	}
	return nil
}

func main() {
	err := createUser(User{Name: "Ana", Age: 200})
	fmt.Println(err)

	// errors.As walks the chain looking for a *ValidationError
	// and, if found, stores it in ve.
	var ve *ValidationError
	if errors.As(err, &ve) {
		fmt.Println("field: ", ve.Field)
		fmt.Println("value: ", ve.Value)
		fmt.Println("reason:", ve.Reason)
	}

	// Go 1.26+: errors.AsType is the generic, type-safe version.
	if ve2, ok := errors.AsType[*ValidationError](err); ok {
		fmt.Println("AsType found field:", ve2.Field)
	}

	fmt.Println(createUser(User{Name: "Bo", Age: 30}))
}
  1. createUser calls validate. The name is fine, so the first guard is skipped.
  2. Age 200 is out of range. We return a *ValidationError with the field, value and reason as real data.
  3. Back in createUser, the error is wrapped with %w. The struct is now one link down the chain.
  4. Printing calls Error() on the wrapper, which includes the struct's own Error() text.
  5. errors.As walks the chain. The second link has type *ValidationError, so it stores it in ve and returns true. Note we pass &ve, a pointer to the variable.
  6. Now we can read the fields directly instead of parsing the message text.
  7. errors.AsType (Go 1.26+) does the same thing generically: it returns the value and a bool, no pointer variable needed.
  8. A valid user passes every check, so createUser returns nil.
create user: invalid age=200: must be 0..150
field:  age
value:  200
reason: must be 0..150
AsType found field: age
<nil>

How errors.As(err, &ve) works: you declare a variable of the type you are looking for (var ve *ValidationError) and pass its address. As walks the chain; the first error that can be assigned to that type is stored in ve, and it returns true. Since Go 1.26 there is also errors.AsType[*ValidationError](err), which returns the value and a bool directly. It reads better and cannot be misused with the wrong pointer level.

Gotcha: pointer or value receiver must match

We defined Error() on *ValidationError (pointer receiver) and returned &ValidationError{...}. So the target must be *ValidationError. If you use var ve ValidationError with errors.As, you get a panic at run time: panic: errors: *target must be interface or implement error. go vet catches it before you run: second argument to errors.As must be a non-nil pointer to either a type that implements error, or to any interface type. Pick pointer receivers for error types and stick to it.

Making a type decide what it "is": Is and behaviour interfaces

Two more tricks used in real libraries:

  • A type can define Is(target error) bool. errors.Is calls it, so one type can "match" a sentinel based on its fields (any 429 response "is" ErrRateLimited).
  • Callers can check for a behaviour instead of a concrete type, by passing a pointer to an anonymous interface into errors.As. This keeps packages decoupled: the caller does not need to import your type.
package main

import (
	"errors"
	"fmt"
	"time"
)

// A custom error can decide what it "is" via an Is method,
// and expose behaviour via small interfaces.
type HTTPError struct {
	Code  int
	Retry time.Duration
}

func (e *HTTPError) Error() string { return fmt.Sprintf("http %d", e.Code) }

var ErrRateLimited = errors.New("rate limited")

// Is lets errors.Is(err, ErrRateLimited) match any 429.
func (e *HTTPError) Is(target error) bool {
	return target == ErrRateLimited && e.Code == 429
}

// Temporary is a behaviour other packages can check for
// without importing our concrete type.
func (e *HTTPError) Temporary() bool { return e.Code == 429 || e.Code >= 500 }

func call(code int) error {
	if code == 200 {
		return nil
	}
	return fmt.Errorf("call payments API: %w", &HTTPError{Code: code, Retry: 2 * time.Second})
}

func main() {
	for _, code := range []int{200, 429, 503, 404} {
		err := call(code)
		if err == nil {
			fmt.Println(code, "ok")
			continue
		}
		var tmp interface{ Temporary() bool }
		retry := errors.As(err, &tmp) && tmp.Temporary()
		fmt.Printf("%d %-28v rateLimited=%-5v retry=%v\n",
			code, err, errors.Is(err, ErrRateLimited), retry)
	}
}
  1. First code is 200. call returns nil, meaning success.
  2. Nil error, so we print ok and continue.
  3. Code 429: call wraps a *HTTPError with %w. The concrete type sits one link down the chain.
  4. errors.As walks the chain looking for anything with a Temporary() bool method. The *HTTPError has one, so tmp is set and Temporary() says true for 429.
  5. errors.Is first compares each link with ==. No link is ErrRateLimited, but it also calls each link's Is method. Ours returns true for a 429.
  6. The line is printed. %-28v pads the message so the columns line up.
  7. 503: Temporary() is true (5xx), but our Is only matches 429, so rateLimited is false.
  8. 404: neither rule matches. A client error is not worth retrying. The caller decided all this without importing HTTPError.
200 ok
429 call payments API: http 429  rateLimited=true  retry=true
503 call payments API: http 503  rateLimited=false retry=true
404 call payments API: http 404  rateLimited=false retry=false
Senior engineer tip: sentinel or type?

Start with a sentinel. Upgrade to a custom type only when callers need fields. If you need both, do what e13 does: a type with fields plus an Is method so simple callers can still use errors.Is(err, ErrRateLimited). Prefer checking behaviour (interface{ Temporary() bool }) across package boundaries; it avoids tight coupling.

Several errors at once: errors.Join and multi-%w

Validating a form? You do not want to tell the user only the first problem, fix, resubmit, see the next one. errors.Join (Go 1.20) combines several errors into one. Its message is each error on its own line, and errors.Is/As look inside all of them. A handy detail: errors.Join returns nil if every argument is nil (or there are none), so you can always return errors.Join(errs...).

fmt.Errorf also accepts more than one %w in the same format string.

package main

import (
	"errors"
	"fmt"
)

var (
	ErrNameMissing  = errors.New("name is required")
	ErrEmailInvalid = errors.New("email is invalid")
	ErrTimeout      = errors.New("timeout")
	ErrDB           = errors.New("database unavailable")
)

func validateForm(name, email string) error {
	var errs []error
	if name == "" {
		errs = append(errs, ErrNameMissing)
	}
	if email == "" || email[0] == '@' {
		errs = append(errs, ErrEmailInvalid)
	}
	return errors.Join(errs...) // nil if errs is empty
}

func main() {
	err := validateForm("", "@nope")
	fmt.Println(err)
	fmt.Println("---")
	fmt.Println("name missing?", errors.Is(err, ErrNameMissing))
	fmt.Println("email bad?   ", errors.Is(err, ErrEmailInvalid))
	fmt.Println("all good =>  ", validateForm("Ana", "ana@x.io"))

	// Several %w verbs in one Errorf (Go 1.20+).
	both := fmt.Errorf("save order: %w (while retrying after %w)", ErrDB, ErrTimeout)
	fmt.Println(both)
	fmt.Println("is DB?     ", errors.Is(both, ErrDB))
	fmt.Println("is Timeout?", errors.Is(both, ErrTimeout))
	fmt.Println("Unwrap() on multi:", errors.Unwrap(both)) // nil! see text

	// Multi-errors expose Unwrap() []error instead.
	if m, ok := both.(interface{ Unwrap() []error }); ok {
		fmt.Println("children:", len(m.Unwrap()))
	}
}
  1. We validate a form with an empty name and a bad email. errs starts as a nil slice.

  3. The email starts with @, so we append a second problem instead of stopping. The user sees every mistake at once.
  4. errors.Join bundles both. Its message puts each child on its own line.
  5. errors.Is searches every child of a joined error, so both checks are true.
  6. Valid input: nothing is appended, and errors.Join() with no non-nil errors returns nil. That is why returning it directly is safe.
  7. Two %w verbs in one Errorf (Go 1.20+) wrap two errors at once.
  8. Both causes are findable with errors.Is.
  9. Gotcha: errors.Unwrap only follows a single Unwrap() error method. A multi-error has Unwrap() []error instead, so you get nil.
  10. To see the branches yourself, assert to interface{ Unwrap() []error }. There are two children.

Adding context at each layer, and handling errors once

Real programs have layers: a handler calls a service, which calls a repository, which calls the database. When something fails at the bottom, each layer above should add what it was doing, in a few words, and pass it up. The top layer, which actually knows what to do (return a 404, retry the job, exit), handles it.

package main

import (
	"errors"
	"fmt"
	"log"
	"os"
)

var ErrNotFound = errors.New("not found")

// --- storage layer: knows about rows and SQL ---
func queryUserRow(id int) (string, error) {
	if id != 1 {
		return "", ErrNotFound
	}
	return "Ana", nil
}

// --- repository layer: adds WHICH record ---
func findUser(id int) (string, error) {
	name, err := queryUserRow(id)
	if err != nil {
		return "", fmt.Errorf("find user %d: %w", id, err)
	}
	return name, nil
}

// --- service layer: adds WHAT we were trying to do ---
func sendWelcome(id int) error {
	name, err := findUser(id)
	if err != nil {
		return fmt.Errorf("send welcome email: %w", err)
	}
	fmt.Println("hello,", name)
	return nil
}

func main() {
	logger := log.New(os.Stdout, "", 0)

	// --- top layer: the ONE place that handles (logs) the error ---
	for _, id := range []int{1, 7} {
		if err := sendWelcome(id); err != nil {
			logger.Printf("ERROR job failed: %v", err)
			if errors.Is(err, ErrNotFound) {
				logger.Println("  -> user is gone; dropping job instead of retrying")
			}
		}
	}
}
  1. First job, id=1. The call goes down three layers: sendWelcome → findUser → queryUserRow.
  2. The row exists, so the storage layer returns "Ana", nil. Each layer's guard is skipped on the way back up.
  3. The service layer does its work and returns nil, so main has nothing to handle.
  4. Second job, id=7. The storage layer returns the bare sentinel ErrNotFound. It does not know which user or why we asked.
  5. The repository layer adds which record and wraps with %w. It does not log: it just passes the error up.
  6. The service layer adds what we were doing. The message now reads like a sentence, outermost context first.
  7. The top layer is the one place that handles the error, so it is logged exactly once.
  8. Because every layer used %w, errors.Is still finds ErrNotFound at the bottom and the top can decide what to do.
hello, Ana
ERROR job failed: send welcome email: find user 7: not found
  -> user is gone; dropping job instead of retrying

Read the final message: send welcome email: find user 7: not found. It is a breadcrumb trail from the top down to the cause, with no stack trace needed. Each layer wrote only its own part.

Rules for good context

  • Add what the caller does not know. The callee already said "not found"; the repository adds "find user 7". Do not repeat the callee's words.
  • Do not start with "failed to" / "error". Every message in the chain is a failure; those words just pile up: failed to send: failed to find: failed to query: .... Name the operation instead.
  • Include the identifying data (id, file name, key) but never secrets (passwords, tokens) or huge payloads.
  • Do not add the function's own arguments twice. os.Open already puts the path in its error (open /x: no such file), so wrapping with "open %s: %w" duplicates it. Say "load config: %w".

Handle errors once: log OR return, never both

func findUser(id int) (*User, error) {
	u, err := db.Get(id)
	if err != nil {
		log.Printf("error finding user: %v", err)
		return nil, err
	}
	return u, nil
}
// the service logs it again, the handler logs
// it again... one failure = 3 log lines with
// less context each time
func findUser(id int) (*User, error) {
	u, err := db.Get(id)
	if err != nil {
		return nil, fmt.Errorf("find user %d: %w", id, err)
	}
	return u, nil
}

Senior engineer tip

"Handling" an error means making a decision: return it, retry it, degrade gracefully, or log it and move on. Logging is handling. If you log, do not also return; if you return, do not also log. Duplicate log lines are the number one source of noise in production dashboards, and they make one incident look like three.

Your repository calls os.ReadFile("users.json") and it fails. Which wrap is best?
os.ReadFile's error already contains the path, so repeating it duplicates text, and "failed to"/"error" add nothing. Option 4 throws away the cause. Option 3 handles the error twice. "load users: %w" adds only what is new: what this layer was trying to do.

panic, recover, and when not to use them

Go does have something exception-like: panic. A panic stops the normal flow of the current goroutine, runs its deferred functions on the way up, and if nobody stops it, prints a stack trace and kills the whole program with exit code 2. The runtime panics on its own for bugs: nil map writes, index out of range, nil pointer dereference, integer divide by zero.

recover

recover() stops a panic, but only when called directly inside a deferred function on the same goroutine that is panicking. It returns the value passed to panic (or nil if there is no panic). Combined with a named result (Chapter 4), the deferred function can turn the panic into a normal error:

package main

import (
	"errors"
	"fmt"
)

// safeDivide turns a panic into an ordinary error.
// The named result err lets the deferred func change what we return.
func safeDivide(a, b int) (q int, err error) {
	defer func() {
		if r := recover(); r != nil {
			err = fmt.Errorf("recovered: %v", r)
		}
	}()
	return a / b, nil // panics when b == 0
}

func getItem(items []string, i int) (s string, err error) {
	defer func() {
		if r := recover(); r != nil {
			// r is `any`; runtime errors also implement error.
			if re, ok := r.(error); ok {
				err = fmt.Errorf("getItem(%d): %w", i, re)
				return
			}
			err = fmt.Errorf("getItem(%d): %v", i, r)
		}
	}()
	return items[i], nil
}

func main() {
	fmt.Println(safeDivide(10, 2))
	fmt.Println(safeDivide(1, 0))

	_, err := getItem([]string{"a", "b"}, 5)
	fmt.Println(err)

	var re interface{ RuntimeError() }
	fmt.Println("is a runtime.Error:", errors.As(err, &re))

	fmt.Println("program keeps running")
}
  1. safeDivide(10, 2) registers its deferred closure first. It can see the named results q and err.
  2. 10 / 2 is fine. return stores 5 and nil into the named results.
  3. The defer runs, recover() returns nil (no panic), so nothing changes. Println prints both results.
  4. safeDivide(1, 0): integer division by zero panics before the return values are set.
  5. The panic unwinds to the deferred closure. recover() stops it and returns the panic value, and we assign a new error to the named err.
  6. The function returns normally with q=0 and our error. The caller never sees a panic.
  7. In getItem, index 5 is out of range for a 2-element slice, so the runtime panics.
  8. The panic value is a runtime.Error, which also implements error. So the type assertion succeeds and we wrap it with %w, keeping it in the chain.
  9. The wrapped message names the call and the cause.
  10. Because we used %w, errors.As finds a value with a RuntimeError() method in the chain.
  11. Both panics were contained. The program carries on.

Gotcha: recover must be called by the deferred function itself

defer recover() does nothing useful, and neither does calling a helper that calls recover from inside a non-deferred path. The rule is exact: recover works only when called directly by a function that was deferred.

Panics in goroutines crash the whole program

This one surprises everyone once. A recover in main cannot catch a panic that happens in another goroutine. Each goroutine has its own stack of deferred calls, and an unrecovered panic in any goroutine terminates the entire process, skipping every other goroutine's defers.

package main

import (
	"fmt"
	"time"
)

func main() {
	defer fmt.Println("main's defer: never printed!")

	// This recover is useless: it runs on main's goroutine,
	// but the panic happens on a different goroutine.
	defer func() {
		if r := recover(); r != nil {
			fmt.Println("caught:", r)
		}
	}()

	go func() {
		var m map[string]int
		m["boom"] = 1 // panic: assignment to entry in nil map
	}()

	time.Sleep(100 * time.Millisecond)
	fmt.Println("unreachable")
}

Senior engineer tip

In long-running servers, any goroutine you start "fire-and-forget" should have its own defer func(){ if r := recover(); r != nil { log... } }() at the top, or be started through a helper that adds one. net/http already does this for each request handler, which is why one buggy handler does not take your server down, but goroutines your handler spawns are not protected. Libraries like errgroup (Chapter 13) help collect errors from goroutines properly.

The Must pattern

Some failures can only come from a programmer mistake, like a typo in a regular expression written in the source code. Waiting until runtime to return an error for that is silly. The standard library offers Must versions that panic instead of returning an error: regexp.MustCompile, template.Must. They are meant for package-level variables initialized at startup, so a bad pattern crashes the program on launch, during development, not in front of a customer.

package main

import (
	"fmt"
	"regexp"
	"text/template"
)

// Package-level values built once at startup. If the pattern
// is wrong, the program dies immediately at launch — which is
// what we want for a programmer bug.
var (
	slugRE = regexp.MustCompile(`^[a-z0-9]+(-[a-z0-9]+)*$`)
	tmpl   = template.Must(template.New("hi").Parse("Hi {{.}}!\n"))
)

// Must is a tiny generic helper in the same spirit.
func Must[T any](v T, err error) T {
	if err != nil {
		panic(err)
	}
	return v
}

func main() {
	fmt.Println(slugRE.MatchString("go-handbook"), slugRE.MatchString("Go Handbook"))
	_ = tmpl.Execute(fmtWriter{}, "Gopher")

	re := Must(regexp.Compile(`\d+`))
	fmt.Println(re.FindAllString("a1 b22 c333", -1))

	defer func() { fmt.Println("panic:", recover()) }()
	_ = Must(regexp.Compile(`(unclosed`))
}

type fmtWriter struct{}

func (fmtWriter) Write(p []byte) (int, error) { return fmt.Print(string(p)) }
  1. Before main even starts, package-level vars are initialized. MustCompile and template.Must would panic right here if the pattern or template were broken.
  2. "go-handbook" fits the slug pattern; "Go Handbook" has capitals and a space, so it does not.
  3. The template writes through our tiny fmtWriter, which just prints the bytes.
  4. Generic Must infers T from the two return values. err is nil, so it returns the compiled regexp.
  5. The regexp finds every run of digits.
  6. We register a deferred func that will recover. It does nothing yet.
  7. The pattern (unclosed is invalid, so Compile returns an error and Must panics with it.
  8. The panic unwinds main, the defer fires, and recover() hands back the error. Only use Must where a failure means a programmer bug, like a constant pattern.
true false

[1 22 333]
panic: error parsing regexp: missing closing ): `(unclosed`

Rule of thumb: MustX is fine with constant inputs at init time or in tests. Never call regexp.MustCompile(userInput): that lets a user crash your server.

1. Checking errors in defer (Close)

defer f.Close() is perfect for files you only read. For files you write, the operating system may buffer data and report "disk full" or "I/O error" only when you close. Ignoring that error means you can tell the user "saved!" when nothing was saved. The fix uses a named result and errors.Join so neither error is lost:

package main

import (
	"errors"
	"fmt"
	"os"
	"path/filepath"
)

// writeReport writes a file and does NOT lose the Close error.
// For files you write, Close can be where the real failure shows up
// (e.g. disk full when the OS flushes buffers).
func writeReport(path string, lines []string) (err error) {
	f, err := os.Create(path)
	if err != nil {
		return fmt.Errorf("create report: %w", err)
	}
	defer func() {
		if cerr := f.Close(); cerr != nil {
			err = errors.Join(err, fmt.Errorf("close report: %w", cerr))
		}
	}()

	for _, l := range lines {
		if _, err := fmt.Fprintln(f, l); err != nil {
			return fmt.Errorf("write report: %w", err)
		}
	}
	return nil
}

func main() {
	dir, _ := os.MkdirTemp("", "report")
	defer os.RemoveAll(dir)

	p := filepath.Join(dir, "r.txt")
	fmt.Println("write ok:", writeReport(p, []string{"a", "b"}))
	b, _ := os.ReadFile(p)
	fmt.Printf("contents: %q\n", b)

	err := writeReport(filepath.Join(dir, "missing", "r.txt"), nil)
	fmt.Println("write err:", err != nil)
}
write ok: <nil>
contents: "a\nb\n"

	f, err := os.Create(path)
	if err != nil {
		return err
	}
	defer func() {
		if cerr := f.Close(); cerr != nil {
			err = errors.Join(err, cerr)
		}
	}()
	_, err = f.WriteString("hello")
	return err

  1. err is a named result: a real variable that lives until the function finishes, and that deferred functions can see.
  2. The file opens fine.
  3. We register the deferred closure. It does not run yet.
  4. The write appears to succeed (the data is sitting in OS buffers). return err sets the result to nil.
  5. Now the deferred func runs. Suppose Close fails. We join it into err. Because err is the named result, we just changed what the caller receives.
  6. The caller gets the close error instead of a false success. Without the named result, there would be no way to report it.

2. Returning a typed nil error

This is the most famous Go error trap. An interface value is a pair: (dynamic type, value). It is nil only when both parts are nil. If you return a nil *MyErr pointer as an error, the interface holds (type=*MyErr, value=nil), which is not nil.

package main

import "fmt"

type MyErr struct{ Msg string }

func (e *MyErr) Error() string { return e.Msg }

// BUG: returns a typed nil pointer inside a non-nil interface.
func doBad(fail bool) error {
	var p *MyErr // nil pointer of type *MyErr
	if fail {
		p = &MyErr{"boom"}
	}
	return p // interface = (type=*MyErr, value=nil) -> NOT nil
}

// FIX: return the literal nil for the success path.
func doGood(fail bool) error {
	if fail {
		return &MyErr{"boom"}
	}
	return nil
}

func main() {
	err := doBad(false)
	fmt.Println("doBad(false) == nil:", err == nil)
	fmt.Printf("  dynamic type=%T value=%v\n", err, err == (*MyErr)(nil))

	err = doGood(false)
	fmt.Println("doGood(false) == nil:", err == nil)
}
  1. doBad(false) declares p, a nil pointer of type *MyErr.
  2. fail is false, so p stays nil.
  3. Returning p as an error boxes it into an interface. The box records the type *MyErr and the nil value. A box with a type inside is not nil.
  4. err == nil is only true when both type and value are empty. Here the type is set, so the success path looks like a failure.
  5. %T reveals the hidden type, and comparing against (*MyErr)(nil) confirms the pointer inside is nil.
  6. doGood(false) skips the if and returns the literal nil: an empty interface with no type.
  7. Now the check works. Rule: on success, write return nil, never a typed variable that happens to be nil.
doBad(false) == nil: false
  dynamic type=*main.MyErr value=true
doGood(false) == nil: true
Gotcha

The function "succeeded" but the caller sees err != nil and reports a failure with message... calling Error() on a nil *MyErr may even panic. Rule: always write return nil literally for the no-error case, and declare variables that hold errors as type error, never as a concrete error pointer type.

3. Shadowing err in an inner scope

Writing v, err := f() inside an if or for block creates a new err that hides the outer one. If you meant to set the outer error (for example, the named result used in a defer), use = instead of :=. The shadow analyzer from golang.org/x/tools and careful review catch this.

4. Comparing error strings

if err.Error() == "not found" or strings.Contains(err.Error(), "timeout") breaks the moment someone adds context or fixes a typo. Use errors.Is / errors.As. Error text is for humans; error values are for code.

Designing errors for an API: mapping to HTTP status codes

Let's put it all together in the shape real services use. The domain (business logic) returns domain errors: sentinels and types that know nothing about HTTP. The HTTP edge has exactly one function that translates them into status codes and safe messages. Internal errors (500) are logged with full detail but the client only sees "internal error", because leaking database messages to users is both confusing and a security risk.

package main

import (
	"encoding/json"
	"errors"
	"fmt"
	"log/slog"
	"net/http"
	"net/http/httptest"
	"os"
)

// ---- domain errors (no HTTP knowledge here) ----
var (
	ErrNotFound     = errors.New("not found")
	ErrConflict     = errors.New("conflict")
	ErrUnauthorized = errors.New("unauthorized")
)

type ValidationError struct{ Field, Msg string }

func (e *ValidationError) Error() string { return e.Field + ": " + e.Msg }

// ---- service ----
func getOrder(id string) (string, error) {
	switch id {
	case "1":
		return "order #1: 2 x coffee", nil
	case "2":
		return "", fmt.Errorf("get order %s: %w", id, ErrNotFound)
	case "3":
		return "", &ValidationError{Field: "id", Msg: "must be numeric"}
	case "4":
		return "", fmt.Errorf("get order %s: %w", id, ErrUnauthorized)
	}
	return "", fmt.Errorf("get order %s: db: connection refused", id)
}

// ---- HTTP edge: the ONE place that maps errors to status codes ----
func writeError(w http.ResponseWriter, r *http.Request, err error) {
	status, msg := http.StatusInternalServerError, "internal error"
	var ve *ValidationError
	switch {
	case errors.As(err, &ve):
		status, msg = http.StatusBadRequest, ve.Error()
	case errors.Is(err, ErrNotFound):
		status, msg = http.StatusNotFound, "order not found"
	case errors.Is(err, ErrConflict):
		status, msg = http.StatusConflict, "conflict"
	case errors.Is(err, ErrUnauthorized):
		status, msg = http.StatusUnauthorized, "login required"
	}
	if status >= 500 {
		// Log full detail; NEVER leak internals to the client.
		slog.Error("request failed", "path", r.URL.Path, "err", err)
	}
	w.Header().Set("Content-Type", "application/json")
	w.WriteHeader(status)
	json.NewEncoder(w).Encode(map[string]string{"error": msg})
}

func handleOrder(w http.ResponseWriter, r *http.Request) {
	o, err := getOrder(r.PathValue("id"))
	if err != nil {
		writeError(w, r, err)
		return
	}
	json.NewEncoder(w).Encode(map[string]string{"order": o})
}

func main() {
	slog.SetDefault(slog.New(slog.NewTextHandler(os.Stdout,
		&slog.HandlerOptions{ReplaceAttr: dropTime})))

	mux := http.NewServeMux()
	mux.HandleFunc("GET /orders/{id}", handleOrder)

	for _, id := range []string{"1", "2", "3", "4", "5"} {
		rec := httptest.NewRecorder()
		mux.ServeHTTP(rec, httptest.NewRequest("GET", "/orders/"+id, nil))
		fmt.Printf("GET /orders/%s -> %d %s", id, rec.Code, rec.Body.String())
	}
}

func dropTime(_ []string, a slog.Attr) slog.Attr {
	if a.Key == slog.TimeKey {
		return slog.Attr{}
	}
	return a
}

Senior engineer tip: an error checklist for a new package

Before you ship a package, write down: (1) which failures callers may need to branch on, as exported sentinels or types; (2) which errors you wrap with %w (part of your API) versus format with %v (hidden detail); (3) a single translation point at each boundary (HTTP, gRPC, CLI exit codes); (4) where logging happens (exactly one place). Document sentinels in the function's doc comment: "returns ErrNotFound if no such order exists".

Each problem should be a *LineError with a Line number and a wrapped cause, so callers can use both errors.As (to get the line) and errors.Is (to check for strconv.ErrSyntax or your own ErrSyntax).

Hint: give LineError an Unwrap() error method, and use strings.Cut to split on =.

Solution
package main

import (
	"errors"
	"fmt"
	"strconv"
	"strings"
)

var ErrSyntax = errors.New("syntax error")

type LineError struct {
	Line int
	Err  error
}

func (e *LineError) Error() string { return fmt.Sprintf("line %d: %v", e.Line, e.Err) }
func (e *LineError) Unwrap() error { return e.Err }

// parseConfig parses "key=int" lines and reports EVERY bad line.
func parseConfig(src string) (map[string]int, error) {
	cfg := map[string]int{}
	var errs []error
	for i, line := range strings.Split(src, "\n") {
		line = strings.TrimSpace(line)
		if line == "" || strings.HasPrefix(line, "#") {
			continue
		}
		k, v, ok := strings.Cut(line, "=")
		if !ok {
			errs = append(errs, &LineError{i + 1, fmt.Errorf("missing '=': %w", ErrSyntax)})
			continue
		}
		n, err := strconv.Atoi(strings.TrimSpace(v))
		if err != nil {
			errs = append(errs, &LineError{i + 1, err})
			continue
		}
		cfg[strings.TrimSpace(k)] = n
	}
	return cfg, errors.Join(errs...)
}

func main() {
	cfg, err := parseConfig("port=8080\n# comment\nworkers\ntimeout=3s\nretries=5")
	fmt.Println(cfg)
	fmt.Println(err)

	var le *LineError
	fmt.Println("first LineError:", errors.As(err, &le), le.Line)
	fmt.Println("has syntax err: ", errors.Is(err, ErrSyntax))
	fmt.Println("has NumError:   ", errors.Is(err, strconv.ErrSyntax))
}

line 4: strconv.Atoi: parsing "3s": invalid syntax

Exercise 2: a retry helper that understands "retryable" errors

Write Do(attempts int, fn func(try int) error) error. It calls fn until it succeeds, but gives up immediately on errors that are not marked retryable. Provide Retryable(err) error to mark an error and IsRetryable(err) bool to check (even through wrapping). When all attempts fail, return an error that wraps the last one.

Hint: a tiny unexported struct type that wraps an error, plus errors.As.

Solution
package main

import (
	"errors"
	"fmt"
)

// retryable marks errors that are worth trying again.
type retryable struct{ err error }

func (r retryable) Error() string { return r.err.Error() }
func (r retryable) Unwrap() error { return r.err }

func Retryable(err error) error { return retryable{err} }

func IsRetryable(err error) bool {
	var r retryable
	return errors.As(err, &r)
}

// Do runs fn up to attempts times, stopping early on a
// non-retryable error.
func Do(attempts int, fn func(try int) error) error {
	var err error
	for try := 1; try <= attempts; try++ {
		err = fn(try)
		if err == nil || !IsRetryable(err) {
			return err
		}
		fmt.Printf("  try %d failed (%v), retrying\n", try, err)
	}
	return fmt.Errorf("gave up after %d attempts: %w", attempts, err)
}

func main() {
	fmt.Println("flaky:")
	err := Do(5, func(try int) error {
		if try < 3 {
			return fmt.Errorf("fetch: %w", Retryable(errors.New("timeout")))
		}
		return nil
	})
	fmt.Println("result:", err)

	fmt.Println("permanent:")
	err = Do(5, func(int) error { return errors.New("401 unauthorized") })
	fmt.Println("result:", err)

	fmt.Println("always failing:")
	err = Do(2, func(int) error { return Retryable(errors.New("503")) })
	fmt.Println("result:", err)
}

  try 2 failed (503), retrying

Exercise 3: spot the bug

This function sometimes reports failure even though everything worked. Why, and how do you fix it?

func check(items []string) error {
	var verr *ValidationError
	for _, it := range items {
		if it == "" {
			verr = &ValidationError{Field: "item", Reason: "empty"}
		}
	}
	return verr
}
Solution

It returns a typed nil: when no item is empty, verr is a nil *ValidationError, and converting it to error produces a non-nil interface. Fix: if verr != nil { return verr }; return nil, or declare var err error instead of a concrete pointer type.

Key takeaways

  • An error is any value with an Error() string method. Return it last; nil means success.
  • if err != nil { return fmt.Errorf("doing X: %w", err) } keeps the happy path on the left and adds context at every step.
  • %w wraps (keeps the cause for code); %v only copies text. Wrapping makes the cause part of your API.
  • Check with errors.Is (specific value), errors.As / errors.AsType (specific type). Never compare strings, and stop using == once errors are wrapped.
  • Sentinels (ErrX) for kinds of failure; custom types (XError) when callers need fields; errors.Join for several at once.
  • Handle each error once: wrap and return, or log and stop. Translate to HTTP codes in one place at the edge.
  • panic is for bugs. recover only works in a deferred func on the same goroutine; a panic in any goroutine kills the program.
  • Watch for typed nil errors, ignored Close errors on writes, and err shadowing.

Context

A user closes their browser tab. A request blows past its time budget. Someone presses Ctrl+C. In every case, a whole tree of goroutines, database queries and HTTP calls should stop — now. The context package is Go's standard way to carry that "stop" signal (plus deadlines and a few request-scoped values) across every function and package boundary.

Why context exists

Picture an HTTP handler that calls a service, which runs three database queries and calls another API. The user gives up after 150ms and closes the tab. Without some shared signal, every one of those calls keeps running to completion, burning CPU, holding DB connections, and producing a result nobody will read.

package main

import (
	"fmt"
	"time"
)

// search pretends to query 3 slow backends. It has no way to be told "stop".
func search(query string) []string {
	var results []string
	for _, backend := range []string{"db", "cache", "index"} {
		time.Sleep(100 * time.Millisecond)
		fmt.Println("  queried", backend)
		results = append(results, backend+":"+query)
	}
	return results
}

func main() {
	start := time.Now()
	// The user gave up after 150ms... but we have no way to tell search().
	res := search("golang")
	fmt.Println(res, "after", time.Since(start).Round(100*time.Millisecond))
}
  1. Main records the start time and calls search. It has no context parameter, so the caller has no handle to stop it.
  2. First backend: sleep 100ms, then print.
  3. Append the result and move on.
  4. The user gave up at 150ms, but search cannot know. It keeps working.
  5. Third backend: 100ms more of work nobody wants.
  6. The full 300ms is spent. A context.Context parameter is exactly the missing "stop" signal.
  queried db
  queried cache
  queried index
[db:golang cache:golang index:golang] after 300ms

The function ran for the full 300ms because nothing could tell it to stop. You could add your own quit channel parameter (like Chapter 13's graceful stop), but then every library would invent its own — one takes a channel, one a timeout int, one a callback. They wouldn't compose.

The context package is the standard answer. A context.Context is a small value you pass as the first parameter of every function that does I/O or may take a while. It carries three things across API boundaries:

  1. A cancellation signal — "stop, nobody needs this anymore."
  2. A deadline — "you must be done by 12:00:00.250."
  3. Request-scoped values — a request ID, the authenticated user (use sparingly).
Mental model

A context is like the work order stapled to a job in a factory. Every worker who touches the job sees the same order. If the customer cancels, the manager stamps "CANCELLED" on the order, and every worker who glances at it stops. Workers can attach a sub-order with a tighter deadline for their own helpers, but they can never loosen the original.

The Context interface

It's just four methods:

type Context interface {
	Deadline() (deadline time.Time, ok bool) // when will I be cancelled automatically?
	Done() <-chan struct{}                   // closed when cancelled or the deadline passes
	Err() error                              // nil while active; Canceled or DeadlineExceeded after
	Value(key any) any                       // request-scoped values
}

Done() is the clever part: it returns a channel that is closed on cancellation. Closing a channel wakes up every receiver at once (a broadcast), and you can wait on it inside a select alongside any other channel. Err() then tells you why: context.Canceled or context.DeadlineExceeded.

Where contexts start: Background and TODO

Contexts form a tree, and every tree needs a root. There are two empty roots — never cancelled, no deadline, no values:

  • context.Background() — the root you use in main, in tests, at the top of a background job.
  • context.TODO() — identical behaviour, but it means "I haven't figured out which context belongs here yet." It's a flag for reviewers and linters during a refactor.

Everything else is derived from a parent with a With… function, which returns a child context and (usually) a cancel function.

WithCancel: stop on demand

context.WithCancel(parent) returns a child context and a cancel function. Calling cancel() closes the child's Done channel. Here's the search again, now cancellable:

package main

import (
	"context"
	"fmt"
	"time"
)

func search(ctx context.Context, query string) ([]string, error) {
	var results []string
	for _, backend := range []string{"db", "cache", "index"} {
		select {
		case <-time.After(100 * time.Millisecond): // the "work"
			fmt.Println("  queried", backend)
			results = append(results, backend+":"+query)
		case <-ctx.Done(): // someone said stop
			return results, ctx.Err()
		}
	}
	return results, nil
}

func main() {
	ctx, cancel := context.WithCancel(context.Background())
	defer cancel() // always release resources, even if we cancel earlier

	go func() {
		time.Sleep(150 * time.Millisecond)
		fmt.Println("  user clicked Cancel")
		cancel()
	}()

	start := time.Now()
	res, err := search(ctx, "golang")
	fmt.Println(res, err, "after", time.Since(start).Round(50*time.Millisecond))
}
  queried db
  user clicked Cancel
[db:golang] context canceled after 150ms

The search stopped at 150ms — the moment the user cancelled — and returned the partial results with the error context canceled.

ctx, cancel := context.WithCancel(context.Background())
defer cancel()

go func() {
	time.Sleep(150 * time.Millisecond)
	cancel()
}()

for _, b := range []string{"db", "cache", "index"} {
	select {
	case <-time.After(100 * time.Millisecond):
		fmt.Println("queried", b)
	case <-ctx.Done():
		fmt.Println("stopped:", ctx.Err())
		return
	}
}
  1. We derive a cancellable context. defer cancel() guarantees cleanup even on the normal path.
  2. A goroutine will call cancel() after 150ms. It starts sleeping.
  3. First backend. select waits on two channels: the 100ms timer, and ctx.Done().
  4. The timer fires first. We print and loop.
  5. Second backend: a fresh 100ms timer (it would fire at 200ms).
  6. At 150ms the goroutine calls cancel(). The Done channel is closed.
  7. A closed channel is always ready to receive, so select picks this case right away. We stop without waiting for the cache.
Gotcha: always call cancel

Every With… function that returns a cancel registers the child with its parent. If you never call cancel, that registration (and for timeouts, a timer) lives until the parent is cancelled — possibly forever for Background(). That's a leak. The rule: defer cancel() on the very next line. Calling cancel more than once is harmless. go vet catches the most obvious version:

package main

import (
	"context"
	"fmt"
	"time"
)

func main() {
	ctx, _ := context.WithTimeout(context.Background(), time.Second) // cancel discarded!
	fmt.Println(ctx.Err())
}
$ go vet ./lostcancel
lostcancel/main.go:10:7: the cancel function returned by context.WithTimeout should be called, not discarded, to avoid a context leak

Timeouts and deadlines

Most of the time you don't cancel by hand; you give work a time budget.

  • WithTimeout(parent, 100*time.Millisecond) — cancel automatically after a duration.
  • WithDeadline(parent, t) — cancel automatically at an absolute time. (WithTimeout is literally WithDeadline(parent, time.Now().Add(d)).)
package main

import (
	"context"
	"errors"
	"fmt"
	"time"
)

func slowQuery(ctx context.Context, d time.Duration) (string, error) {
	select {
	case <-time.After(d):
		return "rows", nil
	case <-ctx.Done():
		return "", ctx.Err()
	}
}

func run(d time.Duration) {
	ctx, cancel := context.WithTimeout(context.Background(), 100*time.Millisecond)
	defer cancel()

	res, err := slowQuery(ctx, d)
	switch {
	case errors.Is(err, context.DeadlineExceeded):
		fmt.Printf("query of %v: timed out (%v)\n", d, err)
	case err != nil:
		fmt.Printf("query of %v: failed: %v\n", d, err)
	default:
		fmt.Printf("query of %v: got %q\n", d, res)
	}
}

func main() {
	run(50 * time.Millisecond)
	run(300 * time.Millisecond)
}
  1. run(50ms) creates a context that will cancel itself in 100ms. defer cancel() frees its timer when run returns.
  2. slowQuery races the 50ms timer against ctx.Done(). The timer wins at 50ms.
  3. It returns "rows", nil.
  4. Neither error case matches, so the default branch prints the result. The deferred cancel runs as run exits.
  5. Second call: a brand-new context, again 100ms.
  6. This time the deadline hits first. ctx.Done() closes and slowQuery returns ctx.Err().
  7. errors.Is(err, context.DeadlineExceeded) is true, so we report a timeout. Use errors.Is, not ==, in case the error was wrapped.
query of 50ms: got "rows"
query of 300ms: timed out (context deadline exceeded)

When the timer wins, ctx.Err() is context.DeadlineExceeded. Always compare with errors.Is, because errors are usually wrapped by the time they reach you ("summary: repo.Find(3): context deadline exceeded").

package main

import (
	"context"
	"fmt"
	"time"
)

func main() {
	// A deadline is an absolute moment; a timeout is "now + duration".
	deadline := time.Now().Add(80 * time.Millisecond)
	ctx, cancel := context.WithDeadline(context.Background(), deadline)
	defer cancel()

	if d, ok := ctx.Deadline(); ok {
		fmt.Println("has deadline, time left ~", time.Until(d).Round(10*time.Millisecond))
	}

	// A child can only SHORTEN the deadline, never extend it.
	child, cancelChild := context.WithTimeout(ctx, 5*time.Second)
	defer cancelChild()
	d, _ := child.Deadline()
	fmt.Println("child deadline == parent deadline:", d.Equal(deadline))

	fmt.Println("err before:", ctx.Err())
	<-ctx.Done()
	fmt.Println("err after: ", ctx.Err())
	fmt.Println("child err: ", child.Err())
}
  1. WithDeadline takes an absolute moment. WithTimeout(d) is just WithDeadline(now+d).
  2. ctx.Deadline() reports it, so downstream code can decide whether there's time to even start.
  3. The child asks for 5 seconds, but a child can never outlive its parent. Go keeps the earlier deadline: the parent's 80ms.
  4. Before the deadline, Err() is nil.
  5. Main blocks on <-ctx.Done() until the deadline passes at about 80ms.
  6. Now Err() explains why: the deadline passed.
  7. Cancellation flows down: the child is done too, with the same reason.
has deadline, time left ~ 80ms
child deadline == parent deadline: true
err before: <nil>
err after:  context deadline exceeded
child err:  context deadline exceeded

Note the second line: the child asked for 5 seconds, but its parent ends in 80ms, so the child's deadline is the parent's. A child can shorten a deadline but never extend it. That's what makes deadlines trustworthy: no library deep down can accidentally outlive the caller's budget.

Senior engineer tip

Set timeouts at the edges of your system — where a request enters (HTTP handler, queue consumer) and where you call out (each DB query, each downstream API). Inner layers just pass ctx along. Pick budgets deliberately: if your SLA is 1s and you call two services in sequence, giving each a 2s timeout means the whole request can never meet its SLA. Many teams use ctx.Deadline() to forward the remaining budget to downstream services (gRPC does this automatically).

A handler creates ctx with a 2s timeout. Deep inside, a library calls context.WithTimeout(ctx, 10*time.Second). When is the library's context cancelled?
A derived context is cancelled when its parent is cancelled, or when its own deadline passes — whichever comes first. The parent's 2s deadline arrives first, so the library's 10s request is cut short.

Saying why: WithCancelCause and WithTimeoutCause

ctx.Err() only ever returns two generic errors. In a big system, "context canceled" in a log is frustrating: cancelled by whom? Go 1.20 added WithCancelCause, whose cancel function takes an error, and context.Cause(ctx) to read it back. Go 1.21 added WithTimeoutCause and WithDeadlineCause.

package main

import (
	"context"
	"errors"
	"fmt"
)

var ErrPaymentDeclined = errors.New("payment declined")

func main() {
	ctx, cancel := context.WithCancelCause(context.Background())

	// Some goroutine discovers WHY we must stop and records it.
	cancel(ErrPaymentDeclined)

	fmt.Println("ctx.Err():         ", ctx.Err())          // always the generic error
	fmt.Println("context.Cause(ctx):", context.Cause(ctx)) // the specific reason
	fmt.Println("is declined?       ", errors.Is(context.Cause(ctx), ErrPaymentDeclined))

	// A context that wasn't cancelled with a cause reports ctx.Err() as its cause.
	plain, stop := context.WithCancel(context.Background())
	stop()
	fmt.Println("plain cause:       ", context.Cause(plain))
}
  1. WithCancelCause gives a cancel function that takes an error: the reason.
  2. We cancel with ErrPaymentDeclined. The context is now done and remembers the cause.
  3. ctx.Err() stays the generic context.Canceled, so existing code that checks for it keeps working.
  4. context.Cause returns the specific reason we passed in.
  5. It's a normal error value, so errors.Is works on it.
  6. A plain WithCancel context is cancelled the old way, with no cause.
  7. With no cause recorded, Cause falls back to ctx.Err(). It never returns nil for a done context.
ctx.Err():          context canceled
context.Cause(ctx): payment declined
is declined?        true
plain cause:        context canceled
package main

import (
	"context"
	"errors"
	"fmt"
	"time"
)

var ErrSlowUpstream = errors.New("inventory service took longer than 50ms")

func main() {
	ctx, cancel := context.WithTimeoutCause(context.Background(), 50*time.Millisecond, ErrSlowUpstream)
	defer cancel()

	<-ctx.Done()
	fmt.Println("Err:  ", ctx.Err())
	fmt.Println("Cause:", context.Cause(ctx))
}
  1. WithTimeoutCause is WithTimeout plus a custom error to record if the timer fires.
  2. Main blocks until the 50ms timer expires and closes Done.
  3. Err() is still the standard DeadlineExceeded.
  4. Cause gives the human-friendly reason, great for logs. If we had called cancel() first, the cause would be plain context.Canceled.
Err:   context deadline exceeded
Cause: inventory service took longer than 50ms

ctx.Err() stays the generic error on purpose, so all existing code that checks errors.Is(err, context.Canceled) keeps working. Use context.Cause(ctx) when you log or report a cancellation. signal.NotifyContext (later in this chapter) uses causes too: its cause is the signal that arrived.

The cancellation tree

Every derived context remembers its parent. When a context is cancelled, it cancels all of its descendants. It never affects its parent or its siblings. This is what lets one cancel() at the top of a request stop dozens of goroutines spread across packages.

package main

import (
	"context"
	"fmt"
)

func status(name string, ctx context.Context) {
	fmt.Printf("  %-8s err=%v\n", name, ctx.Err())
}

func main() {
	root := context.Background()
	request, cancelRequest := context.WithCancel(root)
	db, cancelDB := context.WithCancel(request)
	cache, cancelCache := context.WithCancel(request)
	query, cancelQuery := context.WithCancel(db)
	defer cancelRequest()
	defer cancelDB()
	defer cancelCache()
	defer cancelQuery()

	fmt.Println("cancel db (a middle node):")
	cancelDB()
	status("request", request)
	status("db", db)
	status("query", query)
	status("cache", cache)

	fmt.Println("cancel request (the parent):")
	cancelRequest()
	status("request", request)
	status("cache", cache)
}
cancel db (a middle node):
  request  err=<nil>
  db       err=context canceled
  query    err=context canceled
  cache    err=<nil>
cancel request (the parent):
  request  err=context canceled
  cache    err=context canceled
request, cancelReq := context.WithCancel(context.Background())
db, cancelDB := context.WithCancel(request)
cache, cancelCache := context.WithCancel(request)
query, cancelQuery := context.WithCancel(db)
defer cancelCache()
defer cancelQuery()

fmt.Println(request.Err(), db.Err(), query.Err(), cache.Err())

fmt.Println(cache.Err())
  1. Child of Background: request.
  2. Two children of request: db and cache. They're siblings.
  3. A grandchild: query hangs under db.
  4. We defer the cancels we're not calling explicitly — no leaks, even on early return.
  5. Cancel db. It walks its children and cancels query too. request and cache don't notice.
  6. The four errors confirm it: only the db subtree is cancelled.
  7. Cancel the root of our tree. Every descendant, including cache, is cancelled.
  8. cache was never touched directly but is cancelled through its parent.

Propagating ctx: the first-parameter rule

The convention is strict and universal: if a function might block, do I/O, or call something that does, its first parameter is ctx context.Context. Every layer passes it straight down. You'll see this signature on every database driver, HTTP client, gRPC stub and cloud SDK.

package main

import (
	"context"
	"errors"
	"fmt"
	"time"
)

// --- repository layer -------------------------------------------------

type OrderRepo struct{}

func (OrderRepo) Find(ctx context.Context, id int) (string, error) {
	select {
	case <-time.After(40 * time.Millisecond): // the "SQL query"
		return fmt.Sprintf("order#%d", id), nil
	case <-ctx.Done():
		return "", fmt.Errorf("repo.Find(%d): %w", id, ctx.Err())
	}
}

// --- service layer ----------------------------------------------------

type OrderService struct{ repo OrderRepo }

func (s OrderService) Summary(ctx context.Context, ids []int) ([]string, error) {
	var out []string
	for _, id := range ids {
		o, err := s.repo.Find(ctx, id) // same ctx passed straight down
		if err != nil {
			return out, fmt.Errorf("summary: %w", err)
		}
		out = append(out, o)
	}
	return out, nil
}

// --- "handler" layer ----------------------------------------------------

func handle(ctx context.Context, budget time.Duration) {
	ctx, cancel := context.WithTimeout(ctx, budget)
	defer cancel()

	svc := OrderService{}
	res, err := svc.Summary(ctx, []int{1, 2, 3})
	fmt.Printf("budget %v -> %v\n", budget, res)
	if err != nil {
		fmt.Println("   error:", err)
		fmt.Println("   timed out?", errors.Is(err, context.DeadlineExceeded))
	}
}

func main() {
	handle(context.Background(), 200*time.Millisecond)
	handle(context.Background(), 100*time.Millisecond)
}
budget 200ms -> [order#1 order#2 order#3]
budget 100ms -> [order#1 order#2]
   error: summary: repo.Find(3): context deadline exceeded
   timed out? true

The handler set a single budget. The service and repository didn't know or care about time limits — they just passed ctx on. With 100ms, the third query got cut off, and the error came back up wrapped with context at each layer, while errors.Is still finds DeadlineExceeded underneath.

Checking ctx in loops and select

Context is cooperative. Cancelling doesn't kill anything; it closes a channel. Your code has to look at it. There are two ways:

  • ctx.Err() != nil — a cheap, non-blocking check. Use it between iterations of CPU-bound loops.
  • case <-ctx.Done(): in a select — use it whenever you would otherwise block (a channel send/receive, a timer). Without it, a blocked goroutine can't hear the cancellation.
package main

import (
	"context"
	"fmt"
	"time"
)

// processAll is CPU-bound work with no channels; check ctx between items.
func processAll(ctx context.Context, items []int) (int, error) {
	total := 0
	for i, it := range items {
		if err := ctx.Err(); err != nil { // cheap, non-blocking check
			return total, fmt.Errorf("stopped at item %d: %w", i, err)
		}
		time.Sleep(10 * time.Millisecond) // pretend: expensive computation
		total += it
	}
	return total, nil
}

// produce sends on a channel; use select so a blocked send can be abandoned.
func produce(ctx context.Context, out chan<- int) error {
	for i := 0; ; i++ {
		select {
		case out <- i:
		case <-ctx.Done():
			return ctx.Err()
		}
	}
}

func main() {
	ctx, cancel := context.WithTimeout(context.Background(), 35*time.Millisecond)
	defer cancel()

	items := make([]int, 100)
	for i := range items {
		items[i] = 1
	}
	total, err := processAll(ctx, items)
	fmt.Println("total:", total, "err:", err)

	ctx2, cancel2 := context.WithCancel(context.Background())
	ch := make(chan int)
	done := make(chan error)
	go func() { done <- produce(ctx2, ch) }()

	fmt.Println(<-ch, <-ch, <-ch)
	cancel2() // consumer is done: producer must not block forever
	fmt.Println("producer exited with:", <-done)
}

  1. A 35ms budget for the whole loop.
  2. Item 0: check the context first. Still active.
  3. Do 10ms of "work" and add to the total.
  4. Item 1: check passes, work, total 2.
  5. Items 2 and 3 likewise. Somewhere during item 3 (at 35ms), the deadline passes. The work in progress isn't interrupted — context can't preempt code.
  6. Item 4: the check now sees the error, and we stop. The granularity of cancellation is one loop iteration.
  7. We report the partial result.
Senior engineer tip

"Every blocking operation has an exit" is a great code-review rule. Look at each channel send and receive in a goroutine: if it's not in a select with ctx.Done() (or guaranteed to complete), it's a potential goroutine leak. The producer in loop/main.go would block forever on out <- i after the consumer leaves; the ctx.Done() case is what lets it exit.

Go 1.23 changed timers so that an unstopped time.After in a select is garbage-collected once unreachable. Older advice to avoid time.After in loops for memory reasons no longer applies, though a reusable time.Timer is still a little cheaper in very hot loops.

WithoutCancel and AfterFunc

WithoutCancel: keep the values, lose the cancellation

Sometimes work must outlive the request that triggered it: writing an audit record, sending a "your order shipped" email. If you pass the request context, the work is cancelled the moment the handler returns. context.WithoutCancel(ctx) (Go 1.21) returns a context that keeps all of the parent's values (request ID, user, tracing span) but is never cancelled and has no deadline.

package main

import (
	"context"
	"fmt"
	"time"
)

type ctxKey string

func audit(ctx context.Context, event string) {
	time.Sleep(30 * time.Millisecond) // writing to the audit log takes a while
	fmt.Printf("audit %q for user=%v, ctx.Err()=%v\n", event, ctx.Value(ctxKey("user")), ctx.Err())
}

func main() {
	reqCtx, cancel := context.WithCancel(
		context.WithValue(context.Background(), ctxKey("user"), "ana"))

	// WithoutCancel: keep the values, drop the cancellation.
	bg := context.WithoutCancel(reqCtx)

	done := make(chan struct{})
	go func() {
		audit(bg, "order.created")
		close(done)
	}()

	cancel() // the HTTP request finished: reqCtx is cancelled
	fmt.Println("request ctx:", reqCtx.Err())
	<-done
}
  1. The request context carries user=ana and can be cancelled.
  2. WithoutCancel derives bg: it still sees parent values, but is never cancelled by the parent.
  3. A goroutine starts the audit write with bg. It sleeps 30ms to simulate slow I/O.
  4. Meanwhile the request ends and cancel() is called. Only reqCtx is affected.
  5. Main prints the request context's error.
  6. Main waits on done. The audit wakes, still sees user=ana, and bg is not cancelled, so the write completes.
  7. The goroutine closes done and main exits. Without WithoutCancel, this audit would have seen context canceled.
request ctx: context canceled
audit "order.created" for user=ana, ctx.Err()=<nil>
Gotcha

A context from WithoutCancel has no limit at all. Usually you wrap it again: ctx, cancel := context.WithTimeout(context.WithoutCancel(r.Context()), 5*time.Second). Detached work with no timeout is how you get goroutines that hang forever on a dead connection.

AfterFunc: run cleanup when a context ends

context.AfterFunc(ctx, f) (Go 1.21) schedules f to run in its own goroutine once ctx is done. It returns stop(), which deregisters f and reports whether it stopped it before it started. It's useful for bridging context into APIs that don't understand context — like closing a connection to unblock a read.

package main

import (
	"context"
	"fmt"
	"time"
)

func main() {
	ctx, cancel := context.WithCancel(context.Background())

	// AfterFunc: run f in its own goroutine once ctx is done.
	stop := context.AfterFunc(ctx, func() {
		fmt.Println("ctx done -> closing the connection")
	})

	// A second registration that we deregister before it fires.
	stop2 := context.AfterFunc(ctx, func() {
		fmt.Println("this never prints")
	})
	fmt.Println("stop2 prevented it:", stop2())

	time.Sleep(10 * time.Millisecond)
	cancel()
	time.Sleep(10 * time.Millisecond) // give the AfterFunc goroutine time to run

	fmt.Println("stop after it ran:", stop()) // false: already started
}
  1. A cancellable context.
  2. We register a callback. It does not run now; it will run in its own goroutine once ctx is done.
  3. A second callback is registered too.
  4. stop2() deregisters f2 before it fired, and returns true to say "I stopped it".
  5. cancel() closes the context. Go starts f1 in a new goroutine.
  6. Main sleeps briefly, giving that goroutine time to print.
  7. stop() now returns false: f1 already started, so it was too late to prevent it.
stop2 prevented it: true
ctx done -> closing the connection
stop after it ran: false

Context with HTTP clients and servers

The server side: r.Context()

Every incoming *http.Request carries a context. The net/http server cancels it when the client disconnects, when the request finishes (ServeHTTP returns), or when the server is shut down. Pass r.Context() to everything the handler calls, and an abandoned request stops costing you resources.

package main

import (
	"context"
	"fmt"
	"log"
	"net/http"
	"time"
)

// generateReport stands in for a slow DB query that respects ctx.
func generateReport(ctx context.Context) (string, error) {
	select {
	case <-time.After(2 * time.Second):
		return "report ready", nil
	case <-ctx.Done():
		return "", ctx.Err()
	}
}

func reportHandler(w http.ResponseWriter, r *http.Request) {
	ctx := r.Context() // cancelled when the client disconnects or the server shuts down
	log.Println("report: started")

	report, err := generateReport(ctx)
	if err != nil {
		log.Println("report: abandoned:", err)
		return // the client is gone; nobody would read a response
	}
	fmt.Fprintln(w, report)
}

func helloHandler(w http.ResponseWriter, r *http.Request) {
	// Give each request its own budget, derived from the request context.
	ctx, cancel := context.WithTimeout(r.Context(), 50*time.Millisecond)
	defer cancel()

	select {
	case <-time.After(10 * time.Millisecond):
		fmt.Fprintln(w, "hello, fast path")
	case <-ctx.Done():
		http.Error(w, "too slow", http.StatusGatewayTimeout)
	}
}

func main() {
	log.SetFlags(log.Ltime | log.Lmicroseconds)
	mux := http.NewServeMux()
	mux.HandleFunc("GET /report", reportHandler)
	mux.HandleFunc("GET /hello", helloHandler)
	log.Println("listening on :8089")
	log.Fatal(http.ListenAndServe("localhost:8089", mux))
}

We started this server in the background and hit it with curl, giving up on /report after 0.5s:

$ curl -s --max-time 0.5 localhost:8089/report
curl exit code: 28 (28 = timed out)

Then ran the Go client below (which gives up after 300ms). Here is the server's log for both requests:

23:31:53.252563 listening on :8089
23:31:53.757208 report: started
23:31:54.262487 report: abandoned: context canceled
23:31:55.319059 report: started
23:31:55.603890 report: abandoned: context canceled

Look at the timestamps: each report started and was abandoned at the moment its client hung up (about 0.5s and 0.3s later), not after the full 2 seconds. That's r.Context() doing its job.

func reportHandler(w http.ResponseWriter, r *http.Request) {
	ctx := r.Context()
	log.Println("report: started")

	select {
	case <-time.After(2 * time.Second):
		fmt.Fprintln(w, "report ready")
	case <-ctx.Done():
		log.Println("report: abandoned:", ctx.Err())
	}
}
  1. A request arrives. We grab its context: it's tied to this connection.
  2. Log that work started.
  3. The slow "report" is a 2-second timer. We wait on it and on ctx.Done().
  4. curl's --max-time 0.5 expires and it closes the TCP connection.
  5. The server notices the closed connection and cancels the request context. Done closes.
  6. We log and return. No 1.5 extra seconds of wasted work, no response written to a dead socket.

The client side: NewRequestWithContext

For outgoing calls, build requests with http.NewRequestWithContext(ctx, …). The context covers the whole exchange: DNS, connecting, sending, waiting for headers and reading the body. When it's cancelled, the transport aborts the connection.

package main

import (
	"context"
	"errors"
	"fmt"
	"io"
	"net/http"
	"time"
)

func get(ctx context.Context, url string) (string, error) {
	req, err := http.NewRequestWithContext(ctx, http.MethodGet, url, nil)
	if err != nil {
		return "", err
	}
	resp, err := http.DefaultClient.Do(req)
	if err != nil {
		return "", err
	}
	defer resp.Body.Close()
	b, err := io.ReadAll(resp.Body)
	return string(b), err
}

func main() {
	ctx, cancel := context.WithTimeout(context.Background(), 300*time.Millisecond)
	defer cancel()

	body, err := get(ctx, "http://localhost:8089/hello")
	fmt.Printf("hello:  %q err=%v\n", body, err)

	start := time.Now()
	body, err = get(ctx, "http://localhost:8089/report")
	fmt.Printf("report: %q err=%v\n", body, err)
	fmt.Println("gave up after ~", time.Since(start).Round(100*time.Millisecond))
	fmt.Println("is deadline exceeded:", errors.Is(err, context.DeadlineExceeded))
}
  1. One context with a 300ms budget is shared by both requests below.
  2. NewRequestWithContext attaches ctx to the request, and Do sends it. The context now governs DNS, connect, headers and body.
  3. The fast endpoint answers quickly. We read the body; the deferred Close returns the connection to the pool.
  4. Printed with %q, so the newline shows as \n.
  5. The slow endpoint. Do blocks waiting for response headers.
  6. The shared deadline hits. The transport aborts the connection and Do returns an error wrapping context.DeadlineExceeded.
  7. The error is a *url.Error that names the method and URL.
  8. We waited about the full budget (hello used only a tiny slice of it).
  9. errors.Is unwraps the *url.Error and finds DeadlineExceeded inside.
hello:  "hello, fast path\n" err=<nil>
report: "" err=Get "http://localhost:8089/report": context deadline exceeded
gave up after ~ 300ms
is deadline exceeded: true
Senior engineer tip

http.Get(url) and http.DefaultClient have no timeout at all. A slow server can hang your goroutine forever. In production always either pass a context with a deadline or use a client with Timeout set (&http.Client{Timeout: 10 * time.Second}) — ideally both: the client timeout as a safety net, the context for per-call budgets and cancellation. The same applies to database/sql: use QueryContext, ExecContext, never the context-less versions.

Context values: request-scoped data only

context.WithValue(parent, key, value) attaches a value; ctx.Value(key) looks it up by walking up the tree. It's meant for data that is about the request and must cross API boundaries that you don't control (middleware → handler → logging library): request IDs, trace spans, the authenticated user, a deadline-carrying auth token.

Two rules make it safe:

  1. Use an unexported key type. Keys are compared by type and value. With type ctxKey int declared in your package, no other package can ever create an equal key, so there are no collisions. Never use a plain string like "user" as a key.
  2. Wrap access in typed helpers (WithUser, UserFrom) so callers never see the key or do type assertions.
package main

import (
	"context"
	"fmt"
)

// An unexported key type: no other package can create a colliding key.
type ctxKey int

const (
	requestIDKey ctxKey = iota
	userKey
)

type User struct {
	ID   int
	Name string
}

// Typed helpers hide the key and the type assertion.
func WithRequestID(ctx context.Context, id string) context.Context {
	return context.WithValue(ctx, requestIDKey, id)
}

func RequestID(ctx context.Context) string {
	id, _ := ctx.Value(requestIDKey).(string) // "" if missing
	return id
}

func WithUser(ctx context.Context, u *User) context.Context {
	return context.WithValue(ctx, userKey, u)
}

func UserFrom(ctx context.Context) (*User, bool) {
	u, ok := ctx.Value(userKey).(*User)
	return u, ok
}

func handle(ctx context.Context) {
	u, ok := UserFrom(ctx)
	fmt.Printf("[%s] user=%v ok=%v\n", RequestID(ctx), u, ok)
}

func main() {
	ctx := WithRequestID(context.Background(), "req-7f3a")
	handle(ctx) // no user yet

	ctx = WithUser(ctx, &User{ID: 42, Name: "ana"})
	handle(ctx)

	// A different type with the same underlying value is a DIFFERENT key.
	fmt.Println("lookup with int(0):", context.Background().Value(0), ctx.Value(0))
}
  1. WithRequestID wraps Background in a new context node holding one key/value. Contexts are immutable: we get a new ctx back.
  2. handle asks for the user. ctx.Value(userKey) walks up the chain, finds nothing, returns nil, and the comma-ok assertion gives ok=false instead of panicking.
  3. RequestID finds its key one level up. The typed helpers hide both the key and the assertion.
  4. WithUser adds another node on top. The old ctx is unchanged; we reassign the variable to the new one.
  5. Now the user is found in the top node, and the request ID is still reachable further up.
  6. Looking up plain int(0) finds nothing, even though requestIDKey is also 0. Keys compare by type and value, so an unexported key type cannot collide with other packages.
[req-7f3a] user=<nil> ok=false
[req-7f3a] user=&{42 ana} ok=true
lookup with int(0): <nil> <nil>

ctx = context.WithValue(ctx, "db", db)

Gotcha: context is not a bag of parameters

Database handles, loggers, config and function arguments do not belong in context. They become invisible dependencies: the compiler can't check them, and readers can't see what a function needs. If a function needs it to do its job, make it a parameter or a struct field. Value lookup is also a linear walk up the chain, so deep chains with many values are slow.

Graceful Ctrl+C with signal.NotifyContext

When you press Ctrl+C, the OS sends SIGINT to your process; Docker and Kubernetes send SIGTERM before killing a container. By default Go exits immediately — mid-write, with open connections. signal.NotifyContext turns those signals into a context cancellation, so your whole program can shut down the same way it handles any other cancellation.

package main

import (
	"context"
	"fmt"
	"os"
	"os/signal"
	"syscall"
	"time"
)

func main() {
	// ctx is cancelled on the first Ctrl+C (SIGINT) or SIGTERM (what Docker/Kubernetes send).
	ctx, stop := signal.NotifyContext(context.Background(), os.Interrupt, syscall.SIGTERM)
	defer stop()

	fmt.Println("working... press Ctrl+C to stop")
	tick := time.NewTicker(200 * time.Millisecond)
	defer tick.Stop()

	for n := 1; ; n++ {
		select {
		case <-tick.C:
			fmt.Println("tick", n)
		case <-ctx.Done():
			stop() // restore default behaviour: a 2nd Ctrl+C now kills immediately
			fmt.Println("shutting down:", context.Cause(ctx))
			time.Sleep(100 * time.Millisecond) // flush, close DB, etc.
			fmt.Println("bye")
			return
		}
	}
}

We ran the binary and sent it SIGINT (what Ctrl+C does) after about a second:

working... press Ctrl+C to stop
tick 1
tick 2
tick 3
tick 4
tick 5
^C
shutting down: interrupt signal received
bye

The context's cause is the signal (interrupt signal received). Calling stop() as soon as shutdown begins restores the default behaviour, so an impatient second Ctrl+C really kills the process. In an HTTP service, the ctx.Done() branch is where you'd call server.Shutdown(shutdownCtx) with its own timeout (see Chapter 17).

Senior engineer tip

A clean production main looks like: ctx, stop := signal.NotifyContext(...) → start servers and workers with that ctx (often in an errgroup.WithContext) → <-ctx.Done() → shut down with a fresh, bounded context.WithTimeout(context.Background(), 10*time.Second). Kubernetes waits terminationGracePeriodSeconds (default 30s) after SIGTERM before SIGKILL — keep your shutdown well under that.

An HTTP handler wants to send a confirmation email in a goroutine after responding. Which context should that goroutine use?
r.Context() is cancelled as soon as the handler returns, which would abort the email. WithoutCancel keeps the request ID and trace values for logging while detaching from the request's lifetime, and the wrapping timeout makes sure the email goroutine can't hang forever.

Exercises

Exercise 1 — First response wins

Write first(ctx, replicas []time.Duration) (int, error) that "queries" every replica concurrently (each just waits for its duration) and returns the index of the fastest one. As soon as one answers, cancel the others, and make sure no goroutine leaks. If ctx expires first, return its error.

Solution
package main

import (
	"context"
	"fmt"
	"runtime"
	"time"
)

func query(ctx context.Context, d time.Duration) error {
	select {
	case <-time.After(d):
		return nil
	case <-ctx.Done():
		return ctx.Err()
	}
}

func first(ctx context.Context, replicas []time.Duration) (int, error) {
	ctx, cancel := context.WithCancel(ctx)
	defer cancel() // tells the losers to stop when we return

	winner := make(chan int, len(replicas)) // buffered: losers never block on send
	for i, d := range replicas {
		go func() {
			if query(ctx, d) == nil {
				winner <- i
			}
		}()
	}

	select {
	case i := <-winner:
		return i, nil
	case <-ctx.Done():
		return -1, ctx.Err()
	}
}

func main() {
	replicas := []time.Duration{80 * time.Millisecond, 20 * time.Millisecond, 50 * time.Millisecond}

	i, err := first(context.Background(), replicas)
	fmt.Println("fastest replica:", i, err)

	ctx, cancel := context.WithTimeout(context.Background(), 10*time.Millisecond)
	defer cancel()
	i, err = first(ctx, replicas)
	fmt.Println("with 10ms budget:", i, err)

	time.Sleep(20 * time.Millisecond) // let cancelled goroutines exit
	fmt.Println("goroutines left:", runtime.NumGoroutine())
}

with 10ms budget: -1 context deadline exceeded
goroutines left: 1
Exercise 2 — Request-ID middleware

Write HTTP middleware that reads X-Request-ID (or generates "req-1", "req-2", … if absent), stores it in the request context with a typed key, and a handler that echoes it back. Test it with httptest (a preview of Chapter 15) instead of a real server.

Solution
package main

import (
	"context"
	"fmt"
	"net/http"
	"net/http/httptest"
	"strconv"
	"sync/atomic"
)

type ctxKey int

const requestIDKey ctxKey = 0

func RequestID(ctx context.Context) string {
	id, _ := ctx.Value(requestIDKey).(string)
	return id
}

func WithRequestID(next http.Handler) http.Handler {
	var counter atomic.Int64
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		id := r.Header.Get("X-Request-ID")
		if id == "" {
			id = "req-" + strconv.FormatInt(counter.Add(1), 10)
		}
		ctx := context.WithValue(r.Context(), requestIDKey, id)
		w.Header().Set("X-Request-ID", id)
		next.ServeHTTP(w, r.WithContext(ctx)) // pass the enriched request on
	})
}

func hello(w http.ResponseWriter, r *http.Request) {
	fmt.Fprintf(w, "hello from %s", RequestID(r.Context()))
}

func main() {
	h := WithRequestID(http.HandlerFunc(hello))

	for _, given := range []string{"", "abc-123", ""} {
		req := httptest.NewRequest("GET", "/", nil)
		if given != "" {
			req.Header.Set("X-Request-ID", given)
		}
		rec := httptest.NewRecorder()
		h.ServeHTTP(rec, req)
		fmt.Printf("%d %q header=%s\n", rec.Code, rec.Body.String(), rec.Header().Get("X-Request-ID"))
	}
}

200 "hello from abc-123" header=abc-123
200 "hello from req-2" header=req-2

Key takeaways

  • context.Context carries cancellation, deadlines and request-scoped values across API boundaries. Pass it as the first parameter, named ctx.
  • Roots: Background() (main, tests) and TODO() (placeholder). Derive everything else with With….
  • WithCancel, WithTimeout, WithDeadline all return a cancel — defer cancel() immediately.
  • Cancellation flows down the tree, never up or sideways. A child can shorten a deadline, never extend it.
  • Context is cooperative: check ctx.Err() in loops and select on ctx.Done() wherever you block.
  • WithCancelCause / context.Cause explain why; WithoutCancel detaches background work; AfterFunc runs cleanup on cancel.
  • Servers: use r.Context(). Clients: NewRequestWithContext, and never rely on http.DefaultClient without a deadline.
  • Values: unexported key types, typed helpers, request metadata only — never dependencies or optional parameters.
  • Don't store ctx in structs, don't pass nil, don't ignore cancel. Use signal.NotifyContext for graceful shutdown.

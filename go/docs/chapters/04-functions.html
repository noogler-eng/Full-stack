Functions & Closures

Functions are the building blocks of every Go program. In this chapter you will learn how to write them, how Go passes data into them, and how functions can be stored, passed around and even "remember" things. That last trick is called a closure, and it powers a lot of idiomatic Go.

Why functions exist

Imagine writing a recipe book where every recipe that needs a white sauce re-explains how to make white sauce, step by step. It works, but the book is huge, and if you find a better sauce method you have to fix it in fifty places. A function is the "see page 12: white sauce" of programming. You write a piece of logic once, give it a name, and call it wherever you need it.

Functions give you three big wins:

  • Reuse: write once, call many times.
  • Naming: calculateTax(order) tells the reader what happens without making them read how.
  • Isolation: a function has its own variables. What happens inside does not leak out unless you return it.

Declaring a function

A function declaration has four parts: the keyword func, a name, a list of parameters (the inputs, each with a type), and an optional result type (the output). The body sits between braces.

package main

import "fmt"

// add takes two ints and returns their sum.
func add(a int, b int) int {
	return a + b
}

// When neighbouring parameters share a type, list the type once.
func volume(length, width, height float64) float64 {
	return length * width * height
}

// A function with no parameters and no result.
func sayHello() {
	fmt.Println("hello from sayHello")
}

func greet(name string) string {
	return "Hi, " + name + "!"
}

func main() {
	sayHello()
	fmt.Println(add(2, 3))
	fmt.Println(volume(2, 3, 4))
	fmt.Println(greet("Gopher"))
}
hello from sayHello
5
24
Hi, Gopher!

Notice a few Go-specific details:

  • The type comes after the name: a int, not int a. This reads naturally left to right: "a is an int".
  • When neighbouring parameters share a type you can write the type once: length, width, height float64.
  • There is no function overloading. You cannot have two functions called add with different parameters in the same package. Pick distinct names instead, like addInts and addFloats (or use generics, Chapter 9).
  • There are no default parameter values. If you want optional settings, see the functional options pattern later in this chapter.
  • Function names starting with an uppercase letter (Add) are exported: other packages can call them. Lowercase names (add) are private to the package. That is the whole visibility system.
Vocabulary

Parameter: the variable name in the function declaration (a in func add(a int)). Argument: the actual value you pass when calling (2 in add(2, 3)). Signature: the parameter types plus the result types, e.g. func(int, int) int.

If a function promises a result, every path through it must end in a return. The compiler checks this for you:

package main

func sign(n int) string {
	if n > 0 {
		return "positive"
	} else if n < 0 {
		return "negative"
	}
}

func main() {
	_ = sign(1)
}
./main.go:9:1: missing return

The compiler cannot prove one of the branches runs, so it complains. The fix is to make the final case a plain return "zero" after the ifs.

Parameters are always passed by value

This is the single most important rule about Go functions: every argument is copied into the function's parameter. Go calls this pass by value. The function gets its own private copy, so changing the parameter does not change the caller's variable.

But "copy" means "copy the value you passed", and for some types that value is small and points somewhere else. Let's see all the cases side by side:

package main

import "fmt"

func double(n int) {
	n = n * 2 // changes the local copy only
	fmt.Println("inside double:", n)
}

func resetArray(a [3]int) {
	a[0] = 0 // arrays are copied too
}

func resetSlice(s []int) {
	s[0] = 0 // the slice header is copied, but it points at the SAME backing array
}

func doublePtr(n *int) {
	*n = *n * 2 // write through the pointer
}

func main() {
	x := 10
	double(x)
	fmt.Println("after double:", x)

	arr := [3]int{1, 2, 3}
	resetArray(arr)
	fmt.Println("array after resetArray:", arr)

	sl := []int{1, 2, 3}
	resetSlice(sl)
	fmt.Println("slice after resetSlice:", sl)

	doublePtr(&x)
	fmt.Println("after doublePtr:", x)
}
  1. Execution starts in main. x is 10.
  2. Calling double(x) copies 10 into a brand-new variable n. Doubling n touches only that copy.
  3. Inside the function, n really is 20.
  4. Back in main, n is gone and x was never touched: still 10.
  5. Arrays are values too: resetArray receives a copy of all three ints, and zeroes the copy's first slot.
  6. The caller's array is unchanged.
  7. A slice is different. Only the small header (pointer, len, cap) is copied, and that copy points at the same backing array. Writing s[0] writes the caller's data.
  8. So sl now starts with 0.
  9. To change x itself, we pass its address. *n = *n * 2 writes through the pointer into main's x.
  10. This time the change sticks: x is 20.
inside double: 20
after double: 10
array after resetArray: [1 2 3]
slice after resetSlice: [0 2 3]
after doublePtr: 20

What happened?

  • double(x) got a copy of 10. Changing it inside did nothing outside.
  • resetArray(arr) got a copy of the whole array (all three ints). Arrays are values in Go.
  • resetSlice(sl) got a copy of the slice header: a tiny struct holding a pointer, a length and a capacity. The copy still points at the same underlying array, so writing s[0] changed the caller's data. (Chapter 5 dives deep into this.)
  • doublePtr(&x) got a copy of the address of x. Through that address it can change the original.
Mental model

Passing an argument is like handing someone a photocopy. If the page contains a recipe, they can scribble on their copy and yours stays clean. If the page contains your home address (a pointer, or a slice/map header), they can't change your copy of the address, but they can drive to your house and rearrange the furniture.

Type you passWhat gets copiedCan the callee change the caller's data?
int, bool, string, float64The value itselfNo
Array [N]TAll N elementsNo
StructEvery field (shallow)No (but pointer fields inside still point to shared data)
Pointer *TThe addressYes, through *p
Slice []THeader: ptr, len, cap (24 bytes)Yes, existing elements. No, its length (append is not visible)

Senior engineer tip

Don't reach for pointers "for performance" by default. Copying a struct of a few fields is extremely cheap, and values are easier to reason about (no surprise mutation, no nil checks). Use a pointer when the function must modify the caller's data, or when the struct is genuinely large (think hundreds of bytes) and measured to matter. Clear intent beats micro-optimisation.

Multiple return values

Many languages let a function return only one thing, so programmers resort to tricks: returning a tuple object, using "out" parameters, or returning -1 to mean "failed". Go simply lets a function return several values. Put the result types in parentheses.

package main

import (
	"errors"
	"fmt"
	"strconv"
)

func divmod(a, b int) (int, int) {
	return a / b, a % b
}

var ErrDivByZero = errors.New("division by zero")

func safeDiv(a, b float64) (float64, error) {
	if b == 0 {
		return 0, ErrDivByZero
	}
	return a / b, nil
}

func main() {
	q, r := divmod(17, 5)
	fmt.Println("17 / 5 =", q, "remainder", r)

	// Ignore a value you don't need with the blank identifier _.
	_, rem := divmod(10, 3)
	fmt.Println("10 % 3 =", rem)

	if v, err := safeDiv(1, 0); err != nil {
		fmt.Println("error:", err)
	} else {
		fmt.Println("value:", v)
	}

	// The standard library uses (value, error) everywhere.
	n, err := strconv.Atoi("42x")
	fmt.Println(n, err)
}
  1. Before main runs, the package-level ErrDivByZero is created. It's a sentinel error callers can compare against.
  2. We call divmod(17, 5). One return statement hands back two values: 17/5 and 17%5.
  3. Both results land in q and r in one assignment.
  4. We only care about the remainder, so the quotient goes to _, the blank identifier. Go insists you receive every value, but _ lets you drop one on purpose.
  5. The if short statement calls safeDiv(1, 0). b is zero, so it returns 0, ErrDivByZero.
  6. err is not nil, so we take the error branch. v and err exist only inside this if/else.
  7. The standard library follows the same (value, error) shape. "42x" isn't a number, so Atoi returns the zero value 0 plus an error.
  8. Printing both shows why you always check err first: the 0 is not a real answer.
17 / 5 = 3 remainder 2
10 % 3 = 1
error: division by zero
0 strconv.Atoi: parsing "42x": invalid syntax

The most important use of multiple returns is the (value, error) convention. A function that can fail returns its result and an error as the last value. If the error is nil, the value is good. If not, the caller handles it. You will see this pattern thousands of times in Go code. Chapter 10 covers errors in depth.

You must receive all the return values (or explicitly discard them with _). Go will not silently drop one:

package main

import "fmt"

func pair() (int, string) { return 1, "one" }

func main() {
	n := pair()
	fmt.Println(n)
}
./main.go:8:7: assignment mismatch: 1 variable but pair returns 2 values

Use the "if with a short statement" form, if v, err := f(); err != nil { ... }, when you only need v and err inside the if/else. It keeps those variables scoped tightly so they can't be misused later.

A function is declared func lookup(id int) (string, bool). Which call compiles?
The function returns exactly two values, so you must receive exactly two. _ throws one away on purpose. You also cannot use a multi-value call inside an expression like +.

Named results and naked returns

You can give your result values names. They become ordinary local variables, initialised to their zero values (0, "", nil and so on). A bare return with no values, called a naked return, then returns whatever those variables hold.

package main

import (
	"fmt"
	"strings"
)

// Named results document what comes back. They start at their zero values.
func splitName(full string) (first, last string) {
	parts := strings.Fields(full)
	if len(parts) == 0 {
		return // naked return: returns first="" last=""
	}
	first = parts[0]
	last = parts[len(parts)-1]
	return // naked return: returns the current first and last
}

// The most useful job for named results: letting a deferred func change them.
func parseAge(s string) (age int, err error) {
	defer func() {
		if err != nil {
			err = fmt.Errorf("parseAge(%q): %w", s, err)
		}
	}()
	_, err = fmt.Sscanf(s, "%d", &age)
	return age, err
}

func main() {
	f, l := splitName("Ada King Lovelace")
	fmt.Printf("first=%q last=%q\n", f, l)

	f, l = splitName("   ")
	fmt.Printf("first=%q last=%q\n", f, l)

	fmt.Println(parseAge("37"))
	fmt.Println(parseAge("old"))
}
  1. Calling splitName. The named results first and last already exist as local variables, set to their zero value "".
  2. strings.Fields splits on whitespace into three words, so we skip the early return.
  3. We assign the named results, then a naked return sends back whatever they hold right now.
  4. Back in main, f and l get the two names.
  5. With only spaces, parts is empty. The naked return on line 12 returns the untouched zero values.
  6. Both come back empty.
  7. parseAge("37") first registers the deferred closure (it doesn't run yet). Sscanf fills age through &age and leaves err nil.
  8. On return the deferred func runs, sees err == nil, and does nothing. Result: 37 and nil.
  9. With "old", Sscanf fails. return age, err stores 0 and the error into the named results.
  10. Now the deferred closure runs after the return values were set, and replaces err with a wrapped version. This only works because the result is named.
  11. The caller sees the wrapped error with its extra context.
first="Ada" last="Lovelace"
first="" last=""
37 <nil>
0 parseAge("old"): expected integer

Named results have two genuinely good uses:

  1. Documentation. func splitName(full string) (first, last string) tells the reader which string is which. Compare with (string, string), where you'd have to read the body.
  2. Letting a defer modify the result. In parseAge, the deferred function runs after return has set err, and it can wrap the error with extra context. This only works because err has a name the deferred closure can see.
When to avoid naked returns

In a long function, a bare return forces the reader to scroll up and track what every named result currently holds. That is a bug magnet. The common rule in Go code reviews: naked returns are fine in tiny functions (a handful of lines); otherwise write return first, last explicitly even when the results are named. You get the documentation benefit without the mystery.

func load(path string) (cfg Config, err error) {
	data, err := os.ReadFile(path)
	if err != nil {
		return // what is cfg here? reader must check
	}
	// ... 40 more lines ...
	err = json.Unmarshal(data, &cfg)
	return // which err? which cfg?
}
func load(path string) (Config, error) {
	data, err := os.ReadFile(path)
	if err != nil {
		return Config{}, fmt.Errorf("read %s: %w", path, err)
	}
	var cfg Config
	if err := json.Unmarshal(data, &cfg); err != nil {
		return Config{}, fmt.Errorf("parse %s: %w", path, err)
	}
	return cfg, nil
}

Variadic functions

A variadic function accepts any number of arguments of one type. You mark the last parameter with ...T. Inside the function that parameter is just a []T slice. You have already used one: fmt.Println is declared as func Println(a ...any) (n int, err error).

package main

import (
	"fmt"
	"strings"
)

// nums is a []int inside the function.
func sum(nums ...int) int {
	total := 0
	for _, n := range nums {
		total += n
	}
	return total
}

// Fixed parameters come first; the variadic one must be last.
func joinWith(sep string, words ...string) string {
	return strings.Join(words, sep)
}

func main() {
	fmt.Println(sum())        // zero args -> nums is nil
	fmt.Println(sum(1, 2, 3)) // packed into []int{1, 2, 3}

	scores := []int{90, 85, 77}
	fmt.Println(sum(scores...)) // spread an existing slice

	fmt.Println(joinWith("-", "a", "b", "c"))
	parts := []string{"usr", "local", "bin"}
	fmt.Println("/" + joinWith("/", parts...))

	// fmt.Println itself is variadic: func Println(a ...any)
	args := []any{"x =", 1, true}
	fmt.Println(args...)
}
0
6
252
a-b-c
/usr/local/bin
x = 1 true

The rules:

  • Only the last parameter can be variadic.
  • Calling with zero variadic arguments gives a nil slice (length 0), so range just does nothing.
  • To pass an existing slice, spread it with slice.... You can't mix: sum(1, xs...) does not compile.
func sum(label string, nums ...int) {
	total := 0
	for _, n := range nums {
		total += n
	}
	fmt.Println(label, len(nums), total)
}

func main() {
	sum("none")
	sum("three", 1, 2, 3)
	xs := []int{10, 20}
	sum("spread", xs...)
}
  1. First call passes only the label. No numbers at all.
  2. Inside sum, nums is a nil slice. Its length is 0.
  3. The loop runs zero times, so we print the label, 0 and 0.
  4. Second call: Go builds a brand-new slice []int{1, 2, 3} for us.
  5. The loop adds 1, 2 and 3.
  6. Prints the count and the total.
  7. Third call spreads xs. No new slice is built: nums is xs (same backing array).
  8. So if sum modified nums[0], the caller's xs would change too.
Gotcha: spreading shares memory

When you call f(xs...), the function receives xs itself, not a copy. If the function writes to nums[i], it writes to your slice. If you need isolation, pass slices.Clone(xs)....

Functions are values

In Go, functions are first-class values. That fancy phrase just means a function can be treated like any other value: stored in a variable, put in a map or slice, passed as an argument, and returned from another function. Every function has a type, written like its signature without names: func(int, int) int.

package main

import "fmt"

// A named function type. Any func with this signature fits.
type BinaryOp func(a, b int) int

func add(a, b int) int { return a + b }
func mul(a, b int) int { return a * b }

func apply(op BinaryOp, a, b int) int {
	return op(a, b)
}

func main() {
	// Functions are values: store them in variables...
	var f func(int, int) int = add
	fmt.Println(f(3, 4))

	// ...in maps...
	ops := map[string]BinaryOp{
		"+": add,
		"*": mul,
		"-": func(a, b int) int { return a - b },
	}
	for _, sym := range []string{"+", "*", "-"} {
		fmt.Printf("7 %s 3 = %d\n", sym, apply(ops[sym], 7, 3))
	}

	// The zero value of a func type is nil. Calling nil panics, so check first.
	var hook func(string)
	if hook == nil {
		fmt.Println("no hook registered")
	}
	fmt.Printf("type of add: %T\n", add)
}
  1. A variable of type func(int, int) int can hold any function with that signature. We store add in it (no parentheses: we're not calling it).
  2. Calling f(3, 4) really calls add.
  3. A map from symbol to function: a dispatch table. The "-" entry is an anonymous function written inline.
  4. First iteration: ops["+"] looks up add and passes it to apply, which simply calls op(a, b).
  5. Same code, different function: now op is mul.
  6. The anonymous function works exactly the same way.
  7. The zero value of a func type is nil. Calling hook("x") now would panic, so we check first.
  8. %T shows a function's type: its signature without parameter names.
7
7 + 3 = 10
7 * 3 = 21
7 - 3 = 4
no hook registered
type of add: func(int, int) int

A few things worth noticing:

  • type BinaryOp func(a, b int) int creates a named function type. It makes signatures readable (apply(op BinaryOp, ...)) and lets you attach methods to it (the standard library's http.HandlerFunc does exactly this).
  • A map from strings to functions is a neat replacement for a long switch: a dispatch table.
  • The zero value of any function type is nil. Calling a nil function panics, so check optional callbacks before calling them.
  • Function values can only be compared to nil. add == mul does not compile, so funcs can't be map keys.

Anonymous functions

An anonymous function (also called a function literal) is a function without a name, written right where you need it. You can store it in a variable, call it on the spot, or pass it straight to another function.

package main

import (
	"fmt"
	"slices"
)

func main() {
	// Assign an anonymous function (a "function literal") to a variable.
	square := func(n int) int { return n * n }
	fmt.Println(square(9))

	// Call it immediately (an IIFE): handy for a one-off scope.
	result := func(a, b int) int {
		return a*10 + b
	}(4, 2)
	fmt.Println(result)

	// The most common use: passing behaviour inline.
	people := []string{"Charlie", "al", "Bob"}
	slices.SortFunc(people, func(a, b string) int {
		return len(a) - len(b)
	})
	fmt.Println(people)
}
81
42
[al Bob Charlie]

The third form, passing a small function inline, is what you'll write most often: sort comparators, HTTP handlers, goroutine bodies (go func() { ... }()), cleanup callbacks (t.Cleanup(func() { ... })) and so on.

If an anonymous function grows past roughly ten lines, or you need it in two places, give it a name. Named functions show up in stack traces with a readable name instead of main.main.func3, which makes debugging much easier.

Closures: functions that remember

Here's where things get interesting. An anonymous function can use variables from the function around it. When it does, it captures those variables. The combination of "a function + the variables it captured" is called a closure.

The key word is variables, not values. A closure does not take a snapshot. It holds on to the variable itself, so it sees later changes, and its own changes are visible outside:

x := 1
show := func() { fmt.Println("x is", x) }
show()
x = 2
show()
inc := func() { x++ }
inc()
inc()
show()
  1. We create x with value 1.
  2. We build a closure. It doesn't copy 1; it remembers the variable x.
  3. Calling it reads the current value: 1.
  4. We change x outside the closure.
  5. The closure sees the change, because it shares the same variable.
  6. A second closure, inc, captures the same x and increments it.
  7. Again: x is now 4. Both closures and main all see one variable.
  8. So show prints 4.
x is 1
x is 2
x is 4

The counter: state that outlives its function

The classic closure example is a counter. newCounter creates a local variable count, then returns a function that increments it. Normally a local variable dies when its function returns. But here the returned closure still needs count, so Go keeps it alive. Every call to newCounter creates a fresh count, so each counter is independent.

func newCounter() func() int {
	count := 0
	return func() int {
		count++
		return count
	}
}

func main() {
	c1 := newCounter()
	fmt.Println(c1())
	fmt.Println(c1())
	c2 := newCounter()
	fmt.Println(c2())
	fmt.Println(c1())
}
  1. We call newCounter(). Go is about to create a brand-new count variable.
  2. Inside, count := 0 is created and the function literal captures it. That closure is returned and stored in c1.
  3. Calling c1() runs lines 4 and 5: count becomes 1 and is returned.
  4. Calling again: the same count is still alive, now 2.
  5. A second call to newCounter() creates a separate count for c2.
  6. c2 starts from scratch: 1.
  7. c1 is untouched by c2 and continues from 2 to 3.
Under the hood

How does count survive after newCounter returns? The compiler runs escape analysis: it notices the variable is still referenced after the function ends, so it allocates count on the heap (long-lived memory managed by the garbage collector) instead of the stack (short-lived, per-call memory). You can see this decision with go build -gcflags=-m, which prints lines like moved to heap: count. Chapter 18 explores this more.

Generators

A closure that returns "the next value" each time you call it is called a generator. The captured variables hold the generator's progress:

package main

import "fmt"

// newCounter returns a function that "remembers" count.
func newCounter() func() int {
	count := 0
	return func() int {
		count++
		return count
	}
}

// fibGen returns a generator: each call yields the next Fibonacci number.
func fibGen() func() int {
	a, b := 0, 1
	return func() int {
		r := a
		a, b = b, a+b
		return r
	}
}

func main() {
	c1 := newCounter()
	fmt.Println(c1())
	fmt.Println(c1())
	c2 := newCounter()
	fmt.Println(c2())
	fmt.Println(c1())

	next := fibGen()
	for range 10 {
		fmt.Print(next(), " ")
	}
	fmt.Println()
}
  1. The counter part works just like the walkthrough above: c1 owns one count, which goes 1, 2.
  2. c2 gets its own fresh count; c1 carries on from where it was.
  3. fibGen() creates a and b and returns a closure that captures both. They live on after fibGen returns.
  4. First call: remember the current a (0) in r, then shift the pair forward with a tuple assignment. The right side is evaluated first, so no temp variable is needed.
  5. Second call picks up the saved state: returns 1, pair becomes (1, 2).
  6. Third call returns 1 again, pair becomes (2, 3). fmt.Print adds no newline, so the numbers pile up on one line.
  7. Calls 4 to 10 continue the same way: 2, 3, 5, 8, 13, 21, 34. The generator's whole "progress" is just those two captured variables.
  8. The final Println() ends the line of ten numbers.

2
1
3

Since Go 1.23 there's an even nicer way to express "a sequence of values": range-over-func iterators. An iterator is a function that takes a yield callback and calls it once per value. The iter package names this shape iter.Seq[T], and you can loop over it with plain for ... range:

package main

import (
	"fmt"
	"iter"
)

// Countdown returns an iterator: a func that pushes values to yield.
func Countdown(from int) iter.Seq[int] {
	return func(yield func(int) bool) {
		for i := from; i >= 0; i-- {
			if !yield(i) { // the loop body said "break"
				return
			}
		}
	}
}

func main() {
	for n := range Countdown(5) {
		if n == 1 {
			break
		}
		fmt.Print(n, " ")
	}
	fmt.Println("liftoff?")
}
  1. The range calls Countdown(5), which just returns a function. Nothing has been counted yet.
  2. The compiler turns the loop body (lines 21-24) into a function and passes it as yield. Then the iterator function starts running.
  3. The iterator calls yield(5). Control jumps into the loop body with n = 5; it's not 1, so it prints 5 (no newline yet) and yield returns true.
  4. Back in the iterator, i-- and yield(4): the body prints 4 .
  5. Same for 3 and 2. The iterator and the loop body take turns, one value at a time.
  6. With n == 1, the body hits break. That makes yield return false to the iterator.
  7. The iterator sees false and must stop with return. Calling yield again after false would panic at run time.
  8. The loop is over and main continues on the same line.
5 4 3 2 liftoff?

When the loop body hits break, yield returns false and the iterator must stop. It's closures all the way down: the loop body itself is turned into the yield function by the compiler. You'll use iterators from the slices and maps packages in the next chapter.

Closures in loops (and the Go 1.22 fix)

For over a decade this was the most famous Go bug. Before Go 1.22, a for loop had one loop variable shared by every iteration. Closures created in the loop all captured that same variable, so after the loop they all saw its final value.

package main

import "fmt"

func main() {
	var funcs []func()
	for i := 0; i < 3; i++ {
		// Go 1.22+: each iteration has its OWN i.
		funcs = append(funcs, func() { fmt.Print(i, " ") })
	}
	for _, f := range funcs {
		f()
	}
	fmt.Println()
}

Run with a go.mod that says go 1.21 (old semantics):

3 3 3

The exact same code with go 1.22 or later in go.mod:

0 1 2

Go 1.22 changed loops so that each iteration gets its own fresh copy of the loop variable. Closures (and goroutines) created in different iterations now capture different variables, which is what everyone expected all along. The behaviour is controlled by the go line in your module's go.mod, so old code keeps its old meaning until you upgrade that line.

Gotcha: you'll still see the old workaround

Older codebases are full of i := i lines inside loops, or go func(i int) { ... }(i). Those were workarounds for the shared loop variable. On Go 1.22+ they are harmless but redundant (the copyloopvar linter in golangci-lint flags them). The fix only applies to variables declared by the for statement; a variable declared outside the loop and captured inside is still one shared variable.

With go 1.22 in go.mod, what does this print?
var fs []func(); for i := range 3 { fs = append(fs, func(){ fmt.Print(i) }) }; for _, f := range fs { f() }
Each iteration has its own i, so the three closures capture 0, 1 and 2. Under the pre-1.22 rules a classic three-clause loop would print 333 (the final value after the loop increments past 2).

Higher-order functions

A higher-order function is a function that takes a function as an argument, returns a function, or both. You have already met some: slices.SortFunc takes a comparator, newCounter returns a function. With generics (Chapter 9) you can write reusable Map, Filter and Reduce helpers:

package main

import (
	"fmt"
	"strings"
)

// Map applies f to every element and returns a new slice.
func Map[T, U any](in []T, f func(T) U) []U {
	out := make([]U, 0, len(in))
	for _, v := range in {
		out = append(out, f(v))
	}
	return out
}

// Filter keeps the elements for which keep returns true.
func Filter[T any](in []T, keep func(T) bool) []T {
	var out []T
	for _, v := range in {
		if keep(v) {
			out = append(out, v)
		}
	}
	return out
}

// Reduce folds the slice into a single value.
func Reduce[T, A any](in []T, init A, f func(A, T) A) A {
	acc := init
	for _, v := range in {
		acc = f(acc, v)
	}
	return acc
}

// A function that RETURNS a function: a factory of predicates.
func longerThan(n int) func(string) bool {
	return func(s string) bool { return len(s) > n }
}

func main() {
	nums := []int{1, 2, 3, 4, 5, 6}
	evens := Filter(nums, func(n int) bool { return n%2 == 0 })
	squares := Map(evens, func(n int) int { return n * n })
	total := Reduce(squares, 0, func(acc, n int) int { return acc + n })
	fmt.Println(evens, squares, total)

	words := []string{"go", "gopher", "channel", "map"}
	fmt.Println(Filter(words, longerThan(3)))
	fmt.Println(Map(words, strings.ToUpper))
}
[2 4 6] [4 16 36] 56
[gopher channel]
[GO GOPHER CHANNEL MAP]

Two patterns are shown here. First, taking behaviour as a parameter (Filter(nums, isEven)). Second, returning behaviour: longerThan(3) is a factory that builds a predicate with n baked in. Also notice Map(words, strings.ToUpper): any function with the right signature can be passed directly, no wrapper needed.

Senior engineer tip

Go is not a functional language, and idiomatic Go leans towards a plain for loop. A loop is easy to read, easy to debug, and lets you break early or return an error mid-way. Use Map/Filter helpers when they make code genuinely clearer, but don't build a five-step functional chain where a six-line loop would do. In code review, "just write the loop" is common, friendly feedback.

Composing functions

Higher-order functions really shine for wrapping behaviour. HTTP middleware (Chapter 17) is the canonical case: a function takes a handler and returns a new handler that does something before and after. Here's the shape, in miniature:

func withLogging(next func(string) string) func(string) string {
	return func(in string) string {
		log.Println("calling with", in)
		out := next(in)
		log.Println("returned", out)
		return out
	}
}

Recursion

A recursive function is one that calls itself. It solves a problem by breaking it into a smaller version of the same problem. Every recursive function needs two parts:

  • A base case: a small input you can answer directly, which stops the recursion.
  • A recursive case: call yourself with a smaller input and build the answer from the result.

Each call gets its own stack frame: a fresh set of local variables and parameters. Let's trace fact(3) frame by frame:

func fact(n int) int {
	if n <= 1 {
		return 1
	}
	return n * fact(n-1)
}

func main() {
	fmt.Println(fact(3))
}
  1. main calls fact(3).
  2. Frame for n=3. Not the base case, so it needs fact(2) before it can multiply. This frame pauses.
  3. New frame, n=2. Its own n; the n=3 frame is waiting underneath. Calls fact(1).
  4. n=1 hits the base case and returns 1 right away. No further calls.
  5. Back in the n=2 frame: 2 × 1 = 2. This frame returns 2 and is popped.
  6. Back in the n=3 frame: 3 × 2 = 6. Returns 6.
  7. main receives 6 and prints it.

Here's a fuller example with three classic recursive problems: factorial, a memoised Fibonacci, and walking a tree (the kind of structure you get from a file system, JSON, or an HTML DOM):

package main

import "fmt"

func factorial(n int) int {
	if n <= 1 { // base case: stops the recursion
		return 1
	}
	return n * factorial(n-1) // recursive case: a smaller problem
}

// Naive fib is exponential. Memoising with a map makes it linear.
func fibMemo() func(int) int {
	memo := map[int]int{}
	var fib func(int) int // declare first so the literal can call itself
	fib = func(n int) int {
		if n < 2 {
			return n
		}
		if v, ok := memo[n]; ok {
			return v
		}
		memo[n] = fib(n-1) + fib(n-2)
		return memo[n]
	}
	return fib
}

type Node struct {
	Name     string
	Size     int
	Children []*Node
}

// walk visits every node depth-first and prints it indented.
func walk(n *Node, depth int) int {
	total := n.Size
	fmt.Printf("%*s%s (%d)\n", depth*2, "", n.Name, n.Size)
	for _, c := range n.Children {
		total += walk(c, depth+1)
	}
	return total
}

func main() {
	fmt.Println("5! =", factorial(5))

	fib := fibMemo()
	fmt.Println("fib(50) =", fib(50))

	root := &Node{Name: "/", Children: []*Node{
		{Name: "bin", Size: 40},
		{Name: "home", Children: []*Node{
			{Name: "notes.txt", Size: 3},
			{Name: "photo.jpg", Size: 120},
		}},
	}}
	fmt.Println("total size:", walk(root, 0))
}
5! = 120
fib(50) = 12586269025
/ (0)
  bin (40)
  home (0)
    notes.txt (3)
    photo.jpg (120)
total size: 163

Note the trick in fibMemo: an anonymous function can't refer to itself by name, because it doesn't have one. So we first declare var fib func(int) int, then assign the literal. Inside the literal, fib refers to the captured variable, which by the time it's called holds the function itself.

The %*s verb in walk means "pad to a width given as an argument", a quick way to indent by depth.

Gotcha: Go has no tail-call optimisation

Some languages turn certain recursive calls into loops automatically. Go doesn't. Goroutine stacks start small (a few KB) and grow on demand up to a limit (1 GB on 64-bit by default), so deep recursion works for a while, but a runaway recursion ends in fatal error: stack overflow. For recursion whose depth depends on user input (deeply nested JSON, long linked lists), prefer an explicit loop with your own stack slice.

defer, panic and recover: a first look

Chapter 3 introduced defer, and Chapter 10 covers panic and recover properly. Since they are all about function calls, here is the overview you need now:

  • defer f() schedules f to run when the surrounding function returns, however it returns. Multiple defers run in last-in, first-out order, like a stack of plates.
  • The deferred call's arguments are evaluated immediately, at the defer line. Only the call itself is postponed.
  • panic(v) stops normal execution. Deferred functions still run as the panic travels up the call stack. If nothing stops it, the program crashes with a stack trace.
  • recover(), called inside a deferred function, stops a panic and returns the panic value. Anywhere else it returns nil.
func() {
	for i := 1; i <= 3; i++ {
		defer fmt.Println("defer", i)
	}
	x := 10
	defer fmt.Println("x at defer time:", x)
	x = 99
	fmt.Println("x now:", x)
}()
  1. First iteration: defer evaluates its arguments now ("defer", 1) and pushes the call on the defer stack.
  2. After the loop, three calls are waiting. Nothing printed yet.
  3. We defer a print of x. The value 10 is captured right now.
  4. We change x to 99 and print it immediately.
  5. The function ends. The most recent defer runs first, and prints the old value 10, not 99.
  6. Then the loop's defers, in reverse order: 3, 2, 1.
x now: 99
x at defer time: 10
defer 3
defer 2
defer 1

And here's recover turning a runtime panic into an ordinary error. Notice that it relies on a named result (err) so the deferred closure can set it:

package main

import (
	"errors"
	"fmt"
)

func deferOrder() {
	for i := range 3 {
		defer fmt.Println("deferred", i) // runs when deferOrder returns, LIFO
	}
	fmt.Println("body done")
}

// safeDiv turns a panic into an ordinary error.
func safeDiv(a, b int) (q int, err error) {
	defer func() {
		if r := recover(); r != nil {
			err = fmt.Errorf("recovered: %v", r)
		}
	}()
	return a / b, nil
}

func main() {
	deferOrder()

	fmt.Println(safeDiv(10, 2))
	fmt.Println(safeDiv(1, 0))

	err := errors.New("boom")
	fmt.Println("plain error, no panic needed:", err)
}
  1. main calls deferOrder. Each loop iteration pushes a deferred Println with that iteration's i, evaluated right now.
  2. After three iterations, three calls are waiting. Nothing has printed.
  3. The body finishes normally.
  4. As deferOrder returns, its defers run newest first: 2, 1, 0.
  5. safeDiv(10, 2) registers the recover closure, then return a / b, nil sets q=5, err=nil.
  6. The deferred func runs; recover() returns nil because nothing panicked, so the results are untouched.
  7. Now 1 / 0: integer division by zero panics in the middle of the return statement. Normal execution stops.
  8. While the panic unwinds, deferred functions still run. recover() catches the panic value, and the closure writes the named result err.
  9. safeDiv returns normally to main with q at its zero value and an ordinary error. The program keeps running.
  10. For expected failures you don't need panic at all: just create and return an error.
body done
deferred 2
deferred 1
deferred 0
5 <nil>
0 recovered: runtime error: integer divide by zero
plain error, no panic needed: boom
Senior engineer tip

Panics are for programmer bugs and truly impossible situations, not for "file not found" or "invalid input". Return an error for anything a caller might reasonably expect. The main legitimate place for recover is at a boundary, such as an HTTP server catching a panic in one request so the whole process doesn't die (net/http does this for you). If a library panics on bad input, users will rightly be annoyed.

More function patterns

Three more function-shaped ideas you will meet constantly in real Go code: functional options, method values, and init.

The functional options pattern

Go has no default arguments and no overloading. So how do you build something with many optional settings, like a server with a timeout, a connection limit, TLS config and a logger? Passing ten parameters is awful, and a config struct makes it hard to tell "not set" from "set to zero". The idiomatic answer is functional options: each option is a small function that tweaks the object being built.

package main

import (
	"fmt"
	"time"
)

type Server struct {
	addr    string
	timeout time.Duration
	maxConn int
}

// Option is a function that tweaks a Server.
type Option func(*Server)

func WithTimeout(d time.Duration) Option {
	return func(s *Server) { s.timeout = d }
}

func WithMaxConn(n int) Option {
	return func(s *Server) { s.maxConn = n }
}

// NewServer sets sensible defaults, then applies each option in order.
func NewServer(addr string, opts ...Option) *Server {
	s := &Server{addr: addr, timeout: 30 * time.Second, maxConn: 100}
	for _, opt := range opts {
		opt(s)
	}
	return s
}

func main() {
	a := NewServer(":8080")
	b := NewServer(":9090", WithTimeout(5*time.Second), WithMaxConn(10))
	fmt.Println(a.addr, a.timeout, a.maxConn)
	fmt.Println(b.addr, b.timeout, b.maxConn)
}
  1. NewServer(":8080") passes no options, so opts is a nil slice. The server is built with the defaults first.
  2. The loop over zero options does nothing. a keeps every default.
  3. For b, the arguments are evaluated first. WithTimeout(5*time.Second) doesn't touch any server; it returns a closure that captured d.
  4. WithMaxConn(10) likewise returns a closure capturing n. Both closures are packed into opts.
  5. Inside NewServer, defaults are set first.
  6. First option runs: s.timeout = d overrides the default 30s.
  7. Second option runs: s.maxConn = n. Options apply in order, so a later one can override an earlier one.
  8. The pointer to the configured server is returned into b.
  9. Printing shows the defaults on a and only the changed knobs on b.
:8080 30s 100
:9090 5s 10

Why people like it:

  • Callers only mention what they change: NewServer(":8080") is valid and readable.
  • Adding a new option later doesn't break any existing caller. The signature stays the same.
  • Option names (WithTimeout) document themselves at the call site.

It's built entirely from things in this chapter: a named function type (Option), closures (WithTimeout captures d), and a variadic parameter (opts ...Option). You'll see it in gRPC, Zap, the OpenTelemetry SDK and many other libraries.

Functional options are great for libraries with many knobs. For a struct with three fields used inside your own app, a plain config struct (NewServer(Config{Addr: ":8080"})) is simpler and perfectly idiomatic. Don't add the pattern until you feel the pain it solves.

Method values: a preview

Chapter 7 covers methods (functions attached to a type). One function-related trick is worth seeing now. If g has a method Hello, then g.Hello without parentheses is a function value with g already bound. This is a method value. Writing Greeter.Hello (type name, not variable) gives a method expression, where the receiver becomes the first parameter.

package main

import "fmt"

type Greeter struct{ Name string }

func (g Greeter) Hello(to string) string {
	return g.Name + " says hi to " + to
}

func main() {
	g := Greeter{Name: "Ann"}

	// Method VALUE: the receiver g is bound now. Type: func(string) string
	hello := g.Hello
	fmt.Println(hello("Bob"))

	// Method EXPRESSION: the receiver becomes the first parameter.
	// Type: func(Greeter, string) string
	expr := Greeter.Hello
	fmt.Println(expr(Greeter{Name: "Cy"}, "Dee"))

	// Method values plug straight into higher-order funcs.
	for _, name := range []string{"Eve", "Fay"} {
		run(hello, name)
	}
}

func run(f func(string) string, arg string) {
	fmt.Println(f(arg))
}
  1. We create a Greeter named Ann.
  2. g.Hello without parentheses is a method value: a func(string) string with a copy of g baked in right now.
  3. Calling hello("Bob") runs Hello with Ann as the receiver.
  4. Greeter.Hello (type name, not variable) is a method expression. No receiver is bound; its type is func(Greeter, string) string.
  5. So we pass the receiver as the first argument.
  6. The method value goes into run like any other function. run has no idea it's a method.
  7. Second iteration: still bound to Ann.
Ann says hi to Bob
Cy says hi to Dee
Ann says hi to Eve
Ann says hi to Fay

Method values are common when passing callbacks: http.HandleFunc("/", srv.handleIndex) hands the router a function that already knows which srv to use. Note that the receiver is evaluated (and for value receivers, copied) at the moment you write g.Hello.

init functions

Every package can declare one or more functions named init. They take no arguments, return nothing, can't be called by you, and run automatically once, before main. The full start-up order is:

  1. Imported packages are initialised first (recursively, each only once).
  2. Package-level variables are initialised, in dependency order.
  3. init() functions run, in the order they appear (files are presented to the compiler sorted by name).
  4. main() starts.
package main

import "fmt"

var config = loadConfig() // package-level vars initialise first

func loadConfig() map[string]string {
	fmt.Println("1. loadConfig (package var initialiser)")
	return map[string]string{"env": "dev"}
}

func init() {
	fmt.Println("2. first init(), env =", config["env"])
}

func init() {
	fmt.Println("3. second init() - a file may have several")
}

func main() {
	fmt.Println("4. main()")
}
  1. Before any init or main, package-level variables are initialised. Initialising config means calling loadConfig(), which prints.
  2. config now holds the map.
  3. Next, init functions run in source order. The first one can already rely on config being ready.
  4. A file may declare several init functions; the second runs after the first. You can never call them yourself.
  5. Only now does main start.
1. loadConfig (package var initialiser)
2. first init(), env = dev
3. second init() - a file may have several
4. main()
Use init sparingly

init runs hidden code just because a package was imported. That makes programs harder to test (you can't skip it), harder to reason about (order across files is subtle), and slower to start. Good uses: registering a driver or codec (import _ "image/png" registers the PNG decoder via init), or computing a lookup table. Bad uses: reading config files, connecting to databases, or anything that can fail. Do those explicitly in main and return errors.

Designing good functions

Writing a function that works is the easy part. Writing one that is pleasant to call, hard to misuse and easy to change is the craft. Here's what experienced Go engineers look for.

Keep functions small and focused

A function should do one thing, and its name should say what that is. If you need the word "and" to describe it (validateAndSaveAndNotify), split it. Small functions are easier to test, easier to name, and easier to reuse. A long function is often several small ones in a trench coat.

package main

import (
	"errors"
	"fmt"
)

// Small, focused functions with honest signatures compose well.

type User struct {
	Name  string
	Email string
	Age   int
}

func validateName(name string) error {
	if name == "" {
		return errors.New("name is required")
	}
	return nil
}

func validateAge(age int) error {
	if age < 0 || age > 150 {
		return fmt.Errorf("age %d out of range", age)
	}
	return nil
}

// validate is just a list of small checks.
func validate(u User) error {
	return errors.Join(
		validateName(u.Name),
		validateAge(u.Age),
	)
}

func main() {
	fmt.Println(validate(User{Name: "Sam", Age: 30}))
	fmt.Println(validate(User{Age: 200}))
}
  1. First call: validate evaluates each argument of errors.Join in order, so every small check runs.
  2. The name is non-empty, so validateName returns nil.
  3. 30 is in range, so validateAge also returns nil.
  4. errors.Join skips nil errors; if all are nil it returns nil. Valid user, no error.
  5. Second user has no name: validateName returns an error. Crucially, we don't stop here.
  6. The age check still runs and fails too.
  7. errors.Join combines both; its message puts each error on its own line, so the caller sees every problem at once.
<nil>
name is required
age 200 out of range

validate reads like a checklist. Each rule is tiny and testable on its own, and errors.Join (Go 1.20+) combines them, skipping the nils, so the caller sees every problem at once.

Optimise function signatures for the call site, not the definition. A function is written once and read at every call. Before finalising an API, write three example calls. If any of them make you squint ("which string is the name?"), change the signature. Pure functions (output depends only on input, no side effects) are the easiest code you'll ever test. Exercise 1: build an accumulator with two closures

Write makeAccumulator() that returns two functions: add(n int) and total() int. Both must share the same running sum. Hint: declare the sum once, then create two function literals that capture it. You can use named results to document which function is which.

Solution
package main

import "fmt"

// makeAccumulator returns add and total, sharing one captured sum.
func makeAccumulator() (add func(int), total func() int) {
	sum := 0
	add = func(n int) { sum += n }
	total = func() int { return sum }
	return add, total
}

func main() {
	add, total := makeAccumulator()
	add(5)
	add(10)
	fmt.Println(total())
	add(-3)
	fmt.Println(total())
}

Exercise 2: write a generic Compose

Write Compose(f, g) that returns a new function which runs f and passes its result to g. It should work for any types, so use type parameters [A, B, C any]. Use it to build a "trim, uppercase, add !" pipeline.

Solution
package main

import (
	"fmt"
	"strings"
)

// Compose returns a function that runs f first, then g.
func Compose[A, B, C any](f func(A) B, g func(B) C) func(A) C {
	return func(a A) C { return g(f(a)) }
}

func main() {
	shout := Compose(strings.TrimSpace, strings.ToUpper)
	exclaim := Compose(shout, func(s string) string { return s + "!" })
	fmt.Println(exclaim("   hello gophers  "))

	length := Compose(strings.TrimSpace, func(s string) int { return len(s) })
	fmt.Println(length("  abc  "))
}

Exercise 3: memoize any single-argument function

Write Memoize[K comparable, V any](f func(K) V) func(K) V that remembers results in a map, so repeated calls with the same argument don't call f again. Count the real calls to prove it works. (Bonus thought: why is this unsafe to call from several goroutines at once? You'll fix that with a mutex in Chapter 13.)

Solution
package main

import "fmt"

// Memoize caches results of a pure function of one comparable argument.
func Memoize[K comparable, V any](f func(K) V) func(K) V {
	cache := make(map[K]V)
	return func(k K) V {
		if v, ok := cache[k]; ok {
			return v
		}
		v := f(k)
		cache[k] = v
		return v
	}
}

func main() {
	calls := 0
	slowSquare := func(n int) int {
		calls++
		return n * n
	}
	fast := Memoize(slowSquare)
	fmt.Println(fast(4), fast(4), fast(5), fast(4))
	fmt.Println("real calls:", calls)
}

Key takeaways

  • Go passes every argument by value. Slices, maps and pointers are small values that refer to shared data, which is why changes through them are visible.
  • Functions can return multiple values; (result, error) is the standard way to signal failure.
  • Named results document meaning and let a defer adjust the result; avoid naked returns except in tiny functions.
  • Variadic parameters are slices; f(xs...) passes the slice itself, sharing its memory.
  • Functions are first-class values with types like func(int) int; their zero value is nil.
  • A closure captures variables, not values, and keeps them alive (on the heap) as long as needed.
  • Since Go 1.22 each loop iteration has a fresh loop variable, fixing the classic closure-in-loop bug.
  • Recursion needs a base case; Go has no tail-call optimisation, so prefer loops for unbounded depth.
  • defer runs LIFO and evaluates arguments immediately; recover only works inside a deferred function.
  • Keep functions small, put ctx first and error last, avoid boolean flags, and design for the call site.

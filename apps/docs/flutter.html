Flutter

Flutter takes the opposite approach from React Native: instead of driving native OS widgets, it brings its own rendering engine to every platform and draws every single pixel itself — text, buttons, shadows, scrolling physics, all of it. The OS only provides a blank canvas (a native window) and low-level services (camera, GPS, file system).

01Language & Tooling

LanguageDart — object-oriented, garbage-collected, compiled AOT to native ARM/x64 code
UI model"Everything is a widget" — declarative widget tree, similar shape to React/Compose
EngineFlutter Engine (C/C++) — includes Skia or the newer Impeller renderer
ToolingFlutter SDK, DevTools, Dart Analyzer
Buildflutter build compiles Dart AOT + bundles the engine per platform
Package managerpub.dev via pubspec.yaml

Dart runs in two modes: JIT (Just-In-Time) during development for hot reload, and AOT (Ahead-Of-Time, compiled straight to native machine code) for release builds — which is a big reason Flutter release builds are fast and don't ship an interpreter.

02Architecture

The core architectural bet Because Flutter never touches UIView or Android View, there's no translation layer and no per-platform UI inconsistency — the same pixels render identically on every device. The trade-off: Flutter has to reimplement everything a native toolkit gives you for free (text rendering, accessibility bridging, platform look-and-feel), which it does via the Material and Cupertino widget sets.

03Internal Rendering Pipeline

Flutter's tree isn't one tree — it's three, each optimized for a different job:

  1. Widget tree — immutable, lightweight config objects. Rebuilt constantly and cheaply (this is what build() returns).
  2. Element tree — mutable, persists across rebuilds. Reconciles new widgets against old ones (like React's fiber tree) and decides what actually changed.
  3. RenderObject tree — does the real work: layout (size/position) and painting. Only rebuilt when something in it truly changes.

The RenderObject tree paints onto a Skia (or, on newer versions, Impeller) canvas, which rasterizes directly to the GPU — completely bypassing the platform's native UI toolkit. Impeller was built to replace Skia's runtime shader compilation (a source of jank on iOS) with pre-compiled shaders.

04Threading Model — Why Flutter Is Architecturally Different

This is the part that most clearly explains why Flutter isn't "just another cross-platform wrapper." Native apps mostly reason about one main/UI thread. React Native splits work across a JS thread and the native UI thread, talking through JSI/the Bridge. Flutter goes further: the Dart VM and engine run four dedicated threads per app, each with one job.

Why this makes Flutter different

  • It never asks the OS "please draw a button" — the UI thread + Raster thread pipeline produces pixels itself, every frame.
  • Because the renderer is entirely Flutter's own, animations/scrolling stay smooth even while native plugin code runs on the Platform thread.
  • The same 4-thread pipeline is identical on Android, iOS, web (compiled to Wasm/JS) and desktop — nothing platform-specific in the hot path.

Contrast with the other two

  • Native: one main/UI thread does layout+draw, calls straight into the OS compositor — simplest model, but you own all the threading discipline yourself.
  • React Native: JS thread computes what to render, sends instructions across JSI/Bridge to the Native/UI thread which owns real OS views.
  • Flutter: adds a dedicated Raster thread and IO thread that neither Native nor RN has as a first-class concept — because Flutter, not the OS, is responsible for turning layout into pixels.

05Lifecycle

At the app level, WidgetsBindingObserver exposes AppLifecycleState: resumed (foreground, visible), inactive (transitioning, e.g. a call coming in), paused (backgrounded), detached (engine running, no view attached). This maps roughly onto both Android's Activity states and iOS's UIApplication states underneath.

06Project Structure

The android/ and ios/ folders exist but are mostly just thin native shells (the embedder) — almost all real code lives in lib/.

my_app/ ├─ android/ # thin native shell — just hosts the Flutter engine ├─ ios/ # thin native shell — same idea, hosts a FlutterViewController ├─ lib/ │ ├─ ui/ (or widgets/) # shared design-system widgets — buttons, cards, theme.dart │ ├─ api/ (or services/) # Dio/http clients, repositories, DTO models │ ├─ features/ # one folder per feature/screen │ │ └─ profile/ │ │ ├─ profile_screen.dart │ │ └─ profile_controller.dart # Bloc/Riverpod/Provider state │ ├─ router/ # go_router route definitions │ └─ main.dart # runApp() — true entry point ├─ pubspec.yaml # dependencies + assets manifest ├─ pubspec.lock └─ analysis_options.yaml # lint rules (Dart's ESLint equivalent)
Monorepo pattern at scale Larger Flutter codebases use Dart packages (not just folders) for reuse — packages/ui_kit, packages/api_client, packages/core — each with its own pubspec.yaml, wired together via a Melos-managed monorepo. Same idea as RN's workspace packages, just Dart-native tooling instead of npm workspaces.

08Pros & Cons

✓ Pros

  • Pixel-identical UI across Android, iOS, web, and desktop from one codebase
  • Excellent, consistent performance — compiled Dart, own GPU-backed renderer
  • Best-in-class hot reload — near-instant, preserves app state
  • Highest code-sharing ratio of the three (90–99%)
  • Batteries-included: navigation, animation, testing all first-party

✗ Cons

  • Dart is a smaller ecosystem/talent pool than JS or Kotlin/Swift
  • Because it doesn't use native widgets, platform look-and-feel needs deliberate work to nail
  • Larger baseline app size (ships its own engine/renderer in every binary)
  • Cutting-edge native OS features can lag behind official plugin support

09Terminology Glossary — Every Term You'll Actually Run Into

Grouped by what part of Flutter they belong to. Skim once, then use this page as a lookup while you read real code.

Widgets & UI building blocks

WidgetAn immutable description of a piece of UI. In Flutter, "everything is a widget" — even padding and alignment are widgets, not properties.
StatelessWidgetA widget with no mutable state of its own — its build() output depends only on the config passed in.
StatefulWidgetA widget paired with a separate State object that can hold mutable data and trigger rebuilds via setState().
State<T>The mutable, long-lived object behind a StatefulWidget — survives across rebuilds even though the widget itself is recreated each time.
BuildContextA handle to a widget's location in the tree — used to look up inherited data (theme, media query, navigator) from that point upward.
Key / ValueKey / GlobalKeyIdentity for a widget across rebuilds — critical when reordering lists so Flutter doesn't confuse one item's state for another's.
ScaffoldThe standard Material "page skeleton" widget — app bar, body, floating action button, drawer, bottom nav slot.
MaterialApp / CupertinoAppRoot widget that sets up theming, routing, and localization for an Android-styled or iOS-styled app respectively.
InheritedWidgetA widget that efficiently broadcasts data down the tree without manual prop-drilling — the low-level mechanism Theme, MediaQuery, and most state-management libraries are built on.
const constructorMarks a widget as compile-time constant so Flutter can skip rebuilding it entirely — a real, measurable performance habit.

State & data flow

setState()Tells Flutter "this State object's data changed, please rebuild this widget subtree."
ChangeNotifierA simple observable class (part of the SDK) that widgets can subscribe to for rebuilds — backbone of the provider package.
ValueNotifierA ChangeNotifier that wraps a single value — pairs with ValueListenableBuilder.
Provider / RiverpodDependency-injection + state-management libraries that expose data down the widget tree via BuildContext.
Bloc / CubitEvent-driven state management (flutter_bloc) — UI dispatches events, Bloc emits new states in response.
InheritedModelA more granular InheritedWidget that lets dependents rebuild only for the specific aspect of data they care about.

Rendering & engine internals

ElementThe mutable, persistent counterpart to a Widget — lives in the Element tree, holds the link between a Widget and its RenderObject.
RenderObjectDoes the actual layout math and painting — the third tree beneath Widget/Element, roughly Flutter's version of a DOM render layer.
RenderBoxThe most common RenderObject base class — anything with a rectangular 2D size (width/height).
Layer / Layer TreeThe output of a frame's paint phase — a tree of compositing instructions the Raster thread hands to the GPU.
SkiaGoogle's 2D graphics library; Flutter's original rendering backend on all platforms.
ImpellerFlutter's newer rendering backend (default on iOS, rolling out elsewhere) — precompiles shaders ahead of time to avoid runtime shader-compilation jank.
Dart VMRuns your Dart code — JIT during development (fast iteration/hot reload), AOT-compiled to native machine code for release builds.
IsolateDart's unit of concurrency — independent worker with its own memory heap; isolates communicate via message passing, never shared memory.
compute()Helper that runs a function on a new Isolate — the standard way to keep heavy work off the UI thread.
EmbedderThe thin, platform-specific shell (Android/iOS/web/desktop) that hosts the Flutter Engine and feeds it input/surface access.
Skeleton/ShellEngine term for the C++ core that wires the UI/Raster/IO/Platform threads together per running Flutter instance.

Async & concurrency

FutureDart's promise equivalent — a value that will be available later.
async / awaitSyntax sugar for working with Futures sequentially, same idea as JS.
StreamA sequence of async values over time (Dart's Observable) — used for things like text field input or websockets.
FutureBuilder / StreamBuilderWidgets that rebuild automatically as a Future resolves or a Stream emits.

Navigation & layout helpers

NavigatorMaintains a stack of Routes (screens) — push/pop to navigate.
go_routerThe most common declarative/URL-based routing package, esp. for deep links and web.
MediaQueryGives you the current screen size, padding (notches/safe areas), and text scale — read via BuildContext.
Theme / ThemeDataApp-wide styling (colors, typography) accessible from any widget via Theme.of(context).
Slivers / CustomScrollViewLower-level, composable scrolling building blocks — used for advanced effects like collapsing app bars.

Native interop & tooling

Platform ChannelAsync message-passing bridge between Dart and native Kotlin/Swift code — how plugins reach real OS APIs.
MethodChannel / EventChannelSpecific Platform Channel types — one-shot method calls vs. continuous event streams from native to Dart.
dart:ffiDirect foreign-function interface for calling C libraries from Dart without going through a Platform Channel.
Hot Reload vs Hot RestartReload injects changed code into the running Dart VM, preserving state; Restart re-runs main() from scratch.
pubspec.yamlThe project manifest — dependencies, assets, fonts, SDK constraints (Dart's package.json).
pub.devFlutter/Dart's official package registry (equivalent of npm/Maven Central).
Golden testA test that renders a widget and compares it pixel-for-pixel against a saved reference image.
Tree shakingBuild-time removal of unused code/icons — part of why release binaries aren't as bloated as the engine size alone suggests.

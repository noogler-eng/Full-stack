React Native

Write your UI and logic once in JavaScript/TypeScript using React's component model. Under the hood, React Native doesn't draw its own pixels — it asks Android and iOS to create and update their own real native views. You're not shipping a mini-browser; you're shipping React running against native widgets.

A crucial point people miss: an RN app is not "JS in a WebView." There's no browser and no DOM. JavaScript only ever produces a description of the UI tree; native code does the actual drawing using the same UIView/Android View classes a fully-native app would use.

02Architecture — Old Bridge vs New Architecture

React Native has gone through a major architectural rewrite. Both are worth knowing since both exist in production apps today.

  • JSI (JavaScript Interface) — a C++ layer letting JS call native functions directly (and vice versa) without crossing the Bridge.
  • Fabric — the new renderer; builds the UI tree in C++ (shared, not JS-only) and commits it to native views synchronously.
  • TurboModules — native modules (camera, storage, etc.) are now loaded lazily, on first use, instead of all at app start.
  • Codegen — generates type-safe native bindings from your TypeScript/Flow types at build time.

03Rendering Pipeline

  1. Your React components run on the JS thread, producing React elements (a virtual tree), same as React on web.
  2. React Native's reconciler diffs this into a platform-agnostic Shadow Tree.
  3. Yoga (a cross-platform Flexbox layout engine written in C++) computes the actual x/y/width/height for every node.
  4. The renderer (Fabric, or the old UIManager) commits the tree to real native views — UIView on iOS, android.view.View on Android.
  5. From that point on, the OS's own rendering pipeline takes over exactly as described on the Native page.
Why this matters for performance Because step 4 produces real platform views, scrolling, text rendering, and touch handling feel native — RN isn't repainting a canvas like a game engine. The cost is in getting data between JS and native efficiently, which is exactly what JSI/Fabric was built to fix.

04Lifecycle

Two lifecycles stack on top of each other: React's component lifecycle, and the underlying native app lifecycle (still there, just wrapped).

React component lifecycle (hooks)

  • useState / useReducer — local state init on first render
  • useEffect(fn, []) — runs after mount (≈ componentDidMount)
  • useEffect(fn, [deps]) — runs on update when deps change
  • useEffect cleanup function — runs on unmount

Native app lifecycle (still underneath)

  • AppState API exposes active / background / inactive
  • Android's Activity lifecycle still runs — RN just wraps it in one root Activity
  • iOS's UIApplication lifecycle still runs — RN wraps it in one root view controller
  • Native modules can hook these directly when JS-level events aren't enough

05Project Structure

An RN project is a JS/TS app plus two real native projects sitting alongside it.

my-app/ ├─ android/ # real native Android project (Gradle/Kotlin) ├─ ios/ # real native iOS project (Xcode/Swift) ├─ src/ │ ├─ ui/ # shared component/design-system package │ │ ├─ Button.tsx │ │ └─ theme.ts │ ├─ api/ # network layer — separate from UI, screen-agnostic │ │ ├─ client.ts # axios/fetch instance, interceptors │ │ └─ endpoints/ │ ├─ screens/ # feature screens — import from ui/ and api/ only │ ├─ navigation/ # React Navigation stack/tab definitions │ ├─ store/ # Redux Toolkit / Zustand global state │ └─ App.tsx ├─ index.js # registers root component — RN's true entry point ├─ metro.config.js ├─ babel.config.js ├─ tsconfig.json └─ package.json
Monorepo pattern at scale Larger RN codebases turn ui/ and api/ into real separate workspace packages (Yarn/PNPM workspaces or Nx/Turborepo), e.g. packages/ui, packages/api-client, apps/mobile — so the design system and API layer can be versioned and even reused by a React web app in the same monorepo.

07Pros & Cons

✓ Pros

  • One JS/TS codebase → both platforms, huge code reuse (70–95%)
  • Familiar to any React/web frontend engineer — same mental model
  • Real native UI components, not a rendered canvas — feels native
  • Fast Refresh + huge open-source ecosystem (npm)
  • Can still drop into native Kotlin/Swift modules when needed

✗ Cons

  • Still a JS runtime layer → some overhead vs pure native
  • Heavy native-module dependency trees can cause version/build pain
  • Platform-specific polish sometimes needs native code anyway
  • Large third-party dependency surface = more maintenance risk

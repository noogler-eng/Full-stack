Android & iOS — Native Development

"Native" means you write directly against the OS vendor's own SDK. There is no translation layer, no bridge, no separate engine — your code compiles to what the platform itself runs. Android and iOS are two completely separate stacks; a native app ships two codebases, one per OS.

Both platforms have moved from an imperative, view-mutation UI model (XML layouts + findViewById on Android, UIKit's UIView subclassing on iOS) to a declarative one (Compose, SwiftUI) — you describe what the UI should look like for a given state, and the framework figures out the diffing itself. This mirrors the shift React made in the web world.

02Architecture

Both stacks are layered: your app code sits on top of a UI framework, which sits on top of the OS's application framework, which sits on the kernel.

Key idea There is no "middle layer" translating your code. A Kotlin function call compiles down through the same runtime Android itself is built on. This is why native has the performance ceiling — every other approach adds at least one more layer between your code and the screen.

03Internal Rendering Pipeline

How a declared UI actually becomes pixels on screen, roughly:

Android (Compose)

  • Composition — your @Composable functions run and build a tree describing UI.
  • Layout — each node measures & places its children (single pass, parent-then-child).
  • Draw — nodes emit draw instructions onto a Canvas, backed by Skia.
  • SurfaceFlinger composites all app/system layers and hands the frame to the GPU.

iOS (SwiftUI / UIKit)

  • Layout pass — SwiftUI's view tree resolves sizes/positions (or Auto Layout for UIKit).
  • Core Animation — views become layers (CALayer) that own the actual pixels/texture.
  • Rendering — Core Graphics/Metal rasterizes layers on the GPU.
  • Compositor merges layers into the final framebuffer sent to the display.

Both target 60 / 120 fps by doing this whole pipeline in under ~8–16ms per frame, and both ultimately hand off actual pixel rasterization to the GPU rather than the CPU.

04Lifecycle

Every screen has a life the OS controls, not you — it creates, pauses, and destroys your screens based on user navigation, memory pressure, and backgrounding.

On top of per-screen lifecycles, both platforms also have an app-level lifecycle — Android's Application class and process states (foreground/background/cached), iOS's UIApplicationDelegate with states Not Running → Inactive → Active → Background → Suspended. The OS can kill a backgrounded app at any time to reclaim memory — this is why saving/restoring state matters on both platforms.

05Project Structure

Real native codebases are modularized: the app module wires things together, but UI and networking/data live in their own separate library modules/packages — not dumped in one giant app folder.

Android — Gradle multi-module layout

app/ # the installable module — DI graph, nav host, entry Activity └─ src/main/ ├─ java/com/app/ # MainActivity, Application class └─ AndroidManifest.xml :core:ui/ # design system — Compose theme, shared components :core:network/ # Retrofit/OkHttp clients, API interfaces, DTOs :core:database/ # Room DB, DAOs :core:common/ # utils, extensions shared everywhere :feature:profile/ # self-contained screen + its own ViewModel :feature:checkout/ # depends on :core:network + :core:ui only settings.gradle.kts # declares every module above build.gradle.kts # root-level plugin/version config

iOS — Xcode project + local Swift Packages

MyApp.xcodeproj/ # project file, build settings, schemes MyApp/ ├─ AppDelegate.swift / MyApp.swift # @main entry point ├─ Assets.xcassets # images, colors, icons └─ Info.plist # app config, permissions Packages/ DesignSystem/ # SwiftUI components, colors, typography — a local SPM package NetworkKit/ # URLSession/Alamofire clients, Codable models PersistenceKit/ # CoreData/SwiftData layer FeatureProfile/ # one screen/flow, depends on DesignSystem + NetworkKit Podfile / Package.swift # dependency manifests
Why split it this way UI components and API/data clients go in their own packages so a feature module only ever depends on interfaces (a design-system component, a network client), never on another feature directly. It keeps build times down (Gradle/Xcode only rebuild what changed) and stops teams from tangling screens together.

07Pros & Cons

✓ Pros

  • Best possible performance & responsiveness — no intermediate layer
  • Full, day-one access to every new OS API (widgets, ARKit, Live Activities, etc.)
  • Best-in-class platform look, feel, and accessibility behavior
  • Smaller, more predictable app binaries per platform

✗ Cons

  • Two full codebases, two teams (or one team context-switching languages)
  • Every feature is built twice — slower time-to-market
  • Harder to keep both platforms visually/behaviorally in sync
  • Higher hiring cost — need Kotlin and Swift expertise
